# 2강 — 벡터의 크기와 정규화

> **목표:** 벡터의 크기(Magnitude)를 계산하는 원리와, 정규화(Normalize)가 왜 필요한지 이해한다.
> **선수 지식:** 1강 — 벡터, 위치/방향/변위 벡터.

---

## 1. 도입 — 이동 속도가 대각선에서만 빨라진다

이런 이동 입력 코드를 짰다고 하자.

```cpp
void AMyCharacter::Tick(float DeltaTime)
{
    FVector Input = FVector(ForwardInput, RightInput, 0.0f);
    AddMovementInput(Input, 1.0f);
}
```

`W`와 `D`를 동시에 누르면(대각선 이동), `Input`은 `(1, 1, 0)`이 된다. 이 벡터의 크기는 `sqrt(1² + 1²) = 1.41`이다. 앞으로만 갈 때(`(1, 0, 0)`, 크기 1)보다 **41% 더 빠르게** 움직여버린다. 실제로 옛날 게임에서 자주 나던 버그다 — "대각선으로 이동하면 더 빠르다."

원인은 방향만 필요한 자리에 **크기가 제각각인 벡터**를 그대로 넣었기 때문이다. 방향만 뽑고 싶으면 크기를 항상 1로 맞춰야 한다. 이게 정규화(Normalize)다.

```cpp
// 수정: 정규화해서 크기를 항상 1로
FVector Input = FVector(ForwardInput, RightInput, 0.0f);
FVector NormalizedInput = Input.GetSafeNormal();
AddMovementInput(NormalizedInput, 1.0f);
```

---

## 2. 개념 설명

### 2-1. 벡터의 크기(Magnitude) — 피타고라스 정리 그 자체

벡터 `(X, Y, Z)`의 크기는 다음과 같이 구한다.

```
|V| = sqrt(X² + Y² + Z²)
```

이건 사실 3차원으로 확장된 피타고라스 정리다. 2D에서 직각삼각형의 빗변 길이가 `sqrt(a² + b²)`인 것과 똑같은 원리로, 3D에서는 세 축의 제곱합에 루트를 씌운다.

```cpp
FVector V = FVector(3.0f, 4.0f, 0.0f);
float Length = V.Size();          // sqrt(9 + 16 + 0) = 5.0
float LengthSquared = V.SizeSquared();  // 25.0 (루트 계산 생략)
```

`SizeSquared()`가 따로 있는 이유: 제곱근 연산(`sqrt`)은 상대적으로 비싼 연산이다. 두 거리를 **비교만** 할 거면 굳이 루트를 씌울 필요가 없다 — 제곱값끼리 비교해도 대소 관계는 똑같기 때문이다.

```cpp
// 나쁜 예: 거리 비교에 굳이 sqrt 두 번
if (FVector::Dist(A, B) < FVector::Dist(A, C)) { ... }

// 좋은 예: 제곱 거리로 비교 (sqrt 생략)
if (FVector::DistSquared(A, B) < FVector::DistSquared(A, C)) { ... }
```

수백 마리의 몬스터 중 가장 가까운 걸 찾는 것처럼 거리 비교를 대량으로 하는 로직(타겟팅, 어그로 계산)에서는 이 최적화가 실제로 프레임 타임에 영향을 준다.

### 2-2. 정규화(Normalize) — 방향만 남기고 크기를 1로

정규화는 벡터를 자기 자신의 크기로 나누는 연산이다.

```
Normalized(V) = V / |V|
```

크기가 1인 벡터를 **단위 벡터(Unit Vector)**라고 부른다. 정규화하면 "어느 쪽을 가리키는가"라는 정보만 남고 "얼마나 긴가"는 사라진다(정확히는 1로 고정된다).

```cpp
FVector V = FVector(3.0f, 4.0f, 0.0f);   // 크기 5
FVector Dir = V.GetSafeNormal();          // (0.6, 0.8, 0.0), 크기 1
```

`0.6 = 3/5`, `0.8 = 4/5` — 각 성분을 원래 크기로 나눈 것뿐이다.

### 2-3. 왜 `GetSafeNormal()`을 쓰는가 — 0벡터 함정

수학적으로 정규화는 "크기로 나누기"인데, 크기가 0인 벡터(제자리에 멈춰 있을 때의 이동 입력, 자기 자신과의 변위 등)를 정규화하려고 하면 **0으로 나누기**가 발생한다.

언리얼의 `FVector::Normalize()`는 이 경우를 처리하지 않고 그대로 나눠버려 `NaN`(Not a Number)을 만들 수 있다. 반면 `GetSafeNormal()`은 크기가 너무 작으면(기본 허용 오차 이하) 정규화를 시도하지 않고 **0벡터를 그대로 반환**한다.

```cpp
FVector Zero = FVector::ZeroVector;
FVector Result1 = Zero.GetSafeNormal();   // (0, 0, 0) — 안전
// FVector Result2 = Zero; Result2.Normalize();  // 내부적으로 0 나누기 위험
```

**실무에서는 거의 항상 `GetSafeNormal()`을 쓴다.** 캐릭터가 멈춰 있을 때 이동 입력 벡터가 0벡터가 되는 건 흔한 상황이라, 이걸 안전하게 처리 못 하면 캐릭터 방향이 갑자기 `NaN`이 되어 화면 밖으로 튕겨나가는 버그로 이어질 수 있다.

### 2-4. 정규화가 필요한 대표 상황

| 상황 | 왜 정규화가 필요한가 |
|------|---------------------|
| 이동 입력 벡터 | 대각선 입력이 축 방향 입력보다 빨라지는 걸 막음 |
| `GetActorForwardVector()` 등 방향 벡터 | 애초에 항상 정규화된 상태로 제공됨(크기 1 보장) |
| 두 지점 사이 "방향만" 필요할 때 | `(B-A)`는 거리에 비례해 커지므로, 방향만 쓰려면 정규화 필수 |
| 내적으로 각도를 구할 때 (3강) | 정규화 안 된 벡터로 내적하면 각도가 아니라 거리가 섞인 값이 나옴 |
| 법선 벡터, 회전축 계산 (4강) | 방향의 "순수한 표현"이 필요하므로 항상 단위 벡터로 다룸 |

### 2-5. GetSafeNormal()의 "안전"은 정확히 뭘 기준으로 하나

`GetSafeNormal()`은 내부적으로 벡터 크기가 아주 작은 허용 오차(Tolerance, 기본값 `KINDA_SMALL_NUMBER` 수준의 아주 작은 값)보다 작은지를 먼저 확인한다. 이 오차보다 작으면 "사실상 0벡터"로 간주하고 나누기 자체를 생략한 채 `(0,0,0)`을 반환한다.

이게 왜 "정확히 0인지"가 아니라 "허용 오차 이내인지"를 보는지는 부동소수점(`float`) 특성과 관련 있다. 계산 과정에서 누적된 반올림 오차 때문에 논리적으로는 0이어야 할 값이 `0.0000001`처럼 아주 작은 non-zero 값으로 남는 경우가 흔하다. 정확히 `== 0.0f`로만 비교하면 이런 경우를 놓쳐서 여전히 나누기 문제가 발생할 수 있으므로, 안전한 API는 항상 "충분히 작은 범위"로 판단한다. 이 패턴(정확한 동등 비교 대신 허용 오차 비교)은 부동소수점을 다루는 게임 코드 전반에서 반복해서 나온다.

## 4. 코드로 — 실제 사례: 8방향 이동 정규화

```cpp
void AMyCharacter::ApplyMovementInput(float ForwardAxis, float RightAxis, float DeltaTime)
{
    FVector RawInput = FVector(ForwardAxis, RightAxis, 0.0f);

    // 크기가 0에 가까우면(멈춤 상태) 굳이 정규화 안 해도 안전하게 0 반환
    FVector Direction = RawInput.GetSafeNormal();

    // 정규화된 방향에 실제 속도(스칼라)를 곱해서 최종 이동량 계산
    FVector Movement = Direction * MoveSpeed * DeltaTime;

    AddActorWorldOffset(Movement, true);
}
```

`Direction`은 항상 크기 1(혹은 완전히 정지 상태일 때 0)이므로, 앞으로 가든 대각선으로 가든 `MoveSpeed`가 일정하게 적용된다.

## 5. 흔한 오해

### 오해 1: "정규화하면 벡터의 방향도 바뀐다"

정규화는 **크기만** 바꾼다. 방향(각 축의 비율)은 그대로 유지된다. `(3, 4, 0)`을 정규화하면 `(0.6, 0.8, 0)`이 되는데, 두 벡터 모두 원점에서 같은 각도로 뻗어 있다.

### 오해 2: "Size()가 비싼 건 알겠는데, SizeSquared()도 비슷하게 비쌀 것이다"

`Size()`는 제곱합을 구한 뒤 `sqrt`를 호출하고, `SizeSquared()`는 `sqrt` 호출 없이 제곱합만 반환한다. `sqrt`는 곱셈/덧셈보다 훨씬 비싼 연산이라, 단순 비교 목적이면 `SizeSquared()`가 명확히 더 빠르다.

### 오해 3: "0벡터도 그냥 Normalize() 쓰면 알아서 처리해준다"

언리얼 기준으로 `Normalize()`(멤버 함수, in-place)는 안전장치가 약하고, `GetSafeNormal()`이 0벡터·매우 작은 벡터를 명시적으로 처리해준다. 이름 비슷한 함수 두 개를 헷갈리면 실제로 `NaN` 버그가 난다.

### 오해 4: "방향 벡터끼리는 크기 비교가 의미 없으니 신경 안 써도 된다"

방향 벡터(단위 벡터)는 항상 크기가 1이라 서로 비교할 필요는 없는 게 맞다. 하지만 문제는 **정규화를 빼먹은 벡터를 방향 벡터인 줄 알고 쓰는 것**이다. 함수에 벡터를 넘길 때 "이게 정규화된 벡터인지 아닌지"를 항상 의식해야 한다.

## 6. 면접에서 나오면

**Q1. 벡터의 크기는 어떻게 구하나요?**
→ "각 성분을 제곱해서 더한 다음 제곱근을 씌웁니다. 3차원으로 확장된 피타고라스 정리라고 보면 됩니다."

**Q2. 정규화가 뭔가요?**
→ "벡터를 자기 자신의 크기로 나눠서, 방향은 그대로 두고 크기만 1로 만드는 연산입니다. 결과로 나온 크기 1짜리 벡터를 단위 벡터라고 부릅니다."

**Q3. 거리만 비교할 때 Size() 대신 SizeSquared()를 쓰는 이유는 뭔가요?**
→ "제곱근 연산이 상대적으로 비싸기 때문입니다. 대소 관계만 비교할 거면 제곱값끼리 비교해도 결과가 같아서, sqrt 호출을 아낄 수 있습니다. 몬스터 여러 마리 중 가장 가까운 걸 찾는 것처럼 거리 비교가 많은 로직에서 특히 의미가 있습니다."

**Q4. 이동 입력을 정규화하지 않으면 어떤 문제가 생기나요?**
→ "대각선으로 이동할 때 입력 벡터의 크기가 1보다 커져서, 축 방향으로 이동할 때보다 더 빠르게 움직이는 버그가 생깁니다. 그래서 방향만 필요한 이동 입력은 항상 정규화해서 크기를 1로 고정해야 합니다."

**Q5. Normalize()와 GetSafeNormal()의 차이는 뭔가요?**
→ "Normalize()는 크기로 그냥 나누기 때문에 벡터 크기가 0에 가까우면 0으로 나누기가 발생해서 NaN이 나올 수 있습니다. GetSafeNormal()은 크기가 너무 작으면 정규화를 시도하지 않고 0벡터를 안전하게 반환합니다. 실무에서는 거의 항상 GetSafeNormal()을 씁니다."
> 면접관이 그 다음에 던지기 좋은 질문: "그럼 0벡터를 정규화하려고 하면 실제로 어떤 값이 나오나요?" → 0/0 형태라 정의되지 않고, 구현에 따라 NaN이나 (0,0,0)이 나올 수 있다는 점을 짚어주면 좋다.

**Q6. 캐릭터가 멈춰 있을 때 방향 벡터를 정규화하면 어떤 값이 나올까요? 이걸 처리 안 하면 어떤 문제가 생기나요?**
→ "이동 입력이 없으면 벡터가 (0,0,0)이 되는데, 이걸 그냥 Normalize()로 나누면 NaN이 나올 수 있습니다. NaN이 위치 계산에 섞이면 캐릭터가 화면 밖으로 튕기거나 렌더링이 깨질 수 있어서, GetSafeNormal()로 0벡터를 안전하게 처리해야 합니다."

**Q7. 방향과 거리를 동시에 다뤄야 할 때(예: 이동), 실제로 어떻게 계산하나요?**
→ "먼저 변위 벡터를 정규화해서 방향만 뽑고, 별도로 거리(속도, 스칼라)를 계산해서 방향 벡터에 곱합니다. 방향과 크기를 분리해서 다루는 게 벡터 연산의 기본 패턴입니다."
