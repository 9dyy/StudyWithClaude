# 7-1강 (보충) — 2차원 평면에서 가장 가까운 객체 찾기

> **목표:** 수많은 객체 중 기준점에서 가장 가까운 것을 찾는 문제를 "전수 탐색 → 공간 분할" 순서로 풀고, 언제 어떤 방식을 고를지와 공간 분할의 함정(경계 오답)까지 설명할 수 있게 된다.
> **선수 지식:** 2강(`DistSquared`로 거리 비교), 7강(브로드 페이즈/내로우 페이즈). 4-1강(Cpp 자료구조 보충)이 있으면 더 좋다.

---

## 1. 실제로 받은 질문

> "2차원 평면에서 수많은 객체 중에 **가장 가까운 객체를 찾는 법**"

정답이 하나가 아닌 질문이다. 면접관은 "O(N)으로 다 돌면 돼요"에서 멈추는지, 그 다음을 아는지를 본다. 이 강의는 **다음 단계로 어떻게 답을 확장하는가**를 만드는 강의다.

---

## 2. 1단계 — 전수 탐색: 일단 이게 정답인 경우가 많다

전부 돌면서 제일 작은 거리를 기억한다. **거리 비교에 `sqrt`는 필요 없다** — 2강에서 본 `DistSquared` 그대로다.

```cpp
int32 FindNearest(const TArray<FVector2D>& Points, const FVector2D& Query)
{
    int32 Best = INDEX_NONE;
    double BestDistSq = TNumericLimits<double>::Max();

    for (int32 i = 0; i < Points.Num(); ++i)
    {
        const double DistSq = FVector2D::DistSquared(Points[i], Query);   // sqrt 없음
        if (DistSq < BestDistSq)
        {
            BestDistSq = DistSq;
            Best = i;
        }
    }
    return Best;
}
```

- 시간복잡도 **O(N)**, 공간 추가 없음.
- **원소가 수천 개고 질의가 프레임당 한두 번**(예: 커서 아래 객체, 플레이어의 락온 타겟)이면 이걸로 충분하다. 자료가 연속 배열이라 캐시 지역성이 좋아서(Cpp 4강) 생각보다 빠르다.
- 면접에서 이걸 **먼저 말하는 게 맞다.** "일단 O(N) 전수 탐색이 기본이고, 질의가 많아지면 공간 분할을 쓴다"가 좋은 답의 시작이다. 처음부터 쿼드트리를 꺼내면 과한 설계로 보일 수 있다.

---

## 3. 언제 전수 탐색이 무너지나

**"모든 객체가 각자 가장 가까운 적을 찾는다"** 같은 질의가 N번 일어나는 경우다. AI 몬스터 1,000마리가 매 프레임 가장 가까운 플레이어/오브젝트를 찾으면 1,000 × 1,000 = **100만 번의 거리 계산**이다. N이 10배가 되면 100배가 된다.

핵심 발상은 **"멀리 있는 것들은 볼 필요가 없다"**다. 기준점 근처만 검사하도록 **공간을 미리 나눠 두는 것**이 공간 분할(Spatial Partitioning)이다. 7강의 브로드 페이즈와 같은 아이디어다.

---

## 4. 2단계 — 균등 그리드(Uniform Grid / Spatial Hash)

평면을 **같은 크기의 정사각형 셀**로 나누고, 각 객체를 자기가 속한 셀의 목록에 넣는다.

```
셀 크기 = S
┌───┬───┬───┬───┐
│ · │   │ · │   │   Q(질의점)가 있는 셀부터 바깥으로 넓혀가며 찾는다
├───┼───┼───┼───┤
│   │ ·Q│ · │   │   ← ring 0: Q가 든 셀
├───┼───┼───┼───┤   ← ring 1: 그 둘레 8칸
│ · │   │   │ · │   ← ring 2: 그 바깥 둘레 ...
└───┴───┴───┴───┘
```

```cpp
struct FGrid
{
    float CellSize;
    TMap<FIntPoint, TArray<int32>> Cells;     // 셀 좌표 → 그 셀의 객체 인덱스들

    FIntPoint ToCell(const FVector2D& P) const
    {
        return FIntPoint(FMath::FloorToInt(P.X / CellSize), FMath::FloorToInt(P.Y / CellSize));
    }
    void Insert(int32 Id, const FVector2D& P) { Cells.FindOrAdd(ToCell(P)).Add(Id); }
};
```

### 질의: "내 셀만 보면 안 된다"

가장 가까운 객체가 **내 셀에는 없고 옆 셀에 있을 수 있다.** Q가 셀 경계 바로 옆에 있으면 옆 셀의 점이 내 셀의 점보다 더 가까운 경우가 흔하다.

그래서 **셀을 링(ring) 모양으로 바깥으로 넓히며 검사하고, 충분히 봤으면 멈춘다.**

```cpp
int32 FindNearestGrid(const FGrid& Grid, const TArray<FVector2D>& Points, const FVector2D& Query)
{
    const FIntPoint Center = Grid.ToCell(Query);
    int32 Best = INDEX_NONE;
    double BestDistSq = TNumericLimits<double>::Max();

    for (int32 R = 0; ; ++R)
    {
        // 링 R: Center에서 체비쇼프 거리가 정확히 R인 셀들을 전부 검사
        for (const FIntPoint& Cell : RingCells(Center, R))
        {
            if (const TArray<int32>* List = Grid.Cells.Find(Cell))
            {
                for (int32 Id : *List)
                {
                    const double D = FVector2D::DistSquared(Points[Id], Query);
                    if (D < BestDistSq) { BestDistSq = D; Best = Id; }
                }
            }
        }
        // 종료 조건: 링 R까지 봤다면 그 바깥의 점은 최소 R*S 이상 떨어져 있다.
        // 이미 찾은 거리가 그보다 가깝다면 더 볼 필요가 없다.
        if (Best != INDEX_NONE && BestDistSq <= (double)R * Grid.CellSize * (double)R * Grid.CellSize)
            break;
        if (R > MaxRing) break;     // 객체가 하나도 없는 경우 등 무한 루프 방지
    }
    return Best;
}
```

**종료 조건이 이 알고리즘의 핵심이다.** Q가 중심 셀 안에 있으므로, (2R+1)×(2R+1) 블록 바깥의 점은 Q에서 **최소 R × S** 이상 떨어져 있다. 지금까지 찾은 최선이 R × S 이하라면 블록 바깥에 더 가까운 점이 있을 수 없다. 이 조건 없이 "링 1까지만 본다"처럼 고정하면 **객체가 듬성듬성한 곳에서 오답**이 나온다.

- 객체가 고르게 퍼져 있으면 평균적으로 몇 개 셀만 보므로 **질의당 O(1)에 가깝다.**
- **셀 크기 선택이 성능을 좌우한다.** 너무 작으면 빈 셀을 많이 뒤지고(링이 길어짐), 너무 크면 셀 하나에 객체가 몰려 전수 탐색과 다를 바 없다. 보통 "셀당 평균 객체 수 몇 개" 수준을 목표로 잡는다.
- **객체가 움직이면** 셀이 바뀔 때만 이전 셀에서 빼고 새 셀에 넣는다(갱신 비용이 작다).

## 5. 3단계 — 분포와 용도에 따른 다른 선택지

| 방식 | 잘 맞는 상황 | 약점 |
|------|------|------|
| **균등 그리드 / 공간 해시** | 분포가 비교적 고르고 객체 크기가 비슷, 객체가 자주 움직임 | 분포가 한쪽에 쏠리면 셀 하나가 터짐, 셀 크기 튜닝 필요 |
| **쿼드트리(Quadtree)** | 분포가 불균등(밀집 지역과 빈 지역이 공존), 동적 객체 | 트리 순회/갱신 비용, 구현 복잡 |
| **KD-tree** | **정적인 점 집합**에서 최근접 질의를 아주 많이 할 때(평균 O(log N)) | 객체가 움직이면 재구성 비용이 큼 |
| **BVH(경계 볼륨 계층)** | 크기가 제각각인 객체, 충돌/레이 질의 | 최근접 질의 전용은 아님 |

3차원에서는 쿼드트리가 **옥트리(Octree)**가 된다. 언리얼에도 `TOctree2` 같은 컨테이너가 있고, 물리 엔진(Chaos)이 내부적으로 브로드 페이즈에서 이런 구조를 쓴다.

**어떻게 고르나?** *"객체가 자주 움직이나(→ 그리드/쿼드트리), 정적인가(→ KD-tree), 분포가 고른가(→ 그리드), 쏠려 있나(→ 쿼드트리)"* 로 묻는다. 그리고 항상 **"정말 필요한가"**를 먼저 묻는다 — N이 작으면 전수 탐색이 가장 빠르고 단순하다.

## 6. 언리얼에서는

```cpp
// ❌ 매 프레임 이렇게 하면 월드의 모든 액터를 훑는다
UGameplayStatics::GetAllActorsOfClass(GetWorld(), AEnemy::StaticClass(), AllEnemies);

// ✅ 목록을 직접 캐시하거나 (Cpp 4-1강의 몬스터 매니저)
//    반경 안의 액터만 물리 엔진의 브로드 페이즈로 조회한다
TArray<AActor*> Nearby;
UKismetSystemLibrary::SphereOverlapActors(GetWorld(), Location, Radius, ObjectTypes, AEnemy::StaticClass(), IgnoreActors, Nearby);
```

- 반경 조회는 **엔진이 이미 갖고 있는 공간 분할을 재사용**하는 방법이다. 직접 구조를 짜기 전에 먼저 이걸 쓴다.
- 가장 가까운 것 하나가 목적이라면, 오버랩 결과에서 `DistSquared`로 최솟값을 고르는 식이 된다.
- 액터가 아주 많은 시뮬레이션(군집, 파티클성 오브젝트)은 액터 대신 **배열 기반 자료 + 자체 그리드**로 가는 경우도 있다.

## 7. 흔한 오해

### 오해 1: "가장 가까운 걸 찾으려면 반드시 트리 같은 자료구조가 필요하다"
N이 작거나 질의가 드물면 **O(N) 전수 탐색이 가장 빠르다.** 자료구조는 비용(구현, 갱신)이 있어서 필요할 때만 쓴다.

### 오해 2: "그리드에서 내 셀만 보면 된다"
경계 근처의 질의점은 **옆 셀에 더 가까운 점**이 있을 수 있다. 링을 넓히고 종료 조건을 지켜야 정확하다.

### 오해 3: "거리를 구하려면 sqrt를 해야 한다"
**비교만 하면 제곱 거리로 충분하다**(2강). 실제 거리 값이 필요할 때만 마지막에 sqrt를 한 번 쓴다.

### 오해 4: "공간 분할은 정적 배치일 때만 쓴다"
그리드/쿼드트리는 동적 객체용으로도 쓴다(셀 이동만 갱신). 오히려 갱신이 비싼 쪽은 KD-tree다.

### 오해 5: "셀은 작을수록 좋다"
너무 작으면 빈 셀을 뒤지는 비용이 늘고 메모리도 커진다. **객체 밀도와 질의 반경에 맞춘 크기**가 필요하다.

## 8. 면접에서 나오면

**Q1. 2차원 평면에서 수많은 객체 중 기준점에서 가장 가까운 객체를 찾는 방법은?**
→ "기본은 모든 객체를 돌면서 제곱 거리가 가장 작은 걸 고르는 O(N) 전수 탐색입니다. 제곱 거리로 비교하면 sqrt가 필요 없습니다. 질의가 많아서 이게 부담이면 평면을 그리드로 나눠서 기준점이 속한 셀부터 바깥으로 넓혀가며 찾는 공간 분할을 씁니다. 그러면 근처 셀만 보게 돼서 질의당 평균 O(1)에 가까워집니다."

**Q2. 그리드로 찾을 때 내 셀에서 찾았으면 바로 끝내도 되나요?**
→ "안 됩니다. 기준점이 셀 경계 근처면 옆 셀에 더 가까운 점이 있을 수 있습니다. 링 단위로 넓히면서, 지금까지 찾은 최소 거리가 링 R까지의 안전 거리 R×셀크기 이하가 되면 멈추는 방식으로 정확성을 보장합니다."

**Q3. 그리드와 쿼드트리는 각각 언제 쓰시겠어요?**
→ "객체가 고르게 퍼져 있고 자주 움직이면 구현이 단순하고 갱신이 싼 그리드를 씁니다. 밀집 지역과 빈 지역이 섞여 분포가 불균등하면 쿼드트리처럼 영역에 따라 세분화되는 구조가 낫습니다."

**Q4. KD-tree는 언제 쓰나요?**
→ "점 집합이 거의 변하지 않고 최근접 질의를 아주 많이 할 때입니다. 평균 O(log N)에 찾지만 객체가 움직이면 재구성 비용이 커서 동적인 게임 객체에는 잘 안 맞습니다."

**Q5. 질의가 프레임당 한두 번뿐인데도 공간 분할을 쓰시겠어요?**
→ "아니요. 그런 경우엔 O(N) 전수 탐색이 가장 단순하고 연속 배열이라 캐시 지역성도 좋아서 충분히 빠릅니다. 공간 분할은 질의가 N번 일어나 O(N²)이 되는 경우처럼 실제로 병목일 때 도입합니다."

**Q6. 언리얼에서는 어떻게 구현하시겠어요?**
→ "GetAllActorsOfClass를 매 프레임 부르지 않고, 대상 목록을 서브시스템에 캐시해 두거나 SphereOverlap 같은 물리 엔진의 반경 조회를 쓰겠습니다. 엔진이 이미 브로드 페이즈용 공간 분할을 갖고 있어서 그걸 재사용하는 게 먼저입니다."

면접관이 그 다음에 던지기 좋은 질문: *"가장 가까운 K개를 찾으려면요?"* → 링 확장을 K개를 채울 때까지 계속하고, 종료 조건을 K번째 후보 거리로 바꾼다(최대 힙으로 K개 유지).

## 9. 셀프 체크

- [ ] 전수 탐색이 O(N)이고 `DistSquared`로 sqrt를 피한다는 것을 설명할 수 있다.
- [ ] 전수 탐색이 무너지는 상황(N번의 질의 → O(N²))을 예로 들 수 있다.
- [ ] 균등 그리드에서 링을 넓히며 찾는 방법과 **종료 조건(R × 셀 크기)**의 이유를 설명할 수 있다.
- [ ] "내 셀만 보면 안 되는" 이유를 경계 예시로 설명할 수 있다.
- [ ] 그리드/쿼드트리/KD-tree 중 상황에 맞는 것을 고르고 이유를 말할 수 있다.
