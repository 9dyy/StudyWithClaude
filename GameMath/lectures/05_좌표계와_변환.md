# 5강 — 좌표계와 변환

> **목표:** 월드 좌표와 로컬 좌표의 차이, `FTransform`이 하는 일, 부모-자식 좌표 변환의 원리를 이해한다.
> **선수 지식:** 1~4강 (벡터, 정규화, 내적, 외적).

---

## 1. 도입 — 캐릭터 손에 든 무기가 자꾸 이상한 위치에 붙는다

무기를 캐릭터 손 소켓에 붙일 때 이런 코드를 쓴 적 있을 것이다.

```cpp
Weapon->AttachToComponent(
    Mesh, FAttachmentTransformRules::KeepRelativeTransform, TEXT("hand_r_socket"));
```

여기서 "Relative"라는 단어가 왜 필요한지 생각해본 적 있는가? 만약 무기의 위치를 **월드 좌표**로 고정해서 캐릭터 손에 붙이면 어떻게 될까 — 캐릭터가 걸어가는 순간 무기는 원래 위치에 그대로 남아있고, 손만 무기 없이 움직이게 된다.

무기가 손을 "따라다니게" 하려면, 무기의 위치를 월드 원점 기준이 아니라 **손(소켓) 기준**으로 표현해야 한다. 이게 로컬 좌표(Local/Relative Coordinate)다. 이 강의는 월드 좌표와 로컬 좌표가 왜 분리되어 있고, 이 둘을 잇는 `FTransform`이 정확히 뭘 하는지 다룬다.

---

## 2. 개념 설명

### 2-1. 월드 좌표 vs 로컬 좌표

- **월드 좌표(World Space):** 레벨 전체의 원점(0,0,0)을 기준으로 한 절대 위치. `GetActorLocation()`이 반환하는 값.
- **로컬 좌표(Local/Relative Space):** 특정 부모(부모 액터, 부모 컴포넌트, 소켓 등)를 기준으로 한 상대 위치. `GetRelativeLocation()`이 반환하는 값.

```cpp
// 캐릭터가 (500, 0, 0)에 있고, 무기가 손 소켓 기준 (10, 0, 5)에 붙어있다면
// 무기의 월드 좌표는 캐릭터 위치 + 회전까지 고려한 손 소켓의 월드 위치 + 로컬 오프셋
FVector WeaponWorldLocation = Weapon->GetComponentLocation();       // 월드 기준 실제 위치
FVector WeaponLocalLocation = Weapon->GetRelativeLocation();        // 소켓 기준 상대 위치 (10, 0, 5)
```

무기를 소켓에 `KeepRelativeTransform`으로 붙이면, 무기의 **로컬 좌표는 고정**되고 캐릭터(부모)가 움직이거나 회전할 때마다 무기의 **월드 좌표만 자동으로 재계산**된다. 이게 자식이 부모를 "따라다니는" 원리다.

### 2-2. FTransform — 위치·회전·스케일을 하나로

`FTransform`은 세 가지 정보를 한 번에 담는 구조체다.

```cpp
struct FTransform
{
    FQuat Rotation;      // 회전
    FVector Translation; // 위치(이동)
    FVector Scale3D;     // 크기
};
```

이 세 값을 합쳐서 **"어떤 좌표계를 다른 좌표계로 바꾸는 변환"** 하나를 표현한다. `AActor`의 위치, 회전, 스케일을 각각 따로 들고 있는 대신 `FTransform` 하나로 묶어서 다루면, "이 좌표를 이 트랜스폼 기준으로 변환해라" 같은 연산을 한 번에 처리할 수 있다.

```cpp
FTransform ActorTransform = GetActorTransform();

// 로컬 좌표 (1, 0, 0) 이 이 액터의 회전/위치/스케일을 거치면 월드에서 어디가 되는가?
FVector LocalPoint = FVector(1, 0, 0);
FVector WorldPoint = ActorTransform.TransformPosition(LocalPoint);
```

### 2-3. 로컬 → 월드 변환의 순서 — 스케일 → 회전 → 이동

로컬 좌표를 월드 좌표로 바꿀 때는 이 순서로 계산이 일어난다.

```
월드 좌표 = 이동(회전(스케일(로컬 좌표)))
```

이 순서가 중요한 이유: 스케일을 먼저 적용해야 "그 축 방향으로 늘어난 상태"에서 회전이 걸리고, 회전까지 끝난 다음에야 최종 위치로 옮겨진다. 순서를 바꾸면(예: 회전 먼저, 스케일 나중) 결과가 완전히 달라진다 — 비균등 스케일(X,Y,Z가 서로 다른 스케일)을 준 오브젝트를 회전시키면 이상하게 찌그러져 보이는 버그가 종종 이 순서 문제에서 비롯된다.

`FTransform::TransformPosition()`, `InverseTransformPosition()`은 이 계산을 알아서 처리해준다 — 직접 행렬 곱셈을 짤 필요 없이 함수 호출 하나로 끝난다.

### 2-4. 부모-자식 좌표 변환 — 계층 구조가 쌓일 때

언리얼의 컴포넌트/액터는 부모-자식 계층으로 붙을 수 있다(예: 캐릭터 → 손 소켓 → 무기 메시 → 무기에 붙은 이펙트). 각 단계는 자신의 **부모 기준 로컬 트랜스폼**만 알고 있고, 최종 월드 트랜스폼은 계층을 따라 올라가며 트랜스폼을 순서대로 곱해서 얻는다.

```
월드 트랜스폼(이펙트) = 월드 트랜스폼(캐릭터) * 로컬(손 소켓) * 로컬(무기) * 로컬(이펙트)
```

```cpp
// 개념적으로: 자식의 월드 트랜스폼 = 부모의 월드 트랜스폼과 자신의 로컬 트랜스폼을 합성한 것
FTransform ChildWorldTransform = ChildComponent->GetComponentTransform();
// 내부적으로 GetAttachParent()->GetComponentTransform() 과 자신의 RelativeTransform을 합성해서 계산됨
```

이 계층 구조 덕분에 캐릭터 하나만 움직여도 그 밑에 붙은 무기, 이펙트, 무기에 붙은 파티클까지 전부 자동으로 따라 움직인다 — 매번 월드 좌표를 다시 계산해서 넣어줄 필요가 없다.

### 2-5. 월드 → 로컬 역변환

반대로 "월드 좌표를 이 액터 기준 로컬 좌표로 바꿔줘"가 필요할 때도 있다. 예를 들어 "폭발 지점이 캐릭터 정면 기준 앞인지 뒤인지" 판단할 때.

```cpp
FVector ExplosionWorldLocation = ...;
FTransform CharTransform = GetActorTransform();

// 월드 좌표를 캐릭터 로컬 좌표로 역변환
FVector LocalExplosion = CharTransform.InverseTransformPosition(ExplosionWorldLocation);

// 로컬 X가 양수면 캐릭터 앞, 음수면 뒤 (언리얼 로컬 좌표 기준)
bool bInFront = LocalExplosion.X > 0.0f;
```

3, 4강에서 내적/외적으로 앞/뒤, 좌/우를 판정했던 것과 결과적으로 같은 목적이다. 다만 로컬 좌표 변환을 쓰면 "앞/뒤"뿐 아니라 "정확히 로컬 좌표계에서 어디에 있는지"까지 한 번에 얻을 수 있다는 차이가 있다.

### 2-6. 회전 합성에 행렬 대신 쿼터니언을 쓰는 이유

여러 회전을 순서대로 이어 붙이는 상황(부모의 회전 위에 자식의 회전을 얹는 것)을 생각해보자. 이걸 오일러 각(Pitch/Yaw/Roll, `FRotator`)으로 직접 계산하면 두 가지 문제가 생긴다.

- **짐벌락(Gimbal Lock):** 특정 각도(예: Pitch가 ±90도)에서 회전축 하나가 다른 축과 겹쳐버려서, 자유도 하나를 잃어버리는 현상. 캐릭터가 완전히 위나 아래를 바라볼 때 카메라가 갑자기 홱 돌아가는 버그로 종종 나타난다.
- **보간의 부자연스러움:** 두 오일러 각 사이를 선형으로 보간하면 회전 경로가 최단 경로가 아닐 수 있고, 축마다 따로 보간하면 부자연스럽게 흔들리는 경우가 생긴다.

`FQuat`(쿼터니언)은 이 두 문제를 구조적으로 피한다. 회전 두 개를 합성할 때는 그냥 쿼터니언끼리 곱하면 되고(`QuatA * QuatB`), 두 회전 사이를 부드럽게 보간할 때는 `FQuat::Slerp`(구면 선형 보간)를 쓰면 항상 최단 경로로 자연스럽게 이어진다. 그래서 언리얼 내부적으로 `FTransform`은 회전을 `FQuat`으로 저장하고, `FRotator`는 어디까지나 사람이 값을 읽고 입력하기 편하도록 겉으로 보여주는 표현일 뿐이다. 실무에서 회전을 직접 계산하거나 합성할 일이 있으면 `FRotator`끼리 더하고 빼는 대신 `FQuat` 연산을 쓰는 게 정석이다.

## 3. 그림으로 보면

```
월드 좌표계                    캐릭터 로컬 좌표계
   (0,0,0) 기준                  (캐릭터 위치/회전 기준)

      Y                              Y'
      │                              │
      │   ● Character (500,300,0)   │  ● Weapon (로컬: 10, 0, 5)
      │  ╱                          │ ╱
      │ ╱ (회전됨)                   │╱
      └──────── X            ───────┴──────── X'
                                (캐릭터 기준으로는
                                 항상 같은 상대 위치)
```

캐릭터가 월드에서 어디로 이동하고 얼마나 회전하든, 무기의 **로컬 좌표(10, 0, 5)는 절대 안 바뀐다.** 바뀌는 건 그걸 월드로 환산한 결과뿐이다.

## 4. 코드로 — 실제 사례: 카메라 뒤에서 총알 발사

3인칭 게임에서 "카메라가 보는 방향으로, 캐릭터 손 위치에서" 총알을 발사하는 로직은 여러 좌표계가 섞인다.

```cpp
void AMyCharacter::FireWeapon()
{
    // 총구(무기 메시의 소켓)의 "월드" 위치 — 계층 구조를 따라 자동 계산됨
    FVector MuzzleWorldLocation = WeaponMesh->GetSocketLocation(TEXT("Muzzle"));

    // 카메라가 보는 "월드" 방향
    FVector CameraForward = CameraComponent->GetForwardVector();

    FActorSpawnParameters SpawnParams;
    AProjectile* Projectile = GetWorld()->SpawnActor<AProjectile>(
        ProjectileClass, MuzzleWorldLocation, CameraForward.Rotation(), SpawnParams);
}
```

`GetSocketLocation()`이 내부적으로 캐릭터 → 무기 메시 → 소켓까지 이어지는 로컬 트랜스폼들을 전부 곱해서 월드 좌표 하나로 환산해준다. 이 계산을 직접 짤 필요가 없다는 게 `FTransform`/소켓 시스템이 주는 실질적인 이득이다.

## 5. 흔한 오해

### 오해 1: "GetActorLocation()과 GetRelativeLocation()은 같은 걸 반환한다"

`GetActorLocation()`은 월드 좌표, `GetRelativeLocation()`은 부모(또는 부착된 대상) 기준 로컬 좌표다. 부모가 없는 최상위 액터라면 둘이 우연히 같을 수 있지만, 부모-자식 관계가 있는 컴포넌트에서는 완전히 다른 값이다.

### 오해 2: "스케일, 회전, 이동은 순서 상관없이 적용해도 결과가 같다"

행렬 곱셈(변환의 합성)은 교환법칙이 성립하지 않는다. 언리얼은 스케일 → 회전 → 이동 순서로 고정해서 처리하고, 특히 비균등 스케일이 걸린 오브젝트를 회전시키면 순서에 따라 결과가 눈에 띄게 달라진다.

### 오해 3: "자식을 부모에 붙이면(Attach) 자식의 월드 좌표도 그대로 유지된다"

`AttachToComponent`를 어떤 `AttachmentTransformRules`로 호출하느냐에 따라 다르다. `KeepWorldTransform`은 월드 좌표를 유지하도록 로컬 좌표를 역산해서 맞춰주고, `KeepRelativeTransform`(더 흔히 씀)은 로컬 좌표를 유지하는 대신 월드 좌표가 부모를 따라 즉시 바뀐다. 어떤 규칙을 쓰느냐를 명확히 알고 골라야 한다.

### 오해 4: "월드 좌표만 알면 로컬 좌표는 몰라도 된다"

두 캐릭터의 상대적 위치 관계(정면/후방, 좌/우)를 판정하거나, 부모를 따라다니는 오브젝트를 다룰 때는 로컬 좌표 개념 없이는 설명 자체가 안 된다. 3, 4강에서 내적/외적으로 처리했던 앞/뒤·좌/우 판정도 결국 "월드 좌표를 로컬 좌표계 관점으로 재해석"하는 것과 본질이 같다.

## 6. 면접에서 나오면

**Q1. 월드 좌표와 로컬(상대) 좌표의 차이가 뭔가요?**
→ "월드 좌표는 레벨의 원점을 기준으로 한 절대 위치고, 로컬 좌표는 부모 오브젝트나 소켓 같은 특정 기준점에 대한 상대 위치입니다. 자식이 부모를 따라 움직이게 하려면 로컬 좌표를 고정해두고, 월드 좌표는 매번 자동으로 재계산됩니다."

**Q2. FTransform은 뭘 담고 있나요?**
→ "위치(Translation), 회전(Rotation), 스케일(Scale)을 하나로 묶은 구조체입니다. 이 세 정보를 합치면 한 좌표계를 다른 좌표계로 바꾸는 변환을 표현할 수 있습니다."

**Q3. 로컬 좌표를 월드 좌표로 바꿀 때 순서가 왜 중요한가요?**
→ "행렬 변환은 교환법칙이 성립하지 않아서, 스케일-회전-이동을 적용하는 순서에 따라 최종 위치가 달라집니다. 특히 비균등 스케일이 걸린 오브젝트를 회전시키면 순서 차이가 눈에 보이는 왜곡으로 나타납니다."

**Q4. 캐릭터에 무기를 붙일 때 왜 상대 좌표(Relative)를 쓰나요?**
→ "무기 위치를 월드 좌표로 고정하면 캐릭터가 움직여도 무기는 그 자리에 남습니다. 손 소켓 기준 상대 좌표로 고정해야, 캐릭터가 이동하거나 회전할 때 무기의 월드 좌표만 자동으로 재계산되면서 손을 따라다니게 됩니다."

**Q5. 부모-자식 계층이 여러 단계로 쌓이면 자식의 월드 좌표는 어떻게 구하나요?**
→ "루트부터 시작해서 각 단계의 로컬 트랜스폼을 순서대로 합성(곱)해서 구합니다. 캐릭터, 손 소켓, 무기, 무기에 붙은 이펙트처럼 계층이 깊어져도 각 단계는 바로 위 부모 기준 로컬 트랜스폼만 알면 되고, 최종 월드 트랜스폼은 이 계층을 따라 자동으로 계산됩니다."

**Q6. 어떤 지점이 캐릭터 기준으로 앞에 있는지 뒤에 있는지, 내적 대신 좌표 변환으로 판정한다면 어떻게 하겠어요?**
→ "월드 좌표를 캐릭터의 InverseTransformPosition으로 로컬 좌표로 변환하고, 로컬 X 값의 부호를 보면 됩니다. 내적으로 판정하는 것과 결과는 같지만, 좌표 변환 방식은 앞/뒤뿐 아니라 정확한 상대 위치까지 한 번에 얻을 수 있다는 차이가 있습니다."

**Q7. AttachToComponent에서 KeepRelativeTransform과 KeepWorldTransform 중 뭘 고르겠어요?**
→ "보통은 KeepRelativeTransform을 씁니다. 무기를 손에 붙이는 것처럼 자식이 부모를 따라다니길 원하면 로컬 좌표가 고정되는 게 자연스럽기 때문입니다. 반대로 월드 좌표를 그대로 유지하면서 붙이고 싶을 때만 KeepWorldTransform을 씁니다."

## 7. 셀프 체크

- [ ] 월드 좌표와 로컬 좌표의 차이를 설명할 수 있다.
- [ ] FTransform이 위치·회전·스케일을 함께 담는다는 걸 안다.
- [ ] 좌표 변환에서 스케일-회전-이동 순서가 중요한 이유를 설명할 수 있다.
- [ ] 부모-자식 계층에서 자식의 월드 좌표가 어떻게 계산되는지 안다.
- [ ] KeepRelativeTransform과 KeepWorldTransform의 차이를 설명할 수 있다.
- [ ] 월드 좌표를 로컬 좌표로 역변환하는 상황을 예로 들 수 있다.
