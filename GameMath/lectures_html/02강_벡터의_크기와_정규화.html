벡터의 크기와 정규화

W와 D를 같이 누르면 대각선에서만 41% 더 빨라진다. 크기가 제각각인 벡터를 방향 자리에 넣으면 왜 이런 버그가 나는지, 정규화가 정확히 뭘 하는지 직접 눌러본다.

📏 |V| = √(x²+y²+z²)
🧩 선수지식 1강
⏱️ 약 20분
SECTION 01 · 도입

1이동 속도가 대각선에서만 빨라진다

void AMyCharacter::Tick(float DeltaTime)
{
    FVector Input = FVector(ForwardInput, RightInput, 0.0f);
    AddMovementInput(Input, 1.0f);           // W+D 동시에 누르면 Input = (1, 1, 0)
}

앞으로만 갈 때 (1, 0, 0)의 크기는 1, 대각선 (1, 1, 0)의 크기는 √2 ≈ 1.41. 대각선이 41% 더 빠르게 움직인다. 옛날 게임의 단골 버그 — 원인은 방향만 필요한 자리에 크기가 제각각인 벡터를 넣었기 때문이다.

SECTION 02 · 핵심 · 직접 돌려보기

2대각선 이동 시뮬레이터 — 정규화 안 함 vs GetSafeNormal

방향 패드(또는 키보드 WASD)로 입력을 바꿔보자. 빨간 점선이 정규화 안 한 입력, 초록 화살표가 정규화한 방향이다. 가운데 ●는 입력 없음(0벡터).

정규화 안 함 (MoveSpeed × |Input|)
GetSafeNormal() 적용

MoveSpeed = 500 cm/s. 점선은 500(정상 속도). ① 앞(↑)과 대각선(↗)을 번갈아 눌러 속도 막대가 707로 튀는 것을 보자. ② 가운데 ●(입력 없음)에서는 Normalize()가 0/0으로 NaN이 나오고 GetSafeNormal()은 (0,0)을 안전하게 돌려준다.

SECTION 03 · 크기

3벡터의 크기 — 피타고라스 정리 그 자체

|V| = sqrt(X² + Y² + Z²)     // 3차원으로 확장된 피타고라스 정리 (2D 빗변 sqrt(a²+b²)와 같은 원리)

FVector V = FVector(3.0f, 4.0f, 0.0f);
float Length        = V.Size();          // sqrt(9 + 16 + 0) = 5.0
float LengthSquared = V.SizeSquared();   // 25.0 (루트 계산 생략)

SizeSquared()가 따로 있는 이유: sqrt는 상대적으로 비싼 연산이다. 거리를 비교만 할 거면 제곱끼리 비교해도 대소 관계가 같다. 몬스터 수백 마리 중 가장 가까운 걸 찾는 타겟팅/어그로 계산에서 프레임 타임에 영향을 준다.

// 나쁜 예: 거리 비교에 굳이 sqrt 두 번
if (FVector::Dist(A, B) < FVector::Dist(A, C)) { ... }
// 좋은 예: 제곱 거리로 비교 (sqrt 생략)
if (FVector::DistSquared(A, B) < FVector::DistSquared(A, C)) { ... }
SECTION 04 · 정규화

4방향만 남기고 크기를 1로

Normalized(V) = V / |V|          // 크기 1인 벡터 = 단위 벡터(Unit Vector)

FVector V   = FVector(3.0f, 4.0f, 0.0f);   // 크기 5
FVector Dir = V.GetSafeNormal();           // (0.6, 0.8, 0.0), 크기 1  — 0.6 = 3/5, 0.8 = 4/5

정규화하면 "어느 쪽을 가리키는가"만 남고 "얼마나 긴가"는 1로 고정된다. 방향(각 축의 비율)은 그대로다 — 시뮬레이터에서 빨간 점선과 초록 화살표가 같은 방향을 가리키는 것을 확인했다.

SECTION 05 · 0벡터 함정

5왜 GetSafeNormal()을 쓰는가

크기가 0인 벡터(멈춰 있을 때의 이동 입력, 자기 자신과의 변위)를 정규화하면 0으로 나누기가 된다.

Normalize()

0 근처 처리가 약해 그대로 나눠 NaN을 만들 수 있다.

GetSafeNormal()

크기가 너무 작으면 정규화를 시도하지 않고 0벡터를 그대로 반환한다.

FVector Zero = FVector::ZeroVector;
FVector R1 = Zero.GetSafeNormal();   // (0, 0, 0) — 안전
// FVector R2 = Zero; R2.Normalize();   // 내부적으로 0 나누기 위험

캐릭터가 멈춰 있을 때 이동 입력이 0벡터가 되는 건 흔하다. 이걸 못 다루면 방향이 NaN이 되어 캐릭터가 화면 밖으로 튕겨나가는 버그가 된다. 실무에선 거의 항상 GetSafeNormal().

"안전"의 기준: 정확히 0인지가 아니라 허용 오차(KINDA_SMALL_NUMBER 수준) 이하인지를 본다. 부동소수점 오차 때문에 논리적으로 0인 값이 0.0000001로 남는 경우가 흔해서, == 0.0f 비교로는 놓친다. 정확한 동등 비교 대신 허용 오차 비교 — 게임 코드 전반에서 반복되는 패턴이다.

6정규화가 필요한 대표 상황

상황왜 정규화가 필요한가
이동 입력 벡터대각선 입력이 축 방향 입력보다 빨라지는 걸 막음
GetActorForwardVector() 등애초에 항상 정규화된 상태로 제공됨 (크기 1 보장)
두 지점 사이 "방향만" 필요할 때(B-A)는 거리에 비례해 커지므로 방향만 쓰려면 정규화 필수
내적으로 각도를 구할 때 (3강)정규화 안 하면 각도가 아니라 거리가 섞인 값이 나옴
법선 벡터, 회전축 (4강)방향의 "순수한 표현"이 필요 → 항상 단위 벡터
SECTION 07 · 실전

78방향 이동 정규화

void AMyCharacter::ApplyMovementInput(float ForwardAxis, float RightAxis, float DeltaTime)
{
    FVector RawInput  = FVector(ForwardAxis, RightAxis, 0.0f);
    FVector Direction = RawInput.GetSafeNormal();                  // 멈춤 상태(0벡터)도 안전하게 (0,0,0)
    FVector Movement  = Direction * MoveSpeed * DeltaTime;         // 방향(크기 1) × 속도(스칼라) × 시간
    AddActorWorldOffset(Movement, true);
}

Direction은 항상 크기 1(정지 시 0)이라 앞이든 대각선이든 MoveSpeed가 일정하게 적용된다. 방향과 크기를 분리해서 다루는 것이 벡터 연산의 기본 패턴이다.
