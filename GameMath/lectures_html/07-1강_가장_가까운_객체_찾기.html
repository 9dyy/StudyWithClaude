가장 가까운 객체 찾기

"2차원 평면에서 수많은 객체 중에 가장 가까운 객체를 찾는 법." O(N) 전수 탐색에서 멈추는 답과, 그 다음을 아는 답은 다르다. 그리드를 직접 만져보며 어디까지 봐야 정답이 보장되는지를 확인한다.

🎯 실제로 받은 질문
🧩 선수지식 2강 · 7강
⏱️ 약 25분
SECTION 01 · 실제 질문

1"수많은 객체 중 가장 가까운 걸 어떻게 찾아?"

정답이 하나가 아닌 질문이다. 면접관은 "다 돌면 돼요"에서 멈추는지, 그 다음을 아는지 본다. 좋은 답은 ① 기본(전수 탐색) → ② 언제 무너지는지 → ③ 공간 분할 순서로 확장한다.

SECTION 02 · 1단계

2전수 탐색 — 일단 이게 정답인 경우가 많다

int32 FindNearest(const TArray<FVector2D>& Points, const FVector2D& Query)
{
    int32 Best = INDEX_NONE;
    double BestDistSq = TNumericLimits<double>::Max();

    for (int32 i = 0; i < Points.Num(); ++i)
    {
        const double DistSq = FVector2D::DistSquared(Points[i], Query);   // sqrt 없음 (2강)
        if (DistSq < BestDistSq) { BestDistSq = DistSq; Best = i; }
    }
    return Best;
}

O(N), 추가 메모리 없음. 원소가 수천 개고 질의가 프레임당 한두 번(커서 아래 객체, 락온 타겟)이면 이걸로 충분하다 — 연속 배열이라 캐시 지역성도 좋다(Cpp 4강). 이걸 먼저 말하는 게 맞다. 처음부터 쿼드트리를 꺼내면 과한 설계로 보인다.

언제 무너지나

모든 객체가 각자 가장 가까운 상대를 찾는 질의가 N번 일어날 때. 몬스터 1,000마리 × 1,000 = 100만 번의 거리 계산. N이 10배가 되면 100배다.

발상

"멀리 있는 건 볼 필요가 없다." 공간을 미리 나눠 두고 기준점 근처만 검사한다 — 7강 브로드 페이즈와 같은 아이디어다.

SECTION 03 · 핵심 · 직접 찾아보기

3균등 그리드 최근접 탐색 시각화

캔버스를 클릭해 기준점(십자)을 옮겨보자. 방식을 바꿔가며 거리 계산 횟수와 정답 여부를 본다. 그리드는 기준점이 있는 셀부터 링(ring) 모양으로 바깥으로 넓혀가며 찾고, 충분히 봤다는 조건이 되면 멈춘다. 옆 셀을 안 보거나 링을 고정하면 오답이 나온다.

해볼 것 ① 전수 탐색은 항상 N번 계산한다. ② 링 확장으로 바꾸면 검사한 셀이 몇 칸뿐이고 계산 횟수가 크게 줄어도 답은 같다. ③ 내 셀만으로 바꾸고 기준점을 셀 경계 바로 옆에 놓아보자 — 옆 셀의 점이 더 가까운데 놓치거나, 아예 "못 찾음"이 나온다. ④ 3×3 고정은 N을 줄여(객체가 듬성듬성) 시험하면 오답이 난다. ⑤ 분포를 뭉침으로 바꾸면 셀 하나에 점이 몰려 그리드의 이득이 줄어든다. ⑥ 셀 크기를 너무 작게/크게 잡으면 어떻게 되는지 벤치로 확인해보자.

SECTION 04 · 원리와 선택

4종료 조건 — 언제 멈춰도 정답이 보장되나

for (int32 R = 0; ; ++R)
{
    // 링 R: Center에서 체비쇼프 거리가 정확히 R인 셀들을 전부 검사
    for (const FIntPoint& Cell : RingCells(Center, R)) { /* 셀 안의 점들 DistSquared로 비교 */ }

    // 링 R까지 봤다면, 그 바깥 점은 기준점에서 최소 R×S 이상 떨어져 있다.
    // 이미 찾은 거리가 그보다 가깝다면 더 볼 필요가 없다.
    if (Best != INDEX_NONE && BestDistSq <= (R * S) * (R * S)) break;
    if (R > MaxRing) break;   // 객체가 없는 경우 등 무한 루프 방지
}

이 종료 조건이 알고리즘의 핵심이다. 기준점은 중심 셀 안에 있으니 (2R+1)×(2R+1) 블록 바깥은 최소 R×S만큼 멀다. "링 1까지만 본다"처럼 고정하면 객체가 듬성듬성한 곳에서 오답이 난다. 셀 크기 S는 성능을 좌우한다 — 너무 작으면 빈 셀을 많이 뒤지고(링이 길어짐), 너무 크면 셀 하나에 몰려 전수 탐색과 다를 바 없다.

방식잘 맞는 상황약점
균등 그리드 / 공간 해시분포가 고르고 객체 크기가 비슷, 객체가 자주 움직임쏠리면 셀 하나가 터짐, 셀 크기 튜닝
쿼드트리 (3D는 옥트리)밀집 지역과 빈 지역이 섞인 불균등 분포, 동적 객체트리 순회/갱신 비용, 구현 복잡
KD-tree정적인 점 집합에서 최근접 질의를 아주 많이 (평균 O(log N))객체가 움직이면 재구성 비용이 큼
BVH크기가 제각각인 객체, 충돌/레이 질의최근접 전용은 아님

고르는 질문: "객체가 자주 움직이나?"(→ 그리드/쿼드트리), "정적인가?"(→ KD-tree), "분포가 고른가/쏠려 있나?"(→ 그리드/쿼드트리). 그리고 항상 먼저 "정말 필요한가?" — N이 작으면 전수 탐색이 가장 빠르고 단순하다.

5엔진이 이미 가진 공간 분할을 먼저 쓴다

// ❌ 매 프레임 이렇게 하면 월드의 모든 액터를 훑는다
UGameplayStatics::GetAllActorsOfClass(GetWorld(), AEnemy::StaticClass(), AllEnemies);

// ✅ 대상 목록을 서브시스템에 캐시하거나 (Cpp 4-1강의 몬스터 매니저)
//    반경 안의 액터만 물리 엔진의 브로드 페이즈로 조회한다
TArray<AActor*> Nearby;
UKismetSystemLibrary::SphereOverlapActors(GetWorld(), Location, Radius, ObjectTypes, AEnemy::StaticClass(), IgnoreActors, Nearby);

반경 조회는 엔진이 이미 갖고 있는 공간 분할을 재사용하는 방법이다. 직접 구조를 짜기 전에 먼저 쓴다. 가장 가까운 하나가 목적이라면 오버랩 결과에서 DistSquared 최솟값을 고른다. 액터가 아주 많은 시뮬레이션(군집 등)은 액터 대신 배열 기반 자료 + 자체 그리드로 가기도 한다. 3차원에서는 쿼드트리가 옥트리가 되고, 언리얼에도 TOctree2 같은 컨테이너가 있다.
