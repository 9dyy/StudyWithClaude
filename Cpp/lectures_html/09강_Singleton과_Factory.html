Singleton과 Factory

"딱 하나만 존재해야 한다"를 강제하는 Singleton, "만드는 방법"을 한 곳에 모으는 Factory. 전통적인 Singleton이 언리얼에서 왜 삐걱대는지를 PIE를 여러 번 돌려보며 확인하고, Factory의 진짜 가치는 "수정 지점 수"로 잰다.

SECTION 01 · 도입

1전역 사운드 매니저를 여기저기서 new 하다가 생긴 혼란

배경음악과 효과음을 관리하는 SoundManager가 필요했다. 처음엔 각 시스템(UI, 전투, 대화)이 자기 인스턴스를 만들어 썼다.

class UMenuWidget : public UUserWidget
{
    USoundManager* SoundManager = NewObject<USoundManager>();   // 여기서도 하나
};

class ACombatSystem : public AActor
{
    USoundManager* SoundManager = NewObject<USoundManager>();   // 여기서도 또 하나
};

인스턴스가 여러 개 생기니 "지금 재생 중인 사운드 목록"이 인스턴스마다 따로 관리돼서, 전투 시스템이 재생한 사운드를 메뉴 시스템이 끌 수가 없다. 딱 하나만 존재해야 하는 게 명확한 대상인데 여러 개가 생겨버린 거다. 이럴 때 쓰는 게 Singleton 패턴 — "이 클래스의 인스턴스는 프로그램 전체에서 딱 하나만 존재하게 강제한다."

SECTION 02 · 전통적인 Singleton

2Meyer's Singleton (1강 복습)

지역 static 변수는 "최초 호출 때 딱 한 번만 생성"된다(1강). 이걸 이용한다.

class FSoundManager
{
public:
    static FSoundManager& Get()
    {
        static FSoundManager Instance;   // 최초 호출 때 딱 한 번 생성. C++11부터 초기화 자체는 스레드 안전
        return Instance;
    }

    void PlaySound(USoundBase* Sound) { /* ... */ }

private:
    FSoundManager() = default;                              // 생성자를 private으로 막아 외부에서 new 못하게
    FSoundManager(const FSoundManager&) = delete;            // 복사도 막아야 진짜 "하나"가 보장됨
    FSoundManager& operator=(const FSoundManager&) = delete;
};

FSoundManager::Get().PlaySound(ExplosionSound);   // 어디서든 항상 같은 인스턴스

생성자를 private으로 막고, 복사 생성자/대입 연산자까지 delete로 막는 게 핵심이다. 빼먹으면 FSoundManager Copy = FSoundManager::Get();처럼 실수로 복사본을 만들어 "딱 하나"가 깨질 수 있다.

SECTION 03 · 문제

3이 방식이 언리얼에서 골치 아픈 이유

문제설명
레벨/월드 전환과 생명주기가 안 맞음프로그램이 끝날 때까지 살아있는데, 사운드 매니저는 "이 플레이 세션 동안만" 살아야 할 수도 있음
언리얼 객체 시스템(GC, 리플렉션)과 안 맞음UObject가 아니라서 블루프린트 노출, 가비지 컬렉션 추적이 안 됨
테스트/PIE에서 상태가 안 초기화됨에디터에서 플레이를 여러 번 실행해도 static 인스턴스는 그대로 남아 이전 세션 상태가 남을 수 있음
유닛 테스트가 어려움전역 상태라서 테스트마다 깨끗한 상태로 리셋하기 까다로움

요약: 전통적인 Singleton은 "프로그램 생명주기"에 묶이는데, 게임은 "월드/세션 생명주기"가 그것과 다르다. 세 번째 행을 바로 다음 절에서 직접 재현한다.

SECTION 04 · 핵심 · 직접 돌려보기

4GameInstance/Subsystem — "생명주기가 명확한 Singleton"

언리얼은 이미 생명주기가 정의된 전역 객체 계층을 갖고 있다. 아래는 같은 사운드 관리자를 세 가지 방식으로 만든 세 개의 인스턴스가 에디터 PIE 세션에서 어떻게 사는지 보여준다. 버튼을 눌러 PIE를 시작하고, 사운드를 재생하고, PIE를 종료하고, 다시 시작해보자.

GameInstance          — 게임 실행 시작부터 종료까지 (레벨을 넘나들어도 유지) — 딱 하나
  └─ GameInstanceSubsystem  — GameInstance와 생명주기를 같이함

World                 — 레벨 하나가 로드되어 있는 동안만 (레벨 전환 시 새로 생성)
  └─ WorldSubsystem        — World와 생명주기를 같이함

해볼 것 ① PIE 시작 → 사운드 재생 몇 번 → PIE 종료 → 다시 PIE 시작. 전통 Singleton(왼쪽)만 이전 세션의 사운드가 빨간색으로 남아 있다 — GameInstance/World는 새로 만들어져 깨끗하다. 이게 "PIE에서 상태가 초기화 안 됨"이다. ② 레벨 전환은 WorldSubsystem만 새로 만든다(재생 목록이 비어짐) — GameInstanceSubsystem은 레벨을 넘어 살아남는다. 사운드 매니저가 "세션 동안 살아야 한다"면 GameInstanceSubsystem, "레벨마다 리셋돼야 한다"면 WorldSubsystem으로 수명을 고르는 것이 요점이다. ③ 에디터 종료를 눌러야 비로소 static이 사라진다.

UCLASS()
class USoundManagerSubsystem : public UGameInstanceSubsystem
{
    GENERATED_BODY()

public:
    virtual void Initialize(FSubsystemCollectionBase& Collection) override
    {
        Super::Initialize(Collection);
        UE_LOG(LogTemp, Log, TEXT("SoundManager 초기화 — GameInstance가 생성될 때 자동 호출"));
    }

    virtual void Deinitialize() override
    {
        UE_LOG(LogTemp, Log, TEXT("SoundManager 정리 — GameInstance가 파괴될 때 자동 호출"));
        Super::Deinitialize();
    }

    void PlaySound(USoundBase* Sound) { /* ... */ }
};

// 어디서든 GameInstance를 거쳐 딱 하나뿐인 인스턴스에 접근
USoundManagerSubsystem* SoundManager = GetGameInstance()->GetSubsystem<USoundManagerSubsystem>();
SoundManager->PlaySound(ExplosionSound);

"딱 하나"라는 Singleton의 본질은 그대로다 — GetSubsystem<T>()는 항상 같은 인스턴스를 리턴한다. 다만 그 하나의 생명주기가 프로그램 전체가 아니라 GameInstance나 World에 명확히 묶여서, PIE를 껐다 켜면 자동으로 새로 초기화되고, UObject라서 GC 추적과 블루프린트 노출도 공짜로 딸려온다. 8강 Observer와 조합하면 Subsystem이 전역 이벤트 허브 역할을 하기도 한다.

SECTION 05 · 핵심 · 직접 돌려보기

5Factory Pattern — "생성 로직을 한 곳에 몰아넣기"

Singleton이 "인스턴스 개수"를 통제한다면 Factory는 "생성 방법과 절차"를 한 곳에 모은다. 적을 스폰하는 곳이 5군데 있다고 하자. 요구사항이 왔다 — "오크 초기 체력을 120에서 150으로 올려주세요." 몇 군데를 고쳐야 할까?

구조

① Factory 없음에서 각 스폰 지점의 "체력 150으로 수정"을 눌러 고쳐보자. 하나라도 빠뜨린 채 스폰 테스트를 하면 그 지점의 오크만 120으로 남은 일관성 버그가 드러난다. ② Factory로 모음으로 바꾸면 수정 지점이 1곳이고, 스폰 지점 5곳은 "뭘 만들지"만 안다. 스폰 지점이 몇 개든 상관없다. ③ Factory는 상태가 없으니 인스턴스 없이 호출하는 static 함수(1강)로 만드는 게 자연스럽다. ④ 간단한 경우엔 함수 하나로 충분하고, 복잡해지면 그때 클래스 계층으로 확장해도 늦지 않다.

class FEnemyFactory
{
public:
    static AEnemy* CreateEnemy(UWorld* World, EEnemyType Type, const FTransform& SpawnTransform)
    {
        switch (Type)
        {
        case EEnemyType::Goblin:
        {
            AGoblin* Goblin = World->SpawnActor<AGoblin>(SpawnTransform.GetLocation(), SpawnTransform.Rotator());
            Goblin->SetHealth(50.f);
            Goblin->EquipWeapon(GoblinClub);
            return Goblin;
        }
        case EEnemyType::Orc:
        {
            AOrc* Orc = World->SpawnActor<AOrc>(SpawnTransform.GetLocation(), SpawnTransform.Rotator());
            Orc->SetHealth(120.f);
            Orc->EquipWeapon(OrcAxe);
            return Orc;
        }
        default: return nullptr;
        }
    }
};

// 스폰하는 곳은 이제 "뭘 만들지"만 알면 되고, "어떻게 만들지"는 몰라도 됨
void ASpawnPoint::SpawnEnemy(EEnemyType Type)
{
    AEnemy* NewEnemy = FEnemyFactory::CreateEnemy(GetWorld(), Type, GetActorTransform());
}
SECTION 06 · 함께 쓰기

6Singleton + Factory + Observer

실전에선 셋이 한 시스템 안에서 겹친다. "적 생성 로직은 Factory로 몰고, 그 창구는 Subsystem(사실상 Singleton)으로 둔다."

UCLASS()
class UEnemySpawnSubsystem : public UWorldSubsystem
{
    GENERATED_BODY()

public:
    AEnemy* SpawnEnemy(EEnemyType Type, const FTransform& SpawnTransform)
    {
        AEnemy* NewEnemy = FEnemyFactory::CreateEnemy(GetWorld(), Type, SpawnTransform);
        OnEnemySpawned.Broadcast(NewEnemy);   // 8강 — 스폰 이벤트를 구독자들에게 알림
        return NewEnemy;
    }

    FOnEnemySpawned OnEnemySpawned;
};

Subsystem

"이 월드에서 적 스폰은 딱 한 창구" 보장

Factory

실제로 어떻게 만들지 담당

Delegate

만들어졌다는 걸 누구에게 알릴지 담당
