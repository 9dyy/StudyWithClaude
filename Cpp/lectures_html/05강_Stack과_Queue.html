Stack과 Queue

SECTION 01 · 도입

1Undo를 배열 인덱스로 짜다가 꼬인 코드

레벨 에디터에 되돌리기(Ctrl+Z)를 넣어야 한다. 처음엔 배열에 액션을 쌓고 인덱스로 관리했다.

TArray<FEditAction> ActionHistory;
int32 CurrentIndex = -1;

void Undo()
{
    if (CurrentIndex < 0) return;
    ActionHistory[CurrentIndex].Revert();
    CurrentIndex--;   // 이 인덱스 관리가 점점 꼬인다 — Redo, "되돌린 뒤 새 액션" 처리까지 넣으면 조건문 폭발
}

사실 이 문제는 "가장 최근에 한 일을 가장 먼저 되돌린다" — 정확히 LIFO 구조가 필요한 상황이다. 자료구조 이름을 몰라도 "마지막에 쌓은 것부터 꺼낸다"는 동작이 필요했던 거고, 그게 Stack이다.

SECTION 02 · Stack

2LIFO — 마지막에 넣은 걸 먼저 꺼낸다

한쪽 끝에서만 넣고(Push) 빼는(Pop) 구조. 접시를 쌓고 위에서부터 빼는 그림이다. 아래 에디터에서 액션을 하고 Undo/Redo를 눌러보자 — 스택 두 개가 전부다.

🎬 현재 씬 (아래가 먼저 한 일)

UndoStack (맨 위 = Pop 대상)

RedoStack

액션을 몇 개 하고 Undo → 새 액션을 해보자. Redo 스택이 비워지는 걸 볼 수 있다.
void RecordAction(const FEditAction& A) { UndoStack.Push(A); RedoStack.Empty(); }   // 새 액션 → Redo 무효화
void Undo() { FEditAction A = UndoStack.Pop(); A.Revert();  RedoStack.Push(A); }   // 가장 최근 액션부터 (LIFO)
void Redo() { FEditAction A = RedoStack.Pop(); A.Reapply(); UndoStack.Push(A); }

인덱스로 손수 관리하던 코드가 Stack 두 개로 정리됐다. 핵심은 Push/Pop이라는 이름이 아니라 "가장 최근 걸 먼저 되돌린다 = LIFO"를 알아채는 것. 함수 호출 스택도 정확히 이 구조다(C가 끝나야 B로, B가 끝나야 A로). 3강의 "멤버 소멸이 생성의 역순"도 같은 원리다.

SECTION 03 · Queue

3FIFO — 먼저 넣은 걸 먼저 꺼낸다

한쪽 끝에서 넣고(Enqueue) 반대쪽에서 꺼낸다(Dequeue). 놀이기구 줄서기 그대로다. 언리얼에선 TQueue(스레드 안전 옵션 지원).

TQueue<FUnitCommand> CommandQueue;

void AUnit::IssueCommand(const FUnitCommand& Cmd) { CommandQueue.Enqueue(Cmd); }   // 명령을 큐 끝에 추가

void AUnit::Tick(float DeltaTime)
{
    if (bIsExecutingCommand) return;
    FUnitCommand Next;
    if (CommandQueue.Dequeue(Next)) { ExecuteCommand(Next); }   // 가장 먼저 내려진 명령부터
}

RTS 유닛에 "이동 → 공격 → 방어"를 예약해두면 내린 순서 그대로 실행돼야 한다 — FIFO가 딱 맞는다. Stack을 쓰면 가장 나중에 내린 명령이 먼저 실행돼 플레이어 의도와 어긋난다.

SECTION 04 · 핵심 · 직접 돌려보기

4컨테이너 하나만 바꿨는데 탐색이 달라진다 — BFS vs DFS

길찾기 코드에서 frontier(다음에 방문할 칸들)를 담는 컨테이너를 Queue ↔ Stack으로 바꿔보자. 나머지 로직(이웃 탐색, 방문 체크)은 한 글자도 안 바뀐다.

0

-
찾은 경로 길이
0
frontier 최대 크기
TQueue<FGridCell> Frontier;              // ← 이 한 줄만 TArray(Stack)로 바꾸면 DFS
Frontier.Enqueue(StartCell);  Visited.Add(StartCell);

FGridCell Current;
while (Frontier.Dequeue(Current))
{
    if (Current == GoalCell) break;
    for (const FGridCell& N : GetNeighbors(Current))
        if (!Visited.Contains(N)) { Visited.Add(N); Frontier.Enqueue(N); }   // 가까운 순서를 지키려고 큐 끝에
}

Queue는 가까운 칸부터 물결처럼 퍼지며 최단 경로를 보장한다. Stack은 가장 최근에 넣은 이웃을 먼저 파고들어 한쪽으로 깊게 들어가고 경로가 구불구불하다. "BFS는 Queue, DFS는 Stack" — 자료구조 선택이 알고리즘의 성격을 결정한다.

SECTION 05 · 내부 구현

5내부적으로 뭘로 구현하나 — 배열이냐 LinkedList냐

Stack → 배열(TArray)이 정석

Push/Pop이 전부 끝에서 일어나 O(1). 4강에서 본 배열의 캐시 지역성 이점을 그대로 가져간다.

Queue를 배열 그대로 쓰면

앞에서 빼는 RemoveAt(0)이 나머지를 전부 앞으로 당겨야 해서 O(n). 4강의 "앞 삭제는 배열이 O(n)"과 같은 문제.

방법 1: 원형 버퍼 — 배열이지만 앞/뒤 인덱스를 순환시켜 "앞에서 빼기"도 인덱스만 옮기는 O(1)
┌───┬───┬───┬───┬───┐
│ C │ D │   │   │ A │B│   ← Head가 뒤쪽으로 순환하며 앞에서 뺀 자리를 재활용
└───┴───┴───┴───┴───┘
      ↑Tail          ↑Head (순환)
방법 2: 연결 리스트 기반 — TQueue가 내부적으로 사용

Queue는 앞/뒤 양쪽에서 O(1)로 넣고 뺄 수 있어야 쓸모가 있다. 그걸 어떤 내부 구조로 구현하느냐는 4강의 배열 vs LinkedList 트레이드오프로 다시 판단하는 문제다.

6스킬 콤보 입력 검증

void FComboValidator::PushInput(EComboInput Input)
{
    InputStack.Push(Input);
    if (InputStack.Num() > MaxComboLength) { InputStack.RemoveAt(0); }   // O(n)이지만 길이가 5라 무시 가능
}

bool FComboValidator::CheckCombo(const TArray<EComboInput>& Pattern) const
{
    if (InputStack.Num() < Pattern.Num()) return false;
    int32 Offset = InputStack.Num() - Pattern.Num();          // 스택 "맨 위" 쪽 N개만 패턴과 비교
    for (int32 i = 0; i < Pattern.Num(); ++i)
        if (InputStack[Offset + i] != Pattern[i]) return false;
    return true;
}
