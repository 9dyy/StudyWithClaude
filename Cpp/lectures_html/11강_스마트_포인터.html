SECTION 01 · 버그

1shared_ptr로 돌렸더니 메모리가 안 줄어든다

아이템을 인벤토리(소유자)와 퀵슬롯 UI(참조자)가 같이 들고 있어야 해서, 둘 다 TSharedPtr로 짰다.

class FInventoryItem { public: TSharedPtr<FQuickSlot> AssignedSlot; };
class FQuickSlot     { public: TSharedPtr<FInventoryItem> Item; };

퀵슬롯에서 아이템을 빼고 인벤토리 창을 닫아도 둘 다 소멸자가 안 불린다. 서로가 서로를 붙잡고 있어서 참조 카운트가 0이 될 방법이 없다.

SECTION 02 · 단독 소유

2unique_ptr — 소유권은 하나, 복사는 없다

TUniquePtr<FWeaponData> A = MakeUnique<FWeaponData>();
TUniquePtr<FWeaponData> B = A;              // 컴파일 에러! 복사 생성자 삭제됨
TUniquePtr<FWeaponData> C = MoveTemp(A);    // OK — 소유권이 A에서 C로 이동

복사를 허용하면 두 포인터가 같은 메모리를 이중 해제(double free)하는 사고로 직행한다. 그래서 복사는 컴파일 타임에 막고, 이동만 허용한다.

SECTION 03 · 공동 소유

3shared_ptr — 참조 카운트로 여러 명이 같이 소유

TSharedPtr<FInventoryItem> Item = MakeShared<FInventoryItem>();
TSharedPtr<FInventoryItem> SlotRef = Item;      // 복사 OK — 카운트 2
TSharedPtr<FInventoryItem> TooltipRef = Item;   // 카운트 3
// 카운트가 0이 되는 순간에만 delete

"아무도 안 쓰면 자동으로 사라진다"는 편리함 때문에 여러 시스템이 동시에 참조하는 대상에 자주 쓴다. 하지만 이 편리함엔 함정이 있다 — 다음 섹션에서 직접 확인한다.

SECTION 05 · 해결책

5weak_ptr — 소유권 없이 지켜보기만

void FQuickSlot::UseItem()
{
    TSharedPtr<FInventoryItem> Pinned = Item.Pin();   // 살아있으면 shared_ptr, 죽었으면 nullptr
    if (!Pinned.IsValid()) { /* 이미 삭제됨 */ return; }
    Pinned->Use();
}

weak_ptr는 참조 카운트에 전혀 영향을 안 준다. "누가 진짜 주인이고 누가 들여다보기만 하는가"를 먼저 정하면 순환이 아예 안 생긴다.

SECTION 06 · 기반 문법

6move semantics · Rule of 3/5

MoveTemp는 캐스팅일 뿐, 그 자체로는 아무것도 옮기지 않는다

TUniquePtr<FWeaponData> B = MoveTemp(A);
// MoveTemp(A)는 A를 "버려도 되는 값"으로 표시만 함
// 이동 생성자가 그 표시를 보고 내부 포인터를 옮기고 A는 nullptr로 비움

unique_ptr가 복사를 막고 이동만 허용하는 이유도 같다 — 복사를 허용하면 소유자가 둘이 되니, 원래 소유자를 비우고 넘기는 이동만 허락한다.

Rule of 3 / Rule of 5

소멸자·복사 생성자·복사 대입 연산자 중 하나라도 직접 정의해야 한다면, 나머지도 같이 정의해야 한다(Rule of 3). C++11부터는 이동 생성자·이동 대입 연산자까지 포함(Rule of 5).

실무에서는 이 5개를 손으로 다 쓰는 대신, 애초에 TUniquePtr/TSharedPtr로 자원을 감싸서 컴파일러가 만들어주는 기본 복사/이동이 안전하게 동작하도록 만드는 게 훨씬 흔하다.

8면접에서 나오면 — 카드를 뒤집어보기
