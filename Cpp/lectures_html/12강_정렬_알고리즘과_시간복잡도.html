정렬 알고리즘과 시간복잡도

랭킹보드가 100명일 땐 멀쩡하다가 10만 명이 되니 프레임이 무너졌다. Big-O가 정확히 뭘 재는지, 정렬 알고리즘이 왜 이렇게 다른지 비교 횟수로 직접 세어본다.

SECTION 01 · 도입

1랭킹보드가 100명일 땐 안 보이던 버벅임

시즌 랭킹보드를 만들었다. 매초 점수가 바뀌는 플레이어를 점수 내림차순으로 정렬해 보여줘야 한다. 급한 대로 제일 익숙한 방식으로 짰다.

void SortRankingBubble(TArray<FPlayerScore>& Players)
{
    for (int32 i = 0; i < Players.Num() - 1; ++i)
    {
        for (int32 j = 0; j < Players.Num() - 1 - i; ++j)      // ← 이중 루프
        {
            if (Players[j].Score < Players[j + 1].Score) { Players.Swap(j, j + 1); }
        }
    }
}

100명으로 테스트할 땐 매초 정렬해도 티가 안 났다. 시즌이 진행돼 10만 명이 쌓이자 프레임이 눈에 띄게 떨어졌다. 사람은 1000배 늘었는데 체감 렉은 그보다 훨씬 심하게 늘었다 — 왜?

SECTION 02 · Big-O

2Big-O가 재는 것 — "정확한 시간"이 아니라 "늘어나는 추세"

Big-O는 입력 크기 n이 커질 때 연산 횟수가 어떤 속도로 늘어나는지를 나타낸다. "n이 2배가 되면 연산이 몇 배가 되나"를 보는 척도다.

표기이름n=100 → n=10,000이면 연산 횟수는
O(1)상수그대로
O(log n)로그약 2배
O(n)선형100배
O(n log n)선형 로그약 130배
O(n²)이차10,000배

도입의 버블 정렬은 이중 루프라 O(n²). 100명이면 약 1만 번(정확히는 n²/2라 5천 번)이지만 10만 명이면 100억 번 규모(n²/2로 세면 50억)다. 상수 2는 Big-O가 무시하는 부분이다. 사람은 1000배, 연산은 100만 배 — 이게 체감 렉이 사람 수보다 가파르게 나빠진 이유다. Big-O가 상수를 무시하고 추세만 보는 것도, n이 커질수록 실제 성능을 지배하는 건 상수가 아니라 추세이기 때문이다.

SECTION 03 · 핵심 · 직접 돌려보기

3정렬 레이스 — 비교 횟수를 직접 센다

5가지 정렬을 실제로 돌려서 비교 연산 횟수를 센다. 데이터 모양과 n을 바꿔가며 어느 알고리즘이 언제 무너지는지 보자.

데이터 모양
n 500명

① 이미 정렬됨을 골라보자 — "첫 원소 피벗 퀵정렬"이 O(n²)로 무너지고 삽입 정렬은 O(n)으로 날아간다. ② 거의 정렬은 랭킹보드 상황: 삽입 정렬이 의외로 강하다. ③ n을 30 정도로 줄이면 알고리즘 차이가 거의 사라진다 — Big-O는 n이 클 때의 추세다.

SECTION 04 · O(n²) 계열

4버블 / 선택 / 삽입 — 왜 전부 O(n²)일까

셋 다 "바깥 루프로 한 칸씩 훑으면서, 안쪽 루프로 나머지를 다시 훑는다"는 이중 루프 구조다.

알고리즘동작특이점
버블인접한 두 원소를 비교해 순서가 틀리면 교환. 한 바퀴마다 가장 큰 값이 끝으로 "떠오른다"구현 단순
선택남은 범위에서 최솟값을 찾아 맨 앞과 교환. 매 바퀴 "찾기"가 O(n)교환 횟수가 적음
삽입이미 정렬된 앞부분에 새 원소가 들어갈 자리를 찾아 삽입거의 정렬된 데이터에선 O(n)에 가깝다

n이 작을 땐(수십 개 이하) 구현이 단순하고 상수 오버헤드가 적어서 O(n log n)보다 실측이 나을 수도 있다. "이론 복잡도가 낮다"와 "이 상황에서 실제로 더 빠르다"는 다른 이야기다.

SECTION 05 · O(n log n) 계열

5퀵 / 머지 — 분할정복이 만드는 n log n

[8, 3, 5, 1, 9, 2]
        │  분할
   ┌────┴────┐
[8, 3, 5]  [1, 9, 2]
   │  분할       │  분할
 ┌─┴─┐        ┌─┴─┐
[8][3,5]     [1][9,2]
    │  정복 후 병합    │
  [3,5,8] ◀──────▶ [1,2,9]
        │  병합
   [1, 2, 3, 5, 8, 9]

왜 n log n인가. 절반씩 쪼개니 "쪼개는 깊이"는 log n, 각 층에서 병합/비교하는 총 작업량은 n → 층 수 × 층당 작업 = O(n log n). 이진 탐색이 O(log n)인 것과 같은 원리다.

머지 정렬

항상 O(n log n) — 최악도 보장. 대신 병합용 임시 배열로 추가 메모리 O(n). 안정 정렬.

퀵 정렬

피벗 기준으로 작은 것/큰 것을 나누고(파티션) 재귀. 평균 O(n log n), 제자리(in-place)라 실무에서 가장 흔하다. 안정 정렬 아님.

SECTION 06 · 함정

6퀵정렬이 최악의 경우 O(n²)가 되는 이유

평균 O(n log n)은 피벗이 매번 데이터를 어느 정도 균형 있게 반으로 나눈다는 전제 위에 있다. 시뮬레이터에서 "이미 정렬됨"을 고르면 그 전제가 깨지는 걸 직접 봤다.

int32 Partition(TArray<int32>& Arr, int32 Low, int32 High)
{
    int32 Pivot = Arr[Low];   // 이미 정렬된 배열이면 항상 최솟값이 피벗 → 한 개만 떼어내고 n-1개를 다시 재귀
    // ...
}

실무 방어법: 피벗을 무작위로 고르거나 앞/중간/끝의 중간값(median-of-three)을 쓴다. "랭킹보드가 이미 어느 정도 정렬된 채 매초 재정렬"이라는 도입 상황은 바로 이 최악 케이스에 가깝다.

SECTION 07 · 안정 정렬

7동점자를 원래 순서대로 유지할지 말지

안정 정렬은 비교 기준이 같은 원소들의 상대적 순서를 정렬 후에도 그대로 유지한다.

정렬 전: [(김철수, 100점), (이영희, 100점), (박민수, 90점)]  ← 점수 내림차순 정렬

안정 정렬:   [(김철수, 100), (이영희, 100), (박민수, 90)]   ← 100점 동점자 순서 유지
불안정 정렬: [(이영희, 100), (김철수, 100), (박민수, 90)]   ← 순서가 뒤바뀔 수 있음

"동점이면 먼저 달성한 사람이 위"라는 규칙이 있는데 불안정 정렬로 점수만 기준 삼으면 깨질 수 있다. 머지 정렬은 안정, 일반적인 in-place 퀵정렬은 불안정.

SECTION 08 · 실전

8TArray::Sort는 뭘 쓰나 — 랭킹보드 개선

언리얼 TArray::Sort()는 Introsort 계열: 퀵정렬로 시작하되 재귀가 너무 깊어지면 힙정렬로 갈아타서 최악도 O(n log n)에 가깝게 방어한다.

// ❌ 개선 전: O(n²), 매초 10만 명 재정렬
SortRankingBubble(Players);

// ✅ 개선 후: 평균 O(n log n), 최악도 Introsort가 방어
Players.Sort([](const FPlayerScore& A, const FPlayerScore& B)
{
    if (A.Score != B.Score) { return A.Score > B.Score; }   // 점수 내림차순
    return A.LastScoreTime < B.LastScoreTime;            // 동점이면 먼저 달성한 사람이 위 — 2차 기준을 predicate 안에 직접 명시
});

10만 명 기준 버블은 수십억~100억 번 규모, O(n log n)은 10만 × log₂(10만) ≈ 170만 번. 알고리즘만 바꿨을 뿐인데 수천 배 차이 — 이게 "Big-O를 챙기는 게 왜 실무에서 중요한가"의 가장 직접적인 답이다. Sort()는 안정성을 보장하지 않으니 동점자 규칙은 비교 함수 안에서 직접 챙기자.
