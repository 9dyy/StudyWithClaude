State Pattern

대기·이동·공격·사망 상태 분기가 200줄짜리 if-else로 뒤엉킨다. "캐릭터가 상태를 확인하며 분기"하는 대신 "각 상태가 자기 할 일과 다음 전환을 스스로 아는" 구조 — 직접 조작하며 상태를 오가고, 새 상태를 추가해 수정 범위를 재본다.

SECTION 01 · 도입

1캐릭터 상태 분기가 200줄짜리 if-else가 된 사건

Idle, Move, Attack, Dead 상태를 enum과 if-else로 짰다.

enum class ECharacterState { Idle, Move, Attack, Dead };

void ACharacter::Tick(float DeltaTime)
{
    if (CurrentState == ECharacterState::Idle)
    {
        if (InputVelocity.Size() > 0)   CurrentState = ECharacterState::Move;
        else if (bAttackPressed)          CurrentState = ECharacterState::Attack;
        PlayAnimation(IdleAnim);
    }
    else if (CurrentState == ECharacterState::Move)
    {
        if (InputVelocity.Size() == 0)   CurrentState = ECharacterState::Idle;
        else if (bAttackPressed)          CurrentState = ECharacterState::Attack;   // "이동 중 공격 가능?" 로직이 여기 또
        MoveCharacter(InputVelocity, DeltaTime);
        PlayAnimation(MoveAnim);
    }
    else if (CurrentState == ECharacterState::Attack)
    {
        // 공격 진행 체크, 콤보 입력, 공격 중 이동 불가 처리... 상태가 늘수록 이 블록도 위 블록의 조건도 계속 늘어남
    }
    else if (CurrentState == ECharacterState::Dead) { /* ... */ }
}

상태가 4개일 때도 "다른 상태로 전환 가능한지"를 체크하는 조건이 상태마다 흩어져 있다. 여기에 구르기(Dodge), 스킬 시전, 기절이 추가되면 각 상태 블록 안에 다른 모든 상태로의 전환 조건이 다 들어가야 해서 기하급수적으로 꼬인다. "공격 중엔 이동 입력을 무시" 같은 상태 간 규칙도 여러 블록에 중복돼 하나 고치면 다른 곳도 같이 고쳐야 한다.

SECTION 02 · 발상의 전환

2상태마다 자기가 할 일과 전환 규칙을 스스로 갖는다

"캐릭터가 상태를 확인하며 분기"가 아니라 "각 상태가 자기 할 일과 다음 상태로의 전환 조건을 안다." 캐릭터는 현재 상태 객체 하나만 들고 위임한다.

[if-else 방식]                          [State Pattern]

Character                               Character ──→ 현재 CharacterState* 하나만 들고 있음
  │ if CurrentState == Idle: ...              │
  │ else if == Move: ...                      ▼
  │ else if == Attack: ...              CharacterState (인터페이스)
  │ else if == Dead: ...                  ├── IdleState::Tick()   → 자기 전환 조건도 자기가 앎
  └─ 모든 상태 로직이 한 함수에 뒤섞임      ├── MoveState::Tick()
                                          ├── AttackState::Tick()
                                          └── DeadState::Tick()
class FCharacterState
{
public:
    virtual ~FCharacterState() = default;
    virtual void Enter(ACharacter* Character) {}                    // 이 상태로 들어올 때 한 번
    virtual void Tick(ACharacter* Character, float DeltaTime) = 0;  // 이 상태인 동안 매 프레임
    virtual void Exit(ACharacter* Character) {}                     // 이 상태를 떠날 때 한 번
};

class FIdleState : public FCharacterState
{
public:
    virtual void Enter(ACharacter* Character) override { Character->PlayAnimation(IdleAnim); }

    virtual void Tick(ACharacter* Character, float DeltaTime) override
    {
        if (Character->IsAttackPressed())
            Character->ChangeState(MakeUnique<FAttackState>());   // 스마트 포인터로 상태 소유 (11강)
        else if (Character->GetInputVelocity().Size() > 0)
            Character->ChangeState(MakeUnique<FMoveState>());
    }
};

class FAttackState : public FCharacterState
{
public:
    virtual void Enter(ACharacter* Character) override { Character->PlayAnimation(AttackAnim); ElapsedTime = 0.0f; }

    virtual void Tick(ACharacter* Character, float DeltaTime) override
    {
        // 공격 중엔 이동 입력을 아예 검사조차 안 함 — 이 상태 밖에서 신경 쓸 필요가 없어짐
        ElapsedTime += DeltaTime;
        if (ElapsedTime >= AttackDuration) Character->ChangeState(MakeUnique<FIdleState>());
    }
private:
    float ElapsedTime = 0.0f;
    static constexpr float AttackDuration = 0.6f;
};

class ACharacter : public AActor
{
public:
    void Tick(float DeltaTime) override { CurrentState->Tick(this, DeltaTime); }   // 지금 상태에게 위임만

    void ChangeState(TUniquePtr<FCharacterState> NewState)
    {
        CurrentState->Exit(this);
        CurrentState = MoveTemp(NewState);
        CurrentState->Enter(this);
    }
private:
    TUniquePtr<FCharacterState> CurrentState = MakeUnique<FIdleState>();
};

ACharacter::Tick은 이제 "지금 상태 객체에게 물어봐" 한 줄. FAttackState 안에는 이동 입력을 확인하는 코드 자체가 없으니 "공격 중 이동 불가" 규칙이 검사할 필요조차 없이 자연스럽게 지켜진다.

SECTION 03 · 핵심 · 직접 돌려보기

3상태 머신 시뮬레이터 — Enter · Tick · Exit

위 코드가 그대로 도는 캐릭터다. 1 Tick = 0.1초. 이동 입력을 유지하고, 공격·피격을 눌러 상태가 어떻게 바뀌고 Exit/Enter가 어떤 순서로 불리는지 로그로 확인하자. 공격 상태에서 이동 입력을 눌러도 무시되는 것이 핵심 관찰 포인트다.

IdleMoveAttackDodgeDead← 최근 40 Tick

해볼 것 ① 이동 입력 유지 체크 후 Tick 몇 번 → Idle→Move 전환. ② 공격 입력 → Tick → Move→Attack. 공격 중엔 이동 입력이 켜져 있어도 로그에 "이 상태 코드에 없음"이 찍히며 6 Tick(0.6초) 뒤 자동으로 Idle로 돌아간다. ③ 피격 3~4번이면 HP 0 → 어느 상태에서든 Dead. Dead에선 아무 입력도 안 먹는다(부활로 되살림). ④ 아래 "구르기 추가"를 켠 뒤 다시 해보자.

SECTION 04 · 핵심 · 확장 비교

4구르기(Dodge)를 추가하면 몇 군데를 고치나

위 시뮬레이터에 구르기를 추가해보자. 구르기 중엔 무적(Enter에서 켜고 Exit에서 끔), 0.4초 뒤 Idle로 복귀한다. 스위치를 켜면 시뮬레이터에 상태가 하나 늘어나고, 두 구조에서 고쳐야 하는 곳이 아래에 집계된다.

구르기 상태

if-else / enum 방식

0 곳 수정

모든 상태 블록에 "구르기 입력 체크"를 넣고, 그러고 나서 "어 근데 공격 중엔 구르면 안 되지" 하며 예외 조건을 다시 추가하는 식으로 간다.

State Pattern

0 곳 수정

새 클래스 하나 + 그 상태로 들어가는 조건이 필요한 상태에만 한 줄씩. "구르기가 애초에 불가능한" 상태는 손댈 필요가 전혀 없다. "이 상태에 없는 코드는 실행되지 않는다"가 구조로 보장된다.

class FDodgeState : public FCharacterState
{
public:
    virtual void Enter(ACharacter* Character) override
    {
        Character->PlayAnimation(DodgeAnim);
        Character->SetInvincible(true);    // 구르기 중 무적 — 이 상태만의 고유 로직
    }
    virtual void Tick(ACharacter* Character, float DeltaTime) override { /* ... */ }
    virtual void Exit(ACharacter* Character) override { Character->SetInvincible(false); }
};

// FIdleState::Tick, FMoveState::Tick 에만 전환 조건 한 줄씩 추가
if (Character->IsDodgePressed()) Character->ChangeState(MakeUnique<FDodgeState>());

구르기를 켠 뒤 위 시뮬레이터로 돌아가 구르기 입력 → Tick을 눌러보자. 구르기 중 피격을 누르면 "무적"으로 무시되고(Enter/Exit로 무적을 관리), 공격 중에 구르기를 눌러도 Attack 상태엔 그 코드가 없어서 무시된다.

SECTION 05 · Observer 연결

5상태 전환을 알림으로 (8강)

상태가 바뀔 때 UI(상태 아이콘)나 사운드에 알려야 한다면, 8강의 Observer Pattern을 ChangeState 안에 얹는다.

DECLARE_MULTICAST_DELEGATE_TwoParams(FOnStateChanged, FName /*OldState*/, FName /*NewState*/);

class ACharacter : public AActor
{
public:
    FOnStateChanged OnStateChanged;

    void ChangeState(TUniquePtr<FCharacterState> NewState)
    {
        FName OldName = CurrentState->GetStateName();
        CurrentState->Exit(this);
        CurrentState = MoveTemp(NewState);
        CurrentState->Enter(this);
        OnStateChanged.Broadcast(OldName, CurrentState->GetStateName());   // UI 등이 이걸 구독
    }
private:
    TUniquePtr<FCharacterState> CurrentState = MakeUnique<FIdleState>();
};

캐릭터는 여전히 "누가 이 이벤트를 듣는지" 모른다. State Pattern이 "무슨 상태인가"를, Observer Pattern이 "그 변화를 누구에게 알릴까"를 정리해주는 식으로 두 패턴이 자연스럽게 겹친다.

SECTION 06 · 판단

6State Pattern이 항상 정답은 아니다

// 상태가 딱 둘(문이 열림/닫힘)뿐이라면 이 정도로 충분 — 클래스 여러 개 만들 필요 없음
enum class EDoorState { Open, Closed };

void ADoor::Interact()
{
    CurrentState = (CurrentState == EDoorState::Closed) ? EDoorState::Open : EDoorState::Closed;
    PlayAnimation(CurrentState == EDoorState::Open ? OpenAnim : CloseAnim);
}

판단 기준은 "상태 개수 × 상태별 고유 로직의 양"이다. 상태가 4개 이상으로 늘거나, 상태마다 진입/유지/이탈 시 할 일이 복잡해지는 순간부터 if-else의 유지보수 비용이 클래스로 나누는 비용을 넘어선다.
