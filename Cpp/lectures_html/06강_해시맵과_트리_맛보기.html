해시맵과 트리 맛보기

플레이어 ID로 찾는데 매 프레임이 느려졌다. TMap이 배열을 순회하지 않고 위치를 "계산해서" 찾는 원리를 버킷 위에서 직접 확인하고, 정렬이 필요할 땐 왜 트리인지 탐색 경로로 본다.

🗂️ 평균 O(1), 최악 O(n)
🧩 선수지식 4·5강
⏱️ 약 25분
SECTION 01 · 도입

1플레이어 ID로 찾다가 매 프레임이 느려진 코드

TArray<FPlayerInfo> Players;

FPlayerInfo* FindPlayer(int32 PlayerID)
{
    for (FPlayerInfo& Player : Players)   // 매번 처음부터 끝까지 순회
    {
        if (Player.ID == PlayerID) return &Player;
    }
    return nullptr;
}

10명일 땐 문제없었는데, 100명이 넘는 서버에서 매 프레임 여러 시스템이 호출하니 눈에 띄게 느려졌다. 배열에서 값으로 찾는 건 O(n) — 4강에서 본 "탐색은 배열도 LinkedList도 O(n)"이 바로 이 상황이다. "탐색을 거의 안 하고 바로 찾는" 방식이 필요하다. 그게 해시맵(TMap)이다.

SECTION 02 · 원리

2TMap이 O(1)에 가까운 이유 — 위치를 계산해버린다

배열은 "값이 몇 번째에 있는지 몰라서" 순회한다. 해시맵의 아이디어는 "키를 계산해서 바로 위치를 알아내자"다.

TMap<int32, FPlayerInfo> Players;

키(PlayerID) ──→ 해시 함수 ──→ 버킷 인덱스 ──→ 그 버킷에 값 저장

PlayerID=1001 → Hash(1001) = 37 → 버킷[37]에 저장
PlayerID=2002 → Hash(2002) = 12 → 버킷[12]에 저장
PlayerID=3003 → Hash(3003) = 37 → 버킷[37]에 저장  (충돌! 아래에서)

조회할 땐 같은 해시 함수로 어느 버킷을 봐야 하는지 계산으로 바로 안다. 배열을 순회하지 않고 "37번 버킷만 확인하면 된다"는 걸 계산으로 아는 것 — 이게 평균 O(1)의 근거다. 버킷 배열 자체가 TArray라는 점도 눈여겨보자. 결국 배열의 "인덱스로 접근하면 O(1)"(4강)을 해시 함수로 "아무 키나 인덱스로 바꿔서" 활용하는 게 해시맵의 본질이다.

Players.Add(1001, PlayerInfoA);
Players.Add(2002, PlayerInfoB);

FPlayerInfo* Found = Players.Find(1001);   // Hash(1001) 계산 → 바로 그 버킷 확인. 평균 O(1)
SECTION 03 · 핵심 · 직접 돌려보기

3해시 버킷 시각화 — 충돌과 Rehashing을 눈으로

아래 해시맵은 버킷 8개로 시작하고, 해시 함수는 키 % 버킷 수(설명용 단순 모델), 충돌은 체이닝(같은 버킷에 줄줄이 매달기), 로드 팩터가 0.75를 넘으면 버킷을 2배로 늘려 전부 재배치한다. 키를 넣고, 충돌을 만들고, 찾아보자. (실제 TMap의 내부 구현 세부는 다르지만 원리는 같다.)

키
키를 추가해보자. 버킷 인덱스 = 키 % 버킷 수.

① 1001과 1009를 넣어보자 — 둘 다 8로 나눈 나머지가 1이라 같은 버킷에 충돌한다(노랑 → 빨강으로 체인이 길어짐). 충돌은 버그가 아니라 필연이다. ② 원소를 계속 넣으면 7번째(7/8 = 0.88로 기준 0.75 초과)에 Rehashing이 일어난다 — 버킷 수가 바뀌니 모든 키의 인덱스가 다시 계산돼 버킷이 재배치된다. 그 순간만 O(n)이다. ③ 🧷 Reserve(64)를 누른 뒤 100개를 넣어보면 재배치가 (거의) 안 일어난다 — TArray::Reserve와 같은 이유(4강). ④ Find는 해시로 버킷을 바로 찾은 뒤 그 버킷 안의 체인만 훑는다(초록 = 찾은 노드).

SECTION 04 · 측정

4배열 순회 vs 해시 조회 — 비교 횟수를 재본다

원소 N개에서 랜덤한 키 1000개를 찾는 데 필요한 평균 비교 횟수를 실제로 센다. 배열은 앞에서부터 대조, 해시맵은 버킷 하나의 체인만 대조한다.

원소 수 N 1000   

① N을 키워보자 — 배열은 N/2씩 늘어나지만 해시맵은 거의 1~2번에서 고정이다. ② 나쁜 해시 함수를 켜면 모든 키가 한 버킷에 몰려 체인 = 배열 순회가 된다 — 해시맵의 최악 O(n)이 이것이다. 그래서 "평균 O(1), 최악 O(n)"이라고 답해야 정확하다. ③ 원소가 수십 개 이하면 차이가 무의미하다(해시 계산 비용, 배열의 캐시 지역성).

SECTION 05 · 선택 기준

5배열 대신 맵을 언제 쓰나

상황추천이유
인덱스(0, 1, 2…)로 순서대로 접근TArray배열의 O(1) 인덱스 접근을 그대로 활용
ID/이름처럼 임의의 키로 빠르게 찾기TMap순회 없이 평균 O(1) 조회
순서가 중요(입력 순서, 정렬 유지)TArrayTMap은 내부 저장 순서를 보장 안 함
"이 키가 존재하는지"를 자주 확인TMap/TSet존재 여부 확인도 평균 O(1)
원소 개수가 매우 적음(수십 개 이하)TArray도 충분해시 계산 오버헤드가 순회 비용보다 클 수 있음

핵심 판단 기준은 "접근하는 방식이 인덱스냐, 키냐"다. ID로 찾을 거면 TMap, 스폰된 순서대로 순회할 거면 TArray. 둘 다 필요하면 둘 다 유지하며 동기화하는 것도 흔한 패턴이다.

// ID로 찾을 일이 많다 → TMap이 자연스럽다
TMap<int32, FPlayerInfo> PlayerByID;

FPlayerInfo* FindPlayer(int32 PlayerID)
{
    return PlayerByID.Find(PlayerID);   // 평균 O(1) — 도입 문제 해결
}
SECTION 06 · 트리 맛보기

6정렬을 유지하면서 탐색하고 싶을 때 — 트리

해시맵은 "정확히 이 키"에는 최고지만 "이 값보다 작은 것 중 가장 큰 것", "정렬된 순서대로 순회"에는 약하다(순서 개념이 없다). 이럴 때 이진 탐색 트리(BST)를 쓴다 — 왼쪽 자식은 나보다 작고, 오른쪽 자식은 나보다 크다. 값을 골라 탐색 경로를 따라가 보자.

찾을 값 또는 노드를 클릭
트리에 있는 값(20, 30, 40, 50, 60, 70, 80)이나 없는 값(예: 65)을 찾아보자.

매번 비교할 때마다 후보가 절반으로 줄어든다. 균형 잡힌 트리라면 탐색이 O(log n) — 원소가 100만 개여도 약 20번 비교면 찾는다(배열 순회는 100만 번). 없는 값(65)도 경로 끝(빈 자리)까지 가보면 "없음"을 확정한다.

게임에서 트리가 쓰이는 실제 예

우선순위 큐 (힙)

스킬 쿨다운/타이머를 "가장 빨리 끝날 것부터" 꺼낸다.

랭킹 보드

정렬 순서를 유지하며 삽입/삭제/순회.

공간 분할 (쿼드/옥트리)

"이 근처 오브젝트만" 빠르게 찾는 충돌 판정 최적화.

// 우선순위 큐 예 — 가장 먼저 끝나는 쿨다운을 항상 O(log n)에 꺼냄
struct FCooldownEntry
{
    float EndTime;
    FName SkillName;
    bool operator<(const FCooldownEntry& Other) const { return EndTime < Other.EndTime; }
};

TArray<FCooldownEntry> CooldownHeap;

void AddCooldown(FName SkillName, float Duration)
{
    CooldownHeap.HeapPush(FCooldownEntry{ GetWorld()->GetTimeSeconds() + Duration, SkillName });
}

void TickCooldowns()
{
    while (CooldownHeap.Num() > 0 && CooldownHeap.HeapTop().EndTime <= GetWorld()->GetTimeSeconds())
    {
        FCooldownEntry Entry;
        CooldownHeap.HeapPop(Entry);   // 가장 빨리 끝나는 것부터 O(log n)에 꺼냄
        OnCooldownFinished(Entry.SkillName);
    }
}

TArray의 HeapPush/HeapPop이 트리(힙) 구조를 배열 위에 구현해둔 것이다 — 트리는 항상 포인터로 연결된 노드라는 생각과 달리, i번째 노드의 자식은 2i+1, 2i+2처럼 인덱스 계산으로도 트리를 표현할 수 있다.
