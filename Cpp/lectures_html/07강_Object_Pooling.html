Object Pooling

SECTION 01 · 도입

1총알 하나 쏠 때마다 게임이 살짝 끊긴다

기관총을 쏘는 무기를 만들었다. 총알을 쏠 때마다 스폰하고, 맞거나 수명이 다하면 파괴한다.

void AWeapon::Fire()
{
    ABullet* NewBullet = GetWorld()->SpawnActor<ABullet>(BulletClass, GetMuzzleLocation(), GetMuzzleRotation());
    NewBullet->Init(Damage, Speed);
}

void ABullet::OnLifetimeExpired()
{
    Destroy();   // 매번 액터를 파괴 — 내부적으로 메모리 해제 발생
}

초당 10발씩 쏘는 무기 몇 개가 화면에 있으면 프레임이 미세하게 끊긴다. 프로파일러엔 SpawnActor와 Destroy 근처가 시뻘겋다. 총알 하나 만들고 없애는 게 왜 이렇게 비쌀까?

SECTION 02 · 원인

2new/delete가 매 프레임 비싼 이유

new는 "메모리 한 칸 떼주는" 게 아니라, 할당자에게 "이만한 빈 공간 어디 없나"를 찾아달라고 요청하는 과정이다.

// 총알을 만들고 부수기를 반복한 뒤의 힙
┌────┬──────┬────┬────────┬──┬───────┬────┐
│사용중│  빈공간 │사용중│  빈공간   │사용│  빈공간 │사용중│
└────┴──────┴────┴────────┴──┴───────┴────┘
  ↑ 사용중/빈공간이 조각조각 흩어진 상태 = 메모리 단편화(Fragmentation)

탐색 비용

조각난 빈 공간 중 딱 맞는 자리를 찾느라 매번 탐색한다.

단편화

빈 공간을 다 합치면 충분한데 "연속된 큰 블록"이 없어서 할당이 실패할 수 있다.

Destroy는 더 무겁다

소멸자 + 메모리 반납 + 월드에서 액터 등록 해제까지 얹힌다.

캐시 지역성

새로 할당된 총알은 힙의 예측 불가능한 위치 → 100개를 순회해도 캐시 미스 반복 (4강).

SECTION 03 · 핵심 · 직접 돌려보기

3풀링 시뮬레이터 — 힙 조각화 vs 고정 풀

같은 발사 패턴을 매번 new/delete 하는 힙과 미리 만들어둔 풀에 각각 돌려보자. 색깔 칸 하나가 메모리 한 칸이다.

0
빈 칸 합계
0
가장 큰 연속 빈 블록
0
누적 할당·해제 비용
0
발사 성공
0
발사 실패
발사 속도 2발/틱

힙 모드에서 발사 속도를 3으로 올리고 20틱을 몇 번 돌려보면 빈 칸 합계는 남는데 연속 블록이 없어 실패하는 순간이 나온다. 풀 모드는 누적 비용이 훨씬 낮다. 발사 속도를 5로 올리면 풀도 바닥나는데 — 그래서 풀 크기는 실측으로 정해야 한다.

SECTION 04 · 구현

4풀의 핵심 — "미리 만들고, 숨기고, 깨운다"

게임 시작할 때 넉넉히 만들어두고, 안 쓸 땐 숨겨서 재우고, 필요할 때 깨워서 재사용한다.

class ABulletPool
{
public:
    void Initialize(UWorld* World, TSubclassOf<ABullet> BulletClass, int32 PoolSize)
    {
        for (int32 i = 0; i < PoolSize; ++i)
        {
            ABullet* Bullet = World->SpawnActor<ABullet>(BulletClass);
            Bullet->SetActorHiddenInGame(true);
            Bullet->SetActorTickEnabled(false);
            InactiveBullets.Push(Bullet);   // 5강의 Stack — 순서 무관, O(1)이면 충분
        }
    }

    ABullet* AcquireBullet()
    {
        if (InactiveBullets.Num() == 0) { return nullptr; }   // 풀이 바닥남
        ABullet* Bullet = InactiveBullets.Pop();
        Bullet->SetActorHiddenInGame(false);
        Bullet->SetActorTickEnabled(true);
        return Bullet;
    }

    void ReleaseBullet(ABullet* Bullet)
    {
        Bullet->SetActorHiddenInGame(true);
        Bullet->SetActorTickEnabled(false);
        Bullet->ResetState();   // 데미지, 속도 등 이전 사용 흔적 초기화 — 빠뜨리면 버그
        InactiveBullets.Push(Bullet);
    }

private:
    TArray<ABullet*> InactiveBullets;   // 4강 — 배열이라 캐시 지역성도 챙김
};

핵심은 "객체 생성 비용을 게임플레이 도중이 아니라 로딩 시점으로 옮기는 것"이다. 로딩 화면에서 몇 초 더 걸리는 건 못 느끼지만, 전투 중 프레임 드랍은 바로 느낀다.

SECTION 05 · 3강 연결

5RAII로 반납 깜빡임 막기

임시로 잠깐 쓰고 돌려줄 오브젝트(파티클 한 번 재생 등)는 소멸자에서 자동 반납하게 감싸면 된다.

class FScopedPooledBullet
{
public:
    FScopedPooledBullet(ABulletPool* InPool) : Pool(InPool) { Bullet = Pool->AcquireBullet(); }
    ~FScopedPooledBullet()
    {
        if (Bullet) { Pool->ReleaseBullet(Bullet); }   // 소멸자에서 자동 반납
    }
    ABullet* Get() const { return Bullet; }
private:
    ABulletPool* Pool;
    ABullet*     Bullet;
};

발사 후 한동안 살아있다 알아서 끝나는 총알은 OnLifetimeExpired에서 명시적으로 반납하는 쪽이 자연스럽다. RAII 래퍼는 "이 함수 안에서만 잠깐" 쓰는 경우에 유용하다.

SECTION 06 · 바닥나면

6풀이 바닥나면 — 확장 전략

풀 크기를 고정하면 "동시에 그 이상 필요한 순간"이 온다.

전략 1 · 동적 확장

필요한 순간 추가로 만든다. 스파이크는 처리되지만 그 순간 new 비용을 다시 치른다.

전략 2 · 강제 회수

가장 오래전 활성화된 것(화면 밖으로 나간 지 오래된 총알 등)을 회수해 재사용한다.

어느 쪽이든 풀 크기를 처음부터 실측 기반으로 넉넉히 잡는 게 먼저다. 확장 전략은 예외용 안전망이지, 크기 설계를 대충 해도 되는 핑계가 아니다.

SECTION 07 · OS 7강 연결

7여러 스레드가 같은 풀을 공유한다면

물리 콜백·비동기 로딩 콜백 등 다른 스레드에서 같은 풀에 Acquire/Release를 부르면 TArray의 Pop/Push가 겹쳐 Race Condition이 난다.

ABullet* AcquireBullet()
{
    FScopeLock Lock(&PoolCriticalSection);   // RAII 락 — 스코프 벗어나면 자동 해제
    if (InactiveBullets.Num() == 0) return nullptr;
    return InactiveBullets.Pop();
}

대부분의 게임플레이는 게임 스레드 하나에서만 돈다. "이 함수를 어느 스레드에서 부를 수 있는가"를 먼저 확인하고, 필요할 때만 락을 넣자. 항상 걸면 단일 스레드에서도 불필요한 비용이다.
