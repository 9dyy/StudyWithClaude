생성자·소멸자와 RAII

파일을 열어놓고 return해버린 함수. 정리를 "사람이 기억해야 하는 일"에서 "언어가 보장하는 일"로 옮기는 RAII가 왜 스마트 포인터까지 이어지는지 본다.

SECTION 01 · 도입

1파일을 열어놓고 리턴해버린 함수

레벨 로딩 중에 설정 파일을 읽는 함수를 짰다.

void LoadLevelConfig(const FString& Path)
{
    FILE* File = fopen(TCHAR_TO_ANSI(*Path), "r");
    if (File == nullptr) { return; }                  // 파일 못 열면 리턴 — 여긴 괜찮다
    if (!ParseConfig(File))  { return; }              // 파싱 실패해도 리턴 — fclose(File) 까먹음!
    fclose(File);
}

함수에 return이 세 군데면 세 군데 다 fclose를 챙겨야 하는데, 사람이 손으로 관리하면 언젠가 하나는 까먹는다. new 메모리, 소켓, 뮤텍스도 똑같다 — 근본 원인은 "정리를 사람이 매번 챙겨야 한다"는 것. C++은 이걸 생성자/소멸자로 "정리를 객체의 죽음에 자동으로 묶어버리는" RAII로 푼다.

SECTION 02 · 핵심 · 직접 돌려보기

2함수 종료 경로 시뮬레이터 — 손으로 fclose vs RAII

함수가 어떤 경로로 끝나는지를 골라 실행해보자. 손으로 관리하면 경로마다 누수 여부가 갈리고, RAII는 어떤 경로든 똑같다.

경로 버튼을 눌러 함수를 실행해보자.
0
함수 실행 횟수
0
새고 있는 파일 핸들

손으로 관리 모드에서 B, C를 몇 번 실행해보자 — 핸들이 계속 쌓인다. 그리고 C는 "처음 코드엔 없었는데 나중에 누가 return을 하나 추가한" 경로다. RAII 모드에선 어느 경로든 소멸자가 fclose를 대신 한다.

SECTION 03 · 생성자

3초기화 리스트 vs 본문 대입

차이는 "생성이냐 대입이냐"다.

멤버 초기화 리스트

멤버를 그 값으로 바로 생성한다.

생성자 본문 대입

멤버가 먼저 기본값으로 생성된 뒤 대입 연산으로 덮어쓴다 — 한 단계 더 거친다.

AWeapon(const AActor* InOwner)
    : Damage(10.0f)
    , OwnerName(TEXT("Unknown"))
    , Owner(InOwner)          // const / 참조 멤버는 대입이 불가능 → 초기화 리스트가 필수
{ }

private:
    float Damage;
    FString OwnerName;
    const AActor* const Owner;

FString 같은 클래스 멤버는 본문 대입이면 "기본 생성자 + 대입 연산자" 두 번 일한다. 그리고 초기화 순서는 리스트에 적은 순서가 아니라 클래스에 멤버를 선언한 순서다 — 섹션 8에서 눈으로 확인한다.

SECTION 04 · 암시적 생성자

4안 써도 컴파일러가 만들어주는 것들

생성자를 하나도 안 쓰면 컴파일러가 기본 생성자, 복사 생성자, 소멸자, 대입 연산자를 만들어준다.

class FInventorySlot { public: int32 ItemID; int32 Count; };   // 생성자 없음

FInventorySlot Slot;          // 암시적 기본 생성자 — ItemID, Count는 쓰레기 값일 수 있다!
FInventorySlot Copy = Slot;   // 암시적 복사 생성자 — 멤버를 하나하나 그대로 복사

// 그래서 기본값은 클래스 안에서 직접 지정하는 습관이 안전하다
int32 ItemID = 0;

기본 타입은 0 보장이 없다

FString 같은 클래스 멤버는 자기 기본 생성자로 확실히 초기화되지만 int32/float/포인터는 아니다.

포인터 멤버 = 얕은 복사

암시적 복사 생성자는 포인터 값만 복사한다. 한쪽이 소멸자에서 해제하면 다른 쪽은 댕글링 포인터.

SECTION 05 · 소멸자

5소멸자는 정확히 언제 호출되나

객체가 사는 곳소멸자 호출 시점
지역 변수(스택)그 변수가 선언된 스코프 { }를 벗어날 때
new로 만든 힙 객체delete를 명시적으로 호출할 때
스마트 포인터가 감싼 힙 객체마지막 소유자가 사라질 때 (자동)
전역/static 객체프로그램 종료 시
void LoadLevel()
{
    FScopedLog Log(TEXT("LoadLevel"));    // 생성자 → "시작" 로그
    if (!CheckPrerequisites()) { return; }   // 스코프를 벗어나므로 소멸자 자동 호출 → "종료" 로그
    DoActualLoading();
}                                        // 정상 경로도 여기서 소멸자 호출

return이 몇 군데든, 예외가 던져지든 스코프를 벗어나는 모든 경로에서 소멸자는 반드시 호출된다. 도입 문제의 해결 실마리가 이것이고, 시뮬레이터의 RAII 모드가 정확히 이걸 보여줬다.

SECTION 06 · RAII

6자원 해제를 소멸자에 묶어버리기

RAII(Resource Acquisition Is Initialization) — 생성자에서 자원을 획득하고, 소멸자에서 반드시 해제하도록 클래스로 감싸는 패턴.

class FScopedFile
{
public:
    FScopedFile(const FString& Path) { File = fopen(TCHAR_TO_ANSI(*Path), "r"); }   // 생성자에서 획득
    ~FScopedFile()             { if (File) { fclose(File); } }                                  // 소멸자에서 반드시 해제
    FILE* Get() const { return File; }
private:
    FILE* File = nullptr;
};

// 언리얼의 FScopeLock이 정확히 이 패턴
void UpdateSharedData()
{
    FScopeLock Lock(&CriticalSection);   // 생성자에서 Lock()
    SharedData++;
}                                       // 소멸자에서 Unlock() 자동 호출 — Unlock 깜빡할 일이 없다

자원 해제를 "사람이 기억해야 할 일"에서 "언어가 보장해주는 일"로 옮긴 것이 RAII의 핵심이다.

SECTION 07 · 스마트 포인터로

7RAII의 다음 단계가 스마트 포인터인 이유

new로 잡은 메모리도 결국 "획득한 자원"이니, 똑같이 소멸자에 delete를 묶으면 된다.

class FSimpleOwningPtr
{
public:
    FSimpleOwningPtr(AActor* InPtr) : Ptr(InPtr) {}
    ~FSimpleOwningPtr() { delete Ptr; }       // 소멸자에서 자동 delete — 사실상 TUniquePtr의 원리 그대로
    AActor* Get() const { return Ptr; }
private:
    AActor* Ptr;
};

TSharedPtr는 여기에 "몇 명이 같이 소유하는지" 세는 참조 카운트를 얹어서, 마지막 소유자의 소멸자가 실행될 때만 delete하도록 확장한 것이다. "delete 깜빡함", "이미 delete한 걸 또 delete함"이 원천적으로 줄어든다 (11강).

SECTION 08 · 눈으로 확인

8생성/소멸 순서 — 선언 순서가 결정한다

멤버는 클래스에 선언한 순서로 생성되고, 소멸은 정반대 순서다. 초기화 리스트에 적은 순서는 무시된다.

class FOuter
{
public:
    FOuter() : A(TEXT("A")), B(TEXT("B")) { UE_LOG(..., TEXT("Outer 생성")); }
    ~FOuter() { UE_LOG(..., TEXT("Outer 소멸")); }
private:
    FInner A; FInner B;   // 선언 순서
};
버튼을 눌러 출력 순서를 확인하자.

리스트를 B, A로 적어도 실제 순서는 선언 순서(A → B)다. 나중에 생긴 게 먼저 죽는다(LIFO — 5강 Stack과 같은 원리). 리스트 순서와 선언 순서를 맞춰 쓰는 게 안전한 이유: 한 멤버가 다른 멤버를 참조해 초기화하면 아직 초기화 안 된 멤버를 볼 수 있다.
