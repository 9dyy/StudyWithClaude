Observer Pattern

HP가 바뀔 때마다 UI를 갱신하는 코드를 여기저기 심고 있다면? 발행자가 구독자를 모르게 만드는 "느슨한 결합"을 언리얼 Delegate로 구현한다.

SECTION 01 · 도입

1HP 바뀌는 곳마다 UI 갱신 코드를 심어야 했던 코드

캐릭터가 데미지를 받으면 HP바를 갱신해야 한다. 처음엔 HP를 바꾸는 곳마다 직접 UI를 갱신했다.

void ACharacter::TakeDamage(float Damage)      { HP -= Damage; HPBarWidget->UpdateHP(HP); }   // 여기서도
void ACharacter::ApplyPoisonTick(float Damage) { HP -= Damage; HPBarWidget->UpdateHP(HP); }   // 여기서도
void ACharacter::Heal(float Amount)            { HP += Amount; HPBarWidget->UpdateHP(HP); }   // 여기서도... 반복

하나라도 빠뜨리면 UI가 안 갱신된다. 게다가 "미니맵 체력 아이콘도 바꿔라"는 요구가 오면 모든 데미지/힐 함수를 다시 찾아다니며 코드를 추가해야 한다. ACharacter가 자기와 상관없어야 할 UI 클래스를 전부 알고 있는 강한 결합이다.

SECTION 02 · 발상 전환

2"바뀌었다고 알리기만 하면, 관심 있는 쪽이 알아서 반응한다"

[직접 호출]                              [Observer Pattern]
Character                                 Character
   │ UpdateHP()                              │ "HP 바뀜!" 이벤트 발행 (Broadcast)
   ├──→ HPBarWidget                          │  (누가 듣는지 Character는 모른다)
   ├──→ MinimapIcon                      ┌───┴────┬───────────┐
   └──→ (새 UI 생길 때마다 추가)        HPBar   MinimapIcon   (새 Observer)
                                        (구독)    (구독)     (구독만 추가)

방향이 뒤집힌다. 이게 느슨한 결합(Loose Coupling) — 발행자가 구독자의 존재를 몰라도 협력할 수 있는 구조다. 새 UI가 생겨도 ACharacter는 한 줄도 안 바뀐다.

SECTION 03 · 핵심 · 직접 돌려보기

3HP 이벤트 Broadcast 시뮬레이터

시스템을 추가/제거해보면서 Character 쪽 코드가 몇 곳 바뀌는지 비교하고, AddRaw 구독자를 소멸시켜 댕글링 콜백까지 터뜨려보자.

ACharacter HP100/ 100
0
Character 코드 수정 (곳)
0
구독자 쪽 수정 (줄)
1
현재 연결된 시스템

① 직접 호출 모드에서 시스템을 하나 추가할 때마다 Character 함수 3곳(Take/Poison/Heal)을 고쳐야 한다. ② Observer 모드에서는 Character는 0곳, 구독자가 자기 쪽에 1줄만 넣으면 된다. ③ 로거를 구독 상태로 소멸시킨 뒤 데미지를 주면 이미 죽은 객체의 함수를 호출해 크래시한다 — 체크박스를 켜고 다시 해보면 안전하다.

SECTION 04 · 구현

4언리얼 Delegate로 구현하기

// Character.h — 발행하는 쪽
DECLARE_MULTICAST_DELEGATE_OneParam(FOnHPChanged, float /*NewHP*/);

class ACharacter : public AActor
{
public:
    FOnHPChanged OnHPChanged;   // "HP가 바뀌면 알려줄게" 창구

    void TakeDamage(float Damage) { HP -= Damage; OnHPChanged.Broadcast(HP); }   // 알림만 — 누가 듣는지 모른다
    void Heal(float Amount)       { HP += Amount; OnHPChanged.Broadcast(HP); }   // 데미지든 힐이든 알림 하나로 통일
private:
    float HP = 100.0f;
};
// HPBarWidget.h — 구독하는 쪽
void UHPBarWidget::BindToCharacter(ACharacter* Character)
{
    Character->OnHPChanged.AddUObject(this, &UHPBarWidget::HandleHPChanged);   // 구독
}
void UHPBarWidget::HandleHPChanged(float NewHP) { ProgressBar->SetPercent(NewHP / MaxHP); }

// MinimapIcon — 나중에 추가된 새 Observer. Character 코드는 한 줄도 안 바뀐다.
Character->OnHPChanged.AddUObject(this, &UMinimapIcon::HandleHPChanged);

// UQuestManager — 같은 이벤트로 "HP 30% 이하면 위기 퀘스트" 추가도 가능
void UQuestManager::HandleHPChanged(float NewHP) { if (NewHP / MaxHP < 0.3f) { TriggerCrisisQuest(); } }

TakeDamage, Heal, ApplyPoisonTick 어디에도 HPBarWidget이나 MinimapIcon이라는 이름이 안 나온다. 도입부의 "빠뜨리면 버그", "요구사항마다 캐릭터 수정"이 둘 다 사라진다.

SECTION 05 · 종류

5Multicast vs Single — 몇 명이 들을 수 있나

종류구독자 수쓰는 곳
DECLARE_DELEGATE_... (싱글)1명만 바인딩응답을 딱 한 곳에서만 처리한다고 명확할 때
DECLARE_MULTICAST_DELEGATE_...여러 명Observer처럼 "몇 명이 들을지 모르는" 상황
DECLARE_DYNAMIC_MULTICAST_DELEGATE_...여러 명 + 블루프린트디자이너가 BP에서 이벤트에 반응하게 하고 싶을 때

Observer 구현엔 거의 항상 Multicast 계열을 쓴다. 구독자가 0명이든 10명이든 Broadcast 쪽 코드는 똑같다.

SECTION 06 · 함정 1

6구독 해제를 깜빡하면

Observer의 흔한 함정은 구독은 하는데 해제를 안 하는 것이다.

void UHPBarWidget::NativeDestruct()
{
    if (BoundCharacter)
    {
        BoundCharacter->OnHPChanged.RemoveAll(this);   // 위젯이 사라지기 전에 구독 해제
    }
    Super::NativeDestruct();
}

위젯이 파괴됐는데 구독 해제를 안 했다면 Character가 Broadcast할 때 이미 없어진 객체의 함수를 부르려는 시도가 일어나 크래시로 이어질 수 있다. 소멸 시점에 자동 호출되는 곳(3강 RAII의 발상)에서 해제를 자동화하자.

SECTION 07 · 함정 2 · 시뮬레이터에서 직접 터뜨린 것

7UObject가 아닌 Observer — AddRaw와 댕글링 콜백

AddUObject는 대상 UObject의 생존 여부를 어느 정도 추적해준다. 하지만 일반 C++ 클래스를 AddRaw로 묶으면 이 안전망이 없다.

void SomeFunction()
{
    FDamageLogger Logger;                                       // 지역(스택) 객체 — 스코프 종료 시 소멸
    Logger.SubscribeTo(PlayerCharacter);                        // 내부에서 AddRaw(this, ...) — 원시 포인터 그대로 저장
}   // Logger는 소멸됐지만 Character는 여전히 죽은 주소를 들고 있다!

// 나중에 PlayerCharacter->TakeDamage(...) → Broadcast → 사라진 Logger의 함수 호출 → 미정의 동작(크래시)

FDamageLogger::~FDamageLogger()
{
    if (SubscribedCharacter) { SubscribedCharacter->OnHPChanged.RemoveAll(this); }   // 소멸자에서 반드시 해제
}

RAII가 스코프 종료 때 자원을 자동 정리해준다는 그 성질이, 구독 해제를 안 챙기면 오히려 댕글링 콜백이라는 위험으로 돌아온다.
