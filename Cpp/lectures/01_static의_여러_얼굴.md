# 1강 — static의 여러 얼굴

> **목표:** `static`이 쓰이는 네 가지 상황(지역 변수, 파일 스코프, 클래스 멤버 변수, 클래스 멤버 함수)을 구분하고, 특히 "static 멤버 함수는 왜 `this`가 없는가"를 컴파일러 관점까지 설명할 수 있게 된다.
> **선수 지식:** 없음. 클래스와 인스턴스 개념(`AActor`, `UObject` 정도)만 알면 충분하다.

---

## 1. 총알 몇 발 쐈는지 세다가 만난 버그

FPS 게임에서 "지금까지 발사된 총알 총개수"를 디버그 UI에 띄우고 싶다. 총알 클래스에 카운터를 하나 넣었다.

```cpp
class ABullet : public AActor
{
public:
    int32 FiredCount = 0;   // 총알 하나에 카운터 하나...?

    ABullet()
    {
        FiredCount++;
    }
};
```

총알을 100발 쏘고 아무 총알이나 하나 골라 `FiredCount`를 찍어보면 **1**이 나온다. 100발 쏘면 100이 나와야 할 것 같은데 아니다. 당연하다. `FiredCount`는 **총알 인스턴스마다 따로 갖는 변수**라서, 각 총알은 자기가 태어날 때 자기 카운터만 1로 만들 뿐이다. "전체" 개수를 세려면 **모든 인스턴스가 공유하는 변수**가 필요하다.

```cpp
class ABullet : public AActor
{
public:
    static int32 FiredCount;   // 모든 ABullet이 이 변수 하나를 공유
    // ...
};
```

`static` 하나 붙였을 뿐인데 완전히 다른 얘기가 된다. 이 강의는 이 `static`이라는 키워드가 상황에 따라 얼마나 다른 일을 하는지, 그리고 그 아래에서 컴파일러가 실제로 뭘 하는지를 본다.

---

## 2. static의 네 얼굴 — 먼저 지도부터

`static`은 **어디에 붙느냐에 따라 완전히 다른 의미**가 된다. 이게 헷갈림의 근원이다. 크게 네 군데에서 쓰인다.

| 위치 | 의미 | 한 줄 |
|------|------|------|
| 함수 안의 지역 변수 | **지역 static 변수** | 딱 한 번만 초기화되고, 함수가 끝나도 값이 유지된다 |
| 함수/전역 변수 앞 (파일 스코프) | **내부 링키지** | 이 `.cpp` 파일 밖에서는 안 보인다 |
| 클래스 안의 멤버 변수 | **static 멤버 변수** | 인스턴스마다 따로 있지 않고, 클래스 전체가 하나를 공유 |
| 클래스 안의 멤버 함수 | **static 멤버 함수** | 특정 인스턴스에 속하지 않는다. `this`가 없다 |

공통점 하나: **"인스턴스/함수 호출과 무관하게, 한 곳에 고정되어 산다"**는 성격이다. 하나씩 뜯어본다.

---

## 3. 지역 static 변수 — "딱 한 번만"

함수 안에서 평범한 지역 변수는 함수가 호출될 때마다 새로 만들어지고, 함수가 끝나면 사라진다. `static`을 붙이면 얘기가 달라진다.

```cpp
void PrintCallCount()
{
    static int32 CallCount = 0;   // 최초 호출 때 딱 한 번만 초기화
    CallCount++;
    UE_LOG(LogTemp, Log, TEXT("이 함수가 %d번째 호출됨"), CallCount);
}

PrintCallCount();   // "1번째 호출됨"
PrintCallCount();   // "2번째 호출됨"  ← CallCount가 0으로 안 돌아감
PrintCallCount();   // "3번째 호출됨"
```

일반 지역 변수라면 매번 `CallCount = 0`부터 다시 시작했을 거다. `static`을 붙이면 이 변수는 **함수 스택이 아니라 정적 저장 영역**에 살면서, **최초로 그 코드 줄을 지나갈 때 딱 한 번만 초기화**되고, 이후 호출부터는 그냥 이전 값을 이어받는다. 함수가 끝나도 사라지지 않고 프로그램이 끝날 때까지 살아 있다.

**언제 쓰나:** 매번 다시 만들 필요 없는 무거운 데이터(룩업 테이블, 캐시)를 함수 안에서 "처음 한 번만" 준비할 때, 혹은 도입부의 발사 카운터 같은 누적값에 쓴다.

```cpp
const TArray<FVector>& GetSpawnPoints()
{
    // 매 호출마다 배열을 새로 만들면 낭비 — 최초 1회만 생성
    static TArray<FVector> SpawnPoints = { FVector(0,0,0), FVector(100,0,0), FVector(0,100,0) };
    return SpawnPoints;
}
```

> **멀티스레드 주의(맛보기, 자세한 건 OS 시리즈 참고):** C++11부터 지역 static 변수의 **최초 초기화 자체**는 스레드 안전하게 컴파일러가 보장해준다(여러 스레드가 동시에 처음 호출해도 초기화는 딱 한 번만 일어남). 하지만 초기화된 **값을 여러 스레드가 동시에 읽고 쓰는 것**까지 안전한 건 아니다. "static이면 무조건 스레드 세이프"는 틀린 말이다 — 6번 섹션에서 다시 짚는다.

## 4. 파일 스코프 static — "이 파일 안에서만 보여"

클래스 밖, 전역 함수나 전역 변수에 `static`을 붙이면 완전히 다른 의미다. 이건 **"이 `.cpp` 파일 밖에서는 링커가 이 이름을 못 보게 숨겨라"** 는 뜻이다.

```cpp
// BulletUtils.cpp

static float CalculateFalloff(float Distance)   // 이 파일 안에서만 쓰는 헬퍼 함수
{
    return FMath::Clamp(1.0f - Distance / 1000.f, 0.f, 1.f);
}

// 다른 .cpp 파일에서 CalculateFalloff를 쓰려고 하면 링커 에러 —
// 이름 자체가 이 파일 밖으로 노출이 안 됨(내부 링키지)
```

`static`이 없으면 이 함수는 **외부 링키지**를 갖고, 다른 `.cpp` 파일에서 `extern` 선언만 하면 가져다 쓸 수 있다. `static`을 붙이면 **내부 링키지**가 되어 이 번역 단위(translation unit) 안에서만 존재하는 것처럼 격리된다. 다른 파일에서 우연히 같은 이름의 함수를 만들어도 충돌 안 난다.

> 요즘은 이 용도로 `static` 대신 **익명 네임스페이스**(`namespace { ... }`)를 더 권장하는 분위기지만, 기존 코드베이스에서 `static` 붙은 파일 스코프 함수는 흔히 본다. "이건 다른 static 얼굴들과 아예 다른 의미"라는 것만 구분하면 된다.

---

## 5. static 멤버 변수 — "이 클래스는 하나만 가진다"

도입의 정답이다. 클래스 안에 선언하되 `static`을 붙이면, 그 변수는 **인스턴스마다 복사되는 게 아니라 클래스 전체에 딱 하나만 존재**한다.

```cpp
class ABullet : public AActor
{
public:
    static int32 FiredCount;   // 선언만. 실체(정의)는 밖에서 한 번 잡아준다.

    ABullet()
    {
        FiredCount++;   // 모든 ABullet 인스턴스가 같은 변수를 공유해서 증가시킴
    }
};

// .cpp 파일에서 딱 한 번 정의(메모리 실체를 만들어줌)
int32 ABullet::FiredCount = 0;
```

```
인스턴스별 메모리                     클래스 전체 공유 메모리(정적 저장 영역)
┌─────────────┐                     ┌──────────────────┐
│ Bullet A    │                     │ ABullet::         │
│  Location   │                     │  FiredCount = 100  │ ← 다 같이 이거 하나 봄
├─────────────┤                     └──────────────────┘
│ Bullet B    │
│  Location   │
├─────────────┤
│ Bullet C    │
│  Location   │
└─────────────┘
```

**왜 `.cpp`에서 따로 정의를 해줘야 하나?** 클래스 안의 `static int32 FiredCount;`는 **선언**일 뿐이다. "이런 변수가 있다"고 컴파일러에게 알려줄 뿐 실제 메모리를 만들지 않는다. 이 클래스를 쓰는 `.cpp` 파일이 여러 개일 수 있는데, 그때마다 메모리를 새로 잡으면 중복이다. 그래서 **딱 한 곳에서만 실체(정의)를 만들라**고 강제하는 거다. (C++17부터는 `inline static int32 FiredCount = 0;`로 헤더 안에서 바로 정의까지 끝낼 수 있어서, 언리얼 최신 코드에서는 이 형태도 종종 보인다.)

이 규칙을 깜빡하면 생기는 게 면접에서도 잘 나오는 **"undefined reference" 링커 에러**다 — 8번 섹션 오해에서 다시 다룬다.

## 6. static 멤버 함수 — "인스턴스 없이도 부를 수 있다"

여기가 이 강의의 핵심이자 면접 단골이다. 멤버 함수에 `static`을 붙이면, 그 함수는 **특정 인스턴스에 속하지 않는 함수**가 된다.

```cpp
class FDamageCalculator
{
public:
    // static 멤버 함수 — 인스턴스 없이도 호출 가능
    static float CalculateDamage(float BaseDamage, float DefenseRate)
    {
        return BaseDamage * (1.0f - DefenseRate);
    }
};

// 인스턴스를 만들 필요가 없다
float Result = FDamageCalculator::CalculateDamage(100.f, 0.3f);
```

일반 멤버 함수라면 `FDamageCalculator Calc; Calc.CalculateDamage(...)`처럼 인스턴스를 먼저 만들어야 했을 거다. `static`이 붙으면 클래스 이름으로 바로 부를 수 있다. 언리얼 `FMath::Clamp()`, `FMath::Max()` 같은 함수들이 전부 이 패턴이다 — 상태를 갖는 객체가 필요 없는 "순수 계산 함수"들.

### 왜 `this`가 없나 — 컴파일러 관점

이걸 이해하려면 먼저 **일반 멤버 함수가 실제로 어떻게 컴파일되는지**를 알아야 한다. 아래 코드를 보자.

```cpp
class ABullet
{
public:
    float Damage;
    void ApplyDamage(AActor* Target)
    {
        Target->TakeDamage(Damage, ...);   // Damage는 사실 this->Damage
    }
};

Bullet.ApplyDamage(Enemy);
```

컴파일러는 사실 `ApplyDamage`를 이렇게 컴파일한다(개념적으로).

```cpp
// 컴파일러가 실제로 만드는 모양 (의사코드)
void ABullet_ApplyDamage(ABullet* this, AActor* Target)
{
    Target->TakeDamage(this->Damage, ...);
}

ABullet_ApplyDamage(&Bullet, Enemy);   // Bullet.ApplyDamage(Enemy)가 이렇게 바뀜
```

**일반 멤버 함수는 사실 "숨겨진 첫 번째 매개변수로 `this`를 받는 일반 함수"** 다. 함수 안에서 아무 표시 없이 쓰는 멤버 변수(`Damage`)는 전부 `this->Damage`로 해석된다. 이게 멤버 함수가 "자기가 속한 인스턴스"를 아는 방법의 전부다.

`static` 멤버 함수는 이 규칙에서 **빠진다.** 컴파일러가 `this`를 아예 안 넘겨준다. 그래서:

- **인스턴스 없이 호출 가능하다** — 애초에 `this`를 요구하지 않으니까.
- **non-static 멤버 변수/함수에 직접 접근할 수 없다** — `this`가 없으니 "어느 인스턴스의 것"인지 컴파일러가 알 방법이 없다.
- **`const` 멤버 함수가 될 수 없다(의미 없다)** — `const`는 "이 함수가 `*this`를 안 바꾼다"는 뜻인데, `this` 자체가 없으니 그 개념이 성립 안 한다.

정리하면 **static 멤버 함수는 사실상 "클래스라는 이름공간(namespace) 안에 들어 있는 평범한 전역 함수"** 다. 클래스 소속이라는 문법적 껍데기만 있을 뿐, 동작 방식은 `static` 멤버 변수처럼 인스턴스와 무관하게 딱 한 군데(코드 세그먼트)에 존재하는 함수다.

## 7. static과 const를 같이 쓰면 — 완전히 다른 두 축의 조합

`static`과 `const`를 같이 쓰는 코드는 실전에서 굉장히 흔하다. 그런데 이 둘을 "비슷한 걸 두 번 쓰는 것"으로 착각하는 사람이 많다. 먼저 이 둘이 **완전히 다른 질문에 답하는 키워드**라는 걸 분리해야 한다.

| 키워드 | 답하는 질문 | 관련 축 |
|------|------|------|
| `static` | "이 변수가 어디에, 몇 개 존재하는가" (생명주기·저장 위치) | 존재 방식 |
| `const` | "이 변수의 값을 바꿀 수 있는가" | 불변성 |

**둘은 서로 간섭하지 않는 독립적인 축이라서, 네 가지 조합이 전부 의미가 있다.**

```cpp
void PrintDebugInfo()
{
    int32 A = 10;                 // 매번 새로 생성, 값도 바꿀 수 있음
    const int32 B = 10;           // 매번 새로 생성되지만, 값은 못 바꿈
    static int32 C = 10;          // 딱 한 번만 초기화, 이후 호출에서도 값 유지 + 바꿀 수 있음
    static const int32 D = 10;    // 딱 한 번만 초기화 + 그 값을 절대 못 바꿈 — 사실상 "진짜 상수"
}
```

`C`와 `D`를 헷갈리기 쉬운데, `C`는 "함수 호출 사이에 값이 유지되는 카운터" 같은 데 쓰고(3번 섹션의 `PrintCallCount` 예시), `D`는 "값이 절대 안 바뀌어야 하는 전역 상수"에 쓴다. `static` 혼자서는 "값을 바꿀 수 없다"를 보장해주지 않는다 — 실제로 `C`는 여전히 `C++`처럼 증가시킬 수 있다.

### static const 멤버 변수 — 게임 밸런스 상수의 정석

클래스 전체가 공유하면서(`static`) 값도 못 바꾸는(`const`) 멤버는, 몬스터 최대 체력이나 무기 최대 탄창 수처럼 **디자인 상수**를 표현하는 데 자주 쓰인다.

```cpp
class AGoblin : public AEnemy
{
public:
    static const int32 MaxHealth = 50;   // 정수 계열 const는 클래스 안에서 바로 초기화 가능(선언과 동시에)

    // C++17부터는 constexpr를 쓰면 더 명확하고 안전하다
    static constexpr float MaxSpeed = 350.0f;   // 컴파일 타임 상수, 암묵적으로 inline 처리됨
};
```

**5번 섹션에서 본 "static 멤버 변수는 클래스 안에서 선언만 하고 .cpp에서 정의해야 한다"는 규칙에 여기서 예외가 하나 생긴다.** `static const`인데 **정수 계열 타입(`int32`, `bool`, `enum` 등)**이면, 컴파일러가 그 값을 컴파일 타임에 이미 알고 있어서 클래스 선언 안에서 바로 초기화할 수 있다. 다만 이 예외에도 함정이 있다 — 그 멤버의 **주소를 실제로 참조하는 코드**(예: `const int32&`로 넘기거나 포인터를 뜨는 경우)가 있으면 여전히 `.cpp`에 정의를 한 줄 더 써줘야 한다(ODR-used라고 부르는 상황). `float`, `FString` 같은 비정수 타입은 애초에 이 예외 대상이 아니라서 예전처럼 `.cpp` 정의가 필요했다.

**`static constexpr`를 쓰면 이 함정 자체가 사라진다.** C++17부터 `constexpr` static 멤버는 **암묵적으로 `inline`** 취급되기 때문에, 정수든 실수든 상관없이 클래스 안의 한 줄로 선언과 정의가 동시에 끝나고 별도의 `.cpp` 정의가 필요 없다. 요즘 언리얼 코드에서 게임 밸런스 상수를 `static constexpr`로 선언하는 패턴이 흔한 이유가 이거다.

### static 멤버 함수와 const — 이미 답이 나온 조합

6번 섹션에서 이미 짚은 내용을 여기서 다시 정리하면: static 멤버 함수는 `const`를 붙일 수 없다. `const` 멤버 함수라는 게 "`*this`를 안 바꾸겠다"는 약속인데, static 멤버 함수는 애초에 `this` 자체가 없어서 그 약속을 걸 대상이 없다. `static`과 `const`가 부딪히는 유일한 조합이 이거고, 나머지 조합(지역 변수, 파일 스코프, 멤버 변수)은 전부 자연스럽게 성립한다.

### 메모리로 보면 — static const는 더 "안전한" 자리에 놓인다

바로 다음 섹션에서 볼 데이터 영역 논의를 한 단계 더 깊이 보면, `static const`/`static constexpr`처럼 **값이 절대 안 바뀐다는 게 컴파일 타임에 보장된 데이터**는 컴파일러가 데이터 영역 중에서도 **읽기 전용 영역(.rodata)** 에 배치하는 경우가 많다. 일반 `static` 변수(값이 바뀔 수 있음)는 읽고 쓰기가 다 되는 영역에 있지만, `static const`는 애초에 쓰기 시도 자체가 컴파일 에러로 막히니 하드웨어 차원에서도 "쓰기 금지"로 표시해둘 수 있는 것 — `const`가 단순히 "컴파일러의 약속"을 넘어 실제 메모리 보호로도 이어질 수 있다는 뜻이다.

## 8. static은 메모리 어디에 사는가 — 힙도 스택도 아니다

지금까지 본 네 얼굴이 전부 "한 곳에 고정되어 산다"고 했는데, 그 "한 곳"이 정확히 어디인지 짚고 넘어가야 한다. 프로그램이 쓰는 메모리를 크게 네 구역으로 나눠보면 이렇다.

```
┌────────────────────┐  ← 코드(텍스트) 영역: 컴파일된 함수 코드. 실행되는 명령어들.
├────────────────────┤  ← 데이터 영역(+BSS): 전역/static 변수. 프로그램 시작할 때
│                    │     이미 자리가 잡히고, 끝날 때까지 그 자리 그대로.
├────────────────────┤  ← 힙(Heap): new/malloc으로 "그때그때" 요청해서 할당.
│         ↓ 위로 자람 │     프로그램이 알아서 관리 안 해주면 안 없어짐.
│         ↑ 아래로 자람│  ← 스택(Stack): 함수 호출될 때 생겼다가 리턴하면 사라짐.
└────────────────────┘     지역 변수, 함수 인자가 여기 쌓인다.
```

이 그림에 static의 네 얼굴을 그대로 얹어보면 답이 나온다.

| static의 얼굴 | 사는 곳 | 왜 |
|------|------|------|
| 지역 static 변수 | **데이터 영역(+BSS)** | 함수 호출과 무관하게 프로그램 시작 시점에 이미 자리가 잡힘 |
| 파일 스코프 static 변수 | **데이터 영역(+BSS)** | 전역 변수와 똑같은 자리, 다만 이름만 이 파일 밖에 안 보임 |
| static 멤버 변수 | **데이터 영역(+BSS)** | 인스턴스와 무관하게 클래스 전체에 딱 하나, 프로그램 로드 시 확보 |
| static 멤버 함수 | **코드(텍스트) 영역** | 애초에 "변수"가 아니라 함수(명령어)라서 데이터 저장 개념 자체가 없음 |

**힙과는 완전히 다른 메커니즘이라는 게 핵심이다.** 힙은 "지금 필요하니까 지금 만들어줘"(`new`)라고 런타임에 요청해서 잡는 메모리고, 그래서 주소도 실행하기 전까진 알 수 없다. 반면 static은 **컴파일러가 컴파일 시점에 이미 자리를 정해두고, 프로그램이 로드될 때 OS가 그 자리를 준비해주는** 방식이다. `new`를 한 번도 안 불러도 static 변수는 이미 살아있다.

스택과도 다르다. 스택에 있는 지역 변수는 함수가 리턴하면 그 자리가 다른 호출에 재사용되면서 값이 사라진다(그래서 지역 변수의 주소를 리턴하면 위험하다). static이 붙는 순간 "함수 호출마다 생겼다 사라지는" 성질 자체가 없어지니, 애초에 스택에 있을 이유가 없어지는 거다.

**게임 개발자한테 와닿는 대비:** `AActor`, `UObject` 같은 언리얼 객체는 대부분 힙에 살고 가비지 컬렉션(GC) 대상이다. 레벨을 빠져나가거나 참조가 끊기면 사라진다. 하지만 static 변수는 **GC 대상이 아니고, 어떤 액터/인스턴스가 몇 개 살아있든 죽어있든 상관없이 프로그램이 종료될 때까지 그 자리에 그대로 있다.** 도입의 `FiredCount`가 "총알 인스턴스가 다 사라진 뒤에도" 총 발사 수를 계속 들고 있을 수 있는 이유가 이거다.

## 9. 코드로 체감해보기 — 도입 문제를 제대로 풀기

도입의 총알 카운터를 완성해보자. static 멤버 변수와 static 멤버 함수를 같이 쓰면 "카운트를 올리는 것도, 조회하는 것도" 인스턴스 없이 깔끔하게 정리된다.

```cpp
// Bullet.h
class ABullet : public AActor
{
public:
    ABullet()
    {
        ++TotalFiredCount;   // 총알이 태어날 때마다 공유 카운터 증가
    }

    // 인스턴스 없이 "지금까지 총 몇 발 쐈나"를 조회하는 static 함수
    static int32 GetTotalFiredCount()
    {
        return TotalFiredCount;   // static 멤버 함수라 static 멤버만 건드릴 수 있음
    }

private:
    static int32 TotalFiredCount;
};

// Bullet.cpp
int32 ABullet::TotalFiredCount = 0;

// 사용하는 쪽 — 총알 인스턴스를 몰라도, 클래스 이름만 알면 조회 가능
void AHUDWidget::UpdateDebugText()
{
    int32 Fired = ABullet::GetTotalFiredCount();
    DebugText->SetText(FText::Format(FText::FromString(TEXT("발사된 총알: {0}발")), Fired));
}
```

디버그 UI 코드(`AHUDWidget`)는 총알 인스턴스를 단 하나도 안 갖고 있지만 `ABullet::GetTotalFiredCount()`만으로 전체 개수를 알 수 있다. **static 멤버 변수는 "공유 상태"를, static 멤버 함수는 "인스턴스 없이 그 상태에 접근하는 창구"** 를 만들어주는 조합이다.

## 10. 흔한 오해

### 오해 1: "static 멤버 변수도 인스턴스마다 하나씩 있다"

아니다. 인스턴스가 100개든 0개든 static 멤버 변수는 **딱 하나**다. 도입의 버그가 정확히 이 오해에서 나왔다 — `static` 없는 멤버 변수를 "다들 공유하겠지"라고 착각한 것.

### 오해 2: "static 멤버 함수도 다른 멤버 변수를 자유롭게 쓸 수 있다"

아니다. static 멤버 함수는 `this`가 없어서 **non-static 멤버 변수/함수에는 직접 접근이 안 된다.** 접근하려면 인스턴스를 인자로 따로 받아야 한다.

```cpp
class ABullet
{
public:
    float Damage;

    static void PrintDamage()
    {
        // UE_LOG(LogTemp, Log, TEXT("%f"), Damage);   // ❌ 컴파일 에러. this가 없어서 누구 Damage인지 모름
    }

    static void PrintDamage(const ABullet& Instance)
    {
        UE_LOG(LogTemp, Log, TEXT("%f"), Instance.Damage);   // ✅ 인스턴스를 직접 받으면 OK
    }
};
```

### 오해 3: "헤더에서 `static int32 Count = 0;`라고 쓰면 끝이다"

C++17 이전(`inline` static 아닌 일반 static 멤버 변수) 기준으로는 아니다. 클래스 안의 선언은 실체가 없는 **선언**일 뿐이라, `.cpp`에서 `int32 ABullet::Count = 0;`로 정의를 해줘야 한다. 안 해주면 **링크 단계에서 "unresolved external symbol" / "undefined reference"** 에러가 난다. 컴파일은 되는데 링크에서 터지는 대표 사례라 헷갈리는 사람이 많다. (C++17의 `inline static`은 이 규칙에서 예외라 헤더 한 줄로 끝난다 — 최신 코드는 이 형태를 점점 더 많이 쓴다.)

### 오해 4: "static이니까 멀티스레드에서 무조건 안전하다"

지역 static 변수의 **최초 초기화**는 C++11부터 스레드 안전하게 컴파일러가 보장한다. 하지만 그 변수의 **값을 여러 스레드가 동시에 읽고 쓰는 것**은 별개 문제다. `static int32 Counter = 0;` 를 여러 스레드가 동시에 `Counter++` 하면 여전히 Race Condition이 난다. "초기화가 안전하다"와 "값 변경이 안전하다"는 다른 얘기다.

### 오해 5: "static 변수는 힙(heap)에 저장된다"

아니다. static 변수(4가지 얼굴 중 변수인 셋: 지역 static, 파일 스코프 static, static 멤버 변수)는 전부 **데이터 영역(+BSS)**에 산다. 힙은 `new`로 런타임에 그때그때 요청해서 할당받는 메모리인데, static은 반대로 **컴파일 시점에 이미 주소가 정해지고 프로그램 로드 시 자동으로 준비되는** 메모리다. "프로그램 내내 살아있다"는 성질 때문에 힙과 헷갈리기 쉽지만, 결정적 차이는 **주소가 정해지는 시점**이다 — static은 컴파일 타임, 힙은 런타임.

### 오해 6: "static 지역 변수는 값도 못 바꾼다"

아니다. `static`은 "생명주기/공유"를 정하는 키워드지 "불변성"을 정하는 키워드가 아니다. `static int32 Counter = 0;`은 값을 계속 바꿀 수 있고(그래서 카운터로 쓸 수 있는 것이다), 값까지 못 바꾸게 하려면 `static const`나 `static constexpr`를 따로 붙여야 한다. `static`과 `const`는 완전히 다른 축이라 이 둘을 같이 써야 "바뀌지 않는 값을 한 곳에서만 유지한다"는 의미가 완성된다.

## 11. 면접에서 나오면

**Q1. static 함수에 대해 설명해보세요.**
→ "클래스에 속하지만 특정 인스턴스에 종속되지 않는 멤버 함수입니다. 일반 멤버 함수는 컴파일 시 숨겨진 첫 인자로 `this` 포인터를 받는데, static 멤버 함수는 이 `this`가 없어서 인스턴스 없이 클래스 이름만으로 호출할 수 있습니다. 대신 그 함수 안에서는 non-static 멤버 변수나 함수에 직접 접근할 수 없습니다."

**Q2. static 멤버 변수와 일반 멤버 변수의 차이는?**
→ "일반 멤버 변수는 인스턴스마다 각자 따로 메모리를 갖지만, static 멤버 변수는 클래스 전체가 공유하는 딱 하나의 메모리만 존재합니다. 인스턴스를 몇 개를 만들든 static 멤버 변수는 하나이기 때문에, 총 발사 횟수 같은 공유 카운터에 적합합니다."

**Q3. static 멤버 함수는 왜 this가 없나요?**
→ "일반 멤버 함수는 컴파일러가 내부적으로 첫 번째 인자로 `this` 포인터를 암묵적으로 전달하는 방식으로 동작합니다. static 멤버 함수는 이 규칙에서 제외돼서, 사실상 클래스라는 이름공간 안에 있는 일반 함수처럼 컴파일됩니다. 그래서 인스턴스 없이 호출할 수 있는 대신, 어느 인스턴스의 멤버인지 알 수 없어서 non-static 멤버에 직접 접근할 수 없습니다."

**Q4. 지역 static 변수는 언제, 몇 번 초기화되나요?**
→ "그 코드 줄을 프로그램이 처음 실행할 때 딱 한 번만 초기화됩니다. 이후 같은 함수가 다시 호출돼도 초기화 코드는 건너뛰고 이전 값을 그대로 씁니다. 함수가 끝나도 값이 사라지지 않고 프로그램 종료까지 유지됩니다."

**Q5. 클래스 안에서 `static int32 Count;`만 쓰고 .cpp에서 정의를 안 해주면 어떻게 되나요?**
→ "컴파일은 되지만 링크 단계에서 undefined reference 에러가 납니다. 클래스 안의 선언은 실체 없는 선언일 뿐이라 어딘가에서 메모리를 한 번 만들어줘야 하는데, 그걸 안 했기 때문입니다. C++17의 inline static을 쓰면 헤더 안에서 바로 정의까지 끝낼 수 있어서 이 문제가 없습니다."

**Q6. static 멤버 변수를 멀티스레드 환경에서 여러 스레드가 동시에 증가시키면 안전한가요?**
→ "안전하지 않습니다. static이라는 건 '공유된다'는 뜻이지 '동시 접근이 안전하다'는 뜻이 아닙니다. 여러 스레드가 동시에 `Counter++`를 하면 Race Condition이 발생할 수 있어서, atomic 타입을 쓰거나 락으로 보호해야 합니다."

**Q7. 싱글톤을 구현할 때 static을 어떻게 활용하나요?**
→ "함수 안에 지역 static 객체를 두고 그 참조를 리턴하는 방식(Meyer's Singleton)을 많이 씁니다. 최초 호출 때 한 번만 생성되고, C++11부터는 그 초기화 자체가 스레드 안전하게 보장되기 때문입니다. 언리얼에서는 이 패턴 대신 GameInstance나 Subsystem으로 관리하는 경우가 더 많습니다."

**Q8. static 변수는 스택, 힙 중 어디에 저장되나요?**
→ "둘 다 아닙니다. static 변수는 데이터 영역, 정확히는 초기값에 따라 Data 또는 BSS 세그먼트에 저장됩니다. 힙은 new로 런타임에 동적으로 할당하는 영역이고, static은 컴파일 시점에 이미 주소가 정해져서 프로그램이 로드될 때 자동으로 준비된다는 점이 근본적으로 다릅니다."

**Q9. 몬스터의 최대 체력처럼 클래스 전체가 공유하면서 값도 절대 안 바뀌어야 하는 상수를 선언한다면 어떻게 하시겠어요?**
→ "static const나 static constexpr 멤버 변수로 선언하겠습니다. static은 인스턴스마다 따로 갖지 않고 클래스 전체가 공유하게 해주고, const는 그 값을 실수로라도 바꿀 수 없게 막아줍니다. 둘은 서로 다른 축이라 같이 써야 '공유되면서 절대 안 바뀌는 값'이라는 의도가 정확히 드러납니다. C++17이라면 constexpr를 써서 별도 .cpp 정의 없이 헤더 한 줄로 끝내는 걸 선호합니다."

면접관이 그 다음에 던지기 좋은 질문: *"방금 말한 싱글톤, 언리얼에서는 어떻게 구현하는 게 좋을까요?"* → 9강(Singleton과 Factory)에서 다룬다.

## 12. 셀프 체크

- [ ] static의 네 가지 얼굴(지역 변수 / 파일 스코프 / 멤버 변수 / 멤버 함수)을 구분해서 말할 수 있다.
- [ ] static 멤버 함수가 왜 `this`가 없는지, 일반 멤버 함수의 컴파일 방식과 연결해서 설명할 수 있다.
- [ ] static 멤버 변수를 클래스 안에서 선언만 하면 안 되는 이유(선언 vs 정의)를 안다.
- [ ] 지역 static 변수가 "딱 한 번만 초기화"된다는 걸 예시로 설명할 수 있다.
- [ ] static이 스레드 안전성을 자동으로 보장하지 않는다는 걸 안다.
- [ ] static 멤버 함수 안에서 non-static 멤버에 직접 접근이 안 되는 이유를 안다.
- [ ] static 변수(4형태)가 힙/스택이 아니라 데이터 영역(혹은 static 멤버 함수는 코드 영역)에 산다는 걸 설명할 수 있다.
- [ ] static과 const가 서로 다른 축(생명주기·공유 vs 불변성)이라는 걸 알고, static const/constexpr 멤버 변수를 왜 같이 쓰는지 설명할 수 있다.
