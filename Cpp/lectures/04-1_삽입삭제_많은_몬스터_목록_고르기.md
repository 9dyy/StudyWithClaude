# 4-1강 (보충) — 삽입/삭제가 많은 몬스터 목록, 어떤 자료구조를 쓸까

> **목표:** "매 프레임 순회하는데 삽입/삭제도 많다"는 조건에서 자료구조를 고르는 사고 순서를 익힌다. 결론(`TArray` / `std::vector` + swap-and-pop)만이 아니라, 순회 중 삭제·포인터 무효화 같은 실전 함정까지 답할 수 있게 된다.
> **선수 지식:** 4강(배열 vs LinkedList), 7강(Object Pooling)이면 충분. 6강(해시맵)은 있으면 좋다.

---

## 1. 실제로 받은 질문

> "게임에서 몬스터 객체의 목록을 만들어야 해. 어떤 C++ STL 자료구조를 써야 할까? **매 프레임마다 호출해서 렌더해야 하고, 삽입과 삭제가 많이 일어나.**"

조건이 두 개다. **① 매 프레임 전체 순회**, **② 삽입/삭제가 잦다.** 여기서 "삽입/삭제가 잦다 → `std::list`"로 반사적으로 답하면 4강에서 본 그 함정에 그대로 빠진다. 조건 ①이 순회를 압도적으로 자주 시키기 때문이다.

이 강의는 "vector가 정답이다"를 외우는 강의가 아니다. **어떤 조건이면 vector, 어떤 조건이면 list인지** 판단 순서를 만드는 강의다.

---

## 2. 후보부터 늘어놓기

| STL | 언리얼 대응 | 순회 | 끝에 삽입 | 중간 삭제 | 비고 |
|------|------|------|------|------|------|
| `std::vector` | `TArray` | 매우 빠름(연속 메모리) | O(1) 상각 | O(n) 밀기 (**swap-and-pop이면 O(1)**) | 기본값 |
| `std::list` | `TDoubleLinkedList` | 느림(노드마다 캐시 미스 위험) | O(1) + 노드 할당 | 반복자가 있으면 O(1) | 주소/반복자 안정 |
| `std::deque` | `TDeque` (UE5) | vector보다 조금 느림 | 앞/뒤 O(1) | O(n) | 앞에서도 넣고 뺄 때 |
| `std::set` / `std::map` | `TSet` / `TMap` (해시 기반) | 느림(트리/해시) | O(log n) / O(1) 평균 | O(log n) / O(1) 평균 | **키로 찾을 때** 유리 |
| `std::unordered_set` | `TSet` | 느림(버킷) | O(1) 평균 | O(1) 평균 | 순서 없음, 순회 비효율 |

조건 ①(전 원소 순회)을 걸러내면 **연속 메모리가 아닌 후보는 대부분 탈락**한다. 남는 건 vector 계열이고, 남은 문제는 "그럼 중간 삭제가 O(n)인데 어떡하나"다. 답이 **swap-and-pop**이다.

---

## 3. swap-and-pop — 순서가 상관없다면 삭제를 O(1)로

중간 원소를 지우고 뒤를 전부 당기는 대신, **지울 자리에 맨 마지막 원소를 옮겨 놓고 마지막을 제거**한다.

```
[A][B][C][D][E]   C를 삭제

일반 erase:      [A][B][D][E]        ← D, E를 한 칸씩 앞으로 (n번 이동)
swap-and-pop:    [A][B][E][D][E]  →  마지막 E를 pop  →  [A][B][E][D]
                 (C 자리에 E를 복사/이동, 끝 제거)  ← 이동 1번, 순서는 바뀜
```

```cpp
// std::vector
void RemoveAtSwap(std::vector<FMonster>& V, size_t Index)
{
    V[Index] = std::move(V.back());   // 마지막 원소를 그 자리로
    V.pop_back();                     // 마지막을 제거 — O(1)
}

// 언리얼은 이미 만들어 놨다
TArray<AMonster*> Monsters;
Monsters.RemoveAtSwap(Index);         // 순서가 바뀌어도 되면 이걸 쓴다
```

**조건: 순서가 바뀌어도 되는가?** 몬스터 목록은 대개 "전부 한 번씩 돈다"만 필요하고 순서는 의미가 없다. 그리고 렌더 순서가 중요하면(투명 물체 정렬 등) 그건 **렌더 단계에서 따로 정렬**하는 게 맞다 — 컨테이너 순서에 의미를 싣지 않는 편이 낫다. 순서가 꼭 유지돼야 하면 `RemoveAt`(밀기)로 돌아가되, 그래도 4강에서 봤듯 원소가 수천 개 수준이면 memmove가 싸다.

## 4. 순회 중 삭제 — 가장 자주 터지는 버그

몬스터가 죽으면 목록에서 빼야 하는데, 그게 **순회 도중**에 일어난다.

```cpp
// ❌ range-for 안에서 삭제 — 반복자 무효화, 원소 건너뜀, 크래시
for (AMonster* M : Monsters)
{
    M->Tick(DeltaTime);
    if (M->IsDead())
        Monsters.Remove(M);           // 순회 중인 컨테이너를 변경!
}
```

해법은 세 가지다.

**① 역순 인덱스 순회 + swap-and-pop** — 뒤에서부터 돌면 swap으로 가져오는 원소(이미 검사한 것)가 안전하다.
```cpp
for (int32 i = Monsters.Num() - 1; i >= 0; --i)
{
    Monsters[i]->Tick(DeltaTime);
    if (Monsters[i]->IsDead())
        Monsters.RemoveAtSwap(i);
}
```

**② 지연 삭제** — 순회 중엔 `bPendingKill` 표시만 하고, **프레임 끝에 한 번에 정리**한다. 순회 중 다른 몬스터가 죽은 몬스터를 참조해도 안전하다.
```cpp
Monsters.RemoveAll([](const AMonster* M) { return M->IsDead(); });   // 한 번의 패스
// 표준 C++20: std::erase_if(V, pred);  C++17 이전: erase-remove 관용구
```

**③ 삽입도 지연** — 순회 중 스폰이 일어나면(몬스터가 몬스터를 소환) push_back으로 재할당이 일어나 **순회 중인 반복자/포인터가 전부 무효화**된다. 새로 생긴 건 `PendingSpawns`에 모아뒀다가 순회가 끝난 뒤 합친다.

이 세 번째가 면접에서 "왜 순회 중에 삽입하면 안 되나요?"로 이어지기 쉽다.

## 5. 포인터/참조 안정성 — vector의 진짜 약점

`std::vector`는 용량이 꽉 차 **재할당(4강 6절)이 일어나면 모든 원소의 주소가 바뀐다.**

```cpp
std::vector<FMonster> Monsters;                    // 값으로 저장
FMonster* Boss = &Monsters[0];                     // 어딘가에서 주소를 보관
Monsters.push_back(FMonster{});                    // 재할당 → Boss는 댕글링 포인터!
```

다른 시스템(타겟팅, UI, AI)이 몬스터를 가리키고 있다면 이건 치명적이다. 해결 방법:

| 방법 | 설명 |
|------|------|
| **포인터를 저장** | `TArray<AMonster*>` — 언리얼의 Actor는 원래 힙에 따로 있으므로 이게 기본. 순회 시 한 번 더 따라가야 해서 완전한 연속 접근은 아니지만, 포인터 배열 자체는 연속이다 |
| **`Reserve()`로 미리 확보** | 최대 몬스터 수를 안다면 재할당 자체를 없앤다 |
| **핸들(인덱스+세대)로 참조** | 포인터 대신 `{Index, Generation}`을 들고, 접근 시 검증한다 (Object Pool과 자연스럽게 연결) |
| **Object Pool (7강)** | 미리 N개를 만들어 두고 `bActive` 플래그로 켜고 끈다. **삽입/삭제 자체가 없어진다** |

**언리얼에서는** Actor를 직접 `new`하지 않고 `SpawnActor`로 만들며 GC가 관리하므로, 보통 `TArray<TObjectPtr<AMonster>>` 또는 월드의 액터 목록 위에 필요한 캐시를 올린다.

## 6. 그럼 `std::list`는 언제 쓰나

4강 표 그대로다. **① 반복자/주소가 절대 무효화되면 안 되고 ② 순회는 드물고 ③ 이미 노드를 들고 있는 채로 삽입/삭제**하는 경우다. 예: 이벤트 리스너 목록을 순회하는 도중 자기 자신을 등록 해제하는 콜백 구조 등. 몬스터 목록은 조건 ①(전 원소 순회)과 정면충돌하므로 해당하지 않는다.

`std::set`/`std::map`은 **"ID로 찾아야 할 때"** 쓴다. 매 프레임 순회가 목적이라면 굳이 트리나 해시를 쓸 이유가 없다. 순회와 조회가 둘 다 필요하면 **`TArray`(순회용) + `TMap<ID, 인덱스 또는 포인터>`(조회용)**를 같이 두는 식으로 간다.

## 7. 판단 순서 (답변 프레임)

```
1. 접근 패턴이 뭔가?  → 매 프레임 전체 순회 (연속 메모리 우선)
2. 삽입/삭제는 어디서 일어나는가?  → 끝에 삽입, 중간 삭제
3. 순서가 의미 있는가?  → 아니오 → swap-and-pop
4. 순회 중 변경이 있는가?  → 지연 삭제/지연 삽입
5. 누가 원소를 가리키는가?  → 포인터 저장 / 핸들 / Reserve
6. 생성·파괴 자체가 병목인가?  → Object Pool
```

한 문장 답: *"`TArray`(vector)를 쓰고, 삭제는 순서가 필요 없으니 swap-and-pop, 순회 중 변경은 프레임 끝에 일괄 처리합니다."*

## 8. 코드로 정리 — 몬스터 매니저

```cpp
class UMonsterSubsystem : public UWorldSubsystem
{
public:
    void Register(AMonster* M)   { PendingAdd.Add(M); }          // 순회 중이어도 안전
    void Unregister(AMonster* M) { M->bPendingRemove = true; }    // 표시만

    void TickMonsters(float DeltaTime)
    {
        for (AMonster* M : Monsters)          // 연속 메모리 순회
        {
            if (!M->bPendingRemove) M->Tick(DeltaTime);
        }
        // 프레임 끝: 일괄 정리
        Monsters.RemoveAll([](const AMonster* M) { return M->bPendingRemove; });
        Monsters.Append(PendingAdd);
        PendingAdd.Reset();
    }

private:
    TArray<AMonster*> Monsters;
    TArray<AMonster*> PendingAdd;
};
```

## 9. 흔한 오해

### 오해 1: "삽입/삭제가 많으니 `std::list`다"
조건에 **순회 빈도**가 빠져 있다. 삽입/삭제는 O(1)이어도 매 프레임 전 원소를 도는 비용(캐시 미스)이 그걸 압도한다. 4강 결론 그대로다.

### 오해 2: "`vector`에서 중간 삭제는 무조건 O(n)이라 느리다"
순서가 상관없으면 **swap-and-pop으로 O(1)**이다. 순서가 필요해도 원소 수백~수천 개면 memmove가 캐시 위에서 일어나 생각보다 싸다.

### 오해 3: "`erase`하면 다음 원소를 가리키던 반복자는 그대로 쓸 수 있다"
`std::vector::erase`는 **삭제 지점 이후의 반복자를 전부 무효화**한다. `erase`가 돌려주는 새 반복자를 받아서 써야 한다.

### 오해 4: "vector에 push_back해도 이미 가져온 포인터는 안전하다"
재할당이 일어나는 순간 원소 주소가 전부 바뀐다. 포인터를 밖에 들고 있다면 `Reserve`, 포인터 저장, 핸들 중 하나가 필요하다.

### 오해 5: "STL 자료구조를 고르는 문제니까 표에 있는 복잡도로 답하면 된다"
이 질문의 정답은 복잡도 표에 없다. **접근 패턴(순회), 캐시, 순회 중 변경, 포인터 안정성**까지 말해야 답변이 완성된다.

## 10. 면접에서 나오면

**Q1. 게임에서 몬스터 목록을 관리하려는데, 매 프레임 순회하고 삽입/삭제가 많습니다. 어떤 STL 자료구조를 쓰시겠어요?**
→ "std::vector, 언리얼이라면 TArray를 쓰겠습니다. 매 프레임 전체를 도는 게 가장 잦은 연산이라 연속 메모리의 캐시 지역성이 가장 크게 작용하고, 삽입은 끝에 하면 상각 O(1)입니다. 삭제는 순서가 필요 없으면 마지막 원소와 바꿔서 지우는 swap-and-pop으로 O(1)에 처리합니다. list는 삽입/삭제는 O(1)이지만 순회 때 캐시 미스가 커서 이 조건엔 불리합니다."

**Q2. 순회 중에 원소를 삭제하면 왜 문제가 되나요? 어떻게 해결하나요?**
→ "컨테이너가 바뀌면서 순회 중인 반복자가 무효화되거나 원소를 건너뛰고, 심하면 크래시가 납니다. 역순 인덱스로 돌며 지우거나, 순회 중엔 삭제 표시만 해두고 프레임 끝에 erase-remove나 RemoveAll로 한 번에 정리하는 지연 삭제 방식을 씁니다."

**Q3. vector에 원소를 추가하면 기존 포인터는 안전한가요?**
→ "아닙니다. 용량이 꽉 차서 재할당이 일어나면 모든 원소가 새 버퍼로 옮겨지면서 주소가 바뀌어서, 기존에 들고 있던 포인터와 반복자가 전부 무효화됩니다. Reserve로 용량을 확보하거나, 포인터를 저장하거나, 인덱스+세대 같은 핸들로 참조합니다."

**Q4. swap-and-pop이 뭐고 언제 쓰면 안 되나요?**
→ "지울 원소 자리에 마지막 원소를 옮기고 끝을 제거해서 O(1)에 삭제하는 방법입니다. 대신 원소 순서가 바뀌기 때문에 순서가 의미 있는 컨테이너에는 쓸 수 없습니다. 몬스터 목록처럼 전체를 한 번씩 도는 용도라면 순서가 필요 없어서 잘 맞습니다."

**Q5. 그럼 std::list는 언제 쓰시나요?**
→ "원소의 주소나 반복자가 절대 무효화되면 안 되고, 순회는 드물며, 이미 노드를 들고 있는 상태에서 삽입/삭제할 때입니다. 콜백 목록처럼 순회 중 자기 자신을 지워야 하는 구조가 예입니다."

**Q6. 스폰과 소멸이 너무 잦아서 그것 자체가 병목이면요?**
→ "Object Pooling으로 바꿉니다. 미리 만들어둔 객체를 활성/비활성 플래그로 켜고 꺼서, 컨테이너의 삽입/삭제와 할당/해제를 모두 없앱니다."

면접관이 그 다음에 던지기 좋은 질문: *"몬스터가 수천 마리로 늘면 순회 비용 자체가 문제인데, 어떻게 줄이시겠어요?"* → 활성 범위 밖 몬스터의 업데이트 빈도를 낮추거나(LOD/휴면), 공간 분할로 필요한 것만 순회한다. 공간 분할은 GameMath 7-1강에서 다룬다.

## 11. 셀프 체크

- [ ] "삽입/삭제가 많다"는 조건만으로 list를 고르면 안 되는 이유를 순회 빈도와 캐시 지역성으로 설명할 수 있다.
- [ ] swap-and-pop이 뭔지, 어떤 조건에서만 쓸 수 있는지 설명할 수 있다.
- [ ] 순회 중 삭제/삽입이 왜 위험한지, 지연 삭제로 어떻게 푸는지 코드로 말할 수 있다.
- [ ] vector 재할당이 기존 포인터/반복자를 무효화하는 이유와 대응책을 안다.
- [ ] list와 set/map이 유리한 조건을 각각 한 문장으로 말할 수 있다.
