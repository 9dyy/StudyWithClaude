# 6강 — 해시맵과 트리 맛보기

> **목표:** `TMap`이 내부적으로 어떻게 동작해서 평균 O(1) 조회가 가능한지 설명하고, 배열 대신 맵을 언제 써야 하는지 판단할 수 있게 된다. 트리 기반 탐색의 기본 아이디어도 감을 잡는다.
> **선수 지식:** 4강(배열 vs LinkedList), 5강(Stack과 Queue).

---

## 1. 플레이어 ID로 찾다가 매 프레임이 느려진 코드

접속한 플레이어 정보를 배열에 넣어두고, 플레이어 ID로 찾는 함수를 짰다.

```cpp
TArray<FPlayerInfo> Players;

FPlayerInfo* FindPlayer(int32 PlayerID)
{
    for (FPlayerInfo& Player : Players)   // 매번 처음부터 끝까지 순회
    {
        if (Player.ID == PlayerID)
        {
            return &Player;
        }
    }
    return nullptr;
}
```

플레이어가 10명일 땐 문제없었는데, 100명이 넘는 서버에서 매 프레임 여러 시스템이 `FindPlayer`를 호출하니 눈에 띄게 느려졌다. 배열에서 값으로 찾는 건 **O(n)** — 최악의 경우 배열 전체를 훑어야 한다(4강에서 본 "탐색은 배열도 LinkedList도 O(n)"이 바로 이 상황). 이 문제를 "탐색을 거의 안 하고 바로 찾는" 방식으로 풀어야 한다. 그게 **해시맵(`TMap`)** 이다.

---

## 2. TMap이 O(1)에 가까운 이유 — 해시 함수로 위치를 계산해버린다

배열은 "값이 몇 번째에 있는지 몰라서" 순회해야 한다. 해시맵의 아이디어는 **"키를 계산해서 바로 위치를 알아내자"**다.

```
TMap<int32, FPlayerInfo> Players;

키(PlayerID) ──→ 해시 함수 ──→ 버킷 인덱스 ──→ 그 버킷에 값 저장

PlayerID=1001 → Hash(1001) = 37 → 버킷[37]에 저장
PlayerID=2002 → Hash(2002) = 12 → 버킷[12]에 저장
PlayerID=3003 → Hash(3003) = 37 → 버킷[37]에 저장 (충돌! 아래에서 설명)
```

```
내부 버킷 배열 (실제로는 TArray로 구현됨)
┌────┬────┬────┬─ ... ─┬────┬─ ... ─┬────┐
│ 0  │ 1  │ ...│       │ 12 │       │ 37 │
└────┴────┴────┴───────┴────┴───────┴────┘
                          │             │
                    (2002, ...)   (1001, ...) → (3003, ...)  ← 충돌 시 체이닝
```

조회할 땐 `PlayerID`를 다시 같은 해시 함수에 넣어서 **어느 버킷을 봐야 하는지 계산으로 바로 알아낸다.** 배열을 처음부터 순회하지 않고 "37번 버킷만 확인하면 된다"는 걸 계산으로 아는 것 — 이게 평균 O(1)의 근거다. `TMap`의 내부 버킷 배열 자체는 `TArray`로 구현돼 있다는 것도 눈여겨볼 부분이다. 결국 배열의 "인덱스로 접근하면 O(1)"이라는 성질(4강)을 해시 함수로 "아무 키나 인덱스로 바꿔서" 활용하는 게 해시맵의 본질이다.

```cpp
TMap<int32, FPlayerInfo> Players;

Players.Add(1001, PlayerInfoA);
Players.Add(2002, PlayerInfoB);

FPlayerInfo* Found = Players.Find(1001);   // Hash(1001) 계산 → 바로 그 버킷 확인. 평균 O(1)
```

---

## 3. 해시 충돌 — 서로 다른 키가 같은 버킷에 몰릴 때

버킷 개수는 유한한데 키는 무한히 다양할 수 있어서, **서로 다른 키가 같은 해시값(같은 버킷)으로 계산되는 충돌이 반드시 생긴다.** 위 그림의 `PlayerID=1001`과 `3003`이 둘 다 버킷 37에 걸린 경우다. `TMap`은 이걸 **체이닝**(같은 버킷 안에 여러 개를 리스트처럼 매달아두는 방식)으로 처리한다. 충돌이 많아지면 한 버킷 안에서 다시 순회해야 하니, 최악의 경우(모든 키가 같은 버킷으로 몰림) 조회가 O(n)까지 나빠질 수 있다.

**그래서 "평균 O(1), 최악 O(n)"이라고 말하는 게 정확하다.** 실전에서는 좋은 해시 함수(키를 버킷에 고르게 흩어주는 함수)를 쓰고 버킷 개수를 충분히 넉넉하게 잡아서 충돌을 최소화하면, 사실상 항상 O(1)에 가깝게 동작한다.

---

## 4. 버킷이 꽉 차면 무슨 일이 생기나 — Rehashing

버킷 개수 대비 저장된 원소 수의 비율을 **로드 팩터(Load Factor)**라고 부른다. 원소가 계속 늘어서 로드 팩터가 일정 기준을 넘으면(버킷 하나에 평균 몇 개씩 몰리기 시작하면), 해시 충돌이 잦아져서 평균 O(1)이라는 전제가 무너지기 시작한다. `TMap`은 이걸 막기 위해 **버킷 개수 자체를 늘리고 모든 원소를 다시 배치**한다.

```
버킷 8개, 원소 6개 (로드 팩터 0.75) → 기준 초과!

1. 버킷 개수를 더 크게(보통 2배 정도) 다시 만든다.
2. 기존에 저장된 모든 키를 "새 버킷 개수 기준으로" 해시를 다시 계산해서 재배치한다.
   (버킷 개수가 바뀌면 같은 키라도 계산되는 버킷 인덱스가 달라지기 때문에 전부 다시 계산해야 함)
3. 기존 버킷 배열은 버린다.
```

**이 Rehashing이 일어나는 순간은 O(n)이다** — 4강의 `TArray` 재할당(Growth Factor)과 정확히 같은 패턴이다. 배열이 "용량 꽉 차면 더 큰 버퍼로 복사"하듯, 해시맵은 "로드 팩터 초과하면 더 큰 버킷 배열로 재배치"한다. 두 경우 다 "가끔 비싼 재구성이 일어나지만, 여유 있게 늘려서 평균적으로는 상각(amortized) 비용이 낮게 유지된다"는 같은 설계 철학을 공유한다. 미리 저장할 개수를 알고 있다면 `TMap::Reserve()`로 이 재구성을 아예 피할 수 있는 것도 `TArray::Reserve()`와 동일하다.

## 5. 배열 대신 맵을 언제 쓰나

| 상황 | 추천 | 이유 |
|------|------|------|
| 인덱스(0, 1, 2...)로 순서대로 접근 | `TArray` | 배열의 O(1) 인덱스 접근을 그대로 활용 |
| ID/이름처럼 임의의 키로 빠르게 찾아야 함 | `TMap` | 순회 없이 평균 O(1) 조회 |
| 순서가 중요함(입력 순서, 정렬 유지) | `TArray` | `TMap`은 내부 저장 순서를 보장 안 함 |
| "이 키가 존재하는지"를 자주 확인 | `TMap`/`TSet` | 존재 여부 확인도 평균 O(1) |
| 원소 개수가 매우 적음(수십 개 이하) | `TArray`도 충분 | 해시 계산 오버헤드가 순회 비용보다 클 수 있음 |

**핵심 판단 기준은 "접근하는 방식이 인덱스냐, 키냐"다.** 플레이어를 ID로 찾을 거면 `TMap`, 스폰된 순서대로 순회할 거면 `TArray`. 둘 다 필요하면(ID로도 찾고 순서대로도 순회) 둘 다 유지하면서 동기화하는 것도 실전에서 흔한 패턴이다.

```cpp
// ID로 찾을 일이 많다 → TMap이 자연스럽다
TMap<int32, FPlayerInfo> PlayerByID;

FPlayerInfo* FindPlayer(int32 PlayerID)
{
    return PlayerByID.Find(PlayerID);   // 평균 O(1) — 도입 문제 해결
}
```

## 6. 트리 맛보기 — 정렬을 유지하면서 탐색하고 싶을 때

해시맵은 "정확히 이 키"를 빠르게 찾는 데는 최고지만, **"이 값보다 작은 것 중 가장 큰 것", "정렬된 순서대로 순회"** 같은 질문에는 약하다(해시맵은 순서 개념이 아예 없다). 이럴 때 쓰는 게 **이진 탐색 트리(BST)** 같은 트리 구조다.

```
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80

탐색(40 찾기): 50과 비교(40<50, 왼쪽) → 30과 비교(40>30, 오른쪽) → 40 발견
```

각 노드가 "왼쪽 자식은 나보다 작고, 오른쪽 자식은 나보다 크다"는 규칙을 지키면, 찾을 때마다 **절반씩 후보를 줄여나갈 수 있다.** 균형 잡힌 트리라면 탐색이 O(log n)이다 — 원소가 100만 개여도 약 20번 비교면 찾는다는 뜻이다(배열 순회 O(n)이 100만 번인 것과 비교하면 압도적이다).

**게임에서 트리가 쓰이는 실제 예:**
- 스킬 쿨다운/이벤트 타이머를 "가장 빨리 끝날 것부터" 꺼내는 **우선순위 큐**(내부적으로 힙이라는 트리 구조로 구현됨)
- 랭킹 보드처럼 "정렬된 순서를 유지하면서 삽입/삭제/순회"가 다 필요한 경우
- 공간 분할(쿼드트리/옥트리)로 "이 근처에 있는 오브젝트만" 빠르게 찾는 충돌 판정 최적화

```cpp
// 우선순위 큐 예 — 가장 먼저 끝나는 쿨다운을 항상 O(log n)에 꺼냄
struct FCooldownEntry
{
    float EndTime;
    FName SkillName;
    bool operator<(const FCooldownEntry& Other) const { return EndTime < Other.EndTime; }
};

TArray<FCooldownEntry> CooldownHeap;

void AddCooldown(FName SkillName, float Duration)
{
    CooldownHeap.HeapPush(FCooldownEntry{ GetWorld()->GetTimeSeconds() + Duration, SkillName });
}

void TickCooldowns()
{
    while (CooldownHeap.Num() > 0 && CooldownHeap.HeapTop().EndTime <= GetWorld()->GetTimeSeconds())
    {
        FCooldownEntry Entry;
        CooldownHeap.HeapPop(Entry);   // 가장 빨리 끝나는 것부터 O(log n)에 꺼냄
        OnCooldownFinished(Entry.SkillName);
    }
}
```

`TArray`의 `HeapPush`/`HeapPop`이 바로 트리(힙) 구조를 배열 위에 구현해둔 것이다 — "트리는 항상 포인터로 연결된 노드"라는 생각과 달리, 힙처럼 **배열로도 트리 구조를 표현할 수 있다**는 걸 보여주는 예다.

## 7. 코드로 체감해보기 — 세 자료구조 성능 비교 감각 잡기

```cpp
// 목적: PlayerID로 빠르게 찾기
// (원소 10,000개 기준 평균적인 감각 — 실제 수치는 해시 품질/캐시 상태에 따라 달라짐)

TArray<FPlayerInfo> ArrayVersion;      // Find: O(n) — 순회
TMap<int32, FPlayerInfo> MapVersion;   // Find: 평균 O(1) — 해시 계산 후 버킷 확인
// (정렬 유지 + 로그 시간 탐색이 필요하다면 TSortedMap 계열이나 직접 만든 BST/힙 고려)

FPlayerInfo* FindInArray(int32 ID) { for (auto& P : ArrayVersion) if (P.ID == ID) return &P; return nullptr; }
FPlayerInfo* FindInMap(int32 ID)   { return MapVersion.Find(ID); }
```

원소 개수가 적을 땐(수십 개 이하) 체감 차이가 거의 없지만, 수백~수천 개를 매 프레임 조회하는 순간 `TMap`과 `TArray`의 차이가 프레임 드랍으로 바로 드러난다.

## 8. 흔한 오해

### 오해 1: "TMap은 항상 O(1)이 보장된다"

아니다. **평균** O(1)이고, 해시 충돌이 심하면 최악의 경우 O(n)까지 나빠질 수 있다. "평균/최악"을 구분 안 하고 "무조건 빠르다"고 답하면 면접에서 감점 포인트다.

### 오해 2: "TMap은 넣은 순서대로 순회된다"

아니다. `TMap`은 내부적으로 해시값 기반 버킷에 저장되기 때문에 **순회 순서를 보장하지 않는다.** 입력 순서가 중요하면 `TArray`를 쓰거나, 순서와 빠른 조회가 둘 다 필요하면 두 자료구조를 같이 관리해야 한다.

### 오해 3: "원소가 적어도 TMap이 TArray보다 항상 빠르다"

아니다. 해시 계산 자체에도 비용이 있어서, 원소가 아주 적으면(수십 개 이하) 배열 순회가 캐시 지역성 덕에 오히려 더 빠를 수 있다. "데이터 크기가 작을 땐 단순한 구조가 이긴다"는 4강의 교훈과 같은 맥락이다.

### 오해 4: "트리는 항상 포인터로 연결된 노드로만 구현된다"

아니다. 힙처럼 부모-자식 관계를 **배열 인덱스 계산**(`i번째 노드의 자식은 2i+1, 2i+2`)으로 표현하는 트리도 흔하다. `TArray::HeapPush`/`HeapPop`이 정확히 이 방식이다.

### 오해 5: "해시 충돌은 해시 함수를 잘못 짜서 생기는 버그다"

아니다. 버킷 개수가 유한한 이상 충돌은 **필연적으로** 생긴다. 좋은 해시 함수는 충돌을 "없애는" 게 아니라 "고르게 분산시켜서 최소화하는" 것뿐이다.

### 오해 6: "TMap에 원소를 넣는 연산은 항상 O(1)이다"

대부분은 맞지만, 로드 팩터를 넘어서 Rehashing이 일어나는 그 순간만큼은 O(n)이다. `TArray`의 재할당과 같은 이치로, "평균/상각으로는 O(1), 가끔 한 번씩 O(n)"이 정확한 설명이다.

## 9. 면접에서 나오면

**Q1. TMap이 내부적으로 어떻게 O(1) 조회를 하나요?**
→ "키를 해시 함수에 넣어서 버킷 인덱스를 계산하고, 그 버킷만 확인합니다. 배열을 처음부터 순회하지 않고 계산으로 바로 위치를 알아내는 게 핵심이라, 평균적으로 원소 개수와 무관하게 O(1)에 가깝게 동작합니다."

**Q2. TMap은 항상 O(1)인가요?**
→ "아닙니다. 평균 O(1)이고 최악의 경우 O(n)까지 나빠질 수 있습니다. 서로 다른 키가 같은 버킷으로 계산되는 해시 충돌이 심해지면, 한 버킷 안에서 다시 순회해야 하기 때문입니다."

**Q3. 배열 대신 TMap을 쓰는 게 나은 경우는 언제인가요?**
→ "ID나 이름처럼 임의의 키로 빠르게 조회해야 하는 경우입니다. 반대로 순서가 중요하거나 인덱스로 순회할 일이 많으면 TArray가 더 낫습니다. TMap은 저장 순서를 보장하지 않는다는 점도 고려해야 합니다."

**Q4. 해시 충돌이 뭐고 어떻게 처리하나요?**
→ "서로 다른 키가 같은 해시값(버킷)으로 계산되는 걸 말합니다. TMap은 같은 버킷에 여러 값을 체이닝 방식으로 저장해서 처리하는데, 충돌이 많아지면 조회 성능이 떨어지기 때문에 좋은 해시 함수와 충분한 버킷 크기로 충돌을 최소화하는 게 중요합니다."

**Q5. 매 프레임 100명이 넘는 플레이어를 ID로 조회해야 한다면 TArray와 TMap 중 뭘 쓰시겠어요?**
→ "TMap을 쓰겠습니다. TArray로 매번 순회하면 O(n)이라 플레이어 수가 늘수록 매 프레임 비용이 커지지만, TMap은 평균 O(1)이라 인원수와 거의 무관하게 일정한 성능을 냅니다."

**Q6. 정렬된 순서를 유지하면서 삽입/탐색을 빠르게 하고 싶다면 TMap으로 충분한가요?**
→ "충분하지 않습니다. TMap은 순서 개념이 없어서 정렬 유지에는 안 맞고, 이런 경우엔 이진 탐색 트리나 정렬된 자료구조가 필요합니다. 랭킹 보드처럼 순위 순서를 유지해야 하는 경우가 대표적입니다."

**Q7. 트리 기반 자료구조가 게임에서 실제로 쓰이는 예를 들어주세요.**
→ "스킬 쿨다운을 가장 빨리 끝나는 것부터 꺼내는 우선순위 큐가 대표적입니다. 내부적으로 힙이라는 트리 구조로 구현돼서 삽입과 최솟값(또는 최댓값) 조회가 O(log n)입니다. 공간을 분할해서 근처 오브젝트만 빠르게 찾는 쿼드트리도 충돌 판정 최적화에 자주 쓰입니다."

**Q8. TMap에 원소를 계속 추가하면 내부적으로 무슨 일이 일어나나요?**
→ "버킷 대비 원소 비율인 로드 팩터가 일정 기준을 넘으면, 버킷 개수를 더 크게 만들고 기존 원소를 전부 새 버킷 기준으로 다시 배치하는 Rehashing이 일어납니다. TArray의 재할당과 같은 원리로, 이 순간은 O(n)이지만 여유 있게 늘리기 때문에 평균적으로는 O(1)이 유지됩니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 매 프레임 total order로 정렬된 랭킹을 유지해야 하는데 삽입도 잦다면, TMap과 트리 중 뭘 고르겠어요?"* → 정렬 유지가 필수 요구사항이면 TMap은 애초에 후보가 안 되고, 트리 기반(정렬된 자료구조) 쪽으로 판단해야 한다는 게 핵심이다.

---

## 10. 셀프 체크

- [ ] TMap이 해시 함수로 버킷을 계산해서 O(1)에 가까운 조회를 하는 원리를 설명할 수 있다.
- [ ] TMap이 "평균 O(1), 최악 O(n)"인 이유(해시 충돌)를 안다.
- [ ] 배열과 TMap 중 뭘 쓸지 "인덱스 접근이냐 키 접근이냐" 기준으로 판단할 수 있다.
- [ ] TMap이 저장 순서를 보장하지 않는다는 걸 안다.
- [ ] 트리(힙)가 게임에서 우선순위 큐 같은 형태로 실제로 쓰이는 예를 하나 이상 들 수 있다.
- [ ] TMap의 Rehashing이 TArray의 재할당과 같은 원리라는 걸 설명할 수 있다.
