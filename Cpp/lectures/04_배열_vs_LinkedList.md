# 4강 — 배열 vs LinkedList

> **목표:** 배열과 LinkedList의 삽입/삭제/탐색 시간복잡도를 표로만 외우지 않고, "캐시 지역성" 때문에 실제로는 왜 배열이 이기는 경우가 많은지 CPU 관점까지 설명할 수 있게 된다.
> **선수 지식:** 3강(RAII). 포인터 기본 개념.

---

## 1. "삽입/삭제는 LinkedList가 빠르다"고 배웠는데 실측하면 안 그렇다

인벤토리에 아이템 1000개를 넣고 중간에서 계속 삽입/삭제하는 로직을 짰다. "배열은 중간 삽입 시 뒤 원소를 다 밀어야 해서 느리고, LinkedList는 포인터만 바꾸면 되니까 빠르다"고 배운 대로 `TDoubleLinkedList`로 짰는데, 실제로 프로파일링해보면 `TArray`보다 오히려 **느리다.** 왜 교과서랑 다를까?

이 질문에 "LinkedList가 삽입/삭제가 더 빠르다"고만 답하면 절반만 맞은 거다. 이론적 시간복잡도와 실제 성능이 갈리는 이유 — **캐시 지역성** — 을 알아야 이 강의 목표에 도달한다.

---

## 2. 시간복잡도부터 정리 — 이론상으로는 이렇다

| 연산 | 배열(`TArray`) | LinkedList(`TDoubleLinkedList`) |
|------|------|------|
| 인덱스로 접근 | O(1) | O(n) — 앞에서부터 따라가야 함 |
| 맨 뒤에 추가 | O(1) (평균, 가끔 재할당 시 O(n)) | O(1) |
| 중간에 삽입/삭제 | O(n) — 뒤 원소를 밀어야 함 | O(1) — 위치를 이미 알고 있다면 |
| 탐색(값으로 찾기) | O(n) | O(n) |

표만 보면 "중간 삽입/삭제는 LinkedList가 확실히 이긴다"가 맞다. **그런데 이 O(1)에는 함정이 있다.** LinkedList의 삽입/삭제가 O(1)이려면 "그 위치를 가리키는 노드 포인터를 이미 갖고 있어야" 한다. 대부분의 실전 코드는 "인덱스 500번째에 삽입해줘" 같은 요청을 받는데, 이러면 **그 위치까지 노드를 하나씩 따라가는 데 이미 O(n)**이 걸린다. 결국 "탐색 O(n) + 삽입 O(1)"이라 배열의 "탐색 없이 바로 O(n) 밀기"랑 총 비용이 비슷해진다.

---

## 3. 메모리 구조부터 다르다

두 자료구조가 메모리에 실제로 어떻게 놓이는지 그려보면 왜 성능이 갈리는지 보인다.

```
배열(TArray) — 메모리에 연속으로 붙어있음
┌────┬────┬────┬────┬────┐
│ 0  │ 1  │ 2  │ 3  │ 4  │   ← 주소가 촘촘하게 이어짐
└────┴────┴────┴────┴────┘
 0x1000 0x1004 0x1008 0x100C 0x1010   (int32 기준 4바이트씩)

LinkedList — 메모리 여기저기 흩어져 있음, 포인터로 연결
┌────┐      ┌────┐      ┌────┐      ┌────┐
│ 값 │─────→│ 값 │─────→│ 값 │─────→│ 값 │
└────┘      └────┘      └────┘      └────┘
0x3F20      0x8A10      0x1204      0xB330   (주소가 완전히 제각각)
```

배열은 원소들이 메모리에 **줄줄이 붙어서** 있고, LinkedList는 각 노드가 힙 여기저기 **따로따로** 할당돼서 포인터로만 이어져 있다. 이 차이가 CPU 캐시와 만나면 실제 성능 차이로 이어진다.

---

## 4. 캐시 지역성 — 왜 붙어있는 데이터가 진짜 빠른가

CPU는 메모리(RAM)에서 데이터를 하나씩 가져오지 않는다. **캐시 라인(보통 64바이트) 단위로 통째로** 가져와서 훨씬 빠른 CPU 캐시에 저장해둔다. 배열을 순회할 때 무슨 일이 일어나는지 보자.

```
TArray<int32> Items; (int32 = 4바이트)

Items[0]을 읽으면 CPU는 0x1000부터 64바이트를 캐시 라인에 통째로 가져온다.
→ 이 안에 Items[0]부터 Items[15]까지 이미 다 들어있다!
→ Items[1], Items[2], ... Items[15]는 이미 캐시에 있으니 메모리 접근 없이 바로 읽힘 (엄청 빠름)
```

```
TDoubleLinkedList<int32> Items;

Items의 첫 노드(0x3F20)를 읽으면 그 근처 64바이트만 캐시에 올라온다.
다음 노드는 0x8A10 — 전혀 다른 자리라 캐시에 없음. 다시 메모리에서 가져와야 함(캐시 미스).
그 다음 노드도, 그 다음도... 매번 캐시 미스가 난다.
```

**"배열이 빠르다"의 진짜 이유는 시간복잡도 표에 안 나온다.** 배열을 순회하면 캐시 미스가 거의 안 나지만, LinkedList를 순회하면 노드 하나 읽을 때마다 캐시 미스가 나기 쉽다. 캐시 미스 한 번의 비용(수십~수백 사이클)은 배열 원소를 여러 개 밀어내는 비용(캐시에 이미 있는 데이터를 옮기는 것뿐이라 매우 쌈)보다 훨씬 크다. 그래서 "이론상 O(n)인 배열 삽입"이 "이론상 O(1)인 LinkedList 삽입"을 실측에서 이겨버리는 역전이 흔하게 일어난다.

---

## 5. 숫자로 감 잡기 — 캐시 히트와 캐시 미스는 실제로 몇 배 차이나나

"캐시 미스가 크다"는 말을 감으로만 두지 말고 대략적인 수치로 잡아보자(정확한 수치는 CPU마다 다르지만 자릿수 감각은 어디서나 비슷하다).

| 접근 대상 | 대략적인 지연 | 배열 기준 상대 배수 |
|------|------|------|
| CPU L1 캐시(이미 캐시에 있는 데이터) | 약 1~4 사이클 | 1배 |
| CPU L2 캐시 | 약 10~20 사이클 | 5~10배 |
| 메인 메모리(RAM, 캐시 미스) | 약 100~300 사이클 | **100배 이상** |

배열을 순회하면 캐시 라인 하나로 원소 여러 개를 한 번에 가져오니 대부분 L1 캐시 히트로 처리된다. LinkedList는 노드 하나 읽을 때마다 이 "약 100배 이상 느린" RAM 접근이 반복될 가능성이 높다. **원소 몇 개를 배열에서 밀어내는 연산(캐시에 이미 올라온 데이터를 옮기는 것뿐이라 몇 사이클 수준)과, 캐시 미스 한 번(100 사이클 이상)을 비교하면, 왜 "이론상 O(n)인 배열 삽입"이 "이론상 O(1)인 LinkedList 삽입"을 실측에서 이겨버리는지가 숫자로 납득된다.** 원소 몇백 개를 밀어내도 캐시 미스 한두 번보다 싼 경우가 실제로 흔하다.

## 6. TArray가 커질 때 내부적으로 무슨 일이 일어나나 — 재할당 전략

배열의 강점을 제대로 이해하려면 `TArray`가 원소를 추가할 때 힙 메모리를 어떻게 다루는지도 봐야 한다(1강의 힙/데이터 영역 구분, 7강에서 다룰 할당 비용과 바로 연결되는 내용이다).

```
용량 4, 원소 4개 꽉 찬 상태에서 Add() 한 번 더 호출하면:

1. 기존보다 더 큰 새 버퍼를 힙에 할당한다 (보통 1.5~2배 정도로 여유 있게 — "Growth Factor")
   ┌────┬────┬────┬────┐        ┌────┬────┬────┬────┬────┬────┬────┬────┐
   │ 기존 버퍼(용량4)      │  →   │ 새 버퍼(용량8, 비어있는 자리 포함)          │
   └────┴────┴────┴────┘        └────┴────┴────┴────┴────┴────┴────┴────┘
2. 기존 원소를 전부 새 버퍼로 복사한다 (여기가 O(n) — "가끔 재할당 시 O(n)"의 정체)
3. 기존 버퍼는 해제한다.
4. 새 원소를 그 다음 빈 자리에 추가한다.
```

**매번 딱 필요한 만큼만 할당하면 Add()마다 재할당이 일어나서 최악이 되니까, 여유를 두고 배로 늘리는 전략을 쓴다.** 이 덕분에 재할당은 "가끔"만 일어나고, 재할당이 없는 대부분의 `Add()` 호출은 이미 확보된 공간에 값만 채우는 거라 O(1)이다. n번 추가할 때 재할당에 드는 총 비용을 다 더해도 평균적으로 원소당 O(1)이 된다는 게 "amortized(상각) O(1)"이라는 표현의 의미다.

```cpp
TArray<FInventoryItem> Inventory;
Inventory.Reserve(1000);   // 처음부터 필요한 용량을 알고 있다면 미리 확보 — 재할당 자체를 아예 없앤다
for (int32 i = 0; i < 1000; ++i)
{
    Inventory.Add(MakeItem(i));   // Reserve 덕분에 이 루프에서 재할당이 한 번도 안 일어남
}
```

크기를 미리 알고 있다면 `Reserve()`로 이 재할당 비용 자체를 없앨 수 있다는 것도 실무에서 자주 쓰는 최적화다.

## 7. 그래서 실전에서는 언제 뭘 쓰나

| 상황 | 추천 | 이유 |
|------|------|------|
| 순회가 잦다(매 프레임 인벤토리 UI 갱신 등) | `TArray` | 캐시 지역성 압도적으로 유리 |
| 크기를 예측 못하고 자주 앞/중간에 넣고 뺀다 | `TArray`(대부분) | 캐시 이득이 삽입 비용을 상쇄하는 경우가 많음. 실측 없이 LinkedList로 바꾸지 말 것 |
| 원소가 매우 크고(수백 바이트↑), 삽입/삭제만 압도적으로 많고 순회는 거의 없다 | `TDoubleLinkedList` 고려 | 큰 원소를 통째로 옮기는 비용 > 캐시 이득 |
| 이미 노드 포인터/반복자를 들고 있는 상태에서 그 자리에 삽입/삭제 | LinkedList가 진짜 유리 | O(n) 탐색이 이미 생략됨 |

**결론: "삽입/삭제가 잦으니 무조건 LinkedList"는 실무에서 거의 틀린 판단이다.** 언리얼 코드베이스가 `TArray`를 압도적으로 기본으로 쓰는 것도 이 이유다. LinkedList가 진짜 이기는 경우는 생각보다 좁다 — "이미 위치를 알고 있는 상태에서" 삽입/삭제할 때뿐이다.

## 8. 배열이 유리한 이유가 캐시 지역성 하나만은 아니다 — 벡터화(SIMD)

CPU에는 하나의 명령어로 여러 데이터를 한꺼번에 처리하는 **SIMD(Single Instruction, Multiple Data)** 연산이 있다. 예를 들어 파티클 1000개의 위치를 매 프레임 갱신할 때, 데이터가 배열처럼 메모리에 연속으로 있으면 컴파일러가 이 SIMD 명령어를 자동으로 활용해서(자동 벡터화) 한 번에 4개, 8개씩 묶어 계산할 수 있다.

```cpp
// 배열 순회 — 원소가 메모리에 연속이라 컴파일러가 SIMD로 자동 벡터화하기 좋은 형태
TArray<FVector> ParticlePositions;
for (FVector& Position : ParticlePositions)
{
    Position += Velocity * DeltaTime;   // 이런 단순 반복 연산은 벡터화 후보가 되기 쉬움
}
```

LinkedList는 원소가 메모리에 흩어져 있어서 이런 묶음 처리가 원천적으로 불가능하다. 노드 하나하나를 포인터 따라가며 처리해야 하니, 한 번에 여러 개를 묶어 계산할 방법이 없다. **"배열이 빠르다"는 이유가 캐시 지역성 하나로 끝나는 게 아니라, 하드웨어가 배열 형태의 데이터를 더 잘 활용할 수 있게 설계돼 있다는 것까지 알면 답변이 한 단계 더 깊어진다.** 이런 이유로 파티클 시스템, 물리 시뮬레이션처럼 같은 연산을 대량으로 반복하는 코드는 배열(그리고 더 나아가 "구조체 배열"이 아니라 "배열의 구조체", SoA) 형태를 선호한다.

## 9. 코드로 체감해보기

```cpp
// 배열 — 중간 삽입은 뒤를 밀어야 하지만, 캐시 지역성 덕에 그 자체가 빠르다
TArray<FInventoryItem> Inventory;
Inventory.Insert(NewItem, 500);   // 내부적으로 memmove — 캐시에 이미 올라와 있는 데이터를 옮김

// LinkedList — 삽입 자체는 O(1)이지만, 그 위치까지 가는 데 캐시 미스가 반복됨
TDoubleLinkedList<FInventoryItem> LinkedInventory;
auto* Node = LinkedInventory.GetHead();
for (int32 i = 0; i < 500; ++i)   // 500번 캐시 미스 가능성 있는 순회
{
    Node = Node->GetNextNode();
}
LinkedInventory.InsertNode(NewNode, Node);   // 여기 자체는 빠르지만 이미 늦었다
```

```cpp
// 순회 성능 차이가 극명하게 드러나는 예 — 매 프레임 UI 갱신
void AInventoryWidget::RefreshUI(const TArray<FInventoryItem>& Inventory)
{
    for (const FInventoryItem& Item : Inventory)   // 연속 메모리 순회 — 캐시 지역성 최대 활용
    {
        UpdateSlotWidget(Item);
    }
}
```

## 10. 흔한 오해

### 오해 1: "삽입/삭제가 잦으면 무조건 LinkedList가 유리하다"

시간복잡도 표만 보면 맞지만, 실전에서는 "삽입할 위치까지 찾아가는 비용"과 "캐시 미스 비용"을 더하면 배열이 이기는 경우가 훨씬 많다. 실측 없이 LinkedList로 바꾸는 건 성급한 최적화다.

### 오해 2: "TArray의 중간 삽입은 O(n)이니까 항상 느리다"

"느리다"의 기준이 "이론적 연산 횟수"라면 맞지만, 그 연산 하나하나가 캐시에 이미 올라온 데이터를 옮기는 거라 실제 걸리는 시간은 매우 작다. LinkedList의 노드 하나 따라가는 것보다 배열 원소 여러 개를 밀어내는 게 실측으로 더 빠른 경우가 흔하다.

### 오해 3: "포인터로 연결돼 있으니 LinkedList가 메모리를 더 아낀다"

오히려 반대인 경우가 많다. LinkedList의 각 노드는 데이터 외에 **다음(그리고 이전) 노드를 가리키는 포인터**를 추가로 들고 있어서, 원소당 메모리 오버헤드가 배열보다 크다. 게다가 노드가 힙에 흩어져 있어서 메모리 단편화도 유발한다.

### 오해 4: "캐시 지역성은 이론일 뿐이고 실제 게임에서는 체감이 안 된다"

아니다. 매 프레임 도는 루프(적 AI 순회, 파티클 업데이트, 인벤토리 UI 갱신)에서 자료구조를 배열에서 LinkedList로 바꾸는 것만으로 프레임 드랍이 눈에 띄게 나타나는 경우가 실제로 흔하다. 언리얼이 `TArray`를 기본값으로 미는 이유가 이 체감 차이 때문이다.

### 오해 5: "인덱스로 접근할 일이 없으면 자료구조 선택에 시간복잡도 표만 보면 충분하다"

시간복잡도는 "연산 횟수"만 재는 척도라 하드웨어(캐시, 메모리 계층)를 반영 안 한다. 실전 성능 판단에는 시간복잡도 + 캐시 지역성을 같이 봐야 한다.

### 오해 6: "TArray는 Add()할 때마다 매번 새로 메모리를 할당한다"

아니다. 용량이 꽉 찼을 때만 더 큰 버퍼로 재할당하고, 평소엔 여유분에 값만 채운다. 재할당 자체도 필요한 만큼만이 아니라 1.5~2배 정도로 넉넉하게 늘려서, 재할당이 자주 일어나지 않도록 만들어져 있다.

## 11. 면접에서 나오면

**Q1. 배열과 LinkedList의 차이, 둘 중 누가 삽입/삭제가 더 빠른지?**
→ "시간복잡도만 보면 중간 삽입/삭제는 LinkedList가 O(1), 배열은 O(n)이라 LinkedList가 유리해 보입니다. 하지만 실제로는 그 위치를 찾아가는 탐색 비용이 LinkedList도 O(n)이고, 캐시 지역성 때문에 배열의 연속된 메모리 접근이 훨씬 빠릅니다. 그래서 실무에서는 이미 위치(노드)를 알고 있는 경우가 아니면 배열이 더 빠른 경우가 많습니다."

**Q2. 캐시 지역성이 뭔가요?**
→ "CPU가 메모리에서 데이터를 가져올 때 한 번에 캐시 라인 단위(보통 64바이트)로 통째로 가져오는 걸 이용하는 개념입니다. 배열처럼 데이터가 메모리에 연속으로 있으면 하나를 가져올 때 주변 데이터까지 같이 캐시에 올라와서, 다음 접근이 캐시 히트로 처리되어 훨씬 빠릅니다."

**Q3. LinkedList가 캐시 지역성이 나쁜 이유는 뭔가요?**
→ "각 노드가 힙의 서로 다른 위치에 따로 할당되기 때문입니다. 노드를 순회할 때마다 이전 노드와 전혀 다른 메모리 주소로 이동해야 해서, 매번 캐시 미스가 발생하기 쉽습니다. 캐시 미스 한 번의 비용이 배열에서 원소 몇 개를 밀어내는 비용보다 훨씬 크기 때문에 실측 성능이 역전됩니다."

**Q4. TArray의 인덱스 접근이 O(1)인 이유는 뭔가요?**
→ "배열은 메모리에 연속으로 붙어있어서 시작 주소에 (인덱스 × 원소 크기)만 더하면 바로 그 위치의 주소가 계산됩니다. 몇 번째 원소든 계산 한 번으로 접근할 수 있어서 O(1)입니다."

**Q5. 인벤토리처럼 자주 순회하면서 가끔 중간에 아이템을 삽입/삭제하는 자료구조를 고른다면 뭘 쓰시겠어요?**
→ "TArray를 쓰겠습니다. 순회가 잦다면 캐시 지역성의 이득이 압도적이고, 중간 삽입/삭제 비용은 실측해보면 캐시 미스가 반복되는 LinkedList보다 오히려 낮은 경우가 많습니다. LinkedList는 이미 노드 포인터를 들고 있는 상태에서 반복적으로 삽입/삭제하는 특수한 상황에서만 유리합니다."

**Q6. 그럼 LinkedList가 실제로 유리한 경우는 언제인가요?**
→ "탐색 과정 없이 이미 삽입/삭제할 위치(노드나 반복자)를 들고 있는 경우입니다. 예를 들어 순회하다가 조건에 맞는 노드를 찾은 그 자리에서 바로 삭제하는 경우처럼, O(n) 탐색이 이미 다른 이유로 끝나 있는 상황에서는 LinkedList의 O(1) 삽입/삭제가 그대로 이득이 됩니다."

**Q7. TArray에 원소를 계속 추가하면 내부적으로 무슨 일이 일어나나요?**
→ "내부 버퍼가 꽉 차면 더 큰 새 버퍼를 할당하고 기존 원소를 전부 복사한 뒤 이전 버퍼를 해제합니다. 이 재할당이 일어나는 순간은 O(n)이지만, 보통 필요한 크기보다 여유 있게 할당해두기 때문에 평균적으로는 추가 연산이 O(1)로 취급됩니다."

**Q8. TArray의 재할당 비용이 걱정된다면 어떻게 대처하나요?**
→ "미리 필요한 크기를 알고 있다면 Reserve()로 용량을 먼저 확보해서 재할당 자체를 없앨 수 있습니다. 크기를 모른다면 TArray의 기본 성장 전략(1.5~2배씩 늘리는 방식) 자체가 재할당 빈도를 줄이도록 설계돼 있어서 평균적으로는 상각 O(1)을 기대할 수 있습니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 TMap 같은 해시 기반 자료구조는 이 둘과 비교하면 어떤가요?"* → 6강(해시맵과 트리 맛보기)에서 다룬다.

## 12. 셀프 체크

- [ ] 배열과 LinkedList의 삽입/삭제/탐색/접근 시간복잡도를 표로 말할 수 있다.
- [ ] "LinkedList의 O(1) 삽입"에 탐색 비용이 숨어있다는 함정을 설명할 수 있다.
- [ ] 캐시 지역성이 뭔지, 왜 배열 순회가 실제로 더 빠른지 CPU 캐시 라인 관점에서 설명할 수 있다.
- [ ] LinkedList가 진짜로 유리한 좁은 상황(이미 노드를 들고 있을 때)을 구분할 수 있다.
- [ ] "시간복잡도가 낮다 = 항상 빠르다"가 아니라는 걸 실제 사례로 설명할 수 있다.
- [ ] TArray가 커질 때 재할당(Growth Factor)이 어떻게 일어나는지, Reserve()가 왜 유용한지 설명할 수 있다.
- [ ] 배열이 캐시 지역성뿐 아니라 SIMD 벡터화에도 유리한 이유를 안다.
