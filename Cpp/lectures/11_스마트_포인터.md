# 11강 — 스마트 포인터: unique_ptr, shared_ptr, weak_ptr

> **목표:** unique_ptr/shared_ptr/weak_ptr을 언제 구분해서 써야 하는지, 순환 참조가 왜 메모리를 누수시키는지, move semantics와 Rule of 3/5가 뭔지 설명할 수 있게 된다.
> **선수 지식:** 3강(생성자·소멸자와 RAII). OS 09강(Atomic과 Lock-Free)을 봤으면 6절이 더 잘 이어진다.

---

## 1. 인벤토리 아이템을 shared_ptr로 돌렸더니 메모리가 안 줄어든다

아이템 하나를 인벤토리(소유자)와 퀵슬롯 UI(참조자)가 같이 들고 있어야 해서, 둘 다 `TSharedPtr`로 짰다.

```cpp
class FInventoryItem
{
public:
    FString ItemName;
    TSharedPtr<class FQuickSlot> AssignedSlot;   // 아이템이 자기가 걸린 퀵슬롯을 가리킴
};

class FQuickSlot
{
public:
    TSharedPtr<FInventoryItem> Item;   // 퀵슬롯이 아이템을 가리킴
};
```

퀵슬롯에서 아이템을 빼고 인벤토리 창을 닫아도, 메모리 프로파일러를 보면 `FInventoryItem`과 `FQuickSlot`이 계속 살아있다. 둘 다 소멸자가 안 불린다. `Item`을 `nullptr`로 지워도, `AssignedSlot`을 지워도 딱 하나만 지운 쪽은 카운트가 줄 뿐, **서로가 서로를 붙잡고 있어서 둘 다 참조 카운트가 0이 될 방법이 없다.** shared_ptr을 썼는데 왜 메모리 관리가 자동이 안 되는지, 이 강의에서 정리한다.

---

## 2. unique_ptr — 소유권은 하나, 복사는 없다

3강에서 RAII가 `delete`를 소멸자에 자동으로 묶는 원리라고 배웠다. `TUniquePtr`는 그 원리를 그대로 살린, **소유자가 딱 하나뿐인** 스마트 포인터다.

```cpp
TUniquePtr<FWeaponData> WeaponData = MakeUnique<FWeaponData>();
WeaponData->Damage = 50.0f;
// WeaponData가 스코프를 벗어나면 소멸자가 자동으로 delete
```

핵심은 **복사를 아예 막아놨다는 것**이다.

```cpp
TUniquePtr<FWeaponData> A = MakeUnique<FWeaponData>();
TUniquePtr<FWeaponData> B = A;   // 컴파일 에러! 복사 생성자가 삭제되어 있음
```

왜 막았을까. 소유자가 하나뿐이어야 하는데 복사를 허용하면 `A`와 `B`가 같은 메모리를 각자 "내 것"이라고 착각하게 되고, 둘 다 스코프를 벗어날 때 **같은 메모리를 두 번 delete**하는 이중 해제(double free) 버그로 직행한다. `TUniquePtr`는 이 실수 자체를 컴파일 타임에 막아버린다. 대신 소유권을 **넘기는 것(이동)**은 허용한다.

```cpp
TUniquePtr<FWeaponData> A = MakeUnique<FWeaponData>();
TUniquePtr<FWeaponData> B = MoveTemp(A);   // OK — 소유권이 A에서 B로 넘어감
// 이제 A는 nullptr, B가 유일한 소유자
```

10강에서 캐릭터 상태 객체를 `TUniquePtr<FCharacterState>`로 관리했던 것도 이 이유다 — 상태는 항상 딱 하나의 소유자(캐릭터)만 있으면 되고, 상태가 바뀔 때 이전 객체는 자동으로 죽어야 하니 `unique_ptr`이 정확히 맞는 도구였다.

---

## 3. shared_ptr — 참조 카운트로 여러 명이 같이 소유

아이템을 인벤토리도 들고 있고 퀵슬롯도 들고 있고 툴팁 UI도 들고 있어야 한다면, "소유자가 하나"라는 `unique_ptr`의 전제가 안 맞는다. 이럴 때 `TSharedPtr`를 쓴다.

```cpp
TSharedPtr<FInventoryItem> Item = MakeShared<FInventoryItem>();
TSharedPtr<FInventoryItem> SlotRef = Item;   // 복사 OK — 참조 카운트가 2로 증가
TSharedPtr<FInventoryItem> TooltipRef = Item;   // 참조 카운트 3
```

내부적으로 `TSharedPtr`는 실제 객체와 별도로 **참조 카운트**를 관리한다. 복사될 때마다 카운트를 1 늘리고, 소유자(shared_ptr 변수) 하나가 스코프를 벗어나거나 `nullptr`로 리셋될 때마다 1 줄인다. **카운트가 0이 되는 순간에만** 실제 객체가 `delete`된다.

```
Item ──┐
       ├──→ [참조 카운트: 3] ──→ FInventoryItem 객체
SlotRef ┤
       │
TooltipRef ┘

Item = nullptr        → 카운트 2
SlotRef = nullptr      → 카운트 1
TooltipRef = nullptr   → 카운트 0 → 이때 비로소 delete
```

"아무도 안 쓰면 자동으로 사라진다"는 편리함 때문에 아이템, 액터 참조, 리소스 핸들처럼 **여러 시스템이 동시에 참조하는 대상**에 자주 쓴다. 하지만 이 편리함에는 함정이 있다.

---

## 4. 순환 참조 — shared_ptr끼리 서로 물면 카운트가 0이 안 된다

도입의 버그가 정확히 이거다. `FInventoryItem`이 `TSharedPtr<FQuickSlot>`을 들고, `FQuickSlot`이 `TSharedPtr<FInventoryItem>`을 들면, **두 객체가 서로를 참조 카운트 1씩 붙잡고 있는 상태**가 된다.

```
FInventoryItem ──(shared_ptr)──→ FQuickSlot
      ▲                              │
      └──────(shared_ptr)────────────┘

바깥에서 아무도 안 쓰게 돼도, 둘이 서로를 붙잡고 있어서
두 카운트 모두 1 밑으로 안 떨어짐 → 영원히 delete 안 됨
```

바깥의 다른 변수들이 다 사라져도 이 둘은 서로를 통해서만 참조 카운트 1을 유지하고 있어서, **참조 카운트 메커니즘 자체는 완벽하게 정상 동작했는데도** 메모리는 영원히 회수되지 않는다. 이게 "shared_ptr는 메모리 누수를 완전히 막아준다"는 생각이 위험한 이유다.

---

## 5. weak_ptr — 소유권 없이 지켜보기만

순환 참조를 끊는 표준적인 방법은, **관계 중 한쪽을 소유("나도 살아있게 붙잡는다")가 아니라 관찰("살아있으면 보고, 죽었으면 안다")로 바꾸는 것**이다. 이때 쓰는 게 `TWeakPtr`다.

```cpp
class FQuickSlot
{
public:
    TWeakPtr<FInventoryItem> Item;   // 소유권 없이 참조만 — 참조 카운트 안 늘림
};
```

`TWeakPtr`는 참조 카운트에 전혀 영향을 주지 않는다. 그래서 `FInventoryItem` 쪽 참조 카운트가 0이 되면 `TWeakPtr`가 있든 없든 객체는 정상적으로 delete된다. 대신 `weak_ptr`는 객체에 직접 접근할 수 없고, **`Pin()`(언리얼) 또는 `lock()`(표준)으로 "지금도 살아있는지 확인 + 살아있으면 임시 shared_ptr 받기"**를 거쳐야 한다.

```cpp
void FQuickSlot::UseItem()
{
    TSharedPtr<FInventoryItem> Pinned = Item.Pin();   // 살아있으면 shared_ptr 반환, 죽었으면 nullptr

    if (!Pinned.IsValid())
    {
        UE_LOG(LogTemp, Warning, TEXT("아이템이 이미 삭제됨 — 슬롯 비움"));
        return;
    }

    Pinned->Use();   // 이 블록 안에서는 Pinned가 참조 카운트를 1 늘려서 안전하게 유지
}
```

**소유 관계를 그릴 때 "누가 진짜 주인이고 누가 그냥 들여다보기만 하는가"를 먼저 정하는 게 순서다.** 인벤토리 아이템 예시라면 인벤토리가 진짜 소유자(`shared_ptr`), 퀵슬롯은 관찰자(`weak_ptr`)로 정하면 순환이 아예 생기지 않는다.

## 6. move semantics — 왜 unique_ptr는 이동만 되는가

2절에서 `MoveTemp(A)`로 소유권을 넘기는 걸 봤다. 이게 **move semantics(이동 의미론)** 다. C++의 값은 크게 두 종류로 나뉜다 — **lvalue**(이름이 있고 나중에 또 쓸 수 있는 값, 변수 `A`)와 **rvalue**(이름 없이 잠깐 쓰고 사라질 임시 값, `MakeUnique<FWeaponData>()`의 결과). `MoveTemp`(표준 라이브러리의 `std::move`)는 실제로 아무것도 옮기지 않는다 — **"이 lvalue를 rvalue처럼 취급해도 된다"고 컴파일러에게 허락만 해주는 캐스팅**이다.

```cpp
TUniquePtr<FWeaponData> A = MakeUnique<FWeaponData>();
TUniquePtr<FWeaponData> B = MoveTemp(A);
// MoveTemp(A)는 A를 "이제 버려도 되는 값"처럼 표시만 함
// 그 표시를 본 TUniquePtr의 이동 생성자가 내부 포인터를 B로 옮기고 A는 nullptr로 비움
```

왜 이게 필요한가. 이동이 없다면 소유권을 넘길 때마다 **객체를 통째로 복사**해야 한다. `TArray<FInventoryItem>`처럼 무거운 데이터를 함수에서 리턴할 때, 복사가 아니라 "포인터와 크기만 옮기고 원본은 비워버리는" 이동을 쓰면 진짜 데이터 복사 없이 소유권만 넘어간다. `unique_ptr`가 복사는 막고 이동만 허용하는 이유도 같다 — **복사를 허용하면 소유자가 둘이 되어버리니까, 대신 "원래 소유자를 비우고 새 소유자에게 넘기는" 이동만 허락한 것**이다.

## 7. Rule of 3/5 — 소멸자를 직접 정의했다면 같이 챙겨야 할 것들

3강 오해 3에서 "포인터 멤버가 있으면 암시적 복사 생성자가 얕은 복사를 한다"고 배웠다. 그래서 자원을 소유한 클래스는 보통 소멸자를 직접 써서 해제를 챙기는데, 여기서 끝내면 안 된다.

**Rule of 3**: 클래스에 **소멸자, 복사 생성자, 복사 대입 연산자** 중 하나라도 직접 정의해야 할 이유가 있다면, 나머지 둘도 같이 직접 정의(또는 명시적으로 삭제)해야 한다.

```cpp
class FOwningBuffer
{
public:
    FOwningBuffer(int32 Size) : Data(new uint8[Size]), Length(Size) {}
    ~FOwningBuffer() { delete[] Data; }   // 소멸자를 정의했으니

    FOwningBuffer(const FOwningBuffer& Other)            // 복사 생성자도
        : Data(new uint8[Other.Length]), Length(Other.Length)
    {
        FMemory::Memcpy(Data, Other.Data, Length);       // 얕은 복사 대신 깊은 복사
    }

    FOwningBuffer& operator=(const FOwningBuffer& Other)  // 복사 대입 연산자도 같이
    {
        if (this != &Other)
        {
            delete[] Data;
            Length = Other.Length;
            Data = new uint8[Length];
            FMemory::Memcpy(Data, Other.Data, Length);
        }
        return *this;
    }

private:
    uint8* Data;
    int32 Length;
};
```

소멸자만 정의하고 나머지 둘을 컴파일러 기본값(얕은 복사)에 맡겨두면, 복사된 객체 둘이 같은 `Data`를 가리키다가 **둘 다 소멸자에서 같은 메모리를 delete**하는 이중 해제로 이어진다. **Rule of 5**는 여기에 C++11부터 생긴 **이동 생성자, 이동 대입 연산자**까지 포함한 다섯 가지를 같이 챙기라는 확장판이다. 다만 실무에서는 이 다섯 개를 손으로 다 쓰는 대신, **애초에 `TUniquePtr`/`TSharedPtr`로 자원을 감싸서 컴파일러가 만들어주는 기본 복사/이동이 안전하게 동작하게 만드는 게** 훨씬 흔하다 — Rule of 3/5를 아는 것 자체보다, "왜 스마트 포인터를 쓰면 이 규칙을 손으로 안 지켜도 되는지"를 아는 게 더 실전적이다.

## 8. 흔한 오해

### 오해 1: "shared_ptr를 쓰면 메모리 누수 걱정을 안 해도 된다"

아니다. 4절에서 본 순환 참조는 참조 카운트가 정상 동작하는데도 메모리가 회수되지 않는 경우다. `shared_ptr`는 "아무도 안 쓰면 자동으로 사라진다"를 보장할 뿐, 소유 관계를 잘못 설계하면 여전히 새어나갈 수 있다.

### 오해 2: "unique_ptr도 결국 복사가 되긴 된다, 조금 불편할 뿐이다"

아니다. `unique_ptr`의 복사 생성자/복사 대입 연산자는 `= delete`로 아예 삭제돼 있어서 **컴파일 자체가 안 된다.** 되는 건 이동뿐이다.

### 오해 3: "weak_ptr도 shared_ptr처럼 객체를 살아있게 만든다"

아니다. `weak_ptr`는 참조 카운트에 전혀 관여하지 않는다. 객체가 죽었는지 살았는지 확인만 하고, 살아있을 때 잠깐 접근하려면 `Pin()`/`lock()`으로 임시 `shared_ptr`을 얻어야 한다.

### 오해 4: "TSharedPtr<T, ESPMode::ThreadSafe>면 객체 자체도 스레드 안전해진다"

아니다. `ESPMode::ThreadSafe`는 **참조 카운트의 증감 연산만** atomic으로 만들어준다. 여러 스레드가 동시에 같은 `TSharedPtr`를 복사/소멸시켜도 카운트는 안 깨지지만, 그 포인터가 가리키는 객체의 멤버를 여러 스레드가 동시에 읽고 쓰면 여전히 Race Condition이 난다(OS 09강 참고).

### 오해 5: "MoveTemp(A)를 호출하면 그 시점에 실제로 데이터가 이동한다"

아니다. `MoveTemp`(표준의 `std::move`) 자체는 캐스팅일 뿐, 아무 데이터도 옮기지 않는다. 실제 이동은 그 결과를 받는 쪽의 **이동 생성자/이동 대입 연산자**가 실행될 때 일어난다.

## 9. 면접에서 나오면

**Q1. unique_ptr와 shared_ptr의 차이는 뭔가요?**
→ "unique_ptr은 소유자가 단 하나뿐이라 복사가 금지되고 이동만 가능하고, 스코프를 벗어나면 바로 delete됩니다. shared_ptr은 참조 카운트를 둬서 여러 곳에서 복사해 같이 소유할 수 있고, 마지막 소유자가 사라질 때만 delete됩니다."

**Q2. 멀티스레드에서 shared 포인터를 썼을 때 어떤 문제가 발생할 수 있을까요?**
→ "참조 카운트 증감 자체는 atomic 연산이라 카운트가 깨지진 않습니다. 하지만 그 포인터가 가리키는 객체의 멤버를 여러 스레드가 동시에 읽고 쓰면 별도 보호가 없어서 Race Condition이 생길 수 있습니다. 카운트의 스레드 안전성과 객체 내부 데이터의 스레드 안전성은 별개 문제입니다."

**Q3. 순환 참조가 왜 생기고, 어떻게 해결하나요?**
→ "두 객체가 서로를 shared_ptr로 물고 있으면 바깥에서 아무도 안 써도 서로가 서로의 참조 카운트를 1 이상으로 유지시켜서 둘 다 delete가 안 됩니다. 관계 중 한쪽을 소유가 아니라 관찰 목적인 weak_ptr로 바꿔서, 참조 카운트에 영향을 안 주게 만들어 해결합니다."

**Q4. 여러 시스템이 함께 참조해야 하는 아이템 객체를 만든다면 unique_ptr과 shared_ptr 중 뭘 쓰시겠어요?**
→ "여러 곳이 동시에 접근해야 하고 소유자가 명확히 하나로 정해지지 않는다면 shared_ptr를 씁니다. 다만 그중 진짜 소유자가 아니라 그냥 참조만 하는 관계가 있다면(예: UI가 아이템을 잠깐 들여다보는 경우) weak_ptr로 순환 참조 위험을 먼저 없앤 다음 설계합니다."

**Q5. move semantics가 왜 필요한가요?**
→ "객체를 넘길 때마다 통째로 복사하면 비용이 큰데, 이동은 내부 데이터를 그대로 옮기고 원본은 비우기만 해서 실제 복사 없이 소유권만 넘길 수 있습니다. unique_ptr처럼 소유자가 하나여야 하는 타입은 복사를 막는 대신 이동만 허용해서 이 방식으로 소유권을 넘깁니다."

**Q6. Rule of 3(또는 Rule of 5)가 뭔가요?**
→ "소멸자, 복사 생성자, 복사 대입 연산자 중 하나라도 직접 정의해야 할 이유가 있다면 나머지도 같이 정의해야 한다는 규칙입니다. 자원을 소유한 클래스에서 소멸자만 정의하고 복사는 컴파일러 기본값(얕은 복사)에 맡기면 이중 해제로 이어지기 때문입니다. Rule of 5는 여기에 이동 생성자와 이동 대입 연산자까지 포함합니다."

**Q7. weak_ptr을 Pin()이나 lock() 없이 바로 쓰면 안 되는 이유는요?**
→ "weak_ptr은 객체가 살아있다는 걸 보장하지 않기 때문에, 확인 없이 바로 접근하면 이미 삭제된 객체를 참조하는 댕글링 상태일 수 있습니다. Pin()으로 살아있는지 확인하고 임시 shared_ptr을 받아야 그 블록 안에서는 안전하게 접근할 수 있습니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 순환 참조를 아예 설계 단계에서 막으려면 클래스 관계를 어떻게 그리겠어요?"* → "누가 진짜 소유자인지"를 먼저 정하고 소유 방향이 한쪽으로만 흐르게(트리 구조) 그리면, weak_ptr을 나중에 끼워 맞추지 않아도 순환이 애초에 안 생긴다는 답으로 이어가면 된다.

## 10. 셀프 체크

- [ ] unique_ptr이 왜 복사를 막고 이동만 허용하는지 설명할 수 있다.
- [ ] shared_ptr의 참조 카운트가 어떻게 늘고 줄어드는지, 0이 될 때 무슨 일이 일어나는지 안다.
- [ ] 순환 참조가 왜 메모리 누수로 이어지는지, weak_ptr이 그걸 어떻게 끊는지 설명할 수 있다.
- [ ] TSharedPtr의 ThreadSafe 모드가 참조 카운트만 보호할 뿐 객체 내부는 보호하지 않는다는 걸 안다.
- [ ] Rule of 3/5가 뭔지, 스마트 포인터를 쓰면 왜 이 규칙을 손으로 덜 신경 써도 되는지 설명할 수 있다.
