# 12강 — 정렬 알고리즘과 시간복잡도

> **목표:** Big-O가 정확히 뭘 재는 척도인지, 대표 정렬 알고리즘(버블/삽입/퀵/머지)의 시간복잡도와 그 이유, 안정 정렬이 왜 중요한지 설명할 수 있게 된다.
> **선수 지식:** 4강(배열 vs LinkedList — 캐시 지역성), 5강(Stack과 Queue).

---

## 1. 랭킹보드가 100명일 땐 안 보이던 버벅임이 10만 명이 되니 나타났다

시즌 랭킹보드를 만들었다. 매초 점수가 바뀌는 플레이어들을 점수 내림차순으로 정렬해서 보여줘야 한다. 급한 대로 제일 익숙한 방식으로 짰다.

```cpp
void SortRankingBubble(TArray<FPlayerScore>& Players)
{
    for (int32 i = 0; i < Players.Num() - 1; ++i)
    {
        for (int32 j = 0; j < Players.Num() - 1 - i; ++j)
        {
            if (Players[j].Score < Players[j + 1].Score)
            {
                Players.Swap(j, j + 1);
            }
        }
    }
}
```

내부 테스트에서 100명으로 돌릴 땐 매초 정렬해도 티가 안 났다. 그런데 시즌이 진행되고 랭킹보드에 10만 명이 쌓이자, 매초 이 함수 한 번 도는 데 프레임이 눈에 띄게 떨어졌다. 사람 수가 1000배 늘었는데 왜 체감 렉은 그보다 훨씬 심하게 늘었을까 — 이게 이 강의에서 풀 문제다.

---

## 2. Big-O가 재는 것 — "정확한 시간"이 아니라 "늘어나는 추세"

Big-O 표기법은 **입력 크기 n이 커질 때 연산 횟수가 어떤 속도로 늘어나는지**를 나타낸다. 몇 밀리초 걸리는지가 아니라, **n이 2배가 되면 연산이 몇 배로 늘어나는가**를 보는 척도다.

| 표기 | 이름 | n=100 → n=10,000이면 연산 횟수는 |
|------|------|------|
| O(1) | 상수 | 그대로 |
| O(log n) | 로그 | 약 2배 |
| O(n) | 선형 | 100배 |
| O(n log n) | 선형 로그 | 약 130배 |
| O(n²) | 이차 | 10,000배 |

도입의 버블 정렬은 이중 루프 구조라 **O(n²)** 다. 플레이어가 100명일 때 최대 비교 횟수는 대략 100×100 = 1만 번이지만, 10만 명이 되면 100,000×100,000 = **100억 번**이다. 사람 수는 1000배 늘었는데 연산은 100만 배 늘어난 셈이다 — 체감 렉이 사람 수 증가보다 훨씬 가파르게 나빠진 이유가 여기 있다. Big-O가 상수항이나 세부 구현을 무시하고 이 "늘어나는 추세"만 보는 이유도, 결국 **n이 커질수록 실제 성능을 지배하는 건 상수가 아니라 이 추세**이기 때문이다.

---

## 3. O(n²) 계열 — 버블/선택/삽입 정렬

이 셋은 전부 **"바깥 루프로 한 칸씩 훑으면서, 안쪽 루프로 나머지를 다시 훑는다"**는 이중 루프 구조라 O(n²)가 나온다.

- **버블 정렬**: 인접한 두 원소를 비교해서 순서가 틀리면 교환. 한 바퀴 돌 때마다 가장 큰(또는 작은) 값이 끝으로 "떠오른다."
- **선택 정렬**: 남은 범위에서 최솟값(또는 최댓값)을 찾아 맨 앞과 교환. 매 바퀴 "찾기"에 O(n)이 들어서 전체 O(n²).
- **삽입 정렬**: 이미 정렬된 앞부분에 새 원소를 끼워 넣을 자리를 찾아 삽입. **거의 정렬된 데이터에서는 O(n)에 가깝게 빨라진다**는 게 셋 중 특이점이다 — 랭킹보드처럼 "매초 몇 명 순위만 살짝 바뀌는" 데이터에 의외로 실전에서 잘 맞는다.

세 알고리즘 모두 n이 작을 때(수십 개 이하)는 구현이 단순하고 상수 오버헤드가 적어서, 이론상 더 빠른 O(n log n) 알고리즘보다 실측 속도가 나을 수도 있다. **"이론적 시간복잡도가 낮다"와 "이 상황에서 실제로 더 빠르다"는 다른 이야기**라는 걸 여기서 짚고 가자.

---

## 4. O(n log n) 계열 — 퀵정렬과 머지정렬, 분할정복

n이 커지면 O(n²)는 감당이 안 된다. **분할정복(Divide and Conquer)** — "문제를 반으로 쪼개고, 각각 정렬한 다음, 합친다" — 방식이 여기서 등장한다.

```
[8, 3, 5, 1, 9, 2]
        │  분할
   ┌────┴────┐
[8, 3, 5]  [1, 9, 2]
   │  분할       │  분할
 ┌─┴─┐        ┌─┴─┐
[8][3,5]     [1][9,2]
    │  정복 후 병합    │
  [3,5,8] ◀──────▶ [1,2,9]
        │  병합
   [1, 2, 3, 5, 8, 9]
```

**왜 O(n log n)인가.** 매번 절반으로 쪼개니까 "쪼개는 깊이"는 log n(트리의 높이)이고, 각 깊이 층에서 병합/비교하는 데 걸리는 총 작업량은 그 층 전체를 통틀어 O(n)이다. 층의 개수(log n) × 층마다의 작업량(n) = **O(n log n)**. 4강에서 배열 탐색을 반씩 줄여나가는 이진 탐색이 O(log n)이었던 것과 같은 원리가, 여기서는 "쪼개는 단계 수"에 적용된 것이다.

- **머지 정렬**: 반으로 계속 쪼갠 뒤, 이미 정렬된 두 부분을 **병합(merge)**하며 합친다. 항상 O(n log n) — 최악의 경우에도 성능이 보장된다. 대신 병합 과정에서 임시 배열이 필요해 **메모리를 추가로 O(n)만큼 쓴다.**
- **퀵 정렬**: 기준값(피벗)을 하나 잡아서, 피벗보다 작은 값은 왼쪽, 큰 값은 오른쪽으로 나눈(파티션) 다음 양쪽을 재귀적으로 정렬한다. 평균적으로 O(n log n)이고, **추가 메모리 없이 제자리에서(in-place)** 정렬 가능해서 실무에서 가장 흔히 쓰인다.

---

## 5. 퀵정렬이 최악의 경우 O(n²)가 되는 이유

퀵정렬의 평균 O(n log n)은 **피벗이 매번 데이터를 어느 정도 균형 있게 반으로 나눠준다**는 전제 위에 있다. 이 전제가 깨지면 얘기가 달라진다.

```cpp
// ❌ 위험한 습관: 항상 첫 번째 원소를 피벗으로 고정
int32 Partition(TArray<int32>& Arr, int32 Low, int32 High)
{
    int32 Pivot = Arr[Low];   // 이미 정렬된 배열이면 항상 최솟값이 피벗
    // ...
}
```

만약 입력이 **이미 정렬돼 있거나 거의 정렬돼 있는데**, 피벗을 항상 맨 앞(또는 맨 뒤) 원소로 고정해서 뽑으면, 매번 "피벗보다 작은 건 하나도 없고 나머지 전부가 큰 쪽"으로 갈린다. 데이터를 절반씩 나누는 게 아니라 **한 개씩만 떼어내고 나머지 n-1개를 다시 재귀**하는 꼴이 되어, 결국 버블 정렬과 다를 바 없는 **O(n²)**로 무너진다. 실무에서는 이 위험을 피하려고 피벗을 **무작위로 고르거나, 앞/중간/끝 셋 중 중간값을 고르는(median-of-three)** 방식을 쓴다. "랭킹보드가 이미 어느 정도 정렬된 상태에서 매초 재정렬한다"는 이 강의 도입의 상황이 바로 퀵정렬의 최악 케이스에 가까운 조건이라는 걸 눈여겨봐 두자.

## 6. 안정 정렬 — 동점자를 원래 순서대로 유지할지 말지

**안정 정렬(Stable Sort)** 이란, **비교 기준으로는 같은 값을 가진 두 원소의 상대적 순서를, 정렬 후에도 그대로 유지**하는 정렬을 말한다.

```
정렬 전: [(김철수, 100점), (이영희, 100점), (박민수, 90점)]
점수 기준 내림차순 정렬 후...

안정 정렬:    [(김철수, 100), (이영희, 100), (박민수, 90)]   ← 100점 동점자 순서 유지
불안정 정렬:  [(이영희, 100), (김철수, 100), (박민수, 90)]   ← 순서가 뒤바뀔 수 있음
```

랭킹보드에서 "점수가 같으면 먼저 그 점수를 찍은 사람이 위"라는 2차 정렬 규칙이 있다면, 안정 정렬이 아닌 알고리즘으로 점수만 기준으로 정렬해버리면 이 규칙이 깨질 수 있다. **머지 정렬은 안정적이고, 퀵 정렬은(구현에 따라 다르지만 일반적인 in-place 파티션 방식은) 안정적이지 않다.** 동점자 처리처럼 "같은 값의 순서 보존"이 중요한 요구사항이 있는지가, 알고리즘을 고를 때 시간복잡도 못지않게 중요한 기준이 된다.

## 7. TArray::Sort는 실제로 뭘 쓰나

실무에서 정렬 알고리즘을 직접 구현할 일은 거의 없다. 언리얼의 `TArray::Sort()`는 내부적으로 **Introsort 계열**(퀵정렬 기반으로 시작하되, 재귀가 너무 깊어지면 힙 정렬로 전환해 최악의 경우도 O(n log n)에 가깝게 방어하는 하이브리드 알고리즘)을 쓴다. 그래서 5절의 "퀵정렬 최악의 경우 O(n²)" 걱정을 실무 코드에서 직접 손으로 방어할 일은 드물다.

```cpp
TArray<FPlayerScore> Players;

// 점수 내림차순
Players.Sort([](const FPlayerScore& A, const FPlayerScore& B)
{
    return A.Score > B.Score;
});

// 점수 내림차순, 동점이면 이름 오름차순 — 비교 함수 안에서 2차 기준을 직접 챙긴다
Players.Sort([](const FPlayerScore& A, const FPlayerScore& B)
{
    if (A.Score != B.Score)
    {
        return A.Score > B.Score;
    }
    return A.PlayerName < B.PlayerName;
});
```

`TArray::Sort()`가 안정 정렬을 보장하지 않기 때문에, 동점자 순서 같은 2차 기준이 필요하면 **비교 함수(predicate) 안에서 그 기준까지 직접 명시**하는 게 실무에서 훨씬 안전하다. "안정 정렬에 기대는 것"보다 "비교 조건 자체에 원하는 순서를 다 넣는 것"이 의도를 코드로 명확히 드러내는 방법이기도 하다.

## 8. 코드로 체감해보기 — 랭킹보드 정렬 개선

도입의 버블 정렬을 실제로 바꿔보자.

```cpp
// ❌ 개선 전: O(n²), 매초 10만 명 재정렬
void SortRankingBubble(TArray<FPlayerScore>& Players)
{
    for (int32 i = 0; i < Players.Num() - 1; ++i)
    {
        for (int32 j = 0; j < Players.Num() - 1 - i; ++j)
        {
            if (Players[j].Score < Players[j + 1].Score)
            {
                Players.Swap(j, j + 1);
            }
        }
    }
}

// ✅ 개선 후: 평균 O(n log n), 최악의 경우도 Introsort가 방어
void SortRankingOptimized(TArray<FPlayerScore>& Players)
{
    Players.Sort([](const FPlayerScore& A, const FPlayerScore& B)
    {
        if (A.Score != B.Score)
        {
            return A.Score > B.Score;   // 점수 내림차순
        }
        return A.LastScoreTime < B.LastScoreTime;   // 동점이면 먼저 달성한 사람이 위
    });
}
```

10만 명 기준으로 버블 정렬은 최악의 경우 약 100억 번 비교가 필요했지만, O(n log n) 알고리즘은 10만 × log₂(10만) ≈ 10만 × 17 = 약 170만 번이면 충분하다. 알고리즘만 바꿨을 뿐인데 연산량이 수천 배 차이 나는 게, "Big-O를 챙기는 게 왜 실무에서 중요한가"에 대한 가장 직접적인 답이다.

## 9. 흔한 오해

### 오해 1: "정렬 알고리즘은 다 O(n log n)이다"

아니다. 버블/선택/삽입 정렬은 이중 루프 구조라 O(n²)다. O(n log n)은 분할정복 방식(퀵/머지 정렬)에서 나온다.

### 오해 2: "퀵정렬이 이론상 좋으니까 항상 가장 빠르다"

아니다. 피벗을 잘못 고르면 이미 정렬된 데이터에서 최악의 경우 O(n²)로 무너진다. 최악의 경우 성능을 보장하고 싶으면 머지 정렬이나, 퀵정렬을 방어적으로 개선한 Introsort 계열을 쓴다.

### 오해 3: "Big-O가 낮은 알고리즘이 항상 실제로 더 빠르다"

아니다. Big-O는 n이 충분히 클 때의 추세일 뿐, 작은 n에서는 구현이 단순한 O(n²) 알고리즘(특히 삽입 정렬)이 상수 오버헤드가 적어서 실측 속도가 더 나을 수 있다.

### 오해 4: "TArray::Sort()는 항상 안정 정렬이다"

아니다. 내부적으로 퀵정렬 기반 Introsort를 쓰기 때문에 안정성을 보장하지 않는다. 동점자 순서가 중요하면 비교 함수 안에 2차 기준을 직접 넣어야 한다.

### 오해 5: "정렬은 항상 정렬 알고리즘을 직접 구현해서 써야 한다"

아니다. 실무에서는 `TArray::Sort()`나 `Algo::Sort()`처럼 검증되고 최적화된 표준 정렬 함수를 쓰는 게 기본이다. 직접 구현은 특수한 안정성/성능 요구사항이 있을 때나 학습 목적일 때 의미가 있다.

## 10. 면접에서 나오면

**Q1. Big-O가 뭔가요?**
→ "입력 크기가 커질 때 연산 횟수가 어떤 속도로 늘어나는지를 나타내는 척도입니다. 정확한 실행 시간이 아니라, 상수항을 무시하고 n이 커질수록 지배적인 증가 추세만 봅니다."

**Q2. 버블정렬과 퀵정렬의 시간복잡도 차이는 뭐고, 왜 그런 차이가 나나요?**
→ "버블정렬은 이중 루프로 매번 인접한 두 원소를 비교해서 O(n²)이고, 퀵정렬은 피벗으로 데이터를 반씩 나누는 분할정복 방식이라 평균 O(n log n)입니다. 절반씩 쪼개는 깊이가 log n이고 각 깊이에서의 작업량이 n이라서 곱한 값이 n log n이 됩니다."

**Q3. 퀵정렬이 최악의 경우 왜 O(n²)가 되나요?**
→ "피벗이 데이터를 균형 있게 반으로 못 나누고 한쪽으로 치우치면, 매번 한 개만 떼어내고 나머지를 재귀하는 꼴이 됩니다. 이미 정렬된 배열에서 피벗을 항상 첫 번째 원소로 고정하면 이런 최악의 경우가 발생하기 쉽습니다."

**Q4. 10만 명 규모의 랭킹보드를 매초 정렬한다면 어떤 걸 고려해서 정렬 방식을 고르시겠어요?**
→ "데이터가 매초 아주 조금씩만 바뀐다면 거의 정렬된 상태에서 빠른 삽입 정렬도 고려할 수 있지만, 최악의 경우 성능 보장이 필요하면 TArray::Sort 같은 검증된 하이브리드 정렬을 씁니다. 동점자를 원래 순서대로 유지해야 한다면 안정성 여부도 같이 확인합니다."

**Q5. 안정 정렬이 왜 필요한 경우가 있나요?**
→ "정렬 기준으로는 값이 같은 원소들의 상대적 순서를 유지해야 하는 경우입니다. 예를 들어 점수가 같으면 먼저 그 점수를 찍은 사람이 위에 오도록 하는 2차 규칙이 있다면, 안정 정렬이 아닌 알고리즘으로 점수만 기준으로 정렬하면 그 순서가 깨질 수 있습니다."

**Q6. 이미 정렬된 배열에 퀵정렬을 그대로 쓰면 왜 위험한가요?**
→ "피벗을 고정된 위치(첫 원소 등)로 고르는 구현이라면, 이미 정렬된 데이터에서는 매번 한쪽으로만 쏠리는 최악의 파티션이 발생해서 O(n²)로 느려집니다. 피벗을 무작위로 고르거나 median-of-three 방식으로 고르면 이 위험을 줄일 수 있습니다."

**Q7. TArray::Sort() 내부에서 어떤 알고리즘을 쓰는지 아세요?**
→ "퀵정렬을 기반으로 하되 재귀가 너무 깊어지면 힙정렬로 전환하는 Introsort 계열 하이브리드 알고리즘을 씁니다. 그래서 평균 성능은 퀵정렬만큼 빠르면서, 최악의 경우에도 O(n log n)에 가깝게 방어됩니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 이진 탐색은 왜 O(log n)인가요?"* → 4강에서 다룬 탐색 시간복잡도와 이 강의의 "절반씩 쪼개면 깊이가 log n"이라는 원리가 그대로 이어진다고 답하면 된다.

## 11. 셀프 체크

- [ ] Big-O가 "정확한 시간"이 아니라 "입력 크기에 따른 증가 추세"를 나타낸다는 걸 설명할 수 있다.
- [ ] 버블/선택/삽입 정렬이 왜 O(n²)인지, 퀵/머지 정렬이 왜 O(n log n)인지 설명할 수 있다.
- [ ] 퀵정렬이 최악의 경우 O(n²)가 되는 조건과 그 방어법(피벗 선택)을 안다.
- [ ] 안정 정렬이 뭔지, 그리고 그게 왜 필요한 상황이 있는지 예를 들 수 있다.
- [ ] TArray::Sort()가 안정 정렬을 보장하지 않는다는 걸 알고, 동점자 처리를 어떻게 챙길지 설명할 수 있다.
