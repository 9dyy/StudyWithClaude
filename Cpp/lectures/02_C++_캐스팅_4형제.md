# 2강 — C++ 캐스팅 4형제

> **목표:** `static_cast`, `dynamic_cast`, `reinterpret_cast`, `const_cast`가 각각 뭘 검사하고 뭘 안 하는지 구분하고, 언리얼의 `Cast<T>`가 내부적으로 뭘 쓰는지 설명할 수 있게 된다.
> **선수 지식:** 1강(static). 클래스 상속(부모/자식) 개념.

---

## 1. 히트 판정에서 터진 캐스팅 버그

플레이어가 쏜 총알이 뭔가에 맞았다. 맞은 대상이 `AWeaponPickup`(무기 습득 아이템)이면 무기를 교체하는 로직을 태우고 싶다.

```cpp
void ABullet::OnHit(AActor* HitActor)
{
    AWeaponPickup* Weapon = (AWeaponPickup*)HitActor;   // C-style cast
    Weapon->EquipTo(OwnerCharacter);                    // 크래시 혹은 이상한 동작
}
```

빌드는 잘 된다. 그런데 총알이 `AWeaponPickup`이 아니라 `AWall`에 맞으면 게임이 죽는다. `HitActor`가 진짜로 `AWeaponPickup`인지 컴파일러도, 런타임도 **아무도 확인을 안 했기 때문**이다. `(AWeaponPickup*)HitActor`는 "이 주소를 그냥 `AWeaponPickup*`이라고 우겨라"는 뜻이라, `AWall` 객체의 메모리를 `AWeaponPickup`의 메모리 레이아웃으로 잘못 읽어버린다. `Weapon->EquipTo(...)`는 존재하지도 않는 함수 포인터를 호출하는 거나 마찬가지다.

이 사고를 막으려면 "**진짜로 그 타입이 맞는지 검사하면서 변환**"하는 방법이 필요하다. C++은 이런 상황들을 구분해서 처리하라고 캐스팅 연산자를 4개나 따로 만들어뒀다.

---

## 2. 네 형제 소개 — 뭘 검사하고 뭘 안 하나

| 캐스팅 | 하는 일 | 런타임 검사 | 실패 시 |
|------|------|------|------|
| `static_cast` | 컴파일러가 "관련 있다"고 아는 타입끼리 변환 | ❌ 안 함 | 조용히 틀린 결과(UB) |
| `dynamic_cast` | 다형성 타입의 **실제 객체 타입**을 런타임에 확인하며 변환 | ✅ RTTI로 확인 | 포인터는 `nullptr`, 참조는 예외 |
| `reinterpret_cast` | 타입 무시하고 **비트를 그대로 재해석** | ❌ 안 함 | 정의조차 안 됨(대부분 UB) |
| `const_cast` | `const`/`volatile` **속성만** 떼거나 붙임 | ❌ 안 함(속성 문제만) | 원본이 진짜 const면 UB |

공통 원칙 하나: **컴파일러가 검사해줄 수 있는 건 컴파일 타임에, 실제 객체 타입을 봐야 아는 건 런타임에** 검사한다. 이 원칙을 아는 게 "언제 뭘 쓰나"를 외우지 않고 판단하는 방법이다.

---

## 3. static_cast — "관련 있는 건 아는데, 진짜 그 타입인진 안 봐"

`static_cast`는 **클래스 계층이 컴파일 타임에 이미 확인 가능한** 변환에 쓴다. 업캐스팅(자식→부모), 명확한 다운캐스팅(단, 확신이 있을 때만), 숫자 타입 변환이 대표적이다.

```cpp
class AItemActor : public AActor { public: virtual void Use() {} };
class AWeaponPickup : public AItemActor { public: void EquipTo(ACharacter* C) { /* ... */ } };

AWeaponPickup* Weapon = new AWeaponPickup();
AItemActor* Item = static_cast<AItemActor*>(Weapon);   // 업캐스팅. 항상 안전 — 자식은 부모를 포함하니까

// 다운캐스팅도 문법상 가능하지만...
AWeaponPickup* Back = static_cast<AWeaponPickup*>(Item);   // 컴파일은 됨. 근데 Item이 진짜 Weapon인지 검사 안 함!

float Health = 87.0f;
int32 IntHealth = static_cast<int32>(Health);   // 87. 숫자 변환은 이게 정석 (C-style cast 대신)
```

업캐스팅은 자식 객체 안에 부모 객체가 통째로 포함돼 있다는 게 타입 시스템으로 보장되니 검사할 필요가 없다. 문제는 **다운캐스팅**이다. `static_cast`로 다운캐스팅하면 컴파일은 되지만, `Item`이 진짜 `AWeaponPickup`인지는 아무도 확인 안 한다. "내가 확실히 알고 있다"는 전제가 있을 때만 써야 한다 — 도입의 버그가 바로 이 전제가 틀렸던 경우다.

---

## 4. dynamic_cast — "진짜 그 타입인지 런타임에 확인하고 변환"

`dynamic_cast`는 **다형성 타입(가상 함수가 있는 클래스)**에서만 쓸 수 있고, 변환하기 전에 **그 객체가 실제로 목표 타입인지 런타임에 확인**한다.

```cpp
void ABullet::OnHit(AActor* HitActor)
{
    AWeaponPickup* Weapon = dynamic_cast<AWeaponPickup*>(HitActor);
    if (Weapon != nullptr)   // 진짜 AWeaponPickup일 때만 nullptr이 아님
    {
        Weapon->EquipTo(OwnerCharacter);
    }
    // AWall이었으면 Weapon은 nullptr → EquipTo 호출 자체가 안 일어남. 크래시 방지.
}
```

**어떻게 런타임에 아냐?** 가상 함수가 있는 클래스는 객체마다 **vtable 포인터**를 갖고 있고, 컴파일러는 이 vtable 근처에 **RTTI(Run-Time Type Information)** — "이 객체는 진짜 어떤 클래스인가" 하는 정보 — 를 같이 심어둔다. `dynamic_cast`는 이 RTTI를 뒤져서 "`HitActor`가 가리키는 실제 객체가 `AWeaponPickup`이거나 그 자식인가"를 확인한 다음에야 포인터를 내준다. 이 확인 과정 때문에 `static_cast`보다 **느리다** — 공짜가 아니다.

---

## 5. reinterpret_cast — "타입 신경 안 써, 비트를 그대로 다르게 읽어"

`reinterpret_cast`는 관련 없는 타입끼리 **메모리 비트 패턴을 그대로 유지한 채 타입만 바꿔치기**한다. 타입 계층이고 뭐고 아예 상관없다.

```cpp
uint32 RawColor = 0xFF00FF00;   // 실제로는 색상 비트 패턴
uint8* Bytes = reinterpret_cast<uint8*>(&RawColor);   // 바이트 단위로 뜯어보고 싶을 때
UE_LOG(LogTemp, Log, TEXT("첫 바이트: %d"), Bytes[0]);

// 네트워크 패킷 버퍼를 구조체로 재해석하는 저수준 코드 등에서 씀
```

**언제 쓰나:** 네트워크 패킷 버퍼 파싱, 포인터를 정수로 임시 저장했다가 되돌리기 같은 **정말 저수준의 메모리 조작**일 때만. 일반적인 게임플레이 코드에서 `reinterpret_cast`가 보이면 십중팔구 뭔가 잘못 설계된 신호다.

---

## 6. const_cast — "타입은 그대로, const만 떼거나 붙여"

`const_cast`는 유일하게 **타입 자체는 안 바꾸고 `const`/`volatile` 속성만** 건드린다.

```cpp
void LegacyLogFunction(char* Message)   // 예전에 짜여진, const를 안 받는 함수
{
    UE_LOG(LogTemp, Log, TEXT("%s"), ANSI_TO_TCHAR(Message));
}

void PrintMessage(const char* Msg)
{
    LegacyLogFunction(const_cast<char*>(Msg));   // const를 떼서 넘겨줌
}
```

**언제 안전한가:** 원래 객체가 **진짜로 non-const로 선언되어 있었는데**, 중간에 `const` 참조/포인터를 거쳐온 경우 — 이럴 땐 `const_cast`로 떼도 안전하다. 반대로 **원본 자체가 `const`로 선언된 객체**를 `const_cast`로 떼고 실제로 값을 바꾸면 미정의 동작(UB)이다. `const_cast`는 "속인다"가 아니라 "원래 있던 자격을 되찾아준다"는 느낌으로 써야 안전하다.

---

## 7. C-style cast는 왜 위험한가 — 넷 중 아무거나 조용히 골라 씀

```cpp
AWeaponPickup* Weapon = (AWeaponPickup*)HitActor;
```

이 한 줄이 위험한 진짜 이유는 "검사를 안 해서"가 아니라, **컴파일러가 static_cast / const_cast / reinterpret_cast 중 뭘 적용했는지 코드만 봐서는 알 수 없기 때문**이다. 컴파일러는 상황에 맞춰 이 셋 중 하나(또는 조합)를 알아서 골라 적용하는데, 어떤 상황에서는 `reinterpret_cast`급으로 위험한 변환이 아무 경고도 없이 그냥 통과된다. `dynamic_cast`처럼 런타임 검사를 요구하는 옵션은 **애초에 후보에도 없다.** 그래서 C-style cast는 "다운캐스팅에서 실수해도 컴파일러가 절대 못 잡아주는" 가장 위험한 선택이다.

## 8. 언리얼의 Cast<T> — 내부적으로 뭘 쓰나

언리얼은 `UObject` 계열 타입에 표준 `dynamic_cast`를 그대로 쓰지 않는다. 대신 자체 캐스팅 함수를 제공한다.

```cpp
AWeaponPickup* Weapon = Cast<AWeaponPickup>(HitActor);
if (Weapon)
{
    Weapon->EquipTo(OwnerCharacter);
}

// 확실히 그 타입이라고 확신할 때 — 아니면 크래시(assert)로 바로 잡아냄
AWeaponPickup* Weapon2 = CastChecked<AWeaponPickup>(HitActor);
```

**`Cast<T>`가 하는 일은 `dynamic_cast`와 목적이 같다** — 실제 객체 타입을 확인하고 맞으면 포인터, 아니면 `nullptr`. 다른 건 **확인하는 방법**이다. C++ 표준 RTTI(`dynamic_cast`)는 컴파일러가 심어주는 범용 타입 정보를 쓰는데, 이건 모든 다형성 클래스에 대해 항상 켜져 있어야 하고 비용도 크다. 언리얼은 표준 RTTI를 아예 꺼버리고(`UCLASS()` 매크로 기반 리플렉션 시스템으로) **자체 타입 정보(`UClass`)와 `IsA()` 함수**로 같은 일을 훨씬 가볍게 처리한다. `Cast<T>` 내부는 대략 이런 식이다(개념적으로).

```cpp
// Cast<T>의 개념적 동작 (실제 구현은 언리얼 소스 참고)
template<typename T>
T* Cast(UObject* Obj)
{
    if (Obj && Obj->IsA(T::StaticClass()))   // UClass 기반 타입 확인
    {
        return static_cast<T*>(Obj);          // 확인 끝났으니 이제 안전하게 static_cast
    }
    return nullptr;
}
```

즉 `Cast<T>`는 **"UE 자체 RTTI로 먼저 검사하고, 통과하면 그때 static_cast로 실제 변환"**하는 조합이다. 순수 C++ 타입(`UObject`를 상속 안 하는 일반 클래스)에는 `Cast<T>`를 못 쓰고 표준 `dynamic_cast`를 그대로 써야 한다.

**실전에서는 이 `Cast<T>`가 히트 판정 파이프라인 전체에 체인처럼 걸리는 경우가 많다.** 총알이 맞은 대상이 여러 종류일 수 있을 때, 종류별로 반응이 다 다르다면 이렇게 짠다.

```cpp
void ABullet::OnHit(AActor* HitActor)
{
    if (AEnemyCharacter* Enemy = Cast<AEnemyCharacter>(HitActor))
    {
        Enemy->TakeDamage(Damage, FDamageEvent(), nullptr, this);
        return;
    }

    if (AWeaponPickup* Weapon = Cast<AWeaponPickup>(HitActor))
    {
        Weapon->DestroyByImpact();
        return;
    }

    if (AExplosiveBarrel* Barrel = Cast<AExplosiveBarrel>(HitActor))
    {
        Barrel->TriggerExplosion();
        return;
    }

    // 그 외(벽, 바닥 등)는 아무 반응 없이 총알만 파괴
    Destroy();
}
```

각 `Cast<T>`는 실패하면 그냥 `nullptr`을 리턴하고 다음 줄로 넘어갈 뿐, 크래시가 나지 않는다. 도입에서 본 C-style cast였다면 `AEnemyCharacter`가 아닌 대상을 그렇게 캐스팅하는 순간 바로 사고로 이어졌을 상황이, `Cast<T>` 체인에서는 "여러 후보 타입을 안전하게 순서대로 확인하는" 정상적인 분기 처리가 된다. 다만 **분기가 너무 많아지면(타입이 5개, 10개로 늘어나면) `Cast<T>` 체인 대신 인터페이스(`IDamageable` 같은)를 두고 가상 함수로 처리하는 게 더 깔끔하다** — 캐스팅은 "타입을 몰라서 확인해야 하는" 경계 지점에서만 쓰고, 반복되는 분기 자체는 다형성으로 푸는 게 정석이다.

## 9. dynamic_cast는 왜 static_cast보다 느린가 — 내부 동작까지

"dynamic_cast는 느리다"까지만 알고 넘어가면 표면적 정의 나열이다. 실제로 뭘 하길래 느린지 보자.

```
static_cast<AWeaponPickup*>(Item)
  → 컴파일 타임에 "AWeaponPickup이 AItemActor의 자식"이라는 사실만 확인하고 끝.
    런타임에 실행되는 코드는 사실상 포인터 값 그대로 재해석하는 것뿐. 비용 거의 0.

dynamic_cast<AWeaponPickup*>(Item)
  1. Item의 vtable 포인터를 따라가서, 이 객체가 "실제로" 어떤 클래스인지 나타내는 RTTI 정보를 찾는다.
  2. 그 실제 타입에서부터 상속 계층을 거슬러 올라가며(혹은 내려가며),
     "AWeaponPickup에 도달할 수 있는가"를 문자열/타입 비교로 확인한다.
  3. 다중 상속이 얽혀 있으면 이 탐색이 더 복잡해진다(여러 부모 경로를 다 확인해야 함).
```

**핵심은 static_cast가 "컴파일러 머릿속에서 끝나는 확인"인 반면, dynamic_cast는 "런타임에 상속 계층을 실제로 훑어보는 탐색"이라는 거다.** 이 탐색 비용이 vtable 하나 따라가는 정도가 아니라 **클래스 계층 구조를 순회하는 수준**이라, 가상 함수 호출(vtable에서 함수 포인터 하나 꺼내는 것)보다도 훨씬 무겁다. "그냥 좀 느리다"가 아니라 "**포인터 하나 따라가는 것과 계층 구조를 탐색하는 것의 차이**"라고 설명할 수 있어야 이 강의가 요구하는 깊이다.

언리얼이 표준 RTTI를 꺼두고 `Cast<T>`로 대체한 이유도 여기서 다시 연결된다. `UClass::IsA()`는 각 `UClass`가 자기 부모 `UClass`에 대한 포인터를 직접 들고 있어서(리플렉션 시스템이 이 계층을 미리 구축해둠), 표준 RTTI의 범용 탐색보다 훨씬 좁고 빠른 경로로 "부모인가 아닌가"만 확인한다.

## 10. 흔한 오해

### 오해 1: "C-style cast가 제일 간단하니까 그냥 쓰면 된다"

아니다. 짧아서 편해 보이지만, 어떤 변환이 실제로 일어나는지 코드에서 안 드러나고 컴파일러가 검사도 안 해준다. 다운캐스팅에는 특히 위험하다.

### 오해 2: "static_cast로 다운캐스팅하면 dynamic_cast보다 안전하다"

정반대다. `static_cast` 다운캐스팅은 **아무 검사도 안 한다.** "빠르다"는 장점은 있지만 "확실할 때만" 쓰라는 전제가 붙는다. 확신이 없으면 `dynamic_cast`/`Cast<T>`를 써야 한다.

### 오해 3: "dynamic_cast는 항상 느리니까 게임에서는 쓰면 안 된다"

매 프레임 수천 번 도는 핫패스라면 신경 써야 하지만, 히트 판정 처리처럼 이벤트성으로 가끔 일어나는 곳에서는 문제없다. 그리고 언리얼은 애초에 표준 RTTI를 꺼두고 `Cast<T>`로 대체했으니, "RTTI가 느려서 언리얼은 dynamic_cast 자체를 못 쓴다"가 정확한 표현이다.

### 오해 4: "언리얼은 RTTI를 꺼놨으니 타입 정보 자체가 아예 없다"

아니다. 표준 C++ RTTI(`typeid`, `dynamic_cast`)만 꺼놓은 거고, 그 자리를 `UCLASS()` 리플렉션 기반의 **자체 타입 시스템(`UClass`, `IsA()`)**이 대신한다. `Cast<T>`가 동작하는 근거가 바로 이 자체 타입 정보다.

### 오해 5: "const_cast로 const를 떼면 그 다음부턴 값을 바꿔도 항상 안전하다"

아니다. **원본 객체가 진짜로 `const`로 선언됐던 경우**엔 `const_cast`로 떼고 값을 바꾸면 미정의 동작이다. 안전한 경우는 원본이 애초에 non-const였는데 중간에 `const` 참조를 거쳐온 케이스뿐이다.

### 오해 6: "dynamic_cast가 느린 건 그냥 함수 호출 오버헤드 때문이다"

아니다. 진짜 이유는 **런타임에 상속 계층을 실제로 탐색**하기 때문이다. vtable에서 함수 포인터 하나 꺼내오는 일반 가상 함수 호출과 비교해도, dynamic_cast는 그 위에 "이 타입 계층에서 목표 타입에 도달 가능한가"를 확인하는 탐색 과정이 추가로 붙는다.

## 11. 면접에서 나오면

**Q1. C++ 캐스팅 종류에 대해 설명해주세요.**
→ "static_cast, dynamic_cast, reinterpret_cast, const_cast 네 가지가 있습니다. static_cast는 컴파일 타임에 관련이 확인된 타입 간 변환이고, dynamic_cast는 다형성 타입에서 실제 객체 타입을 런타임에 RTTI로 확인하며 변환합니다. reinterpret_cast는 타입과 무관하게 비트를 그대로 재해석하고, const_cast는 const/volatile 속성만 떼거나 붙입니다."

**Q2. static_cast와 dynamic_cast의 차이는 뭔가요?**
→ "가장 큰 차이는 런타임 검사 여부입니다. static_cast는 다운캐스팅을 해도 실제 객체 타입을 검사하지 않아서 잘못 캐스팅하면 미정의 동작이 나지만, dynamic_cast는 RTTI로 실제 타입을 확인하고 아니면 nullptr이나 예외를 던져서 안전합니다. 대신 dynamic_cast는 이 검사 비용 때문에 더 느립니다."

**Q3. 언리얼의 Cast<T>는 내부적으로 뭘 쓰나요?**
→ "언리얼은 표준 C++ RTTI를 꺼두고, UCLASS 리플렉션 기반의 자체 타입 시스템을 씁니다. Cast<T>는 UObject의 IsA() 함수로 UClass 정보를 확인해서 실제 타입이 맞는지 검사한 다음, 맞으면 static_cast로 변환해 리턴합니다. 목적은 dynamic_cast와 같지만 표준 RTTI보다 가볍게 동작합니다."

**Q4. C-style cast를 쓰면 안 좋은 이유는 뭔가요?**
→ "C-style cast는 상황에 따라 static_cast, const_cast, reinterpret_cast 중 하나를 컴파일러가 알아서 골라 적용하는데, 코드만 봐서는 어떤 변환이 일어나는지 알 수 없습니다. 특히 다운캐스팅에서 실수해도 컴파일러가 전혀 경고를 안 해줘서, 명시적인 캐스팅 연산자를 쓰는 게 훨씬 안전합니다."

**Q5. reinterpret_cast는 언제 쓰나요?**
→ "네트워크 패킷 버퍼를 구조체로 파싱하거나 포인터를 정수로 임시 저장했다가 복원하는 것처럼, 타입 계층과 무관하게 메모리를 비트 그대로 재해석해야 하는 저수준 상황에서만 씁니다. 일반적인 게임플레이 로직에서는 거의 쓸 일이 없습니다."

**Q6. 히트 판정에서 맞은 액터가 특정 서브클래스인지 확인하고 처리해야 한다면, static_cast와 dynamic_cast(혹은 Cast) 중 뭘 쓰시겠어요?**
→ "dynamic_cast나 언리얼이라면 Cast를 쓰겠습니다. 히트 판정은 맞은 액터가 어떤 타입인지 확신할 수 없는 상황이라, 실제 타입을 검사하지 않는 static_cast를 쓰면 잘못된 타입일 때 크래시로 이어질 수 있습니다. 이런 이벤트성 처리는 매 프레임 도는 핫패스가 아니라서 dynamic_cast의 성능 비용도 부담이 적습니다."

**Q7. const 함수 매개변수를 const_cast로 떼서 값을 바꾸는 게 항상 안전한가요?**
→ "아닙니다. 원본 객체가 애초에 non-const로 선언됐는데 const 참조를 거쳐서 넘어온 경우에만 안전합니다. 원본 자체가 const로 선언된 객체를 const_cast로 떼고 값을 바꾸면 미정의 동작이 됩니다."

면접관이 그 다음에 던지기 좋은 질문: *"dynamic_cast가 런타임에 타입을 어떻게 확인하는지, 그 내부 원리도 설명해볼 수 있나요?"* → 위 4번 섹션의 vtable/RTTI 설명이 답이다. 더 깊게 들어가면 다형성 자체(가상 함수 테이블)를 짚어주면 좋다.

**Q8. dynamic_cast가 static_cast보다 느린 이유를 좀 더 자세히 설명해줄 수 있나요?**
→ "static_cast는 컴파일 타임에 타입 관계가 이미 확인돼서 런타임 비용이 거의 없습니다. dynamic_cast는 런타임에 객체의 vtable을 따라가 실제 타입 정보를 확인하고, 그 타입에서 목표 타입까지 상속 계층을 탐색하는 과정을 거치기 때문에 단순 포인터 연산보다 훨씬 무겁습니다."

## 12. 셀프 체크

- [ ] 4가지 캐스팅이 각각 뭘 검사하고 뭘 안 하는지 표로 구분해서 말할 수 있다.
- [ ] static_cast로 다운캐스팅했을 때 왜 위험할 수 있는지 예시로 설명할 수 있다.
- [ ] dynamic_cast가 실제 타입을 확인하는 원리(vtable, RTTI)를 안다.
- [ ] C-style cast가 명시적 캐스팅보다 위험한 이유(어떤 변환이 적용됐는지 알 수 없음)를 안다.
- [ ] 언리얼 Cast<T>가 표준 dynamic_cast와 어떻게 다른 방식으로 같은 목적을 이루는지 설명할 수 있다.
- [ ] dynamic_cast가 느린 이유를 "런타임에 상속 계층을 탐색한다"는 수준까지 설명할 수 있다.
