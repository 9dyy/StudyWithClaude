# 10-1강 (보충) — 몬스터 A·B·C의 Attack을 if문 없이: 다형성과 가상 함수

> **목표:** "몬스터 종류마다 Attack이 다른데 if문으로 계속 종류를 찾고 있다"는 문제를 가상 함수(다형성)로 푸는 원리를 vtable 수준까지 설명하고, 상속·컴포지션·데이터 주도 중 무엇을 언제 고를지 판단할 수 있게 된다.
> **선수 지식:** 2강(캐스팅 — RTTI/가상 함수 언급), 10강(State Pattern — 같은 문제를 상태에 적용한 것).

---

## 1. 실제로 받은 질문

> "몬스터 A, B, C가 각각 Attack을 구현하면, 공격을 할 때 if문으로 어떤 몬스터인지 계속 찾아야 해. 이걸 해결하기 위해 넌 어떻게 구현 또는 설계할 거야?"

10강에서 "상태별 if-else"를 상태 클래스로 쪼갰다. 이건 그 문제의 **종류(Type) 버전**이다. 뿌리가 같다: **"무엇인지 확인하고 → 분기해서 → 그에 맞는 행동을 한다"** 를 **"객체에게 그 행동을 시킨다"**로 뒤집는 것.

---

## 2. 문제 코드 — 종류를 찾는 if문은 번식한다

```cpp
enum class EMonsterType { Slime, Archer, Golem };

struct FMonster { EMonsterType Type; /* ... */ };

void DoAttack(FMonster& M, AActor* Target)
{
    if (M.Type == EMonsterType::Slime)       { /* 몸통 박치기 */ }
    else if (M.Type == EMonsterType::Archer) { /* 화살 발사 */ }
    else if (M.Type == EMonsterType::Golem)  { /* 광역 내려찍기 */ }
}
```

여기서 끝나지 않는다. **공격뿐 아니라 이동, 피격, 사망 연출, 사운드까지 전부** 같은 if문이 생긴다.

```cpp
void DoMove(FMonster& M)        { if (M.Type == ...) ... }
void OnHit(FMonster& M)         { if (M.Type == ...) ... }
void OnDeath(FMonster& M)       { if (M.Type == ...) ... }
```

몬스터 종류 하나를 추가하면(예: `Dragon`) **이 분기가 있는 모든 함수를 찾아서 고쳐야** 하고, 하나라도 빠뜨리면 그 종류만 조용히 아무것도 안 한다(컴파일러도 안 잡는다). 10강 State에서 본 문제와 똑같다.

---

## 3. 해법 ① — 가상 함수(다형성): 종류마다 "자기 Attack"을 갖는다

```cpp
class AMonster
{
public:
    virtual ~AMonster() = default;                 // ★ 반드시 virtual (5절)
    virtual void Attack(AActor* Target) = 0;       // 순수 가상: 자식이 반드시 구현
};

class ASlime : public AMonster
{
public:
    void Attack(AActor* Target) override { /* 몸통 박치기 */ }
};
class AArcher : public AMonster
{
public:
    void Attack(AActor* Target) override { /* 화살 발사 */ }
};
class AGolem : public AMonster
{
public:
    void Attack(AActor* Target) override { /* 광역 내려찍기 */ }
};

// 호출하는 쪽 — 종류를 전혀 모른다
for (AMonster* M : Monsters)
{
    M->Attack(Player);      // 실제 타입에 맞는 Attack이 알아서 불린다
}
```

**호출하는 쪽에 `if`가 하나도 없다.** `Dragon`을 추가하려면 **새 클래스 하나**만 만들고 `Attack`을 구현하면 된다. 기존 코드는 손대지 않는다(개방-폐쇄 원칙: 확장에는 열려 있고 수정에는 닫혀 있다). `override`를 안 붙이거나 구현을 빠뜨리면 **컴파일 에러**가 나서 "조용히 아무것도 안 하는" 버그도 막힌다.

---

## 4. 어떻게 동작하나 — vptr과 vtable

가상 함수가 있는 클래스의 객체에는 **숨은 포인터(vptr)** 가 들어 있다. 이 포인터는 **그 클래스 전용 함수 표(vtable)** 를 가리킨다.

```
Slime 객체            Slime의 vtable          Archer의 vtable
┌──────────┐         ┌──────────────┐        ┌──────────────┐
│ vptr ────┼────────→│ Attack → Slime::Attack │  │ Attack → Archer::Attack │
│ HP ...   │         │ ~AMonster → ...        │  │ ~AMonster → ...         │
└──────────┘         └──────────────┘        └──────────────┘

M->Attack(Player)
  = ① M의 vptr을 읽는다  ② vtable에서 Attack 칸을 읽는다  ③ 그 주소로 간접 호출
```

- **if 분기**는 종류 수만큼 비교가 늘지만, **가상 호출은 종류가 몇 개든 "포인터 두 번 따라가고 간접 호출" 한 번**이다.
- 이걸 **동적 바인딩(런타임 다형성)**이라 한다. 컴파일 시점에 어떤 함수를 부를지 정하는 **정적 바인딩**(일반 함수, 템플릿)과 대비된다.
- 비용: 간접 호출이라 **인라인이 안 되고**, vtable/vptr 접근이 캐시에 없으면 미스가 난다. 대부분의 게임 로직에선 무시해도 되는 수준이지만, **수만 개를 매 프레임 도는 핫루프**라면 문제가 될 수 있다(7절).

---

## 5. 다형성을 쓸 때 반드시 알아야 할 함정

### 5-1. 기반 클래스 소멸자는 `virtual`이어야 한다

```cpp
class AMonster { public: ~AMonster() {} };            // ❌ virtual 아님
class AGolem : public AMonster { TArray<int32> Big; };

AMonster* M = new AGolem();
delete M;     // ~AMonster만 호출됨 → AGolem의 멤버(Big) 소멸자 안 불림 → 누수/미정의 동작
```

기반 포인터로 `delete`하는 순간 **`virtual` 소멸자가 아니면 자식 소멸자가 호출되지 않는다.** (표준상 미정의 동작이다.) 다형적으로 쓸 클래스는 소멸자를 `virtual`로 둔다. 언리얼의 `UObject`/`AActor` 계열은 소멸자가 이미 virtual이고 엔진이 수명을 관리하지만, **순수 C++ 클래스(`F` 접두사)에서 상속을 쓸 때**는 직접 챙겨야 한다.

### 5-2. 슬라이싱 — 값으로 저장하면 다형성이 사라진다

```cpp
TArray<AMonster> Monsters;          // ❌ 기반 타입을 "값"으로 저장 (순수 C++ 클래스라고 가정 — AActor는 애초에 값 복사가 불가능)
Monsters.Add(ASlime());             // 자식 부분이 잘려나감(slicing) — 가상 함수도 Base 버전이 됨
```

다형성은 **포인터/참조**를 통해서만 작동한다. 그래서 컨테이너에는 `TArray<AMonster*>`, `TArray<TUniquePtr<AMonster>>`처럼 포인터를 넣는다(11강 스마트 포인터).

### 5-3. 생성자/소멸자 안에서 가상 함수를 부르지 않는다

기반 클래스 생성자가 도는 동안 객체는 아직 "기반 타입"이라서, 그 안에서 `Attack()`을 부르면 자식 버전이 아니라 **기반 버전**이 불린다. 초기화에서 다형 동작이 필요하면 별도의 `Init()`을 만든다.

## 6. 해법 ② — 상속 대신 컴포지션(Strategy): "행동을 갈아 끼운다"

상속 트리는 몬스터 종류가 늘고 **행동이 조합**되기 시작하면 무너진다.

```
"근접 공격 + 독 + 원거리 회피" 몬스터? "원거리 공격 + 근접 공격" 몬스터?
→ Slime / Archer / Golem 계층에 끼워 맞추기 어렵다 (다중 상속의 늪)
```

이럴 땐 **행동을 별도 객체(Strategy)로 빼서 몬스터가 갖게** 한다.

```cpp
class IAttackBehavior
{
public:
    virtual ~IAttackBehavior() = default;
    virtual void Execute(AMonster* Owner, AActor* Target) = 0;
};
class FMeleeAttack  : public IAttackBehavior { /* ... */ };
class FRangedAttack : public IAttackBehavior { /* ... */ };

class AMonster
{
public:
    void Attack(AActor* Target) { AttackBehavior->Execute(this, Target); }   // 위임
    void SetAttack(TUniquePtr<IAttackBehavior> B) { AttackBehavior = MoveTemp(B); }  // 런타임 교체
private:
    TUniquePtr<IAttackBehavior> AttackBehavior;
};
```

이 구조는 **10강 State Pattern과 뼈대가 같다**(현재 행동 객체에게 위임). 차이는 State는 "상태가 바뀌며 스스로 전환"하고, Strategy는 "바깥에서 정책을 주입"한다는 점이다. 보스가 페이즈 2에서 공격 방식이 바뀌는 건 State에 가깝고, 몬스터 프리셋마다 공격 방식을 조립하는 건 Strategy에 가깝다.

---

## 7. 해법 ③ — 아예 클래스로 나누지 않는다(데이터 주도)

**종류마다 다른 게 "행동"이 아니라 "숫자"라면** 클래스를 나눌 이유가 없다. 사거리, 데미지, 쿨다운, 이펙트가 다를 뿐이면 **하나의 클래스 + 데이터 테이블**이 낫다.

```cpp
USTRUCT() struct FMonsterRow : public FTableRowBase { float Damage; float Range; float Cooldown; /* ... */ };
// UDataTable / UDataAsset에서 읽어 와서 AMonster 하나로 처리 — 새 몬스터 = 행 추가
```

**판단 기준은 "무엇이 다른가"다.**

| 다른 것 | 선택 |
|------|------|
| 수치(데미지, 사거리…) | **데이터 테이블** — 클래스 필요 없음 |
| 행동 자체(공격 방식) 몇 종류 | **가상 함수** — 가장 단순 |
| 행동이 조합되거나 런타임에 교체 | **컴포지션(Strategy) / 컴포넌트** |
| 상태에 따라 행동이 바뀜 | **State Pattern**(10강) |

**성능 관점(선택 사항):** 몬스터가 수만 개라면 가상 호출과 포인터 추적이 부담이 될 수 있어서, **종류별로 배열을 나눠 한 종류씩 일괄 처리**(`TArray<FSlime>`, `TArray<FArcher>`…)하는 데이터 지향 방식이 쓰이기도 한다. 하지만 이건 "if를 없애는" 것과 다른 문제이고, 일반적인 게임 로직에선 가상 함수로 충분하다.

## 8. 흔한 오해

### 오해 1: "if/switch로 종류를 나누는 게 빠르니까 가상 함수는 느리다"
가상 호출은 간접 호출 한 번이라 비용이 아주 작다. 종류가 늘면 if 체인의 비교 횟수가 오히려 더 커지고, 무엇보다 **수정 범위와 누락 버그**가 실제 비용이다. 병목이 프로파일러로 확인될 때만 데이터 지향을 고려한다.

### 오해 2: "다형성은 상속이 있어야만 가능하다"
템플릿(컴파일 타임 다형성), 함수 객체/델리게이트, 컴포지션도 같은 효과를 낸다. 가상 함수는 **런타임에 종류가 정해질 때** 쓰는 도구 중 하나다.

### 오해 3: "자식 클래스에서 `override`는 붙여도 그만 안 붙여도 그만이다"
`override`를 붙이면 **시그니처가 어긋났을 때 컴파일 에러**로 잡아준다. 안 붙이면 오타 하나로 **새 함수가 만들어져 기반 버전이 그대로 호출**되는 버그가 조용히 생긴다.

### 오해 4: "기반 클래스 소멸자는 상관없다"
기반 포인터로 delete하는 구조라면 `virtual ~`가 필수다. 아니면 자식 소멸자가 안 불려 누수/미정의 동작이다.

### 오해 5: "몬스터 종류가 다르면 무조건 클래스를 나눠야 한다"
다른 게 수치뿐이면 데이터 테이블이 정답이다. 클래스를 나누는 건 **행동이 다를 때**다.

## 9. 면접에서 나오면

**Q1. 몬스터 A, B, C가 각자 Attack을 구현해야 하는데, 공격할 때마다 if문으로 종류를 확인해야 합니다. 어떻게 설계하시겠어요?**
→ "기반 클래스에 Attack을 가상 함수로 선언하고, 몬스터마다 그걸 override하게 만들겠습니다. 호출하는 쪽은 기반 포인터로 Attack만 부르면 되고 실제 타입에 맞는 함수가 런타임에 선택돼서 if 분기가 사라집니다. 새 몬스터를 추가해도 클래스 하나만 만들면 돼서 기존 코드를 수정하지 않아도 됩니다."

**Q2. 가상 함수는 내부적으로 어떻게 동작하나요?**
→ "가상 함수가 있는 클래스의 객체는 vptr이라는 숨은 포인터를 갖고, 이게 그 클래스의 vtable을 가리킵니다. 호출할 때 vptr로 vtable을 찾아 해당 칸의 함수 주소로 간접 호출합니다. 그래서 컴파일 시점이 아니라 런타임에 실제 타입의 함수가 선택되는 동적 바인딩이 됩니다."

**Q3. 가상 함수의 비용은 뭔가요?**
→ "간접 호출이라 인라인이 안 되고 vptr/vtable 접근에서 캐시 미스가 날 수 있습니다. 대부분은 무시할 수준이지만 수만 개를 매 프레임 도는 핫루프라면 종류별로 배열을 나눠 일괄 처리하는 방식을 고려합니다."

**Q4. 기반 클래스 소멸자를 virtual로 두는 이유는요?**
→ "기반 포인터로 delete할 때 virtual이 아니면 기반 소멸자만 호출돼서 자식 클래스의 멤버가 정리되지 않고 미정의 동작이 됩니다. virtual이면 자식 소멸자부터 순서대로 호출됩니다."

**Q5. 몬스터를 `TArray<AMonster>`처럼 값으로 저장하면 어떻게 되나요?**
→ "슬라이싱이 일어나서 자식 부분이 잘려나가고 가상 함수도 기반 버전으로 동작합니다. 다형성은 포인터나 참조로만 작동하므로 포인터나 스마트 포인터를 담아야 합니다."

**Q6. 상속 말고 다른 방법은 없나요? 몬스터 행동이 조합되는 경우는요?**
→ "행동을 별도 객체로 분리하는 Strategy나 컴포넌트 방식으로 몬스터가 행동을 갖게 하고 위임합니다. 조합이 자유롭고 런타임에 교체도 가능합니다. 또 종류마다 다른 게 수치뿐이라면 클래스를 나누지 않고 데이터 테이블로 처리합니다."

면접관이 그 다음에 던지기 좋은 질문: *"이 Attack 로직이 상태에 따라 바뀌면요?"* → 10강 State Pattern으로 이어진다.

## 10. 셀프 체크

- [ ] 종류별 if/switch가 왜 번식하는지, 새 종류를 추가할 때 어떤 문제가 생기는지 설명할 수 있다.
- [ ] 가상 함수로 if를 없애는 구조를 코드로 쓸 수 있다.
- [ ] vptr/vtable로 동적 바인딩이 어떻게 일어나는지 그림으로 설명할 수 있다.
- [ ] virtual 소멸자, 슬라이싱, `override`의 이유를 각각 설명할 수 있다.
- [ ] 다른 게 수치인지, 행동인지, 조합인지, 상태 의존인지에 따라 데이터 테이블/가상 함수/Strategy/State를 고를 수 있다.
