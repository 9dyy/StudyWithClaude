## Part A. C++ 문법 심화 (1~3강)

**Q1. static 함수에 대해 설명해보세요.** *(1강)*
→ "클래스에 속하지만 특정 인스턴스에 종속되지 않는 멤버 함수입니다. 컴파일러가 암묵적으로 넘겨주는 this 포인터가 없어서 인스턴스 없이 클래스 이름만으로 호출할 수 있고, 대신 non-static 멤버에는 직접 접근할 수 없습니다."

**Q2. static 변수는 스택, 힙 중 어디에 저장되나요?** *(1강)*
→ "둘 다 아니고 데이터 영역(Data/BSS 세그먼트)에 저장됩니다. 힙은 new로 런타임에 동적 할당하는 영역이고, static은 컴파일 시점에 이미 주소가 정해져서 프로그램 로드 시 자동으로 준비된다는 게 근본적인 차이입니다."

**Q3. C++ 캐스팅 종류에 대해 설명해주세요.** *(2강)*
→ "static_cast, dynamic_cast, reinterpret_cast, const_cast 네 가지입니다. static_cast는 런타임 검사 없이 관련 타입 간 변환, dynamic_cast는 RTTI로 실제 타입을 확인하며 변환, reinterpret_cast는 비트를 그대로 재해석, const_cast는 const/volatile 속성만 조정합니다."

**Q4. 언리얼의 Cast<T>는 dynamic_cast와 뭐가 다른가요?** *(2강)*
→ "목적은 같지만 방법이 다릅니다. dynamic_cast는 표준 C++ RTTI를 쓰는데, 언리얼은 이걸 꺼두고 UCLASS 리플렉션 기반의 자체 타입 시스템(IsA, UClass)으로 실제 타입을 확인한 뒤 static_cast로 변환합니다. 더 가볍게 동작하도록 만든 대체 구현입니다."

**Q5. RAII가 뭐고, 왜 스마트 포인터로 이어지나요?** *(3강)*
→ "자원 획득을 생성자에, 해제를 소멸자에 묶어서 스코프를 벗어나면 자동으로 정리되게 하는 패턴입니다. new로 획득한 메모리도 결국 관리해야 할 자원이라 같은 원리를 적용하면 스마트 포인터가 되고, unique_ptr은 소유자 하나, shared_ptr은 참조 카운트로 여러 소유자를 지원하도록 확장한 것입니다."

## Part B. 자료구조 기본기 (4~6강)

**Q6. 배열과 LinkedList의 차이, 둘 중 누가 삽입/삭제가 더 빠른지?** *(4강)*
→ "이론적 시간복잡도는 중간 삽입/삭제가 LinkedList O(1), 배열 O(n)이라 LinkedList가 유리해 보입니다. 하지만 그 위치를 찾아가는 탐색 비용이 LinkedList도 O(n)이고, 캐시 지역성 덕분에 배열의 연속 메모리 접근이 실측에서는 더 빠른 경우가 많습니다."

**Q7. 캐시 지역성이 뭔가요?** *(4강)*
→ "CPU가 메모리를 캐시 라인 단위로 통째로 가져오는 특성을 이용하는 개념입니다. 배열처럼 데이터가 연속으로 있으면 하나를 읽을 때 주변 데이터까지 캐시에 올라와서 다음 접근이 훨씬 빨라집니다."

**Q8. Stack과 Queue의 차이는 뭔가요?** *(5강)*
→ "Stack은 LIFO로 가장 나중에 넣은 걸 먼저 꺼내고, Queue는 FIFO로 가장 먼저 넣은 걸 먼저 꺼냅니다. Undo 기능처럼 최근 작업을 먼저 되돌려야 할 땐 Stack, 커맨드 처리처럼 순서를 지켜야 할 땐 Queue를 씁니다."

**Q9. BFS는 왜 Queue를 쓰고 DFS는 왜 Stack을 쓰나요?** *(5강)*
→ "BFS는 가까운 노드부터 순서대로 탐색해야 하는데 Queue가 먼저 넣은 이웃을 먼저 꺼내서 이 순서를 보장합니다. Stack을 쓰면 가장 최근에 넣은 이웃을 먼저 파고들게 되어 DFS가 됩니다."

**Q10. TMap이 어떻게 O(1)에 가까운 조회를 하나요?** *(6강)*
→ "키를 해시 함수에 넣어 버킷 위치를 계산해서 바로 그 버킷만 확인합니다. 평균적으로 O(1)이지만, 서로 다른 키가 같은 버킷으로 몰리는 해시 충돌이 심하면 최악의 경우 O(n)까지 나빠질 수 있습니다."

## Part C. 디자인 패턴 (7~10강)

**Q11. Object Pooling에 대해 설명해주세요.** *(7강)*
→ "자주 생성되고 짧게 사는 오브젝트를 매번 new/delete 하지 않고, 미리 만들어둔 풀에서 꺼내 쓰고 반납하는 패턴입니다. 총알이나 이펙트처럼 반복 생성되는 대상에 써서 할당 비용과 메모리 단편화를 줄입니다."

**Q12. new/delete를 반복하면 왜 성능 문제가 생기나요?** *(7강)*
→ "힙 할당자가 빈 공간을 찾는 탐색 비용이 들고, 반복하면 사용 중인 블록과 빈 블록이 조각나는 메모리 단편화가 생깁니다. 새로 할당된 메모리는 위치가 제각각이라 캐시 지역성도 나빠집니다."

**Q13. Observer Pattern에 대해 설명해주세요.** *(8강)*
→ "어떤 객체의 상태 변화를 그 변화에 관심 있는 여러 객체에게 알려서 각자 반응하게 하는 패턴입니다. 발행자는 구독자가 누구인지 몰라도 되기 때문에 두 쪽이 느슨하게 결합됩니다."

**Q14. HP가 바뀔 때 UI가 자동으로 갱신되는 구조는 어떻게 만드나요?** *(8강)*
→ "캐릭터에 HP 변화 멀티캐스트 델리게이트를 두고 데미지/힐 로직에서 Broadcast만 합니다. HP바나 미니맵 같은 UI는 이 이벤트를 구독해서 각자 갱신하기 때문에 캐릭터 코드가 특정 UI 클래스를 몰라도 됩니다."

**Q15. Singleton 패턴을 C++로 어떻게 구현하나요?** *(9강)*
→ "생성자를 private으로 막고 복사 생성자/대입 연산자를 삭제해서 외부에서 인스턴스를 못 만들게 합니다. 정적 함수 안에 지역 static 객체를 두고 참조를 리턴하는 Meyer's Singleton 방식이 흔하고, C++11부터 이 초기화 자체는 스레드 안전합니다."

**Q16. 언리얼에서는 왜 전통적인 Singleton 대신 GameInstance/Subsystem을 쓰나요?** *(9강)*
→ "전통적인 Singleton은 프로그램 전체 생명주기에 묶이는데, 게임은 레벨/세션 단위로 생명주기가 다릅니다. Subsystem은 GameInstance나 World의 생명주기에 맞춰 자동으로 초기화/정리되고, UObject라서 GC와 블루프린트 노출도 자연스럽게 지원됩니다."

**Q17. State Pattern이 if-else 상태 관리보다 나은 점은 뭔가요?** *(10강)*
→ "상태가 늘어날수록 if-else는 모든 상태 블록에 전환 조건이 중복돼서 쌓이는데, State Pattern은 각 상태를 클래스로 분리해서 상태 스스로 전환 조건을 갖게 합니다. 새 상태를 추가해도 무관한 기존 상태 클래스는 건드릴 필요가 없습니다."

## Part D. 판단형 · 종합형 (여러 강의를 엮어서)

**Q18. 인벤토리처럼 자주 순회하면서 가끔 중간에 아이템을 삽입/삭제하는 자료구조를 고른다면 뭘 쓰시겠어요?** *(4강)*
→ "TArray를 쓰겠습니다. 순회가 잦으면 캐시 지역성 이득이 크고, 중간 삽입/삭제 비용도 실측하면 캐시 미스가 반복되는 LinkedList보다 낮은 경우가 많습니다. LinkedList는 이미 위치를 알고 있는 상태에서 반복 삽입/삭제할 때만 유리합니다."

**Q19. 매 프레임 100명이 넘는 플레이어를 ID로 조회해야 한다면 TArray와 TMap 중 뭘 쓰시겠어요?** *(6강)*
→ "TMap을 쓰겠습니다. TArray로 매번 순회하면 O(n)이라 인원이 늘수록 비용이 커지지만, TMap은 평균 O(1)이라 인원수와 거의 무관하게 일정한 성능을 냅니다."

**Q20. Object Pooling, Observer, Singleton/Factory, State 패턴 중 두 개 이상을 같이 써야 하는 시스템을 하나 설계해볼 수 있나요?** *(7~10강 종합)*
→ "적 스폰 시스템을 예로 들면, Object Pool에서 적 액터를 꺼내고(7강), Factory가 적 타입별 초기화를 담당하고(9강), 이 전체를 관리하는 창구를 WorldSubsystem 하나로 두고(9강), 적이 스폰/사망할 때 이벤트를 Broadcast해서 UI나 퀘스트 시스템이 구독하게(8강) 만들 수 있습니다. 적의 대기/추격/공격 상태는 State Pattern으로 분리합니다(10강)."

## 면접 직전 30초 암기 카드

| 키워드 | 한 줄 요약 |
|------|------|
| static 4형태 | 지역 static(1회 초기화) / 파일스코프(내부링키지) / 멤버변수(공유) / 멤버함수(this 없음) — 전부 데이터·코드 영역, 힙 아님 |
| 캐스팅 4형제 | static(검사X) / dynamic(RTTI 검사) / reinterpret(비트 재해석) / const(속성만) |
| RAII | 생성자=획득, 소멸자=해제 → 스마트 포인터의 원리 |
| 배열 vs LinkedList | 이론은 LinkedList 삽입 유리, 실측은 캐시 지역성 때문에 배열이 이기는 경우 많음 |
| Stack/Queue | LIFO=최근 것 먼저(Undo), FIFO=순서 보장(커맨드 큐), BFS=Queue·DFS=Stack |
| TMap | 해시로 버킷 계산 → 평균 O(1), 최악 O(n)(충돌), 순서 보장 안 함 |
| Object Pooling | 미리 만들고 재사용 → 할당 비용/단편화 제거 (메모리 절약 아님!) |
| Observer | 발행-구독으로 느슨한 결합, 발행자는 구독자를 모름 |
| Singleton | 생성자 private + 복사 금지, 언리얼은 GameInstance/Subsystem으로 대체 |
| State Pattern | 상태별 클래스 분리, 전환 조건은 상태 자신이 앎 |
