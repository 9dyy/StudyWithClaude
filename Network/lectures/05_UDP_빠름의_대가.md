# 5강 — UDP, 빠름의 대가

> **목표:** UDP가 신뢰성을 버리고 무엇을 얻는지, 그리고 FPS 같은 실시간 게임이 왜 UDP를 쓰는지 이해한다.
> **선수 지식:** 4강(TCP). 특히 TCP의 신뢰성·순서 보장과 그 대가(HOL 블로킹)를 알고 있어야 비교가 된다.

---

## 1. TCP로 FPS를 만들면 생기는 일

4강에서 본 문제를 다시 보자. FPS 게임에서 내 캐릭터 위치를 TCP로 1초에 60번 보낸다. 그런데 중간에 위치 패킷 하나가 유실된다.

```
위치1(0ms) → 위치2(16ms) 유실! → 위치3(32ms) 도착 but 대기 → 위치4(48ms) 도착 but 대기
                  │
                  └ TCP: "위치2 재전송될 때까지 위치3,4 못 줘" (순서 보장 때문)

내 화면: 캐릭터가 16ms 지점에서 멈춤 → 위치2 재전송 도착 → 갑자기 48ms로 순간이동
```

근데 잘 생각해보자. **위치2는 이미 쓸모없다.** 32ms, 48ms 위치가 이미 도착해 있는데, 굳이 16ms 전 위치를 기다릴 이유가 없다. 최신 위치만 보여주면 끝이다.

TCP는 "다 도착해야 하고 순서대로여야 한다"는 신념 때문에 이걸 못 한다. 그래서 실시간 게임은 다른 도구가 필요하다. 그게 **UDP**다.

---

## 2. UDP의 철학 — "일단 던지고 신경 안 쓴다"

UDP(User Datagram Protocol)는 TCP와 정반대다. **그냥 보낸다. 도착 여부는 신경 안 쓴다.**

| | TCP | UDP |
|---|-----|-----|
| 연결 | 맺음 (handshake) | 안 맺음 |
| 신뢰성 | 보장 (재전송) | 보장 안 함 (유실돼도 끝) |
| 순서 | 보장 | 보장 안 함 |
| 속도 | 느림 | 빠름 |
| 헤더 크기 | 20바이트+ | 8바이트 |

UDP는 데이터를 **데이터그램(datagram)** 이라는 독립적인 덩어리로 던진다. 각 덩어리는 서로 모른다. 받든 말든, 순서가 맞든 틀리든 UDP는 관여 안 한다.

> **핵심 비유:**
> - TCP는 **등기우편**이다. 받았다는 사인을 받고, 안 오면 다시 보낸다. 느리지만 확실하다.
> - UDP는 **전단지 뿌리기**다. 그냥 뿌린다. 몇 장이 바람에 날아가도 신경 안 쓴다. 빠르다.

### UDP 헤더는 단순하다

TCP 헤더(20바이트+)는 시퀀스 번호, ACK 번호, 윈도우 크기 등 신뢰성을 위한 정보로 빵빵하다. UDP 헤더는 단 **8바이트** — 출발지 포트, 목적지 포트, 길이, 체크섬. 끝.

```
UDP 헤더 (8바이트)
┌────────────┬────────────┬────────┬────────┐
│ 출발지포트 │ 목적지포트 │  길이  │ 체크섬 │
└────────────┴────────────┴────────┴────────┘
신뢰성 관련 필드가 아예 없다 = 가볍고 빠르다
```

---

## 3. UDP가 게임에 맞는 이유

FPS 위치 동기화로 돌아가자. UDP로 보내면:

```
위치1 → 위치2 유실 → 위치3 도착(바로 표시) → 위치4 도착(바로 표시)
              │
              └ 그냥 버림. 어차피 위치3이 더 최신이라 상관없음

내 화면: 위치2만 살짝 건너뛰고 위치3,4로 부드럽게 진행 (멈춤 없음)
```

핵심 깨달음: **실시간 게임 데이터는 "최신성"이 "완전성"보다 중요하다.** 0.1초 전 위치를 정확히 받느니, 지금 위치를 대충 받는 게 낫다. 유실된 패킷을 재전송 받아봤자 이미 늙은 데이터다.

이게 FPS, 레이싱, 액션 게임이 위치/입력 동기화에 UDP를 쓰는 이유다. **유실을 감수하는 대신 지연을 없앤다.**

---

## 4. "근데 그럼 막 유실돼도 되나?" — 아니다

UDP를 쓴다고 모든 걸 운에 맡기는 건 아니다. 게임은 보통 **UDP 위에 자기만의 신뢰성 로직을 직접 얹는다.** 이게 핵심이다.

예를 들어:

- **위치 데이터:** 유실돼도 됨 → 그냥 UDP. 어차피 다음 패킷이 곧 옴.
- **"플레이어가 죽었다" 이벤트:** 유실되면 안 됨 → UDP로 보내되, **중요한 것만 골라서** 직접 ACK/재전송 로직을 얹음.

즉 TCP처럼 "전부 신뢰성"이 아니라, **"필요한 것만 골라서 신뢰성"** 을 직접 구현한다. 이걸 **신뢰성 UDP(Reliable UDP)** 라고 부르고, 언리얼·대부분의 게임 엔진이 이 방식을 쓴다. (6강에서 더 다룬다.)

> 면접 포인트: "게임은 UDP를 쓰되, 중요한 데이터엔 애플리케이션 레벨에서 신뢰성을 직접 구현한다"고 말하면 깊이 있어 보인다. "UDP라서 그냥 다 유실돼도 됨"은 얕은 답이다.

---

## 5. 코드로 체감해보기

언리얼에서 UDP 소켓의 모양(개념용).

```cpp
// NAME_DGram = UDP. (TCP는 NAME_Stream)
FSocket* UdpSocket = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)
    ->CreateSocket(NAME_DGram, TEXT("UdpSocket"), true);

// 주목: Connect()가 없다! UDP는 연결을 안 맺으니까 handshake도 없다.
// 그냥 "이 주소로 보내" 하면 끝.
int32 BytesSent = 0;
FVector MyLocation = GetActorLocation();
UdpSocket->SendTo(
    (uint8*)&MyLocation, sizeof(FVector), BytesSent, *ServerAddr);
//  ↑ 도착 보장 없음. 보내고 끝. ACK도 재전송도 없음.

// 받기 — 온 게 있으면 받고, 없으면 그냥 없는 것
uint8 Buffer[1024];
int32 BytesRead = 0;
TSharedRef<FInternetAddr> Sender =
    ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)->CreateInternetAddr();
if (UdpSocket->RecvFrom(Buffer, sizeof(Buffer), BytesRead, *Sender))
{
    // 받은 데이터 처리. 순서/유실은 내가 알아서 처리해야 함
}
```

TCP 코드(4강)와 비교해보면 차이가 확 보인다:

- TCP는 `Connect()`로 연결을 먼저 맺음 → UDP는 없음
- TCP는 `Send()` → UDP는 `SendTo()`로 매번 목적지를 지정 (연결이 없으니 매번 주소가 필요)
- TCP는 "도착하겠지" 믿어도 됨 → UDP는 도착 여부를 내가 챙겨야 함

## 6. 흔한 오해

### 오해 1: "UDP는 신뢰성이 없으니 게임에 위험하다"

위치·입력 같은 실시간 데이터는 유실돼도 다음 패킷이 곧 와서 메운다. 오히려 TCP의 HOL 블로킹이 더 위험하다. 그리고 중요한 데이터는 UDP 위에 신뢰성을 직접 얹어서 처리한다. "UDP = 위험"은 단순한 생각이다.

### 오해 2: "UDP는 순서가 보장된다"

전혀 아니다. 먼저 보낸 데이터그램이 나중에 도착할 수 있다. 순서가 필요하면 패킷에 직접 번호를 붙여서 받는 쪽이 정렬해야 한다. UDP는 순서를 책임지지 않는다.

### 오해 3: "UDP가 TCP보다 항상 빠르다"

UDP 자체는 오버헤드가 적어 가볍지만, 게임이 그 위에 신뢰성 로직을 얹으면 그만큼 비용이 추가된다. "잘 만든 신뢰성 UDP"는 빠르지만, 신뢰성을 어설프게 얹으면 TCP보다 나을 게 없을 수도 있다. "UDP = 무조건 빠름"은 절반만 맞다.

### 오해 4: "UDP는 연결을 안 맺으니 상대가 누군지 모른다"

데이터그램마다 출발지 IP·포트가 들어 있어서, 받는 쪽은 누가 보냈는지 안다. 다만 TCP처럼 "연결 상태"를 유지하지 않을 뿐이다. 서버는 보통 IP·포트로 어느 플레이어인지 매핑해서 관리한다.

## 7. 면접에서 나오면

**Q1. UDP가 뭔가요?**
→ "비연결형 전송 계층 프로토콜입니다. 연결을 맺지 않고 데이터그램을 그냥 보내며, 도착 여부나 순서를 보장하지 않습니다. 대신 헤더가 8바이트로 가볍고 재전송 대기가 없어서 빠릅니다. 실시간성이 중요한 게임이나 스트리밍에 씁니다."

**Q2. UDP는 신뢰성이 없는데 왜 게임에서 쓰나요?**
→ "실시간 게임에선 데이터의 완전성보다 최신성이 더 중요하기 때문입니다. 캐릭터 위치 패킷이 하나 유실돼도 곧 다음 위치가 오기 때문에, 옛날 위치를 재전송받느라 화면이 멈추는 것보다 그냥 버리고 최신 위치를 쓰는 게 낫습니다. TCP의 Head-of-Line Blocking을 피하려는 거죠."

**Q3. UDP로 보낸 데이터가 꼭 도착해야 한다면 어떻게 하나요?**
→ "애플리케이션 레벨에서 신뢰성을 직접 구현합니다. 중요한 패킷에만 시퀀스 번호와 ACK를 붙이고, 응답이 없으면 재전송하는 로직을 게임 코드에서 얹습니다. 이걸 신뢰성 UDP라고 하고, 언리얼을 포함한 대부분의 게임 엔진이 이 방식을 씁니다."

**Q4. TCP 헤더와 UDP 헤더의 차이는?**
→ "TCP 헤더는 시퀀스 번호, ACK 번호, 윈도우 크기 등 신뢰성을 위한 정보가 많아 최소 20바이트입니다. UDP 헤더는 출발지·목적지 포트, 길이, 체크섬 네 개만 있어서 8바이트입니다. UDP가 그만큼 가볍고 빠릅니다."

**Q5. UDP는 순서를 보장하나요?**
→ "보장하지 않습니다. 먼저 보낸 데이터그램이 더 늦게 도착할 수 있어서, 순서가 필요하면 패킷에 직접 번호를 붙여 받는 쪽에서 정렬해야 합니다. 다만 실시간 위치 같은 데이터는 애초에 최신 것만 쓰면 되니 순서가 큰 의미가 없는 경우도 많습니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 게임에서 TCP랑 UDP를 어떤 기준으로 골라 쓰나요?"* → 6강(TCP vs UDP, 게임은 뭘 쓰나)에서 정리한다.

## 8. 셀프 체크

- [ ] 실시간 게임에서 "최신성 > 완전성"인 이유를 위치 동기화 예로 설명할 수 있다.
- [ ] UDP 헤더가 왜 8바이트로 가벼운지 안다.
- [ ] 신뢰성 UDP(Reliable UDP)가 뭔지, 왜 필요한지 설명할 수 있다.
- [ ] UDP는 순서도 도착도 보장 안 한다는 걸 명확히 안다.
