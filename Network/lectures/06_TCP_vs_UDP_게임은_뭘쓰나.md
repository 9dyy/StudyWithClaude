# 6강 — TCP vs UDP, 게임은 뭘 쓰나

> **목표:** 어떤 데이터에 TCP, 어떤 데이터에 UDP를 쓰는지 실제 게임 기준으로 정리하고, 둘을 섞어 쓰는 법과 신뢰성 UDP를 이해한다.
> **선수 지식:** 4강(TCP), 5강(UDP). 두 프로토콜의 장단점을 알고 있어야 비교가 의미 있다.

---

## 1. "그래서 우리 게임은 뭘 써요?"

신입이 멀티플레이 기능을 맡으면 가장 먼저 부딪히는 질문이다. 채팅은? 위치 동기화는? 로그인은? 아이템 거래는?

답을 "TCP요" 또는 "UDP요" 하나로 못 한다. **데이터마다 다르다.** 좋은 멀티플레이 게임은 거의 항상 **둘 다** 쓴다. 이 강의는 그 선택 기준을 정리한다.

면접에서도 "TCP랑 UDP 중 뭐가 좋아요?"라고 물으면, "데이터 성격에 따라 다릅니다"로 시작하는 게 정답이다. 하나만 찍으면 얕은 답이다.

---

## 2. 선택의 한 가지 질문

복잡하게 생각할 거 없다. 데이터 하나를 두고 이 질문만 던지면 된다.

> **"이 데이터, 늦더라도 반드시 도착해야 하나? 아니면 유실되더라도 빨라야 하나?"**

```
반드시 도착해야 함 (정확성)  →  TCP
유실돼도 됨, 대신 빨라야 함 (실시간)  →  UDP
```

조금 더 풀면:

| 질문 | TCP | UDP |
|------|-----|-----|
| 하나라도 빠지면 게임이 깨지나? | 예 → TCP | 아니오 → UDP |
| 0.1초 늦은 데이터가 의미 있나? | 예(과거도 중요) → TCP | 아니오(최신만 중요) → UDP |
| 자주 갱신되나? | 가끔 → TCP | 초당 수십 번 → UDP |

---

## 3. 게임 데이터별 분류 (실전 기준)

### TCP가 맞는 것 — "한 번 빠지면 큰일"

| 데이터 | 이유 |
|--------|------|
| 로그인 / 인증 | 빠지면 접속 자체가 안 됨. 정확성 100% 필요 |
| 아이템 거래 / 결제 | "골드 1000 보냄" 유실 = 경제 붕괴 |
| 채팅 | "GG"가 깨져서 도착하면 안 됨. 약간 늦어도 됨 |
| 인벤토리 / 퀘스트 상태 | 자주 안 바뀌고, 정확해야 함 |
| 매치메이킹 / 방 입장 | 한 번의 명령, 반드시 처리돼야 함 |

공통점: **자주 안 바뀌고, 한 번이라도 빠지면 치명적이고, 약간 늦어도 괜찮다.**

### UDP가 맞는 것 — "최신만 중요, 옛날 건 버려도 됨"

| 데이터 | 이유 |
|--------|------|
| 캐릭터 위치 / 회전 | 초당 수십 번 갱신. 하나 빠져도 다음 게 곧 옴 |
| 플레이어 입력 (이동키, 마우스) | 실시간. 늦으면 무의미 |
| 총알 궤적 / 이펙트 위치 | 잠깐 튀어도 괜찮음 |
| 음성 채팅 (VoIP) | 끊겨도 다음 소리가 곧 옴 |

공통점: **초당 수십 번 갱신되고, 최신 값만 의미 있고, 지연이 치명적이다.**

---

## 4. 둘을 섞어 쓴다 — 하이브리드

실제 게임은 한 클라이언트가 **TCP 연결과 UDP 연결을 동시에** 유지하는 경우가 많다.

```
                    게임 클라이언트
                   ┌──────┴──────┐
              TCP 채널         UDP 채널
                   │              │
          로그인/거래/채팅    위치/입력/이펙트
                   │              │
                   └──────┬───────┘
                       게임 서버
```

예시 — MMORPG:

- 접속·로그인: **TCP** (정확해야 함)
- 캐릭터 이동 동기화: **UDP** (실시간)
- 길드 채팅: **TCP** (빠지면 안 됨)
- 스킬 이펙트 위치: **UDP** (잠깐 튀어도 됨)
- 아이템 거래: **TCP** (절대 유실 금지)

이게 정상이다. "게임은 UDP만 쓴다"도 "TCP만 쓴다"도 틀렸다.

---

## 5. 신뢰성 UDP — UDP인데 골라서 신뢰성

5강에서 잠깐 나온 개념을 제대로 보자. 문제 상황:

- "플레이어가 죽었다", "보스 페이즈 전환" 같은 이벤트는 **UDP 채널로 흐르는데 반드시 도착해야 한다.**
- 그렇다고 위해서 TCP를 따로 또 연결하긴 부담스럽다.

해법: **UDP 위에 "필요한 패킷만" 신뢰성을 직접 얹는다.** TCP의 핵심 아이디어(시퀀스 번호 + ACK + 재전송)를 애플리케이션에서 골라 구현하는 것.

```
일반 위치 패킷:   그냥 보냄 (유실 OK)
중요 이벤트 패킷: 시퀀스 번호 + ACK 요구 + 응답 없으면 재전송
```

이걸 **신뢰성 UDP(Reliable UDP)** 라고 한다. TCP와 차이는:

- TCP: **전부** 신뢰성 (HOL 블로킹 발생) → 늙은 위치가 최신 위치를 막음
- 신뢰성 UDP: **골라서** 신뢰성 → 위치는 막힘 없이 흐르고, 중요 이벤트만 재전송

언리얼 네트워킹도 이 철학으로 돌아간다. RPC를 보낼 때 `Reliable`/`Unreliable`을 직접 고른다(14강).

```cpp
// 언리얼 RPC — 신뢰성을 데이터마다 직접 선택
UFUNCTION(Server, Reliable)      // 반드시 도착 (거래, 사망 처리 등)
void Server_RequestTrade(int32 ItemId);

UFUNCTION(Server, Unreliable)    // 유실 OK (이동 입력 등 자주 갱신되는 것)
void Server_SendMoveInput(FVector Input);
```

> **이게 면접의 깊이 포인트다.** "게임은 UDP 기반에서 데이터 성격에 따라 신뢰성을 직접 선택한다. 언리얼은 RPC에 Reliable/Unreliable 플래그로 이걸 제공한다"고 말하면 실무를 아는 답이 된다.

## 6. 흔한 오해

### 오해 1: "좋은 게임은 UDP만 쓴다"

FPS도 로그인·결제·채팅은 TCP나 신뢰성 채널로 처리한다. 순수 UDP만으로 게임 전체를 돌리지 않는다. 데이터 성격에 따라 섞는 게 정상이다.

### 오해 2: "TCP는 게임에 절대 못 쓴다"

실시간 위치엔 부적합하지만, 턴제 게임·보드게임·카드게임처럼 **실시간성이 약한 장르는 TCP만으로 충분**하다. 오히려 신뢰성을 공짜로 얻으니 개발이 편하다. "TCP = 게임에 부적합"은 장르를 무시한 일반화다.

### 오해 3: "신뢰성 UDP면 그냥 TCP 쓰는 거랑 똑같다"

다르다. 신뢰성 UDP는 **선택적**이다. 위치 패킷은 막힘 없이 흐르고, 중요 패킷만 재전송한다. TCP는 전부 순서 보장이라 HOL 블로킹이 모든 데이터에 걸린다. "골라서 신뢰성" vs "전부 신뢰성"이 핵심 차이다.

### 오해 4: "TCP랑 UDP를 동시에 쓰면 포트가 충돌한다"

TCP 포트와 UDP 포트는 별개 공간이다. 같은 번호 7777을 TCP와 UDP가 동시에 써도 충돌하지 않는다. OS가 프로토콜별로 따로 관리하기 때문이다.

## 7. 면접에서 나오면

**Q1. TCP와 UDP 중 게임에선 뭘 쓰나요?**
→ "데이터 성격에 따라 둘 다 씁니다. 로그인·거래·채팅처럼 반드시 도착해야 하는 건 TCP, 캐릭터 위치나 입력처럼 실시간성이 중요하고 유실돼도 다음 패킷이 메우는 데이터는 UDP를 씁니다. 보통 한 게임이 두 프로토콜을 동시에 운용합니다."

**Q2. 어떤 기준으로 TCP와 UDP를 선택하나요?**
→ "핵심 질문은 '이 데이터가 늦더라도 반드시 도착해야 하는가, 아니면 유실되더라도 빨라야 하는가'입니다. 정확성이 중요하면 TCP, 실시간성이 중요하고 최신 값만 의미 있으면 UDP입니다. 갱신 빈도도 기준인데, 초당 수십 번 갱신되는 데이터는 UDP가 적합합니다."

**Q3. 신뢰성 UDP가 뭔가요?**
→ "UDP 위에 애플리케이션 레벨에서 신뢰성을 선택적으로 구현하는 방식입니다. 시퀀스 번호와 ACK, 재전송을 중요한 패킷에만 적용해서, 위치 같은 데이터는 막힘 없이 흐르게 두고 사망 처리 같은 중요한 이벤트만 보장합니다. TCP처럼 모든 데이터에 순서를 강제하지 않아 Head-of-Line Blocking을 피할 수 있습니다."

**Q4. 언리얼에서는 신뢰성을 어떻게 선택하나요?**
→ "RPC를 선언할 때 Reliable과 Unreliable 플래그로 데이터마다 고릅니다. 거래나 사망 처리처럼 반드시 도착해야 하는 건 Reliable, 이동 입력처럼 자주 갱신되는 건 Unreliable로 선언합니다. 엔진이 UDP 기반 위에서 이 구분을 처리해줍니다."

**Q5. 턴제 게임도 UDP를 써야 하나요?**
→ "아닙니다. 턴제나 카드게임처럼 실시간성이 약한 장르는 TCP만으로 충분합니다. 한 턴의 행동이 정확히 전달되는 게 중요하고 지연은 큰 문제가 아니라서, TCP의 신뢰성을 공짜로 얻는 게 오히려 개발에 유리합니다. 프로토콜 선택은 장르의 실시간성에 달려 있습니다."

면접관이 그 다음에 던지기 좋은 질문: *"TCP가 느린 또 다른 이유로 Nagle 알고리즘이라고 들어봤나요?"* → 7강(흐름·혼잡 제어와 Nagle)에서 다룬다.

## 8. 셀프 체크

- [ ] "늦더라도 도착 vs 유실돼도 빠름" 한 질문으로 TCP/UDP를 가를 수 있다.
- [ ] 게임 데이터 5개 정도를 TCP/UDP로 분류할 수 있다.
- [ ] 한 게임이 TCP·UDP를 동시에 쓰는 게 정상이라는 걸 안다.
- [ ] 신뢰성 UDP가 TCP와 어떻게 다른지(골라서 vs 전부) 설명할 수 있다.
- [ ] 언리얼 RPC의 Reliable/Unreliable이 이 개념의 구현이라는 걸 안다.
