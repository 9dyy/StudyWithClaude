# 12강 — DNS

> **목표:** 도메인(game.example.com)이 어떻게 실제 IP로 바뀌는지(리졸빙 과정), 그리고 캐싱과 게임에서 서버 주소를 도메인으로 쓰는 이유를 이해한다.
> **선수 지식:** 2강(IP, 유동 IP), 3강(포트 53), 11강(HTTP의 Host).

---

## 1. 서버 주소를 IP로 박았더니 생긴 일

게임 접속 서버 주소를 IP로 직접 박았다.

```cpp
Connect(TEXT("203.0.113.10"), 7777);   // 서버 IP를 코드에 하드코딩
```

처음엔 잘 됐다. 그런데 몇 달 뒤 서버를 이전하면서 IP가 `198.51.100.25`로 바뀌었다. 이미 배포된 클라들은 옛날 IP로 접속을 시도한다 → **전부 접속 불가.** 패치를 다시 내려야 한다.

또 다른 문제: 사람이 `203.0.113.10`을 외울 수 있나? 못 외운다. 그래서 우리는 IP 대신 **도메인 이름**을 쓴다.

```cpp
Connect(TEXT("connect.mygame.com"), 7777);   // 도메인. IP가 바뀌어도 이건 그대로
```

도메인을 쓰면 서버 IP가 바뀌어도 도메인 → IP 매핑만 갱신하면 클라는 그대로 접속된다. 그 "도메인 → IP 변환"을 해주는 시스템이 **DNS(Domain Name System)** 다.

---

## 2. DNS = 인터넷의 전화번호부

DNS는 **도메인 이름을 IP 주소로 바꿔주는** 시스템이다.

```
사람이 기억하는 것:  connect.mygame.com
컴퓨터가 필요한 것:  198.51.100.25
                  ↑
               DNS가 변환
```

전화번호부 비유가 딱 맞다. "홍길동"(도메인)을 찾으면 "010-1234-5678"(IP)을 알려준다. 우리는 이름만 기억하고, 실제 연결은 번호로 한다.

> 포트는 DNS 53번을 쓴다(3강의 well-known 포트). DNS 자체도 네트워크 통신이라 패킷을 주고받는다 — 주로 UDP(빠르고 작아서), 큰 응답은 TCP.

---

## 3. 리졸빙 과정 — 도메인이 IP가 되기까지

`connect.mygame.com`을 입력하면, 한 군데에 물어보고 끝나는 게 아니라 **여러 DNS 서버를 거친다.** 이걸 리졸빙(resolving)이라고 한다. 면접에서 "DNS 동작 과정" 물으면 이걸 답하면 된다.

```
내 PC                                   각 DNS 서버
  │
  │ 1. "connect.mygame.com IP 뭐야?"
  ├──────────────→ [로컬 DNS 서버] (보통 통신사/공유기)
  │                      │
  │                      │ 캐시에 있으면 바로 응답. 없으면 ↓ 대신 물어봐줌
  │                      │
  │                      │ 2. "com 도메인 담당 누구?"
  │                      ├──→ [루트 DNS] → ".com 서버는 저기야"
  │                      │
  │                      │ 3. "mygame.com 담당 누구?"
  │                      ├──→ [.com TLD 서버] → "mygame.com 서버는 저기야"
  │                      │
  │                      │ 4. "connect.mygame.com IP는?"
  │                      ├──→ [mygame.com 권한 서버] → "198.51.100.25야"
  │                      │
  │ 5. "198.51.100.25래" │
  │ ←────────────────────┘
  │
  └─→ 이제 그 IP로 게임 서버 접속
```

단계 정리:

1. **로컬 DNS 서버**(통신사 것)한테 묻는다. 얘가 대신 다 알아봐 준다(재귀 질의).
2. 모르면 **루트 DNS** → "`.com`은 저쪽" 안내
3. **TLD 서버**(`.com` 담당) → "`mygame.com`은 저쪽" 안내
4. **권한 있는 네임서버**(`mygame.com` 담당) → 최종 IP 응답
5. 로컬 DNS가 결과를 내게 돌려주고, 동시에 **캐시**해둔다

> **핵심 비유:** 모르는 사람 전화번호를 찾는데, 안내데스크(루트)가 "그건 인사팀에 물어봐", 인사팀(TLD)이 "그 부서 담당자한테 물어봐", 담당자(권한 서버)가 마침내 번호를 알려주는 식. 한 번에 다 아는 곳은 없고 위에서 아래로 좁혀간다.

---

## 4. 캐싱 — 매번 이 짓을 하면 느리다

위 과정을 접속할 때마다 다 거치면 느리다. 그래서 **곳곳에 캐시**가 있다. 한 번 알아낸 도메인→IP를 일정 시간 저장해두고 재사용한다.

```
캐시 위치 (가까운 순):
  내 브라우저/앱 캐시  →  OS 캐시  →  로컬 DNS 서버 캐시  →  (없으면) 전체 리졸빙
```

각 DNS 기록엔 **TTL(Time To Live)** 이 있다. "이 정보는 N초 동안 유효" 라는 유효기간. TTL이 지나면 캐시를 버리고 다시 물어본다.

게임 운영에서 이게 중요해진다:

- 서버 IP를 바꾸기 **전에** TTL을 짧게 줄여두면, 변경이 빨리 전파된다.
- TTL이 길면 옛날 IP가 캐시에 오래 남아, IP 바꿔도 한동안 옛 서버로 접속이 간다.

> 윈도우에서 `ipconfig /flushdns`로 OS의 DNS 캐시를 비울 수 있다. "도메인 바꿨는데 옛날 IP로 가요" 할 때 디버깅용으로 쓴다.

## 5. 코드로 체감해보기

언리얼에서 도메인을 IP로 바꾸는 것(리졸빙)도 결국 함수 호출이다.

```cpp
ISocketSubsystem* SocketSub = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM);

// 도메인 → IP 변환(리졸빙). 이 안에서 위의 DNS 과정이 일어난다.
FAddressInfoResult Result = SocketSub->GetAddressInfo(
    TEXT("connect.mygame.com"),     // 도메인
    nullptr,
    EAddressInfoFlags::Default,
    NAME_None);

if (Result.ReturnCode == SE_NO_ERROR && Result.Results.Num() > 0)
{
    TSharedRef<FInternetAddr> ResolvedAddr = Result.Results[0].Address;
    ResolvedAddr->SetPort(7777);
    UE_LOG(LogTemp, Log, TEXT("Resolved IP: %s"), *ResolvedAddr->ToString(false));
    // 출력 예: 198.51.100.25  ← 도메인이 IP로 바뀌었다

    Socket->Connect(*ResolvedAddr);   // 변환된 IP로 접속
}
```

주의: 리졸빙은 네트워크를 타는 작업이라 **시간이 걸릴 수 있다(블로킹 위험).** 캐시에 없으면 위의 전체 과정을 거치니, 게임 스레드에서 동기로 호출하면 잠깐 멈출 수 있다. 보통 비동기로 처리하거나 접속 단계에서만 한다(9강의 블로킹 주의와 연결).

또 하나: `OpenLevel`이나 HTTP 모듈(11강)에 도메인을 넘기면 엔진이 내부에서 알아서 리졸빙해준다. 그래서 클라 개발자가 `GetAddressInfo`를 직접 부르는 일은 드물지만, "도메인은 결국 IP로 변환되어 접속된다"는 흐름은 알아야 한다.

## 6. 흔한 오해

### 오해 1: "DNS 서버 한 대가 모든 도메인 IP를 다 안다"

아니다. 계층적으로 나눠져 있다. 루트는 "`.com` 담당이 누군지"만 알고, TLD는 "`mygame.com` 담당이 누군지"만 알고, 권한 서버가 최종 IP를 안다. 한 곳이 전부 아는 게 아니라 위에서 아래로 위임된다.

### 오해 2: "도메인 입력하면 매번 전체 리졸빙을 한다"

대부분 캐시에서 끝난다. 브라우저·OS·로컬 DNS 서버에 캐시가 있어서, TTL이 안 지났으면 전체 과정을 안 거친다. 전체 리졸빙은 캐시가 없을 때만 일어난다.

### 오해 3: "DNS는 도메인을 IP로 바꿔주기만 한다"

주된 역할은 맞지만 그 외 기록도 있다. A 레코드(도메인→IPv4), AAAA(→IPv6), MX(메일 서버), CNAME(별칭) 등. 게임 클라 면접엔 보통 "A 레코드로 도메인→IP" 수준이면 충분하다.

### 오해 4: "서버 IP 바꾸면 즉시 모두에게 적용된다"

캐시와 TTL 때문에 즉시가 아니다. 기존 캐시가 TTL 동안 옛 IP를 들고 있어서, 그 시간만큼은 옛 서버로 접속이 갈 수 있다. 그래서 이전 전에 TTL을 줄여두는 운영 기법을 쓴다.

## 7. 면접에서 나오면

**Q1. DNS가 뭔가요?**
→ "도메인 이름을 IP 주소로 변환해주는 시스템입니다. 사람은 connect.mygame.com 같은 이름을 기억하고, 실제 통신은 그에 대응하는 IP로 하기 때문에, 그 사이를 이어주는 인터넷의 전화번호부 역할을 합니다. 기본 포트는 53번입니다."

**Q2. DNS 동작 과정을 설명해보세요.**
→ "먼저 로컬 DNS 서버에 묻고, 캐시에 없으면 로컬 DNS가 대신 알아봅니다. 루트 DNS에 물어 .com 담당 서버를 찾고, 그 TLD 서버에서 해당 도메인의 권한 네임서버를 찾고, 마지막으로 그 권한 서버가 최종 IP를 응답합니다. 루트에서 아래로 위임받으며 좁혀가는 계층 구조입니다."

**Q3. 게임에서 서버 주소를 IP가 아니라 도메인으로 쓰는 이유는?**
→ "서버 IP는 바뀔 수 있는데, IP를 코드에 하드코딩하면 IP가 바뀔 때마다 클라이언트를 다시 배포해야 합니다. 도메인을 쓰면 DNS의 도메인-IP 매핑만 갱신하면 되니까, 클라이언트 수정 없이 서버를 이전할 수 있습니다."

**Q4. DNS 캐싱과 TTL이 뭔가요?**
→ "한 번 알아낸 도메인-IP 매핑을 일정 시간 저장해두고 재사용하는 게 캐싱이고, 그 유효 기간이 TTL입니다. 브라우저, OS, 로컬 DNS 서버 등 여러 곳에 캐시가 있어서 매번 전체 조회를 안 해도 됩니다. TTL이 지나면 캐시를 버리고 다시 조회합니다."

**Q5. 서버 IP를 바꿨는데 일부 유저가 옛 서버로 접속하면 왜 그런가요?**
→ "DNS 캐시와 TTL 때문입니다. TTL이 끝나기 전까지는 캐시에 옛 IP가 남아 있어서 그쪽으로 접속이 갑니다. 그래서 IP 변경 전에 미리 TTL을 짧게 줄여두면 변경이 더 빨리 전파됩니다."

면접관이 그 다음에 던지기 좋은 질문: *"HTTPS 주소로 접속할 때, 그 서버가 진짜 그 서버인지 어떻게 믿나요?"* → 13강(TLS와 게임 보안)에서 다룬다.

---

## 8. 셀프 체크

- [ ] DNS가 도메인↔IP 변환이라는 걸 한 문장으로 말할 수 있다.
- [ ] 리졸빙 과정(로컬→루트→TLD→권한 서버)을 순서대로 설명할 수 있다.
- [ ] 게임이 IP 대신 도메인을 쓰는 이유(IP 변경 대응)를 안다.
- [ ] 캐싱과 TTL이 뭔지, 서버 이전 시 왜 중요한지 안다.
- [ ] 리졸빙이 시간이 걸려 블로킹될 수 있다는 걸 안다.
