# 7강 — 흐름 제어·혼잡 제어와 Nagle

> **목표:** TCP가 상대와 네트워크를 배려하는 방식(흐름 제어, 혼잡 제어)을 이해하고, 게임이 왜 Nagle 알고리즘을 꺼버리는지(`TCP_NODELAY`) 안다.
> **선수 지식:** 4강(TCP). 시퀀스/ACK, 윈도우 개념의 토대.

---

## 1. "내 패킷은 분명 빨리 보냈는데 왜 늦게 도착하지?"

TCP로 작은 명령 패킷을 보내는 게임을 만들었다. 키 입력을 1바이트씩 서버로 보낸다.

```cpp
// 키 누를 때마다 작은 패킷 전송
TcpSocket->Send((uint8*)&KeyCode, 1, BytesSent);   // 1바이트
```

테스트해보니 입력이 **뭉쳐서 늦게** 처리된다. 내 코드는 분명 즉시 보냈는데, 서버는 한참 뒤에 여러 개를 한꺼번에 받는다. 버그인가? 아니다. **TCP가 일부러 모아서 보내고 있다.** 범인은 **Nagle 알고리즘**이다.

이걸 이해하려면 TCP가 "혼자 빨리 가는" 프로토콜이 아니라 **상대와 네트워크를 배려하는** 프로토콜이라는 걸 알아야 한다. 그 배려가 흐름 제어, 혼잡 제어, Nagle이다.

---

## 2. 흐름 제어 — "받는 쪽이 감당 못 하면 천천히"

빠른 서버가 느린 클라이언트한테 데이터를 쏟아붓는다고 하자. 클라이언트의 수신 버퍼가 꽉 차면, 넘치는 데이터는 버려진다. 낭비다.

**흐름 제어(Flow Control)** 는 이걸 막는다. 받는 쪽이 "나 지금 이만큼 받을 수 있어"라고 **남은 버퍼 크기(수신 윈도우)** 를 알려주고, 보내는 쪽은 그만큼만 보낸다.

```
받는 쪽:  "내 버퍼 8KB 남았어" (Window = 8KB)
보내는 쪽: 8KB까지만 보내고 ACK 기다림
받는 쪽:  처리해서 비움. "이제 16KB 남았어"
보내는 쪽: 더 보냄
```

이걸 **슬라이딩 윈도우(Sliding Window)** 로 구현한다. "ACK 안 받고도 미리 보낼 수 있는 양"을 윈도우라고 하고, ACK가 오는 만큼 윈도우가 앞으로 미끄러진다. 한 개 보내고 ACK 기다리고를 반복하면 너무 느리니, 윈도우만큼 **미리 여러 개를 보내** 효율을 높인다.

> **핵심 비유:** 흐름 제어는 **상대 그릇 크기에 맞춰 음식 덜어주기**다. 상대 그릇이 작으면 조금씩, 크면 많이. 상대가 감당할 만큼만 준다.

---

## 3. 혼잡 제어 — "네트워크가 막히면 양보"

흐름 제어가 *받는 쪽*을 배려하는 거라면, 혼잡 제어(Congestion Control)는 **네트워크 전체**를 배려한다.

도로가 막히는데 모두가 차를 더 밀어넣으면 완전히 마비된다. 네트워크도 똑같다. 라우터가 처리 못 할 만큼 패킷이 몰리면 유실이 폭증한다. 그래서 TCP는 **패킷 유실을 "길 막힘 신호"로 해석**하고 전송 속도를 스스로 줄인다.

대략의 동작:

```
처음엔 조금씩 보냄 (Slow Start)
  ↓ 잘 도착하면
점점 빠르게 (전송량 증가)
  ↓ 패킷 유실 감지 (= 혼잡 신호)
확 줄임 → 다시 조심스럽게 증가
```

이걸 **혼잡 윈도우(congestion window)** 로 조절한다. 면접에선 용어보다 **"TCP는 유실을 혼잡으로 보고 스스로 속도를 줄인다"** 는 개념이 중요하다.

> 주의: 무선 환경에선 신호 간섭으로 유실이 나도 TCP는 "길이 막혔다"고 오해하고 속도를 줄인다. 와이파이에서 TCP 성능이 들쭉날쭉한 이유 중 하나다.

---

## 4. Nagle 알고리즘 — 그리고 게임이 그걸 끄는 이유

이제 도입의 범인이다. **Nagle 알고리즘**은 TCP의 효율화 기법이다.

문제 의식: 1바이트 데이터를 보내려고 TCP/IP 헤더 40바이트를 붙이면, **실제 내용보다 포장이 더 크다.** 1바이트 보내려고 41바이트를 쓰는 셈. 이런 작은 패킷이 많으면 네트워크 낭비다.

Nagle의 해법: **"작은 데이터는 좀 모았다가 한 번에 보내자."** 구체적으로, 아직 ACK 안 받은 데이터가 있으면, 작은 패킷들을 버퍼에 모아뒀다가 ACK가 오거나 버퍼가 찰 때 묶어서 보낸다.

```
Nagle 켜짐 (기본):
  키입력1 → (모음) 키입력2 → (모음) 키입력3 → ACK 오면 [1+2+3] 한 번에 전송
  → 대역폭 효율적, 하지만 약간 지연됨

Nagle 꺼짐 (TCP_NODELAY):
  키입력1 → 즉시 전송
  키입력2 → 즉시 전송
  → 지연 없음, 하지만 작은 패킷 많아짐
```

**게임에선 이 지연이 독이다.** 키 입력, 스킬 발동 같은 작은 패킷은 **모으지 말고 즉시** 보내야 반응성이 좋다. 그래서 게임 서버/클라는 거의 항상 Nagle을 끈다.

```cpp
// 언리얼 소켓에서 Nagle 끄기 = 작은 패킷 즉시 전송
TcpSocket->SetNoDelay(true);
//        ↑ TCP_NODELAY 옵션. "모으지 말고 바로 보내"
```

> **면접 포인트:** "게임은 반응성이 중요해서 `TCP_NODELAY`로 Nagle 알고리즘을 끈다. 대역폭 효율을 약간 포기하는 대신 지연을 없앤다"고 말하면 실무를 아는 답이다.

### Nagle + Delayed ACK = 최악의 궁합

가끔 Nagle 알고리즘이 받는 쪽의 **Delayed ACK**(ACK를 조금 모았다 보내는 기법)와 겹치면, 서로 상대를 기다리며 수백 ms가 깨지는 현상이 생긴다. 작은 패킷 위주 게임에서 이게 터지면 핑이 튄다. 해결책도 결국 `TCP_NODELAY`다.

## 5. 코드로 체감해보기

```cpp
// 게임 클라이언트 소켓 설정의 전형
FSocket* TcpSocket = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)
    ->CreateSocket(NAME_Stream, TEXT("GameTcp"), false);

TcpSocket->Connect(*ServerAddr);

// (1) Nagle 끄기 — 작은 입력 패킷을 즉시 보낸다
TcpSocket->SetNoDelay(true);

// (2) 송수신 버퍼 크기 조절 — 흐름 제어 윈도우에 영향
int32 NewSize = 0;
TcpSocket->SetSendBufferSize(64 * 1024, NewSize);
TcpSocket->SetReceiveBufferSize(64 * 1024, NewSize);

// 이제 작은 패킷을 보내면 모으지 않고 바로 나간다
TcpSocket->Send((uint8*)&KeyCode, 1, BytesSent);   // 즉시 전송됨
```

`SetNoDelay(true)` 한 줄이 도입의 "입력이 뭉쳐서 늦게 오던" 문제를 해결한다. 이게 게임 네트워크 코드에서 거의 관용구처럼 들어간다.

## 6. 흔한 오해

### 오해 1: "흐름 제어랑 혼잡 제어는 같은 거다"

다르다. **흐름 제어는 받는 쪽(상대)을 배려**하는 거고, **혼잡 제어는 네트워크 전체를 배려**하는 거다. 흐름 제어는 상대 버퍼가 넘치지 않게, 혼잡 제어는 길이 막히지 않게. 면접에서 자주 구분을 물어본다.

### 오해 2: "Nagle 알고리즘은 버그라서 꺼야 한다"

Nagle은 버그가 아니라 **대역폭을 아끼는 정상 최적화**다. 파일 전송 같은 큰 데이터엔 도움이 된다. 다만 작은 패킷을 빠르게 보내야 하는 게임엔 안 맞아서 끄는 것뿐이다. 용도에 따른 선택이다.

### 오해 3: "TCP_NODELAY를 켜면 무조건 빨라진다"

지연은 줄지만 작은 패킷이 많아져 **대역폭 효율과 패킷 수**는 나빠진다. 대량 전송에선 오히려 손해다. "반응성을 위해 효율을 약간 포기하는 트레이드오프"지 공짜 가속이 아니다.

### 오해 4: "UDP도 혼잡 제어를 한다"

UDP는 혼잡 제어가 **없다.** 네트워크가 막혀도 보내던 속도로 계속 던진다. 그래서 UDP를 막 쓰면 네트워크를 망가뜨릴 수 있어서, 게임은 신뢰성 UDP 위에 직접 전송량을 조절하는 로직을 넣기도 한다.

## 7. 면접에서 나오면

**Q1. 흐름 제어가 뭔가요?**
→ "받는 쪽이 처리할 수 있는 양에 맞춰 보내는 속도를 조절하는 기법입니다. 수신 측이 남은 버퍼 크기를 수신 윈도우로 알려주고, 송신 측은 그만큼만 보냅니다. 슬라이딩 윈도우로 구현해서, ACK를 받기 전에도 윈도우 크기만큼 미리 보내 효율을 높입니다."

**Q2. 혼잡 제어가 뭔가요?**
→ "네트워크 전체가 막히지 않도록 전송량을 조절하는 기법입니다. TCP는 패킷 유실을 네트워크 혼잡 신호로 해석해서, 처음엔 천천히 보내다 점점 늘리고, 유실이 감지되면 전송 속도를 확 줄입니다. 흐름 제어가 상대를 배려하는 거라면, 혼잡 제어는 네트워크 전체를 배려하는 겁니다."

**Q3. 흐름 제어와 혼잡 제어의 차이는?**
→ "둘 다 전송 속도를 조절하지만 대상이 다릅니다. 흐름 제어는 수신자의 버퍼가 넘치지 않게 상대를 배려하는 거고, 혼잡 제어는 중간 네트워크가 마비되지 않게 전체를 배려하는 겁니다."

**Q4. Nagle 알고리즘이 뭔가요? 게임에서 왜 끄나요?**
→ "작은 패킷을 모아서 한 번에 보내 대역폭을 아끼는 TCP 최적화입니다. 아직 ACK를 못 받았으면 작은 데이터를 버퍼에 모았다가 묶어 보냅니다. 그런데 게임은 키 입력이나 스킬 같은 작은 패킷을 즉시 보내야 반응성이 좋아서, TCP_NODELAY 옵션으로 Nagle을 끕니다. 대역폭 효율을 약간 포기하고 지연을 없애는 선택입니다."

**Q5. 슬라이딩 윈도우가 뭔가요?**
→ "ACK를 받기 전에도 미리 보낼 수 있는 데이터의 양을 윈도우로 정해두고, ACK가 오는 만큼 윈도우를 앞으로 이동시키는 방식입니다. 한 개 보내고 ACK를 기다리는 대신 윈도우 크기만큼 연속으로 보낼 수 있어서 처리량이 크게 올라갑니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 이제 소켓을 직접 만들어서 통신한다면 어떤 함수들이 필요한가요?"* → 8강(소켓 프로그래밍 기초)에서 다룬다.
