# 14강 — 언리얼 네트워크 모델

> **목표:** 언리얼 멀티플레이의 뼈대인 서버 권한, Replication, RPC(Server/Client/Multicast)가 각각 뭘 하고 언제 쓰는지 이해한다.
> **선수 지식:** 1~13강 전부의 응용. 특히 6강(Reliable/Unreliable), 13강(서버 권한)이 직접 연결된다.

---

## 1. 지금까지 배운 게 다 여기서 만난다

1강부터 13강까지 배운 게 결국 이걸 위한 거였다. 언리얼로 멀티플레이를 짤 때:

- TCP/UDP 선택? → 엔진이 UDP 기반 + 신뢰성 선택(6강)으로 해결
- 패킷 직렬화·경계? → 엔진이 자동 처리(10강)
- 클라 믿지 마라? → 서버 권한 구조로 강제(13강)

언리얼은 이 저수준을 다 가려주고, 우리는 **세 가지 도구**만 쓴다: **서버 권한, Replication, RPC.** 이 강의가 그 셋이다. 면접에서 "언리얼 네트워킹 해봤어요?" 하면 이 셋을 설명할 수 있어야 한다.

---

## 2. 서버 권한 — "서버가 진실, 클라는 화면"

언리얼 멀티플레이의 기본 모델은 **Dedicated Server(또는 Listen Server) + 클라이언트들**이다. 핵심 철학:

> **서버가 게임의 "진짜 상태"를 가진다. 클라이언트는 그걸 받아서 보여줄 뿐이다.**

이게 13강의 "클라를 믿지 마라"의 구현이다. 적 HP, 내 위치, 아이템 개수 — 진짜 값은 전부 서버에 있다. 클라는 그 복사본을 보여준다.

언리얼에서 "지금 이 코드가 서버에서 도나, 클라에서 도나"를 구분하는 게 핵심이다.

```cpp
if (HasAuthority())   // 이 액터에 대한 권한이 있나 = 서버인가
{
    // 서버에서만 도는 코드 (실제 게임 로직, 판정)
}
else
{
    // 클라에서 도는 코드 (표현, 예측)
}

// 역할 확인
GetLocalRole();     // 이 머신에서 이 액터의 역할
GetRemoteRole();    // 반대편에서의 역할
// ROLE_Authority(권한 있음=서버) / ROLE_AutonomousProxy(내가 조종) / ROLE_SimulatedProxy(남)
```

중요한 판정(데미지, 재화, 사망)은 전부 `HasAuthority()` 안, 즉 **서버에서** 해야 한다.

---

## 3. Replication — 서버의 상태를 클라로 자동 복제

서버가 가진 값을 클라들이 보려면 계속 보내줘야 한다. 매번 패킷을 손으로 짜는 대신(10강), 언리얼은 **변수에 표시만 하면 자동으로 동기화**해준다. 이게 **Replication(복제)** 이다.

```cpp
// 헤더: 복제할 변수 표시
UPROPERTY(ReplicatedUsing = OnRep_Health)   // 값 바뀌면 OnRep_Health 호출
float Health = 100.f;

UPROPERTY(Replicated)
FVector ReplicatedLocation;

// cpp: 어떤 변수를 복제할지 등록
void AMyCharacter::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutProps) const
{
    Super::GetLifetimeReplicatedProps(OutProps);
    DOREPLIFETIME(AMyCharacter, Health);
    DOREPLIFETIME(AMyCharacter, ReplicatedLocation);
}

// 클라에서 Health가 복제돼 바뀌면 자동 호출되는 콜백
void AMyCharacter::OnRep_Health()
{
    UpdateHealthBar(Health);   // HP바 갱신 (표현)
}
```

동작 방식:

- **서버에서만** 값을 바꾼다 (`Health -= Damage`).
- 엔진이 그 변화를 감지해 **관련된 클라들에게 자동 전송**한다.
- 클라에선 값이 갱신되고, `ReplicatedUsing` 콜백(`OnRep_`)이 호출돼 화면을 업데이트한다.

핵심 특징:

- **단방향: 서버 → 클라.** 클라가 복제 변수를 바꿔도 서버엔 안 간다(보안). 클라가 서버에 뭘 요청하려면 RPC를 쓴다(다음).
- **상태(state) 동기화에 적합.** "지금 HP가 얼마"처럼 지속적인 값. 자주 안 바뀌어도, 늦게 들어온 클라도 현재 값을 받는다.

> Replication은 6강의 "신뢰성 UDP"로 처리된다. 엔진이 알아서 도착을 보장한다(Reliable). 그래서 클라는 HP 변화를 놓치지 않는다.

---

## 4. RPC — 한쪽에서 다른 쪽 함수를 실행

Replication이 "변수 상태 동기화"라면, RPC(Remote Procedure Call)는 **"이벤트성 동작"** 을 위한 것이다. "지금 이 함수를 저쪽에서 실행해" 라는 원격 함수 호출. 세 종류가 있고, 방향이 다르다. 면접 단골이다.

```
Server RPC   :  클라 → 서버   "서버야 이거 해줘" (입력, 요청)
Client RPC   :  서버 → 특정 클라 "너한테만 알려줘" (개인 알림)
Multicast RPC:  서버 → 모든 클라 "다같이 봐" (이펙트, 사운드)
```

```cpp
// (1) Server RPC — 클라가 서버에 "공격하겠다" 요청 (13강의 좋은 설계)
UFUNCTION(Server, Reliable)
void Server_RequestAttack(int32 TargetId);

// (2) Client RPC — 서버가 특정 클라에게만 (예: "너 레벨업했어")
UFUNCTION(Client, Reliable)
void Client_OnLevelUp(int32 NewLevel);

// (3) Multicast RPC — 서버가 모두에게 (예: 폭발 이펙트)
UFUNCTION(NetMulticast, Unreliable)
void Multicast_PlayExplosion(FVector Location);
```

각 RPC가 **어디서 실행되는지**가 핵심:

| RPC 종류 | 호출하는 곳 | 실행되는 곳 |
|----------|------------|------------|
| Server | 클라 | 서버 |
| Client | 서버 | 그 클라 한 명 |
| Multicast | 서버 | 모든 클라 (+서버) |

### Reliable / Unreliable — 6강이 여기서 쓰인다

RPC마다 신뢰성을 직접 고른다(6강의 신뢰성 UDP).

- **Reliable:** 반드시 도착. 공격 요청, 레벨업 알림 등 놓치면 안 되는 것.
- **Unreliable:** 유실 OK. 이펙트·사운드처럼 자주 일어나고 하나쯤 빠져도 되는 것. (Reliable을 남발하면 트래픽이 폭증하니 이펙트는 Unreliable.)

## 5. 셋을 언제 쓰나 — 정리

| 하고 싶은 것 | 도구 |
|------------|------|
| HP, 위치, 점수 등 지속 상태를 모두가 보게 | **Replication** (변수) |
| 클라의 입력/요청을 서버로 | **Server RPC** |
| 특정 클라에게만 알림 | **Client RPC** |
| 모두에게 일회성 이펙트/사운드 | **Multicast RPC** |

전형적인 공격 흐름 한 번에 보기:

```
1. 클라: 마우스 클릭
2. 클라 → Server_RequestAttack(TargetId)   [Server RPC, Reliable]
3. 서버: 사거리·쿨다운 검증 (13강) → Target->Health -= Damage
4. 서버: Health가 [Replicated]라 모든 클라에 자동 복제 → 적 HP바 갱신
5. 서버 → Multicast_PlayHitEffect(Location)  [Multicast RPC, Unreliable]
6. 모든 클라: 타격 이펙트 재생
```

이 한 흐름에 서버 권한, Replication, 세 RPC가 다 들어 있다. 이걸 말로 설명할 수 있으면 언리얼 네트워킹 면접은 통과 수준이다.

## 6. 흔한 오해

### 오해 1: "복제 변수를 클라에서 바꾸면 서버에도 반영된다"

아니다. Replication은 **서버 → 클라 단방향**이다. 클라가 복제 변수를 바꿔도 로컬에서만 잠깐 바뀌고 다음 복제 때 서버 값으로 덮어쓰인다. 클라가 서버 상태를 바꾸려면 반드시 Server RPC로 요청해야 한다(보안).

### 오해 2: "RPC랑 Replication은 같은 거다"

다르다. Replication은 **변수의 상태를 지속적으로 동기화**하고(서버→클라), RPC는 **특정 함수를 한 번 원격 실행**한다(방향 다양). "지금 HP가 얼마"는 Replication, "방금 폭발했다"는 Multicast RPC다.

### 오해 3: "모든 RPC를 Reliable로 하면 안전하다"

Reliable은 재전송·순서 보장 비용이 든다. 이펙트·사운드처럼 초당 여러 번 일어나는 걸 다 Reliable로 하면 트래픽이 폭증하고 오히려 중요한 패킷을 밀어낸다(6강). 놓쳐도 되는 건 Unreliable이 맞다.

### 오해 4: "Multicast는 서버에서 호출하든 클라에서 호출하든 된다"

Multicast RPC는 **서버에서 호출**해야 모든 클라로 퍼진다. 클라에서 호출하면 그 클라 로컬에서만 실행되고 전파 안 된다. RPC는 "어디서 호출해서 어디서 실행되는지"의 방향이 정해져 있다.

## 7. 면접에서 나오면

**Q1. 언리얼의 네트워크 모델을 설명해보세요.**
→ "서버 권한 모델입니다. 서버가 게임의 진짜 상태를 가지고, 클라이언트는 그걸 복제받아 보여주는 구조입니다. 상태 동기화는 Replication으로, 이벤트성 동작은 RPC로 처리하고, 중요한 판정은 모두 서버에서 검증합니다. 클라이언트를 신뢰하지 않는 구조라 치팅 방어에도 유리합니다."

**Q2. Replication이 뭔가요?**
→ "서버가 가진 변수의 값을 클라이언트들에게 자동으로 동기화해주는 기능입니다. UPROPERTY에 Replicated를 붙이고 GetLifetimeReplicatedProps에 등록하면, 서버에서 값이 바뀔 때 엔진이 관련 클라이언트에 전송합니다. 서버에서 클라로 가는 단방향이고, HP나 위치 같은 지속 상태에 씁니다."

**Q3. RPC 세 종류를 설명해보세요.**
→ "Server RPC는 클라이언트가 서버에서 함수를 실행시키는 거고 주로 입력이나 요청에 씁니다. Client RPC는 서버가 특정 클라이언트 한 명에게 실행시키는 거고 개인 알림에 씁니다. Multicast RPC는 서버가 모든 클라이언트에서 실행시키는 거고 폭발 이펙트처럼 다같이 보는 연출에 씁니다."

**Q4. Replication과 RPC의 차이는?**
→ "Replication은 변수의 상태를 지속적으로 동기화하는 거고, RPC는 특정 함수를 한 번 원격으로 실행하는 겁니다. 예를 들어 '현재 HP가 얼마인지'는 Replication으로 계속 맞추고, '방금 폭발이 일어났다'는 일회성 이벤트는 Multicast RPC로 알립니다."

**Q5. RPC의 Reliable과 Unreliable은 어떻게 선택하나요?**
→ "놓치면 안 되는 건 Reliable, 유실돼도 되는 건 Unreliable로 합니다. 공격 요청이나 레벨업 알림은 Reliable, 이펙트나 사운드처럼 자주 발생하고 하나쯤 빠져도 되는 건 Unreliable입니다. 모든 걸 Reliable로 하면 트래픽이 늘고 중요한 패킷을 밀어내서 오히려 안 좋습니다."

**Q6. 클라이언트가 서버의 상태를 바꾸려면 어떻게 하나요?**
→ "Replication은 서버에서 클라로만 가는 단방향이라, 클라가 복제 변수를 직접 바꿔도 서버엔 반영되지 않습니다. 클라가 서버 상태를 바꾸려면 Server RPC로 요청을 보내고, 서버가 검증한 뒤 직접 값을 바꿔야 합니다. 이게 서버 권한과 보안의 핵심입니다."

면접관이 그 다음에 던지기 좋은 질문: *"서버에서 판정하면 핑만큼 늦을 텐데, 그럼 내 캐릭터도 핑만큼 늦게 움직이나요?"* → 15강(레이턴시와 지연 보상)에서 다룬다.

## 8. 셀프 체크

- [ ] "서버가 진실, 클라는 화면" 모델을 `HasAuthority()`와 함께 설명할 수 있다.
- [ ] Replication이 서버→클라 단방향 상태 동기화라는 걸 안다.
- [ ] RPC 세 종류의 호출 위치와 실행 위치를 표로 말할 수 있다.
- [ ] Replication과 RPC를 언제 각각 쓰는지 구분할 수 있다.
- [ ] Reliable/Unreliable 선택 기준을 안다.
- [ ] 공격 한 번의 전체 흐름(Server RPC→검증→Replication→Multicast)을 말할 수 있다.
