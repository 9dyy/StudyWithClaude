# 15강 — 레이턴시와 지연 보상

> **목표:** RTT/핑이 뭔지, 서버 권한 구조에서 입력이 늦는 문제를 클라이언트 예측·서버 보정·지연 보상으로 어떻게 해결하는지 이해한다.
> **선수 지식:** 14강(서버 권한, Replication, RPC). 4강의 RTT 개념.
> **이번 강의로 Part 5(게임 네트워킹)와 본강 전체가 끝난다. 마지막에 전 강의 정리표가 있다.**

---

## 1. 14강이 남긴 문제

14강에서 "서버가 진실, 클라는 화면"이라고 했다. 그럼 내가 이동키를 누르면:

```
1. 클라: W키 누름
2. 클라 → Server_Move(input)        [Server RPC]   ← 서버까지 가는 데 핑/2
3. 서버: 위치 계산, 검증
4. 서버 → 위치 Replication           ← 다시 클라로 오는 데 핑/2
5. 클라: 그제서야 캐릭터가 움직임
```

핑이 100ms면, **W 누르고 0.1초 뒤에** 캐릭터가 움직인다. 키보드와 캐릭터 사이에 고무줄이 달린 느낌. 이건 게임으로 못 쓴다. 그런데 실제 온라인 게임은 핑이 좀 있어도 내 캐릭터는 즉각 반응한다. **어떻게?** 이 강의가 그 트릭이다.

---

## 2. RTT와 핑 — 먼저 용어

- **RTT(Round Trip Time):** 패킷이 서버까지 갔다가 돌아오는 **왕복** 시간.
- **핑(Ping):** 사실상 RTT를 가리키는 게임 용어. "핑 50"이면 왕복 50ms.
- **레이턴시(Latency):** 지연. 보통 편도 또는 왕복 지연을 통칭.

```
클라 ──(편도 ≈ 핑/2)──→ 서버 ──(편도 ≈ 핑/2)──→ 클라
└──────────── RTT (= 핑) ───────────────┘
```

핑은 거리(빛의 속도 한계)·경유 라우터 수·혼잡(7강)으로 결정된다. 한국↔미국이면 물리적으로 100ms 이상은 깔린다. **핑을 0으로 만들 순 없다.** 그래서 "핑을 숨기는" 기법이 필요하다.

---

## 3. 클라이언트 예측 (Client-Side Prediction)

핵심 아이디어: **서버 응답을 기다리지 말고, 클라가 미리 결과를 예측해서 즉시 보여준다.**

```
W키 누름 → (서버에 요청 보내는 동시에) → 클라가 즉시 자기 캐릭터를 앞으로 이동
         서버 응답은 나중에 와서 "맞는지 확인"만
```

내 캐릭터의 이동은 결과가 뻔하다(앞으로 감). 그러니 서버 확인을 기다릴 필요 없이 클라가 먼저 움직여 버린다. 입력 즉시 반응 = 고무줄 사라짐.

언리얼의 `CharacterMovementComponent`가 이걸 기본 내장하고 있다. 그래서 캐릭터 이동은 별 설정 없이도 예측이 된다.

```cpp
// AutonomousProxy(내가 조종하는 클라)는 입력을 받아 즉시 이동 예측
// 동시에 서버로 입력을 보내 검증받음 — 둘이 동시에 일어남
if (GetLocalRole() == ROLE_AutonomousProxy)
{
    // 로컬에서 즉시 이동 (예측) + 서버로 입력 전송
}
```

## 4. 서버 보정 (Server Reconciliation)

예측은 **틀릴 수 있다.** 클라는 "앞으로 갔다"고 예측했는데, 서버에선 그 사이 벽이 생겼거나 넉백을 당했을 수 있다. 서버가 진실이니(14강), 예측이 틀리면 **서버 값으로 되돌려야** 한다.

```
클라 예측: 좌표 (100, 0)으로 이동했다고 표시
서버 판정: 실은 벽에 막혀 (90, 0)
              ↓
서버 → 클라: "네 위치는 (90,0)이야" (Replication)
클라: 어긋났네 → (90,0)으로 보정
```

문제: 그냥 확 순간이동시키면 캐릭터가 튄다(rubber-banding). 그래서:

- 클라는 자기가 보낸 입력들을 **기억**해뒀다가,
- 서버 확정 위치를 받으면 그 지점부터 **기억한 입력을 다시 적용(re-simulate)** 해서 부드럽게 현재로 따라잡는다.

예측이 대부분 맞으면 보정은 거의 티가 안 난다. 핑이 튀거나 충돌이 있을 때만 살짝 보정된다. 이 "예측 + 보정" 콤보가 현대 온라인 게임 반응성의 핵심이다.

---

## 5. 보간 (Interpolation) — 남의 캐릭터는 다르게

내 캐릭터는 예측한다. 그럼 **다른 플레이어**는? 남의 입력은 내가 예측 못 한다(그 사람이 뭘 누를지 모름). 남의 위치는 서버에서 띄엄띄엄 온다(예: 초당 20번).

그냥 받은 위치로 순간이동시키면 뚝뚝 끊긴다. 그래서 **보간(Interpolation)**: 받은 위치들 **사이를 부드럽게 이어서** 보여준다.

```
서버에서 온 남의 위치:  A ── (빈 구간) ── B ── (빈 구간) ── C
화면 표시(보간):       A→→→→→→→→→→B→→→→→→→→→→C  (부드럽게 채움)
```

대신 보간은 "조금 과거"를 보여준다. B를 받아도 A→B를 그리는 중이라 약간 늦다. 이게 다음 절(지연 보상)의 배경이 된다.

정리:

- **내 캐릭터:** 예측 (즉시 반응, 미래를 추측)
- **남의 캐릭터:** 보간 (부드럽게, 약간 과거)

---

## 6. 지연 보상 (Lag Compensation) — FPS 명중 판정

FPS에서 진짜 골치 아픈 문제. 내 화면에서 적을 정확히 조준해 쐈다. 그런데:

- 내가 보는 적은 보간 때문에 **약간 과거** 위치(5번)
- 내 사격 패킷이 서버 가는 데 또 **핑/2**만큼 지연
- 서버가 받을 땐 적이 이미 다른 곳 → "빗나감" 판정

분명 맞췄는데 안 맞는다. 핑 높은 사람이 손해를 본다. 이걸 해결하는 게 **지연 보상**이다.

핵심: **서버가 과거 상태를 기억해뒀다가, "이 플레이어가 쏜 시점에 적이 어디 있었는지"로 되돌려서 판정한다.**

```
서버: 각 플레이어 위치를 최근 N프레임 저장 (히스토리)
       │
클라A 사격 패킷 도착 (찍힌 시각 = 100ms 전)
       │
서버: "100ms 전으로 되감으면 적이 어디였지?" → 그 위치로 명중 판정
       │
       └ 클라A 화면에서 맞은 게 맞으면 → 명중 인정
```

즉 서버가 "쏜 사람 입장의 과거 시점"으로 시간을 되감아서 판정한다. 핑이 높아도 자기 화면에서 맞췄으면 인정된다.

대가: 맞은 쪽 입장에선 "엄폐물 뒤로 숨었는데 맞는"(behind-cover death) 현상이 가끔 생긴다. 쏜 사람의 과거 시점에선 아직 안 숨었으니까. 모든 지연 보상은 **"쏜 사람 vs 맞은 사람" 중 누구 경험을 우선할지의 트레이드오프**다. 대부분의 FPS는 쏜 사람을 우선한다(조준한 대로 맞는 게 중요하니까).

> **면접 포인트:** "클라 예측으로 내 반응성을 살리고, 서버 보정으로 진실을 맞추고, 남은 보간으로 부드럽게 하고, FPS 명중은 서버가 과거로 되감는 지연 보상으로 판정한다" — 이 네 개를 엮어 말하면 게임 네트워크를 제대로 아는 답이 된다.

## 7. 흔한 오해

### 오해 1: "핑은 최적화하면 0으로 만들 수 있다"

물리적 거리에 따른 빛의 속도 한계가 있어서 0은 불가능하다. 한국↔미국은 왕복 100ms 이상이 깔린다. 그래서 핑을 없애는 게 아니라 예측·보간으로 **숨기는** 게 목표다.

### 오해 2: "클라 예측은 서버 권한을 깨는 거 아닌가"

아니다. 예측은 어디까지나 **화면 표현**이고, 진실은 여전히 서버다. 예측이 틀리면 서버 값으로 보정된다(서버 보정). 클라는 미리 보여줄 뿐, 판정 권한은 서버가 유지한다(13·14강).

### 오해 3: "지연 보상이 있으면 핑 높아도 완전 공평하다"

완화일 뿐 완벽한 공평은 없다. 지연 보상은 쏜 사람을 유리하게 하지만, 그 대가로 맞은 사람이 "숨었는데 맞는" 경험을 한다. 트레이드오프지 만능이 아니다.

### 오해 4: "내 캐릭터랑 남 캐릭터를 똑같이 처리한다"

다르게 처리한다. 내 캐릭터는 입력을 아니까 예측하고, 남 캐릭터는 입력을 모르니 받은 위치들 사이를 보간한다. 처리 방식이 근본적으로 다르다.

## 8. 면접에서 나오면

**Q1. RTT(핑)가 뭔가요?**
→ "패킷이 서버까지 갔다가 돌아오는 왕복 시간입니다. 게임에서 핑이라고 부르는 게 보통 이 RTT인데, 물리적 거리와 경유 라우터, 네트워크 혼잡으로 결정됩니다. 빛의 속도 한계 때문에 0으로 만들 수는 없어서, 예측 같은 기법으로 체감 지연을 줄입니다."

**Q2. 서버 권한 구조에서 입력 지연 문제를 어떻게 해결하나요?**
→ "클라이언트 예측을 씁니다. 서버 응답을 기다리지 않고 클라이언트가 입력 결과를 미리 예측해 즉시 화면에 반영하고, 동시에 서버로 입력을 보내 검증받습니다. 예측이 맞으면 그대로 가고, 틀리면 서버가 보낸 정확한 값으로 보정합니다. 덕분에 핑이 있어도 내 캐릭터는 즉각 반응하는 것처럼 느껴집니다."

**Q3. 클라이언트 예측과 서버 보정을 설명해보세요.**
→ "예측은 클라이언트가 입력 결과를 미리 계산해 보여주는 거고, 보정은 서버의 확정 값과 어긋났을 때 맞추는 겁니다. 클라이언트는 보낸 입력들을 기억해뒀다가, 서버 확정 위치를 받으면 그 시점부터 입력을 다시 적용해서 부드럽게 현재 위치로 따라잡습니다. 예측이 대부분 맞으면 보정은 거의 티가 안 납니다."

**Q4. 다른 플레이어의 움직임은 어떻게 부드럽게 보여주나요?**
→ "보간을 씁니다. 남의 입력은 예측할 수 없고 위치가 띄엄띄엄 오기 때문에, 받은 위치들 사이를 부드럽게 이어서 그립니다. 대신 약간 과거를 보여주게 되는데, 내 캐릭터는 예측으로 미래를, 남의 캐릭터는 보간으로 과거를 다루는 식으로 구분합니다."

**Q5. 지연 보상(lag compensation)이 뭔가요?**
→ "FPS에서 핑 때문에 맞췄는데 안 맞는 문제를 줄이는 기법입니다. 서버가 각 플레이어의 최근 위치 히스토리를 저장해뒀다가, 어떤 플레이어가 쏜 패킷이 오면 그 사람이 쏜 시점으로 시간을 되감아서 그때 적 위치로 명중을 판정합니다. 핑이 높아도 자기 화면에서 조준한 대로 맞게 해주는 대신, 맞은 쪽은 엄폐물 뒤에서 맞는 경험을 할 수 있는 트레이드오프가 있습니다."

**Q6. 예측을 쓰면 클라이언트가 위치를 조작할 수 있지 않나요?**
→ "예측은 화면 표현일 뿐 진실은 서버가 가집니다. 클라가 위치를 조작해도 서버가 입력과 물리를 검증해서 맞지 않으면 서버 값으로 보정합니다. 그래서 예측은 반응성을 위한 것이고, 권한과 검증은 서버에 남아 있어 치팅을 막습니다."

## 9. 셀프 체크

- [ ] RTT/핑이 왕복 시간이고 0이 될 수 없다는 걸 안다.
- [ ] 클라이언트 예측이 왜 입력 지연을 숨기는지 설명할 수 있다.
- [ ] 서버 보정(re-simulation)이 예측 오차를 어떻게 메우는지 안다.
- [ ] 내 캐릭터(예측)와 남 캐릭터(보간)를 다르게 다루는 이유를 안다.
- [ ] 지연 보상이 "과거로 되감아 판정"이고 트레이드오프가 있다는 걸 설명할 수 있다.

## 10. Part 5 + 전체 정리

### Part 5 한눈에

| 개념 | 한 줄 |
|------|------|
| 서버 권한 | 서버가 진실, 클라는 화면. 중요한 판정은 서버 |
| Replication | 서버 변수 상태를 클라로 자동 동기화 (단방향) |
| RPC | 원격 함수 실행. Server/Client/Multicast, Reliable/Unreliable |
| 클라 예측 | 내 입력 결과를 미리 보여줘 핑을 숨김 |
| 서버 보정 | 예측 오차를 서버 진실로 부드럽게 교정 |
| 보간 | 남의 캐릭터를 받은 위치들 사이로 부드럽게 |
| 지연 보상 | 쏜 시점으로 되감아 FPS 명중 판정 |

### 본강 15강 전체 지도

```
Part 1 기초     1 네트워크/계층   2 IP/라우팅     3 포트/소켓
                      │
Part 2 전송     4 TCP ──→ 5 UDP ──→ 6 선택 ──→ 7 흐름·혼잡·Nagle
                      │  (면접 핵심 구간)
Part 3 소켓     8 소켓 함수 ──→ 9 블로킹/멀티플렉싱 ──→ 10 패킷/직렬화
                      │
Part 4 응용     11 HTTP/S ──→ 12 DNS ──→ 13 TLS/보안
                      │
Part 5 게임     14 언리얼 모델(권한/Replication/RPC) ──→ 15 지연 보상
                      │
                  → 이 모든 게 "멀티플레이가 즉각 반응하면서도 공정하게"를 위한 것
```

각 Part가 다음 Part의 토대다. 전송(2)을 알아야 소켓(3)이 보이고, 소켓을 알아야 응용 프로토콜(4)이 보이고, 그 위에서 언리얼(5)이 다 가려준다. 면접에선 어느 강의 주제든 "그래서 게임에선 어떻게?"로 연결할 수 있으면 합격권이다.
