# 13강 — TLS와 게임 보안

> **목표:** TLS가 어떻게 암호화하고 서버를 인증하는지(대칭/비대칭, 핸드셰이크), 그리고 "클라이언트를 믿지 마라"는 게임 보안의 대원칙을 이해한다.
> **선수 지식:** 11강(HTTP/HTTPS), 12강(도메인). 4강의 handshake 개념.

---

## 1. "치트 좀 막아주세요"

멀티플레이 게임을 냈더니 핵이 돈다.

- 누가 패킷을 가로채서 비밀번호를 빼간다.
- 누가 "내 데미지 9999" 패킷을 서버에 보내서 한 방에 보스를 잡는다.
- 누가 "내 좌표 순간이동" 패킷을 조작해서 벽을 통과한다.

이건 사실 **두 개의 다른 문제**다.

1. **전송 중 도청·변조** → 암호화로 막는다 (TLS, HTTPS)
2. **클라가 거짓말하는 것** → 서버 권한 검증으로 막는다 ("클라를 믿지 마라")

이 강의는 둘 다 다룬다. 면접에서 게임 보안 물으면 이 두 축으로 답하면 깔끔하다.

---

## 2. 암호화의 두 종류 — 대칭과 비대칭

TLS를 이해하려면 먼저 암호화 두 종류를 알아야 한다.

### 대칭키 암호화 (Symmetric)

**같은 키**로 잠그고 푼다. 빠르다. 문제는 "그 키를 상대에게 어떻게 안전하게 전달하지?" 키를 그냥 보내면 중간에서 가로챈다.

```
평문 ──[키 K로 암호화]──→ 암호문 ──[같은 키 K로 복호화]──→ 평문
       빠름. 근데 K를 어떻게 공유?
```

### 비대칭키 암호화 (Asymmetric / 공개키)

**키가 두 개.** 공개키(Public)와 개인키(Private). 공개키로 잠그면 **개인키로만** 풀린다. 공개키는 아무나 가져도 된다(잠그는 용도라서). 개인키는 서버만 갖는다.

```
공개키로 잠근 것  →  개인키로만 열림
개인키는 서버만 가짐 → 남이 가로채도 못 엶

단점: 느림
```

### TLS는 둘을 섞어 쓴다

- 비대칭은 **안전하지만 느림** → 키를 안전하게 교환하는 데만 씀
- 대칭은 **빠르지만 키 공유가 문제** → 실제 데이터 암호화에 씀

그래서: **비대칭으로 "대칭키"를 안전하게 주고받은 뒤, 이후 통신은 빠른 대칭키로 한다.** 이게 TLS의 핵심 아이디어다.

---

## 3. TLS 핸드셰이크 — 자물쇠를 거는 절차

HTTPS로 접속할 때, 실제 데이터를 주고받기 전에 **TLS 핸드셰이크**를 한다(개념 흐름).

```
[클라이언트]                                   [서버]

   ── 1. "암호화 통신하자" (지원 방식 목록) ─────→
   ←──── 2. 인증서 전송 (공개키 포함) ────────────
        (서버가 "내가 진짜 mygame.com이야" 증명)

   3. 클라가 인증서 검증 — CA 서명이 맞나 확인

   ── 4. 대칭키 재료를 공개키로 암호화해 전송 ────→
        (개인키 가진 서버만 풀 수 있음)

   5. 양쪽이 같은 대칭키 확보
   ════ 이후 빠른 대칭키로 암호화 통신 ════
```

핵심 두 가지:

1. **인증(Authentication):** 서버가 **인증서(Certificate)** 를 보낸다. "내가 진짜 mygame.com이다"를 **CA(인증기관)** 가 보증한 문서다. 클라는 이걸 검증해서 가짜 서버(피싱)를 거른다. 이게 12강 끝의 질문 — "이 서버가 진짜인지 어떻게 믿나"의 답이다.
2. **키 교환:** 비대칭으로 대칭키를 안전하게 나눈 뒤, 이후엔 빠른 대칭키로 암호화.

> **핵심 비유:** 서버가 **자물쇠(공개키)** 를 잔뜩 뿌린다. 클라는 그 자물쇠로 비밀(대칭키 재료)을 잠가 보낸다. **열쇠(개인키)는 서버만** 갖고 있어 남이 가로채도 못 연다. 그렇게 둘만의 비밀키를 만든 뒤, 빠른 대칭 암호로 대화한다.

---

## 4. 게임 보안의 대원칙 — "클라이언트를 믿지 마라"

TLS가 막는 건 **전송 중**의 도청·변조다. 그런데 핵의 상당수는 전송 중이 아니라 **클라이언트 자체가 거짓말**하는 거다. TLS로 암호화돼 있어도, 그 클라가 보낸 내용 자체가 조작이면 소용없다.

> **대원칙: 클라이언트가 보내는 모든 것은 의심하라. 중요한 판정은 서버가 한다.**

### 나쁜 설계 — 클라가 결과를 보냄

```cpp
// ❌ 클라가 "나 데미지 9999 줬어"라고 통보 → 서버가 그대로 믿음
void Server_DealDamage(float Damage)   // 클라가 Damage를 보냄
{
    Enemy->HP -= Damage;   // 9999가 와도 그대로 적용 → 핵 천국
}
```

핵 유저가 `Damage`에 9999를 넣어 보내면 끝이다. 클라를 믿었기 때문.

### 좋은 설계 — 클라는 "의도"만, 판정은 서버가

```cpp
// ✅ 클라는 "공격하겠다"는 의도만 보냄. 데미지 계산·검증은 서버가.
void Server_RequestAttack(int32 TargetId)
{
    AEnemy* Target = FindEnemy(TargetId);
    if (!Target) return;

    // 서버가 직접 검증: 사거리 안인가? 쿨다운 됐나? 살아있나?
    if (!IsInRange(Target) || !IsAttackReady()) return;

    // 데미지도 서버가 가진 정확한 스탯으로 계산 (클라 값 안 씀)
    float Damage = CalculateDamage(MyStats, Target->Defense);
    Target->HP -= Damage;
}
```

클라는 "공격할게"라는 의도만 보내고, **사거리·쿨다운·데미지는 전부 서버가 자기 데이터로 판정**한다. 클라가 보낸 숫자를 그대로 쓰지 않는다.

이게 14강(언리얼 네트워크 모델)의 **서버 권한(Server Authority)** 으로 이어진다. 언리얼이 "서버 권위" 구조를 기본으로 미는 이유가 바로 이 보안 원칙이다.

> **면접 포인트:** 게임 보안 질문엔 "전송은 TLS로 암호화하고, 무엇보다 클라이언트를 신뢰하지 않고 중요한 판정을 서버에서 검증한다"고 답하면 깊이가 보인다. 암호화만 말하면 절반이다.

## 5. 코드로 — 언리얼에서 TLS는 거의 자동

다행히 클라 개발자가 TLS를 직접 구현할 일은 없다. `https://`로 요청하면 엔진이 핸드셰이크·검증·암호화를 다 해준다(11강의 HTTP 모듈).

```cpp
// https 만 쓰면 TLS는 엔진이 알아서 처리한다
Request->SetURL(TEXT("https://game.example.com/api/login"));   // 자동 암호화
Request->ProcessRequest();

// 신경 쓸 것: 로그인/결제/개인정보는 반드시 https. http(평문)로 보내면 비번이 그대로 노출.
```

진짜 신경 써야 하는 건 TLS 구현이 아니라 **4번의 설계 원칙**이다. RPC를 만들 때 "이 판정을 클라가 하나, 서버가 하나"를 항상 따져야 한다. 그게 클라 개발자가 보안에 기여하는 지점이다.

## 6. 흔한 오해

### 오해 1: "HTTPS 쓰면 핵을 막을 수 있다"

HTTPS는 **전송 구간 도청·변조**만 막는다. 클라이언트가 조작된 값을 정상적으로 암호화해서 보내면 서버는 그걸 정상 요청으로 받는다. 핵 방어의 핵심은 암호화가 아니라 **서버 측 검증**이다.

### 오해 2: "대칭키가 비대칭키보다 약하다"

약한 게 아니라 **용도가 다르다.** 대칭키는 빠르지만 키 공유가 어렵고, 비대칭키는 키 공유가 안전하지만 느리다. TLS는 비대칭으로 키를 나누고 대칭으로 데이터를 암호화해 둘의 장점을 합친다.

### 오해 3: "인증서는 암호화를 위한 것이다"

인증서의 1차 목적은 **암호화가 아니라 신원 증명**이다. "이 서버가 진짜 그 도메인의 주인인가"를 CA가 보증하는 것. 이게 없으면 가짜 서버가 중간에 끼는 중간자 공격(MITM)을 막을 수 없다.

### 오해 4: "중요한 계산을 클라에서 하면 빠르고 좋다"

성능엔 좋아 보여도 보안엔 치명적이다. 클라에서 한 계산 결과는 조작될 수 있다. 데미지·재화·아이템 획득 같은 중요한 판정은 반드시 서버에서 해야 한다. 클라 계산은 어디까지나 **예측/표현용**이지 판정의 근거가 아니다(15강의 클라 예측과 연결).

## 7. 면접에서 나오면

**Q1. 대칭키와 비대칭키 암호화의 차이는?**
→ "대칭키는 암호화와 복호화에 같은 키를 쓰고 빠르지만, 그 키를 상대에게 안전하게 전달하는 게 어렵습니다. 비대칭키는 공개키와 개인키 두 개를 쓰는데, 공개키로 잠그면 개인키로만 풀 수 있어 키 공유가 안전하지만 느립니다. TLS는 둘을 섞어, 비대칭으로 대칭키를 교환하고 이후엔 빠른 대칭키로 통신합니다."

**Q2. TLS 핸드셰이크 과정을 설명해보세요.**
→ "클라이언트가 암호화 통신을 요청하면 서버가 공개키가 담긴 인증서를 보냅니다. 클라이언트는 그 인증서가 신뢰할 수 있는 CA가 서명한 건지 검증해서 서버 신원을 확인하고, 공개키로 대칭키 재료를 암호화해 보냅니다. 그 재료는 개인키를 가진 서버만 풀 수 있어서, 양쪽이 같은 대칭키를 안전하게 확보하고 이후엔 그 대칭키로 빠르게 암호화 통신합니다."

**Q3. HTTPS만 쓰면 게임 보안이 충분한가요?**
→ "아닙니다. HTTPS는 전송 구간의 도청과 변조를 막을 뿐, 클라이언트가 조작된 값을 정상적으로 암호화해 보내는 건 막지 못합니다. 그래서 데미지나 재화 같은 중요한 판정은 클라이언트를 믿지 않고 서버에서 검증해야 합니다. 암호화와 서버 권한 검증은 별개의 방어선입니다."

**Q4. "클라이언트를 믿지 마라"가 무슨 뜻인가요?**
→ "클라이언트가 보내는 데이터는 조작될 수 있으니, 중요한 판정을 클라이언트의 통보에 맡기지 말고 서버가 직접 검증하라는 원칙입니다. 예를 들어 클라가 '데미지 9999 줬다'고 보내면 그대로 믿지 말고, 서버가 사거리·쿨다운·스탯을 확인해서 데미지를 직접 계산해야 합니다. 클라는 '공격하겠다'는 의도만 보내는 거죠."

**Q5. 인증서는 왜 필요한가요?**
→ "접속한 서버가 진짜 그 도메인의 주인인지 신원을 증명하기 위해서입니다. CA라는 신뢰된 기관이 서명한 인증서를 통해, 클라이언트는 중간에 가짜 서버가 끼어드는 중간자 공격을 걸러낼 수 있습니다. 암호화 이전에 '상대가 진짜인가'를 보장하는 장치입니다."

면접관이 그 다음에 던지기 좋은 질문: *"그 서버 권한 검증을 언리얼에서는 어떻게 구현하나요?"* → 14강(언리얼 네트워크 모델)에서 다룬다.

---

## 8. 셀프 체크

- [ ] 대칭키와 비대칭키의 차이, 그리고 TLS가 둘을 섞는 이유를 안다.
- [ ] TLS 핸드셰이크의 두 목적(인증 + 키 교환)을 설명할 수 있다.
- [ ] 인증서가 "신원 증명"이라는 걸 안다.
- [ ] "클라이언트를 믿지 마라" 원칙을 데미지 예시로 설명할 수 있다.
- [ ] HTTPS(전송 암호화)와 서버 검증(핵 방어)이 별개 방어선임을 안다.
