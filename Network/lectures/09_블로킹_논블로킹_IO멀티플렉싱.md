# 9강 — 블로킹·논블로킹과 I/O 멀티플렉싱

> **목표:** 블로킹/논블로킹의 차이, 한 스레드로 수천 연결을 받는 I/O 멀티플렉싱(select·IOCP)의 개념을 이해한다.
> **선수 지식:** 8강(소켓 함수). OS 강의의 블로킹 I/O 개념이 있으면 더 쉬움.
> **깊이:** 클라 면접 선까지. IOCP 내부 구현이 아니라 "왜 필요하고 무슨 모델인가"까지.

---

## 1. 8강 서버의 치명적 결함

8강 끝에서 본 문제. 서버가 `recv()`로 한 클라의 데이터를 기다리는 동안 다른 클라는 접속도 못 한다.

```cpp
FSocket* ClientA = ListenSocket->Accept(...);
ClientA->Recv(Buffer, size, Read);   // ❌ A가 데이터 보낼 때까지 여기서 멈춤(블로킹)
                                     //    그동안 B, C, D는 못 받음
```

`recv()`는 데이터가 올 때까지 **함수가 리턴을 안 하고 멈춘다.** 이게 **블로킹(blocking)** 이다. 이 상태론 동시 접속 2명도 못 받는다. 게임 서버가 수천 명을 받으려면 이걸 깨야 한다. 방법이 몇 가지 있고, 그게 이 강의다.

---

## 2. 블로킹 vs 논블로킹

### 블로킹 (Blocking)

데이터가 준비될 때까지 **함수가 멈춰서 기다린다.** 코드는 단순하지만, 기다리는 동안 그 스레드는 아무것도 못 한다.

```cpp
Socket->Recv(Buffer, size, Read);   // 데이터 올 때까지 여기 묶임
// 데이터 도착해야 다음 줄 실행
```

> **비유:** 택배를 집에서 **계속 문 앞에 서서** 기다리는 것. 올 때까지 다른 일을 못 한다.

### 논블로킹 (Non-blocking)

데이터가 없으면 **"지금 없음"을 즉시 리턴하고** 코드는 계속 진행한다.

```cpp
Socket->SetNonBlocking(true);
if (Socket->Recv(Buffer, size, Read))  // 데이터 있으면 받고
{ /* 처리 */ }
else
{ /* 없으면 그냥 넘어가서 다른 일 함 */ }
```

> **비유:** 택배가 왔나 **가끔 문을 확인하고** 없으면 하던 일 계속. 안 묶인다.

논블로킹이면 한 스레드로 여러 소켓을 "돌아가며 확인"할 수 있다. 하지만 소켓이 수천 개면 매번 다 확인(폴링)하는 게 낭비다. "데이터 온 소켓만 골라서 알려주면" 좋겠다. 그게 I/O 멀티플렉싱이다.

---

## 3. I/O 멀티플렉싱 — "여러 소켓을 한 번에 감시"

핵심 아이디어: **소켓 수천 개를 OS한테 맡기고, "이 중에 데이터 온 거 있으면 알려줘"** 하고 한 곳에서 기다린다. 스레드 하나로 수천 연결을 감시할 수 있다.

```
        ┌──────────────────────────┐
        │   감시 함수 (select 등)    │  "이 소켓들 중 준비된 거 알려줘"
        └────────────┬─────────────┘
          소켓1  소켓2  소켓3 ... 소켓5000
                       │
              소켓3, 소켓117에 데이터 도착!
                       │
        "소켓3이랑 117 준비됨" ──→ 그 둘만 처리
```

대표 방식들:

| 방식 | 특징 | 비고 |
|------|------|------|
| `select` | 가장 기본. 감시할 소켓을 매번 등록. 소켓 많으면 느림 | 이식성 좋음 |
| `poll` | select의 개선판. 개수 제한 완화 | 유닉스 |
| `epoll` | 리눅스 고성능. 수만 연결도 효율적 | 리눅스 서버 |
| **IOCP** | **윈도우 고성능 모델** | 윈도우 게임 서버 |

`select`의 한계는, 매번 "이 소켓들 봐줘" 하고 전체 목록을 넘기고 OS가 전부 훑어야 한다는 것. 연결이 수천이면 이 훑기 자체가 부담이다. 그래서 대규모는 epoll(리눅스)/IOCP(윈도우)를 쓴다.

---

## 4. IOCP — 윈도우 게임 서버의 표준 (개념만)

게임 서버가 윈도우면 거의 **IOCP(I/O Completion Port)** 를 쓴다. 면접에서 "윈도우 고성능 서버" 하면 IOCP가 나온다.

select와의 결정적 차이:

- **select:** "준비됐는지 내가 물어본다" (확인하러 감)
- **IOCP:** "끝나면 OS가 알려준다" (완료 통보를 받음)

IOCP는 비동기 I/O다. "이 데이터 읽어줘"라고 OS에 요청만 던지고 다른 일을 한다. OS가 읽기를 **다 끝내면** "완료됐어" 하고 완료 큐에 넣어준다. 워커 스레드 몇 개가 그 완료 통보를 꺼내서 처리한다.

```
요청: "소켓들에서 읽기 시작해" → OS에 맡기고 끝
       ↓ (OS가 백그라운드에서 다 처리)
완료 큐: [소켓3 읽기완료] [소켓117 읽기완료] ...
       ↓
워커 스레드 몇 개가 완료된 것만 꺼내 처리
```

장점: 스레드 몇 개로 **수만 연결**을 감당한다. 연결마다 스레드를 주면(과거 방식) 스레드가 수천 개라 컨텍스트 스위칭 비용으로 죽는다(OS 강의의 컨텍스트 스위칭 참고). IOCP는 소수 스레드 + OS 비동기로 이걸 해결한다.

> **클라 개발자 기준:** IOCP 구현을 직접 짤 일은 보통 없다. 하지만 "윈도우 게임 서버는 왜 IOCP를 쓰나 → 적은 스레드로 대량 연결을 비동기로 처리하려고" 정도는 면접에서 답할 수 있어야 한다.

---

## 5. 언리얼은 어떻게 하나

언리얼 클라는 이 저수준을 거의 안 건드린다. 멀티플레이는 `Replication`/RPC(14강)가 알아서 처리한다. 다만 직접 소켓을 쓸 때(커스텀 프로토콜, 외부 서버 연동 등)는 논블로킹 + 별도 스레드 패턴을 쓴다.

```cpp
// 흔한 패턴: 수신 전용 스레드에서 논블로킹으로 폴링
class FSocketReceiver : public FRunnable
{
    FSocket* Socket;
    virtual uint32 Run() override
    {
        Socket->SetNonBlocking(true);
        while (bRunning)
        {
            uint32 PendingSize = 0;
            if (Socket->HasPendingData(PendingSize))   // 온 게 있을 때만
            {
                uint8 Buffer[2048];
                int32 Read = 0;
                Socket->Recv(Buffer, sizeof(Buffer), Read);
                // 받은 데이터를 게임 스레드로 안전하게 전달 (동기화 필요 — OS 강의)
            }
            FPlatformProcess::Sleep(0.001f);   // CPU 다 안 쓰게 살짝 양보
        }
        return 0;
    }
};
```

여기서 OS 지식이 연결된다: 수신은 **별도 스레드**에서 하고, 받은 데이터를 게임 스레드로 넘길 때 **동기화(락)** 가 필요하다. 네트워크와 멀티스레드가 만나는 지점이다.

## 6. 흔한 오해

### 오해 1: "논블로킹이면 무조건 빠르다"

논블로킹은 "안 멈춘다"는 거지 "더 빠르다"가 아니다. 잘못 쓰면 데이터 없는데 계속 확인(busy polling)하느라 CPU만 태운다. 그래서 보통 I/O 멀티플렉싱(select/IOCP)과 함께 써서 "준비된 것만" 처리한다.

### 오해 2: "연결마다 스레드 하나씩 주면 되지 않나"

수백 명까진 되지만 수천 명이면 스레드가 수천 개가 된다. 컨텍스트 스위칭 비용과 메모리(스레드마다 스택)로 서버가 무너진다. 그래서 IOCP/epoll로 **소수 스레드 + 비동기**를 쓴다. (OS 강의의 "스레드 많이 만들면 안 되는 이유"와 직결.)

### 오해 3: "select랑 IOCP는 같은 거다"

방향이 반대다. select는 "준비됐는지 내가 물어보는" 모델이고, IOCP는 "완료되면 OS가 알려주는" 비동기 완료 모델이다. IOCP가 대규모에서 훨씬 효율적이다.

### 오해 4: "멀티플렉싱은 멀티스레드다"

다르다. I/O 멀티플렉싱은 **한 스레드로 여러 소켓을 감시**하는 기법이다. 멀티스레드는 여러 스레드를 쓰는 것. 멀티플렉싱은 스레드를 늘리지 않고 동시성을 얻는 방법이라 둘은 별개 개념이다(실무에선 섞어 쓰지만).

## 7. 면접에서 나오면

**Q1. 블로킹과 논블로킹의 차이는?**
→ "블로킹은 데이터가 준비될 때까지 함수가 멈춰서 기다리는 방식이고, 논블로킹은 데이터가 없으면 즉시 리턴해서 다른 일을 계속할 수 있는 방식입니다. 블로킹은 코드가 단순하지만 기다리는 동안 그 스레드가 묶이고, 논블로킹은 안 묶이는 대신 데이터가 왔는지 확인하는 로직이 필요합니다."

**Q2. 서버 하나가 수천 명을 동시에 처리하는 방법은?**
→ "I/O 멀티플렉싱을 씁니다. 소켓 수천 개를 OS에 맡기고 그 중 데이터가 준비된 것만 골라 처리하는 방식으로, 한 스레드로 많은 연결을 감시할 수 있습니다. 리눅스는 epoll, 윈도우는 IOCP를 주로 쓰고, 연결마다 스레드를 주는 방식은 컨텍스트 스위칭 비용 때문에 대규모에선 안 씁니다."

**Q3. IOCP가 뭔가요?**
→ "윈도우의 고성능 비동기 I/O 모델입니다. I/O 요청을 OS에 던져놓고, OS가 작업을 완료하면 완료 통보를 큐에 넣어주면, 소수의 워커 스레드가 그것만 꺼내 처리합니다. select처럼 준비됐는지 매번 물어보는 게 아니라 완료를 통보받는 방식이라, 적은 스레드로 수만 연결을 감당할 수 있습니다."

**Q4. select의 한계는 뭔가요?**
→ "감시할 소켓 목록을 매번 OS에 넘기고 OS가 전부 훑어야 해서, 연결 수가 많아지면 그 훑는 비용 자체가 부담이 됩니다. 그래서 대규모 서버는 리눅스의 epoll이나 윈도우의 IOCP처럼 더 효율적인 모델을 씁니다."

**Q5. I/O 멀티플렉싱과 멀티스레드는 같은 건가요?**
→ "다릅니다. I/O 멀티플렉싱은 한 스레드로 여러 소켓을 동시에 감시하는 기법이고, 멀티스레드는 여러 스레드로 일을 나누는 겁니다. 실무에선 IOCP 같은 멀티플렉싱 위에 워커 스레드 몇 개를 얹어 둘을 함께 쓰지만, 개념적으로는 별개입니다."

면접관이 그 다음에 던지기 좋은 질문: *"받은 바이트를 어떻게 게임 패킷으로 해석하나요? TCP는 메시지 경계가 없다던데?"* → 10강(패킷 설계와 직렬화)에서 다룬다.
