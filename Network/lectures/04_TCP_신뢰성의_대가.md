# 4강 — TCP, 신뢰성의 대가

> **목표:** TCP가 "빠짐없이, 순서대로" 데이터를 도착시키는 원리(연결, 시퀀스/ACK, 재전송)와, 그 신뢰성의 대가가 뭔지 이해한다.
> **선수 지식:** 3강(포트/소켓). 패킷이 유실될 수 있다는 1강 내용.

---

## 1. "보냈는데 안 왔다" 를 누가 책임지나

채팅 기능을 만든다. 플레이어가 "GG"를 친다. 이게 상대한테 안 가면 큰일이다. 거래 시스템이면 더하다 — "골드 1000개 보냄" 메시지가 유실되면 게임 경제가 박살난다.

그런데 1강에서 배웠듯 **네트워크는 기본적으로 못 믿는다.** 패킷은 사라지고, 순서가 뒤바뀌고, 늦게 온다.

```cpp
// 거래 패킷을 보냈다. 그런데 도착했는지 내가 어떻게 알지?
SendPacket(TradeRequest);
// 도착했나? 안 했나? 중간에 사라졌나? ... 모름
```

이걸 게임 코드에서 직접 처리하려면 지옥이다. "보냈는데 답이 없네? 다시 보내야 하나? 근데 사실 도착했고 답만 유실된 거면 두 번 보내지는 거 아냐?" ...

이 모든 걸 **대신 해결해주는 게 TCP**다. TCP는 "내가 책임지고 빠짐없이, 순서대로 갖다줄게"라고 약속하는 전송 계층 프로토콜이다.

---

## 2. TCP의 약속 세 가지

TCP(Transmission Control Protocol)가 보장하는 것:

1. **신뢰성** — 데이터가 반드시 도착한다. 유실되면 다시 보낸다.
2. **순서 보장** — 보낸 순서대로 도착한다. 뒤바뀌면 재정렬한다.
3. **연결 지향** — 통신 전에 먼저 "연결"을 맺는다.

이걸 어떻게 하느냐가 면접의 핵심이다. 하나씩 보자.

---

## 3. 연결 지향 — 3-way handshake

TCP는 데이터를 보내기 **전에** 먼저 양쪽이 "통신 시작하자"고 합의한다. 이걸 **3-way handshake** 라고 한다. 면접 최빈출이다.

```
클라이언트                              서버
   │                                    │
   │ ──────  SYN  ───────────────────→ │  "연결하자" (내 시작 번호 x)
   │                                    │
   │ ←─────  SYN + ACK  ─────────────── │  "좋아, 나도 연결하자" (내 번호 y, 네 x 받음)
   │                                    │
   │ ──────  ACK  ───────────────────→ │  "확인" (네 y 받음)
   │                                    │
   │════════  이제 데이터 전송  ════════│
```

- **SYN** (Synchronize): "연결하자. 내 시퀀스 번호는 x야."
- **SYN + ACK**: "좋아(SYN). 그리고 네 x 잘 받았어(ACK). 내 번호는 y야."
- **ACK** (Acknowledge): "네 y도 잘 받았어. 시작하자."

왜 3번이냐? **양쪽이 서로 "보낼 수 있고 받을 수 있다"는 걸 확인**하려면 최소 3번이 필요하다. 2번이면 서버가 "클라가 내 응답을 받았는지" 확신할 수 없다.

> **핵심 비유:** 전화 거는 거랑 똑같다.
> - "여보세요?" (SYN)
> - "어 들려, 너도 들려?" (SYN+ACK)
> - "응 들려" (ACK)
> → 이제 본론 시작. 서로 잘 들린다는 걸 확인하고 대화를 시작한다.

### 끊을 땐 4-way handshake

연결을 끊을 땐 4번 주고받는다. 양쪽이 각자 "나 이제 그만 보낼게(FIN)"를 따로 말하고 따로 확인받기 때문이다.

```
클라 ── FIN ──→ 서버     "나 다 보냈어"
클라 ←─ ACK ─── 서버     "알았어"
클라 ←─ FIN ─── 서버     "나도 다 보냈어"
클라 ── ACK ──→ 서버     "알았어"  → 종료
```

연결은 양방향이라, 한쪽이 끝나도 반대 방향은 아직 보낼 게 남았을 수 있다. 그래서 각 방향을 따로 닫는다.

---

## 4. 신뢰성과 순서 — 시퀀스 번호와 ACK

TCP는 데이터를 쪼개서 보내는데, 각 조각(세그먼트)에 **시퀀스 번호(Sequence Number)** 를 붙인다. 받는 쪽은 받았다고 **ACK(확인 응답)** 를 보낸다.

```
보내는 쪽                      받는 쪽
  Seq=1 "Hel" ───────────────→ 받음. "Seq=4 줘" (ACK=4)
  Seq=4 "lo " ───────────────→ 받음. "Seq=7 줘" (ACK=7)
  Seq=7 "GG"  ──────X (유실)    ... 안 옴
                              
  (일정 시간 ACK 안 오면)
  Seq=7 "GG"  ───────────────→ 받음. "Seq=9 줘" (ACK=9)  ← 재전송!
```

핵심 동작:

- **유실 감지:** ACK가 일정 시간(타임아웃) 안에 안 오면 "유실됐구나" 판단하고 **재전송**한다.
- **순서 보장:** 받는 쪽이 시퀀스 번호를 보고 **원래 순서로 재정렬**한다. Seq=7이 Seq=4보다 먼저 도착해도, 4를 기다렸다가 순서대로 위로 올려준다.
- **중복 제거:** 같은 시퀀스 번호가 두 번 오면(재전송 때문에) 하나만 쓴다.

이 덕분에 게임 코드는 "보내면 순서대로 다 온다"고 믿고 짜면 된다. 그 아래의 유실·재전송·재정렬은 TCP가 다 처리한다.

---

## 5. 그럼 대가는? — TCP가 느린 이유

여기가 게임 개발자한테 제일 중요하다. TCP의 신뢰성은 **공짜가 아니다.**

### 대가 1: 연결 비용

데이터 한 글자 보내기도 전에 3-way handshake로 **왕복 1.5번**을 먼저 쓴다. 짧은 통신엔 오버헤드.

### 대가 2: 재전송 지연 = 게임에선 치명적

이게 핵심이다. 패킷 하나가 유실되면, TCP는 **그게 도착할 때까지 그 다음 데이터를 위로 안 올려준다.** 순서를 보장해야 하니까.

```
FPS 게임에서 캐릭터 위치를 TCP로 보낸다고 하자:

위치1 도착 ─→ 위치2 유실! ─→ 위치3 도착(했지만 대기) ─→ 위치4 도착(대기)
                  │
                  └ 위치2 재전송될 때까지 위치3,4는 묶여서 못 올라감 (Head-of-Line Blocking)

결과: 위치2 기다리는 동안 캐릭터가 멈췄다가, 한꺼번에 순간이동
```

이걸 **Head-of-Line Blocking(HOL 블로킹)** 이라고 한다. 줄 맨 앞 사람이 막히면 뒤가 다 막히는 현상.

FPS에서 0.1초 전 위치는 **이미 쓸모없다.** 그런데 TCP는 그 낡은 위치가 도착할 때까지 최신 위치를 막아버린다. **"순서 보장"이 오히려 독이 되는 상황**이다.

그래서 실시간 게임은 위치 같은 데이터엔 TCP를 안 쓰고 UDP를 쓴다(5강). 반대로 채팅·거래·로그인처럼 **반드시 도착해야 하고 순서가 중요한** 건 TCP를 쓴다.

## 6. 코드로 체감해보기

언리얼에서 TCP 소켓을 만드는 모양(개념용).

```cpp
// NAME_Stream = TCP. (UDP는 NAME_DGram, 다음 강의)
FSocket* TcpSocket = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)
    ->CreateSocket(NAME_Stream, TEXT("TcpClient"), false);

// 연결 — 이 한 줄이 내부적으로 3-way handshake를 일으킨다
bool bConnected = TcpSocket->Connect(*ServerAddr);
//   ↑ 여기서 SYN → SYN+ACK → ACK 가 오간다. 끝나야 true

// 보내기 — TCP가 알아서 시퀀스 번호 붙이고, ACK 관리하고, 유실 시 재전송
int32 BytesSent = 0;
FString Msg = TEXT("Trade:Gold1000");
TcpSocket->Send((uint8*)TCHAR_TO_UTF8(*Msg), Msg.Len(), BytesSent);

// 게임 코드는 "보냈으니 순서대로 도착하겠지"라고 믿어도 된다
// 단, 그 신뢰성 때문에 유실 시 지연이 생긴다는 걸 알아야 함
```

게임 개발자 입장에서 기억할 것: **TCP를 골랐다는 건 "신뢰성을 위해 지연을 감수하겠다"는 선택**이다. 채팅엔 맞고, 실시간 위치엔 안 맞는다.

## 7. 흔한 오해

### 오해 1: "TCP는 데이터 손실이 절대 없으니 무조건 좋다"

손실이 없게 **보이는** 건 맞지만, 그건 유실된 걸 재전송해서 메우기 때문이다. 그 과정에서 **지연**이 생긴다. 실시간 게임에선 "늦게 온 정확한 데이터"보다 "지금 온 대략적인 데이터"가 나을 때가 많다. 그래서 TCP가 항상 정답은 아니다.

### 오해 2: "TCP로 보내면 받는 쪽에서 보낸 단위 그대로 받는다"

아니다. TCP는 **스트림(byte stream)** 이다. "Hello"랑 "GG"를 따로 두 번 보내도, 받는 쪽에선 "HelloGG"로 합쳐 오거나 "Hel" + "loGG"로 쪼개져 올 수 있다. TCP는 바이트 순서만 보장하지 "메시지 경계"는 보장 안 한다. 이걸 직접 처리해야 한다 — 10강(패킷 설계)에서 다룬다.

### 오해 3: "3-way handshake는 데이터를 3번 보내는 거다"

handshake는 **연결을 맺는 절차**일 뿐, 실제 데이터 전송이 아니다. SYN/ACK는 제어용 신호고, 실제 게임 데이터는 handshake가 끝난 **다음에** 흐른다.

### 오해 4: "TCP는 양쪽이 동시에 연결을 끊는다"

TCP 연결은 양방향이라 각 방향을 따로 닫는다(4-way). 한쪽이 FIN을 보내도 반대 방향은 살아 있어서 데이터를 더 보낼 수 있다. 그래서 "한쪽만 닫힌" 반쪽 연결(half-close) 상태가 존재한다.

## 8. 면접에서 나오면

**Q1. TCP가 뭔가요?**
→ "신뢰성 있는 연결 지향 전송 계층 프로토콜입니다. 데이터가 유실되면 재전송하고, 순서가 뒤바뀌면 재정렬해서, 보낸 데이터가 빠짐없이 순서대로 도착하도록 보장합니다. 채팅이나 거래처럼 정확성이 중요한 통신에 씁니다."

**Q2. 3-way handshake를 설명해보세요.**
→ "TCP가 연결을 맺는 과정입니다. 클라이언트가 SYN을 보내 연결을 요청하고, 서버가 SYN과 ACK로 응답하고, 클라이언트가 다시 ACK를 보내면 연결이 성립합니다. 세 번을 주고받는 이유는 양쪽이 서로 데이터를 보내고 받을 수 있다는 걸 모두 확인하기 위해서입니다."

**Q3. TCP는 어떻게 신뢰성을 보장하나요?**
→ "각 데이터 조각에 시퀀스 번호를 붙이고, 받는 쪽이 ACK로 확인 응답을 보냅니다. 일정 시간 안에 ACK가 안 오면 유실로 판단해 재전송하고, 시퀀스 번호로 순서를 재정렬하며 중복도 제거합니다."

**Q4. TCP의 단점은 뭔가요?**
→ "신뢰성을 위한 오버헤드가 있습니다. 연결을 맺는 handshake 비용이 들고, 무엇보다 패킷이 하나 유실되면 그게 재전송될 때까지 그 뒤 데이터를 못 올려주는 Head-of-Line Blocking이 생깁니다. 실시간 게임에선 이 지연 때문에 캐릭터가 멈췄다 순간이동하는 문제가 생겨서, 위치 같은 데이터엔 UDP를 쓰는 게 보통입니다."

**Q5. 연결을 끊을 때 왜 4-way handshake인가요?**
→ "TCP 연결은 양방향이라 각 방향을 따로 닫아야 하기 때문입니다. 한쪽이 FIN으로 '다 보냈다'고 알리고 상대가 ACK로 답한 뒤, 반대 방향도 똑같이 FIN과 ACK를 주고받습니다. 한 방향이 닫혀도 다른 방향은 데이터를 더 보낼 수 있어서 단계가 하나 더 필요합니다."

**Q6. Head-of-Line Blocking이 뭔가요?**
→ "앞선 패킷 하나가 유실되면, 뒤에 도착한 패킷들이 멀쩡해도 앞 패킷이 재전송돼 순서가 맞춰질 때까지 위로 전달되지 못하고 막히는 현상입니다. TCP가 순서를 보장하기 때문에 생기는데, 실시간성이 중요한 게임에선 이게 큰 문제라 UDP를 고려하게 됩니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 게임은 다 UDP를 쓰나요?"* → 5강(UDP)·6강(선택 기준)에서 다룬다.

## 9. 셀프 체크

- [ ] TCP의 세 가지 보장(신뢰성·순서·연결지향)을 말할 수 있다.
- [ ] 3-way handshake의 SYN/SYN+ACK/ACK 흐름을 그릴 수 있고, 왜 3번인지 설명할 수 있다.
- [ ] 시퀀스 번호와 ACK로 신뢰성·순서를 어떻게 보장하는지 안다.
- [ ] Head-of-Line Blocking이 왜 실시간 게임에 치명적인지 설명할 수 있다.
- [ ] TCP가 "스트림"이라 메시지 경계를 보장 안 한다는 걸 안다.
