# 11강 — HTTP / HTTPS

> **목표:** HTTP의 요청/응답 구조, 메서드, 상태 코드, REST를 이해하고, 게임에서 로그인·랭킹·상점 같은 기능에 왜 커스텀 소켓 대신 HTTP를 쓰는지 안다.
> **선수 지식:** 3강(포트, 80/443), 10강(직렬화). TCP가 신뢰성 있다는 4강 내용.

---

## 1. 로그인은 왜 커스텀 패킷으로 안 짤까

10강에서 직접 패킷을 설계했다. 그럼 로그인도 그렇게 짜면 될까?

```cpp
// 직접 짠다면... 로그인 패킷 타입 만들고, 직렬화하고, 경계 처리하고...
EPacketType::Login, 직렬화, 길이접두사, 핸들러 분기, ...
```

가능은 하다. 하지만 로그인·랭킹·상점·공지사항 같은 건 거의 다 **HTTP**로 짠다. 이유:

- 이미 전 세계가 쓰는 **표준** — 서버 프레임워크, 라이브러리, 도구가 다 있음
- **요청-응답**이 명확 — "로그인 정보 줄게 → 토큰 받기" 한 번이면 끝. 실시간 스트림이 아님
- 웹 서버·CDN·로드밸런서 등 **인프라가 HTTP 기준**으로 다 갖춰져 있음
- 디버깅 쉬움 — 브라우저나 Postman으로 바로 테스트

정리하면 **실시간 게임 플레이는 커스텀 UDP/TCP, 그 외 부가 기능은 HTTP** 가 업계 표준 구도다. 그래서 HTTP를 알아야 한다.

---

## 2. HTTP란 — 요청과 응답

HTTP(HyperText Transfer Protocol)는 **요청(Request)을 보내면 응답(Response)이 오는** 단순한 약속이다. 클라가 묻고 서버가 답한다. 응용 계층(1강) 프로토콜이고, 그 아래는 TCP(신뢰성 필요하니까)로 돈다. 포트는 기본 80(HTTP)/443(HTTPS).

```
클라이언트 ──── 요청(Request) ────→ 서버
클라이언트 ←──── 응답(Response) ──── 서버
```

### 요청의 생김새

```
POST /api/login HTTP/1.1          ← 메서드 + 경로 + 버전
Host: game.example.com            ← 헤더들 (메타정보)
Content-Type: application/json
Content-Length: 42

{"id":"Koo","pw":"1234"}          ← 몸통(Body): 실제 보내는 데이터
```

### 응답의 생김새

```
HTTP/1.1 200 OK                   ← 버전 + 상태 코드
Content-Type: application/json
Content-Length: 55

{"token":"abc123","nickname":"코딩전사"}   ← 몸통: 결과 데이터
```

10강에서 손으로 짠 "헤더 + 몸통" 구조를 HTTP가 텍스트로 표준화해놓은 거라고 보면 된다.

---

## 3. 메서드 — 뭘 하려는 건지

요청 맨 앞의 메서드가 "이 요청의 의도"를 나타낸다. 면접 단골이다.

| 메서드 | 의미 | 게임 예시 |
|--------|------|----------|
| GET | 조회 (가져오기) | 랭킹 조회, 공지 목록 |
| POST | 생성 (새로 만들기) | 로그인, 회원가입, 결제 |
| PUT | 전체 수정 | 프로필 통째로 교체 |
| PATCH | 부분 수정 | 닉네임만 변경 |
| DELETE | 삭제 | 계정 삭제, 친구 삭제 |

핵심 구분: **GET은 데이터를 바꾸지 않는다(조회만).** POST/PUT/DELETE는 서버 상태를 바꾼다. GET 요청은 주소(URL)에 정보를 담고, POST는 보통 몸통(Body)에 담는다. 그래서 비밀번호 같은 건 GET이 아니라 POST로 보낸다(URL에 노출되면 안 되니까).

---

## 4. 상태 코드 — 결과가 어땠는지

응답의 숫자 코드가 결과를 알려준다. 백 자리로 분류한다. 외워두면 면접·디버깅에 둘 다 쓴다.

| 범위 | 의미 | 대표 |
|------|------|------|
| 2xx | 성공 | 200 OK, 201 Created |
| 3xx | 리다이렉트 | 301 이동, 304 안 바뀜 |
| 4xx | **클라 잘못** | 400 잘못된 요청, 401 인증 안 됨, 403 권한 없음, 404 없음, 429 너무 많이 요청 |
| 5xx | **서버 잘못** | 500 서버 에러, 503 서버 과부하 |

게임에서 자주 보는 것:

- **401 Unauthorized:** 토큰 없거나 만료 → 다시 로그인시켜야 함
- **403 Forbidden:** 로그인은 됐는데 권한 없음 (예: 남의 계정 정보 요청)
- **404 Not Found:** 잘못된 API 경로
- **429 Too Many Requests:** 클라가 요청 폭주 → 어뷰징 방어. 클라에서 호출 빈도 조절 필요
- **500/503:** 서버 문제 → 클라가 재시도 로직을 넣어야 함

> **핵심 구분:** 4xx면 **내(클라) 요청이 잘못**된 것, 5xx면 **서버가 잘못**된 것. 이 한 줄이 디버깅 방향을 정한다.

---

## 5. REST — API 설계 스타일

게임 백엔드 API는 보통 **REST** 스타일로 만든다. 핵심 아이디어: **URL은 자원(명사), 메서드는 동작(동사).**

```
GET    /api/players/7/inventory      → 7번 플레이어의 인벤토리 조회
POST   /api/players/7/items          → 7번 플레이어에게 아이템 추가
DELETE /api/players/7/items/55       → 55번 아이템 삭제
GET    /api/rankings?season=3        → 시즌3 랭킹 조회
```

URL만 봐도 "무엇을"이 보이고, 메서드로 "어떻게"가 정해진다. `/getPlayerInventory?id=7` 처럼 URL에 동사를 넣는 건 비REST. 면접에서 "REST가 뭐냐" 물으면 "자원을 URL로 표현하고 HTTP 메서드로 행위를 표현하는 API 설계 원칙"이라고 답하면 된다.

## 6. 코드로 — 언리얼 HTTP 요청

언리얼은 `FHttpModule`로 HTTP를 깔끔하게 지원한다. 클라 개발자가 실제로 자주 쓴다.

```cpp
#include "HttpModule.h"
#include "Interfaces/IHttpRequest.h"
#include "Interfaces/IHttpResponse.h"

void ULoginSubsystem::RequestLogin(const FString& Id, const FString& Pw)
{
    // 1) 요청 객체 생성
    TSharedRef<IHttpRequest> Request = FHttpModule::Get().CreateRequest();

    Request->SetURL(TEXT("https://game.example.com/api/login"));
    Request->SetVerb(TEXT("POST"));                    // 메서드
    Request->SetHeader(TEXT("Content-Type"), TEXT("application/json"));

    // 2) 몸통(JSON) 채우기
    FString Body = FString::Printf(TEXT("{\"id\":\"%s\",\"pw\":\"%s\"}"), *Id, *Pw);
    Request->SetContentAsString(Body);

    // 3) 응답 콜백 등록 — HTTP는 비동기다 (블로킹 X, 게임 멈추면 안 되니까)
    Request->OnProcessRequestComplete().BindUObject(
        this, &ULoginSubsystem::OnLoginResponse);

    // 4) 전송
    Request->ProcessRequest();
}

void ULoginSubsystem::OnLoginResponse(
    FHttpRequestPtr Req, FHttpResponsePtr Resp, bool bSuccess)
{
    if (!bSuccess || !Resp.IsValid())
    {
        // 네트워크 실패 (서버 다운, 끊김 등)
        return;
    }

    int32 Code = Resp->GetResponseCode();   // 상태 코드
    if (Code == 200)
    {
        FString Json = Resp->GetContentAsString();   // {"token":"..."}
        // 토큰 파싱해서 저장
    }
    else if (Code == 401)
    {
        // 인증 실패 → "아이디/비번 확인" 안내
    }
    else if (Code >= 500)
    {
        // 서버 문제 → 잠시 후 재시도
    }
}
```

주목할 점: **HTTP 요청은 비동기**다. 응답을 기다리며 게임을 멈추면(블로킹) 화면이 얼어붙으니, 콜백으로 처리한다(9강의 논블로킹/비동기와 연결). 그리고 상태 코드로 분기하는 게 실무의 핵심이다.

## 7. HTTPS — HTTP에 자물쇠

HTTP는 **평문**이다. 중간에서 누가 가로채면 아이디·비번이 그대로 보인다. 그래서 실제 서비스는 전부 **HTTPS**(HTTP + TLS)를 쓴다. HTTP 메시지를 TLS로 암호화해서 보내는 것. 포트는 443.

```
HTTP:  {"pw":"1234"}          ← 중간에서 그대로 읽힘 (위험)
HTTPS: a8$#kf9@x...           ← 암호화돼서 못 읽음 (안전)
```

TLS가 어떻게 암호화하는지, 어떻게 "이 서버가 진짜 그 서버"임을 증명하는지는 **13강(TLS와 게임 보안)** 에서 자세히 다룬다. 여기선 "HTTPS = HTTP + 암호화, 로그인·결제는 무조건 HTTPS"만 기억하면 된다.

## 8. 흔한 오해

### 오해 1: "게임은 다 커스텀 패킷으로 통신한다"

실시간 플레이(위치/입력)는 커스텀 UDP/TCP가 맞지만, 로그인·랭킹·상점·공지·결제 같은 부가 기능은 거의 HTTP다. 표준이라 인프라와 도구가 다 갖춰져 있어서 굳이 직접 안 짠다.

### 오해 2: "GET이랑 POST는 그냥 취향 차이다"

아니다. GET은 조회(서버 상태 안 바꿈)이고 정보가 URL에 노출된다. POST는 생성/변경이고 몸통에 데이터를 담는다. 비밀번호를 GET으로 보내면 URL과 로그에 남아 위험하다. 의미가 정해진 규약이다.

### 오해 3: "HTTP는 상태를 기억한다"

HTTP는 기본적으로 **무상태(stateless)** 다. 요청 하나하나가 독립적이라 서버가 "방금 그 사람"을 기억 안 한다. 그래서 로그인 후 받은 **토큰**을 매 요청 헤더에 실어 "나 아까 로그인한 사람"임을 증명한다. 이게 401이 나는 흐름과 연결된다.

### 오해 4: "HTTPS면 완전히 안전하다"

HTTPS는 **전송 구간**을 암호화할 뿐이다. 서버에 저장된 데이터가 털리거나, 클라가 변조된 요청을 보내는 건 못 막는다. 그래서 서버는 항상 클라 요청을 검증해야 한다(13강의 서버 권한). HTTPS는 보안의 일부지 전부가 아니다.

## 9. 면접에서 나오면

**Q1. HTTP가 뭔가요?**
→ "클라이언트가 요청을 보내면 서버가 응답하는 응용 계층 프로토콜입니다. 요청에는 메서드와 경로, 헤더, 몸통이 있고, 응답에는 상태 코드와 헤더, 몸통이 있습니다. 신뢰성이 필요해서 아래는 TCP로 동작하고, 기본 포트는 80번, HTTPS는 443번입니다."

**Q2. GET과 POST의 차이는?**
→ "GET은 데이터를 조회하는 메서드로 서버 상태를 바꾸지 않고 정보를 URL에 담습니다. POST는 새로운 데이터를 생성하거나 서버 상태를 바꾸는 메서드로 데이터를 몸통에 담습니다. 그래서 비밀번호 같은 민감한 정보는 URL에 노출되는 GET이 아니라 POST로 보냅니다."

**Q3. HTTP 상태 코드를 분류해서 설명해보세요.**
→ "백 자리로 나뉩니다. 2xx는 성공, 3xx는 리다이렉트, 4xx는 클라이언트 잘못, 5xx는 서버 잘못입니다. 게임에선 인증 실패인 401, 권한 없음인 403, 요청 폭주인 429, 서버 에러인 500을 자주 보는데, 4xx면 요청을 고쳐야 하고 5xx면 재시도 로직으로 대응합니다."

**Q4. REST가 뭔가요?**
→ "URL로 자원을 표현하고 HTTP 메서드로 그 자원에 대한 행위를 표현하는 API 설계 원칙입니다. 예를 들어 플레이어 인벤토리 조회는 GET /players/7/inventory, 아이템 삭제는 DELETE /players/7/items/55처럼 URL은 명사, 메서드는 동사로 설계합니다."

**Q5. 게임에서 실시간 통신과 HTTP를 어떻게 나눠 쓰나요?**
→ "캐릭터 위치나 입력처럼 실시간성이 중요한 건 커스텀 UDP나 TCP로 처리하고, 로그인·랭킹·상점·공지처럼 요청-응답으로 충분하고 정확성이 중요한 부가 기능은 HTTP로 처리합니다. HTTP는 표준이라 서버 인프라와 도구가 잘 갖춰져 있어서 개발과 운영이 편합니다."

**Q6. HTTP는 무상태라는데 로그인 상태는 어떻게 유지하나요?**
→ "HTTP는 요청마다 독립적이라 서버가 이전 요청을 기억하지 않습니다. 그래서 로그인하면 서버가 토큰을 발급하고, 클라이언트가 이후 요청마다 그 토큰을 헤더에 실어 보내 자신을 증명합니다. 토큰이 없거나 만료되면 401이 돌아옵니다."

면접관이 그 다음에 던지기 좋은 질문: *"그 서버 주소를 IP가 아니라 도메인으로 쓰던데, 그건 어떻게 IP로 바뀌나요?"* → 12강(DNS)에서 다룬다.

## 10. 셀프 체크

- [ ] 게임에서 HTTP를 쓰는 기능과 커스텀 소켓을 쓰는 기능을 구분할 수 있다.
- [ ] HTTP 요청/응답 구조(메서드·경로·헤더·몸통 / 상태코드)를 그릴 수 있다.
- [ ] GET과 POST의 차이를 명확히 안다.
- [ ] 상태 코드 4xx(클라 잘못)와 5xx(서버 잘못)를 구분하고 대표 코드 몇 개를 안다.
- [ ] REST의 핵심(자원=URL, 행위=메서드)을 말할 수 있다.
- [ ] HTTP가 무상태라 토큰으로 인증을 유지한다는 걸 안다.
