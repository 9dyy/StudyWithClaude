# 8강 — 소켓 프로그래밍 기초

> **목표:** 소켓으로 연결을 맺는 함수들(socket/bind/listen/accept/connect/send/recv)이 각각 뭘 하는지, 서버와 클라이언트의 흐름이 어떻게 다른지 코드로 읽고 이해한다.
> **선수 지식:** 3강(포트/소켓), 4강(TCP handshake). 소켓이 IP+포트 끝점이라는 것.
> **깊이:** 클라 면접 선까지. 직접 고성능 서버를 짜는 게 아니라 "어떤 함수가 무슨 일을 하나"를 읽고 설명할 수 있는 수준.

---

## 1. 엔진이 다 해주는데 이걸 왜 배우나

언리얼 클라 개발자는 `socket()`을 직접 부를 일이 거의 없다. `Replication`이 다 해준다. 그런데 면접관은 묻는다.

> "소켓 통신 흐름을 설명해보세요. 서버랑 클라이언트가 각각 어떤 함수를 호출하나요?"

이걸 못 답하면 "네트워크 안다"고 말하기 어렵다. 엔진이 가려주는 그 아래에서 정확히 무슨 함수가 어떤 순서로 도는지 — 이 강의는 그 골격만 짚는다. 직접 서버를 구현하는 게 목적이 아니라, **흐름을 그릴 수 있는 것**이 목표다.

---

## 2. 소켓 API의 뿌리 — Berkeley Socket과 Winsock

소켓 프로그래밍의 표준은 1980년대 유닉스의 **Berkeley Socket(BSD 소켓)** 이다. 지금도 거의 모든 OS가 이 모양을 따른다.

- **리눅스/맥:** BSD 소켓 거의 그대로
- **윈도우:** **Winsock**(Windows Sockets). BSD와 거의 같지만 `WSAStartup()`으로 초기화하고 `closesocket()`으로 닫는 등 약간 다름

게임 클라가 주로 도는 윈도우는 Winsock을 쓴다. 언리얼의 `FSocket`은 이걸 플랫폼별로 감싼 추상화다. 우리는 `FSocket`만 보면 되지만, 그 아래는 결국 이 함수들이다.

---

## 3. 함수 7개 — 이게 전부다

소켓 통신의 핵심 함수는 7개다. 각각 한 줄로:

| 함수 | 하는 일 | 누가 |
|------|---------|------|
| `socket()` | 소켓 하나 생성 | 서버·클라 둘 다 |
| `bind()` | 소켓에 IP·포트 묶기 | 서버 (듣는 주소 고정) |
| `listen()` | "연결 받을 준비 됨" 표시 | 서버 |
| `accept()` | 들어온 연결 수락, 연결 소켓 반환 | 서버 |
| `connect()` | 서버로 연결 시도 (handshake) | 클라 |
| `send()` / `recv()` | 데이터 보내기 / 받기 | 서버·클라 둘 다 |
| `close()` | 소켓 닫기 (자원 반납) | 서버·클라 둘 다 |

서버와 클라가 호출하는 순서가 다르다. 이게 핵심이다.

---

## 4. 흐름도 — 서버와 클라이언트

```
       서버                                클라이언트
        │                                     │
   socket()   소켓 생성                    socket()   소켓 생성
        │                                     │
   bind()     "나 7777번 포트 쓸게"            │
        │                                     │
   listen()   "연결 받을 준비 됨"              │
        │                                     │
   accept()   ←──── 연결 대기 ────       connect()   "연결하자"
        │     ← ─ ─ 3-way handshake ─ ─ →     │   (SYN/SYN+ACK/ACK)
   (연결 소켓                                  │
    하나 생김) ────── 연결 성립 ──────────────  │
        │                                     │
   recv()/send() ←──── 데이터 교환 ────→  send()/recv()
        │                                     │
   close()    연결 종료                     close()
```

핵심 포인트:

- **서버는 bind → listen → accept** 를 거친다. "내 주소를 정하고, 받을 준비를 하고, 들어오면 수락"
- **클라는 connect** 하나로 끝. "정해진 서버 주소로 연결 시도"
- `accept()`가 반환하는 건 **새 연결 소켓**이다. 원래 듣던 소켓(listen 소켓)은 계속 새 연결을 받고, 실제 통신은 accept가 만들어준 연결 소켓으로 한다. 그래서 서버가 여러 클라를 동시에 받을 수 있다(3강의 4-tuple 기억).

---

## 5. 코드로 — 클라이언트 (언리얼 FSocket)

클라가 제일 단순하다. `socket → connect → send/recv → close`.

```cpp
ISocketSubsystem* SocketSub = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM);

// 1) socket() — TCP 소켓 생성
FSocket* Socket = SocketSub->CreateSocket(NAME_Stream, TEXT("Client"), false);

// 2) 서버 주소 구성 (IP + 포트)
TSharedRef<FInternetAddr> ServerAddr = SocketSub->CreateInternetAddr();
bool bValid;
ServerAddr->SetIp(TEXT("203.0.113.10"), bValid);
ServerAddr->SetPort(7777);

// 3) connect() — 내부적으로 3-way handshake 발생
if (Socket->Connect(*ServerAddr))
{
    // 4) send() — 데이터 보내기
    FString Msg = TEXT("Login:Koo");
    int32 Sent = 0;
    Socket->Send((uint8*)TCHAR_TO_UTF8(*Msg), Msg.Len(), Sent);

    // 5) recv() — 응답 받기
    uint8 Buffer[1024];
    int32 Read = 0;
    if (Socket->Recv(Buffer, sizeof(Buffer), Read))
    {
        // 받은 데이터 처리
    }
}

// 6) close() — 자원 반납 (3강에서 강조한 것)
Socket->Close();
SocketSub->DestroySocket(Socket);
```

## 6. 코드로 — 서버 (개념용 골격)

서버는 `socket → bind → listen → accept → recv/send → close`. 클라 개발자는 직접 짤 일이 드물지만, 흐름은 읽을 줄 알아야 한다.

```cpp
ISocketSubsystem* SocketSub = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM);

// 1) socket()
FSocket* ListenSocket = SocketSub->CreateSocket(NAME_Stream, TEXT("Server"), false);

// 2) bind() — "나 7777번 포트로 들을게"
TSharedRef<FInternetAddr> BindAddr = SocketSub->CreateInternetAddr();
BindAddr->SetAnyAddress();      // 모든 인터페이스에서
BindAddr->SetPort(7777);
ListenSocket->Bind(*BindAddr);

// 3) listen() — 연결 대기열 준비 (인자 = 대기 큐 크기)
ListenSocket->Listen(8);

// 4) accept() — 들어온 연결을 수락, "연결 소켓"을 새로 반환
bool bPending = false;
if (ListenSocket->HasPendingConnection(bPending) && bPending)
{
    FSocket* ClientSocket = ListenSocket->Accept(TEXT("ClientConn"));
    //       ↑ 이 소켓으로 이 클라와 통신. ListenSocket은 계속 새 연결을 받음

    // 5) recv()/send() — ClientSocket으로 데이터 교환
    uint8 Buffer[1024];
    int32 Read = 0;
    ClientSocket->Recv(Buffer, sizeof(Buffer), Read);
    // ... 처리 후 응답 send ...

    // 6) close()
    ClientSocket->Close();
    SocketSub->DestroySocket(ClientSocket);
}
```

**여기서 면접용 포인트:** listen 소켓과 연결 소켓은 **다른 소켓**이다. listen 소켓은 "문 앞에서 손님 받는 직원"이고, accept가 만든 연결 소켓은 "그 손님 전담 직원"이다. 손님(클라)마다 전담 소켓이 생기니 동시에 여럿을 처리할 수 있다.

---

## 7. 그런데 문제 — 손님 한 명 받는 동안 다른 손님은?

위 서버 코드엔 함정이 있다. `accept()`로 한 명을 받아 `recv()`로 그 사람 데이터를 기다리는 동안, **다른 클라는 접속을 못 한다.** `recv()`가 데이터 올 때까지 멈춰 있기(블로킹) 때문이다.

손님 100명을 동시에 받으려면? 이게 다음 강의(9강)의 주제다. 미리 한 줄로:

- 블로킹을 안 쓰거나(논블로킹)
- 한 스레드로 여러 소켓을 감시하거나(`select`, IOCP)
- 연결마다 스레드를 주거나

게임 서버가 수천 명을 받는 비밀이 거기 있다. 이 강의는 "함수 흐름"까지가 목표이고, 동시 처리는 9강에서 본다.

## 8. 흔한 오해

### 오해 1: "서버랑 클라가 같은 함수를 똑같이 호출한다"

다르다. 서버는 `bind → listen → accept`로 "받는 쪽" 준비를 하고, 클라는 `connect`로 "거는 쪽" 역할을 한다. `socket`, `send`, `recv`, `close`는 공통이지만 연결을 맺는 과정이 비대칭이다.

### 오해 2: "accept()가 반환하는 소켓이 원래 listen 소켓이다"

아니다. `accept()`는 **새 연결 전용 소켓**을 만들어 반환한다. listen 소켓은 그대로 두고 계속 새 연결을 받는다. 둘을 헷갈리면 "서버가 어떻게 여러 명을 받나"를 설명 못 한다.

### 오해 3: "bind는 클라이언트도 꼭 해야 한다"

클라는 보통 `bind`를 명시적으로 안 한다. `connect`할 때 OS가 알아서 빈 포트를 하나 골라 붙여준다(임시 포트, ephemeral port). 서버만 "정해진 포트"가 필요해서 `bind`를 명시한다.

### 오해 4: "UDP도 listen/accept를 한다"

UDP는 연결이 없으니 `listen`/`accept`/`connect`가 없다. `socket → bind`(서버) 후 바로 `sendto`/`recvfrom`으로 주고받는다. listen/accept는 연결 지향인 TCP만의 절차다.

## 9. 면접에서 나오면

**Q1. TCP 소켓 통신의 흐름을 설명해보세요.**
→ "서버는 socket으로 소켓을 만들고, bind로 포트를 묶고, listen으로 연결 받을 준비를 한 뒤 accept로 들어온 연결을 수락합니다. 클라이언트는 socket을 만들고 connect로 서버에 연결하는데, 이때 3-way handshake가 일어납니다. 연결이 맺어지면 양쪽이 send와 recv로 데이터를 주고받고, 끝나면 close로 닫습니다."

**Q2. accept()는 뭘 반환하나요?**
→ "들어온 연결을 위한 새 소켓을 반환합니다. 원래 listen하던 소켓은 계속 새 연결을 받고, accept가 만든 연결 소켓으로 그 클라이언트와 실제 통신을 합니다. 그래서 서버가 여러 클라이언트를 동시에 처리할 수 있습니다."

**Q3. bind는 왜 서버만 하나요?**
→ "서버는 클라이언트가 찾아올 수 있도록 정해진 포트에서 기다려야 하기 때문에 bind로 포트를 고정합니다. 클라이언트는 자기 포트가 뭐든 상관없어서, connect할 때 OS가 임시 포트를 자동으로 할당해줍니다."

**Q4. listen 소켓과 연결 소켓의 차이는?**
→ "listen 소켓은 새 연결 요청을 받는 전용 소켓이고, accept가 반환하는 연결 소켓은 특정 클라이언트와 데이터를 주고받는 소켓입니다. 문 앞에서 손님을 맞는 직원과 손님별 전담 직원의 차이로 보면 됩니다."

**Q5. Berkeley 소켓과 Winsock의 차이는?**
→ "둘 다 거의 같은 소켓 API인데, Berkeley 소켓은 유닉스 계열 표준이고 Winsock은 윈도우 버전입니다. Winsock은 WSAStartup으로 초기화하고 closesocket으로 닫는 등 세부가 조금 다릅니다. 언리얼의 FSocket이 이런 플랫폼 차이를 감싸줍니다."

면접관이 그 다음에 던지기 좋은 질문: *"서버가 recv에서 멈춰 있으면 다른 클라는 어떻게 받나요?"* → 9강(블로킹/논블로킹, I/O 멀티플렉싱)에서 다룬다.

## 10. 셀프 체크

- [ ] 소켓 함수 7개의 역할을 한 줄씩 말할 수 있다.
- [ ] 서버 흐름(socket→bind→listen→accept)과 클라 흐름(socket→connect)을 그릴 수 있다.
- [ ] accept가 새 연결 소켓을 반환한다는 걸, 그게 왜 중요한지와 함께 안다.
- [ ] 클라는 보통 bind를 안 한다는 걸(임시 포트) 안다.
- [ ] UDP엔 listen/accept/connect가 없다는 걸 안다.
