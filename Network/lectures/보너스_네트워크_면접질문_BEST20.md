# 보너스 — 클라 개발자가 받는 네트워크 면접 질문 BEST 20

> **목표:** 본강 15강에서 면접에 가장 자주 나오는 질문 20개를 모아, 외워서 말할 수 있는 답변 + "면접관이 그 다음에 던지는 질문"까지 정리한다.
> **선수 지식:** 본강 1~15강. 이건 복습/실전용이다.
> **사용법:** 답을 가리고 질문만 보며 입으로 말해보라. 막히면 해당 강의로 돌아간다.

---

## 쓰는 법

- 답변은 **실제 면접에서 입으로 말하는 톤**이다(존댓말). 토씨까지 외우지 말고 **키워드**(굵게 표시 같은 핵심어)를 중심으로 자기 말로 풀어라.
- 각 질문 끝의 `↪ 꼬리질문`은 면접관이 이어서 던지기 쉬운 것. 거기까지 답할 수 있으면 그 주제는 합격권이다.
- 질문 옆 `[N강]`은 출처 강의.

## Part A. 전송 계층 (가장 많이 나옴)

### Q1. TCP와 UDP의 차이는? [4·5강]
TCP는 연결 지향이고 신뢰성과 순서를 보장합니다. handshake로 연결을 맺고, 시퀀스 번호와 ACK로 유실 시 재전송하며 순서를 맞춥니다. UDP는 비연결형이고 그런 보장이 없는 대신 헤더가 가볍고 빠릅니다. 정확성이 중요하면 TCP, 실시간성이 중요하면 UDP를 씁니다.
↪ 꼬리질문: "그럼 게임은 뭘 쓰나요?" → Q2

### Q2. 게임에서 TCP와 UDP를 어떻게 나눠 쓰나요? [6강]
데이터 성격에 따라 둘 다 씁니다. 로그인·거래·채팅처럼 반드시 도착해야 하는 건 TCP, 캐릭터 위치나 입력처럼 실시간성이 중요하고 유실돼도 다음 패킷이 메우는 건 UDP입니다. 보통 한 게임이 두 프로토콜을 동시에 운용합니다.
↪ 꼬리질문: "위치 데이터를 TCP로 보내면 왜 안 되나요?" → Q3

### Q3. 실시간 게임에 TCP가 부적합한 이유는? [4강]
Head-of-Line Blocking 때문입니다. TCP는 순서를 보장해서, 앞선 패킷 하나가 유실되면 그게 재전송될 때까지 뒤에 도착한 멀쩡한 패킷들도 막힙니다. FPS에서는 이미 지난 위치를 기다리느라 캐릭터가 멈췄다 순간이동하는 문제가 생겨서, 위치 같은 데이터엔 UDP를 씁니다.
↪ 꼬리질문: "그럼 UDP인데 꼭 도착해야 하는 데이터는요?" → Q4

### Q4. UDP인데 신뢰성이 필요하면? (신뢰성 UDP) [5·6강]
애플리케이션 레벨에서 신뢰성을 선택적으로 구현합니다. 중요한 패킷에만 시퀀스 번호와 ACK, 재전송을 붙여서, 위치 같은 데이터는 막힘 없이 흐르게 두고 사망 처리 같은 중요한 이벤트만 보장합니다. 언리얼도 RPC에 Reliable/Unreliable 플래그로 이걸 제공합니다.
↪ 꼬리질문: "TCP랑 뭐가 다른가요?" → "TCP는 전부 순서 보장이라 HOL 블로킹이 걸리지만, 신뢰성 UDP는 골라서 보장해서 안 걸립니다."

### Q5. 3-way handshake를 설명해보세요. [4강]
TCP가 연결을 맺는 과정입니다. 클라이언트가 SYN을 보내 연결을 요청하고, 서버가 SYN과 ACK로 응답하고, 클라이언트가 다시 ACK를 보내면 연결됩니다. 세 번인 이유는 양쪽이 서로 보내고 받을 수 있다는 걸 모두 확인하기 위해서입니다.
↪ 꼬리질문: "끊을 땐 왜 4-way인가요?" → "연결이 양방향이라 각 방향을 따로 닫기 때문입니다."

### Q6. TCP의 흐름 제어와 혼잡 제어 차이는? [7강]
둘 다 전송 속도를 조절하지만 대상이 다릅니다. 흐름 제어는 받는 쪽 버퍼가 넘치지 않게 상대를 배려하는 거고, 혼잡 제어는 중간 네트워크가 마비되지 않게 전체를 배려하는 겁니다. TCP는 패킷 유실을 혼잡 신호로 보고 속도를 줄입니다.
↪ 꼬리질문: "Nagle 알고리즘은 들어봤나요?" → Q7

### Q7. Nagle 알고리즘이 뭐고 게임에서 왜 끄나요? [7강]
작은 패킷을 모아서 한 번에 보내 대역폭을 아끼는 TCP 최적화입니다. 그런데 게임은 키 입력 같은 작은 패킷을 즉시 보내야 반응성이 좋아서, TCP_NODELAY 옵션으로 Nagle을 끕니다. 대역폭 효율을 약간 포기하고 지연을 없애는 선택입니다.

## Part B. 네트워크·기초

### Q8. OSI 7계층과 TCP/IP 모델 [1강]
OSI는 통신을 역할별로 7개 층으로 나눈 참조 모델이고, TCP/IP는 실제 인터넷이 동작하는 4계층 모델입니다. 실무에서 가장 중요한 건 IP로 목적지 컴퓨터를 찾는 네트워크 계층과, TCP·UDP로 어느 프로그램에 줄지 정하는 전송 계층입니다.
↪ 꼬리질문: "캡슐화가 뭔가요?" → "데이터가 하위 계층으로 내려갈 때 각 계층이 헤더를 앞에 붙이는 과정입니다."

### Q9. IP와 포트와 소켓의 관계 [2·3강]
IP는 어느 컴퓨터, 포트는 그 안의 어느 프로그램을 가리키고, 이 둘을 합친 통신 끝점이 소켓입니다. 아파트로 치면 IP가 동, 포트가 호수, 소켓이 그 집 현관문입니다.
↪ 꼬리질문: "서버 하나가 어떻게 수천 명을 받나요?" → Q10

### Q10. 서버 하나가 수천 명을 동시에 처리하는 법 [3·9강]
연결은 출발지 IP·포트와 목적지 IP·포트, 네 값의 조합으로 구분되기 때문에 서버 포트가 같아도 클라마다 연결이 고유합니다. 그리고 I/O 멀티플렉싱으로, 소켓 수천 개 중 데이터가 준비된 것만 골라 처리합니다. 윈도우는 IOCP, 리눅스는 epoll을 씁니다.
↪ 꼬리질문: "연결마다 스레드를 주면 안 되나요?" → "수천 개면 컨텍스트 스위칭 비용으로 서버가 무너져서, 소수 스레드와 비동기로 처리합니다."

### Q11. 공인 IP, 사설 IP, NAT [2강]
공인 IP는 인터넷 전체에서 유일한 주소, 사설 IP는 내부망에서만 쓰는 주소입니다. 집 안 기기들은 사설 IP를 쓰고, 외부로 나갈 때 공유기가 NAT로 공인 IP로 변환합니다. 그래서 서로 다른 집에 같은 사설 IP가 있을 수 있습니다.
↪ 꼬리질문: "P2P 게임에서 왜 문제가 되나요?" → "양쪽이 NAT 뒤에 있어 직접 연결이 안 돼서, 중앙 서버를 두거나 NAT 홀 펀칭을 씁니다."

### Q12. DNS 동작 과정 [12강]
도메인을 IP로 변환하는 시스템입니다. 로컬 DNS에 묻고, 없으면 루트 DNS에서 .com 담당을 찾고, TLD 서버에서 해당 도메인의 권한 네임서버를 찾고, 그 서버가 최종 IP를 응답합니다. 결과는 TTL 동안 캐싱됩니다.
↪ 꼬리질문: "게임이 IP 대신 도메인을 쓰는 이유는?" → "서버 IP가 바뀌어도 클라 수정 없이 매핑만 갱신하면 되기 때문입니다."

## Part C. 소켓·패킷

### Q13. TCP 소켓 통신 흐름 [8강]
서버는 socket, bind, listen, accept 순으로 연결을 받을 준비를 하고, 클라이언트는 socket 후 connect로 연결합니다. 이때 3-way handshake가 일어나고, 연결되면 양쪽이 send와 recv로 주고받다가 close로 닫습니다.
↪ 꼬리질문: "accept가 뭘 반환하나요?" → "해당 연결 전용 소켓을 새로 반환합니다. listen 소켓은 계속 새 연결을 받습니다."

### Q14. TCP 메시지 경계 문제와 해결 [10강]
TCP는 바이트 스트림이라 보낸 단위와 받는 단위가 일치하지 않습니다. 두 번 보낸 게 합쳐 오거나 한 번 보낸 게 쪼개져 옵니다. 그래서 패킷 앞에 길이를 붙이는 길이 접두사 방식으로, 버퍼에 쌓아두고 길이만큼 모이면 잘라 처리합니다.
↪ 꼬리질문: "UDP도 그런가요?" → "UDP는 데이터그램 단위라 경계는 유지되지만 유실·순서를 직접 처리해야 합니다."

### Q15. 블로킹과 논블로킹 [9강]
블로킹은 데이터가 올 때까지 함수가 멈추는 거고, 논블로킹은 없으면 즉시 리턴해 다른 일을 계속하는 겁니다. 블로킹은 단순하지만 스레드가 묶이고, 논블로킹은 멀티플렉싱과 함께 써서 한 스레드로 많은 연결을 처리할 수 있습니다.
↪ 꼬리질문: "IOCP와 select 차이는?" → "select는 준비됐는지 물어보는 모델이고, IOCP는 완료되면 OS가 통보하는 비동기 모델이라 대규모에 유리합니다."

## Part D. 보안

### Q16. 대칭키와 비대칭키, TLS [13강]
대칭키는 같은 키로 암복호화해 빠르지만 키 공유가 어렵고, 비대칭키는 공개키·개인키로 키 공유가 안전하지만 느립니다. TLS는 비대칭으로 대칭키를 안전하게 교환한 뒤, 이후 통신은 빠른 대칭키로 암호화해 둘의 장점을 합칩니다.
↪ 꼬리질문: "서버가 진짜인지 어떻게 믿나요?" → "CA가 서명한 인증서로 서버 신원을 검증합니다."

### Q17. 게임에서 치팅을 어떻게 막나요? [13강]
두 축입니다. 전송 구간은 TLS로 암호화해 도청·변조를 막고, 무엇보다 클라이언트를 신뢰하지 않습니다. 데미지나 재화 같은 중요한 판정은 클라가 보낸 값을 그대로 쓰지 않고 서버가 사거리·쿨다운·스탯을 직접 검증해 계산합니다. 클라는 의도만 보냅니다.
↪ 꼬리질문: "HTTPS만 쓰면 안 되나요?" → "HTTPS는 전송만 보호하지, 클라가 조작된 값을 정상 암호화해 보내는 건 못 막아서 서버 검증이 따로 필요합니다."

## Part E. 게임 네트워킹 (언리얼)

### Q18. 언리얼 Replication과 RPC 차이 [14강]
Replication은 서버 변수의 상태를 클라로 자동 동기화하는 거고(단방향), RPC는 특정 함수를 한 번 원격 실행하는 겁니다. 현재 HP가 얼마인지는 Replication, 방금 폭발이 일어났다는 일회성 이벤트는 Multicast RPC로 처리합니다.
↪ 꼬리질문: "RPC 세 종류는?" → "Server는 클라→서버, Client는 서버→특정 클라, Multicast는 서버→전체입니다."

### Q19. 클라이언트 예측과 서버 보정 [15강]
서버 권한 구조에선 입력이 핑만큼 늦으니, 클라가 입력 결과를 미리 예측해 즉시 보여주고 동시에 서버로 검증을 보냅니다. 예측이 틀리면 서버 확정 값으로 보정하는데, 클라가 보낸 입력들을 기억했다가 다시 적용해 부드럽게 따라잡습니다. 덕분에 핑이 있어도 즉각 반응합니다.
↪ 꼬리질문: "예측하면 서버 권한이 깨지지 않나요?" → "예측은 화면 표현일 뿐, 진실과 판정 권한은 서버에 남아 있어 틀리면 보정됩니다."

### Q20. FPS 지연 보상(lag compensation) [15강]
핑 때문에 맞췄는데 안 맞는 문제를 줄이는 기법입니다. 서버가 플레이어 위치 히스토리를 저장해뒀다가, 누가 쏜 패킷이 오면 그 사람이 쏜 시점으로 시간을 되감아 그때 적 위치로 명중을 판정합니다. 핑이 높아도 조준한 대로 맞게 해주는 대신, 맞은 쪽은 엄폐물 뒤에서 맞는 트레이드오프가 있습니다.
↪ 꼬리질문: "내 캐릭터랑 남의 캐릭터를 똑같이 처리하나요?" → "내 캐릭터는 예측, 남의 캐릭터는 받은 위치 사이를 보간으로 부드럽게 처리합니다."

## 면접 직전 30초 암기 카드

- TCP=신뢰성·순서·연결(handshake), UDP=빠름·무보장. 게임은 **둘 다**.
- 실시간에 TCP 안 쓰는 이유 = **HOL 블로킹**. 해법 = **신뢰성 UDP**(골라서 보장).
- IP=컴퓨터, 포트=프로그램, 소켓=IP+포트. 연결은 **4-tuple**로 구분.
- 대량 동시 접속 = **I/O 멀티플렉싱**(IOCP/epoll), 스레드 남발 X.
- TCP는 **스트림** → 길이 접두사로 경계 처리.
- 보안 = **TLS(전송 암호화) + 서버 검증(클라 믿지 마라)**, 두 축.
- 언리얼 = **서버 권한 + Replication(상태) + RPC(이벤트)**.
- 핑 숨기기 = **클라 예측 + 서버 보정 + 보간 + 지연 보상**.
