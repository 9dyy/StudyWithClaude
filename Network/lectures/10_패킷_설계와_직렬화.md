# 10강 — 패킷 설계와 직렬화

> **목표:** 게임 데이터를 바이트로 만드는 직렬화, 그리고 TCP가 메시지 경계를 보장 안 해서 생기는 문제(부분 수신·합쳐짐)와 그 해결법을 이해한다.
> **선수 지식:** 4강(TCP는 스트림), 8강(send/recv). 5강의 데이터그램 개념.

---

## 1. "분명 한 번에 보냈는데 반만 왔다"

채팅 메시지를 TCP로 보내는 코드를 짰다.

```cpp
// 보내는 쪽: "Hello"와 "GG"를 따로 두 번 보냄
Socket->Send((uint8*)"Hello", 5, Sent);
Socket->Send((uint8*)"GG", 2, Sent);
```

받는 쪽에서 찍어보니, 기대와 다르게 온다.

```
기대:  "Hello"  그리고  "GG"   (보낸 단위 그대로)
현실:  "HelloGG"            (합쳐져서 한 번에)
또는:  "Hel"  그리고  "loGG"  (엉뚱하게 쪼개져서)
```

버그가 아니다. **TCP는 "메시지"가 아니라 "바이트 스트림"** 이기 때문이다(4강). 보낸 단위를 기억해주지 않는다. 그냥 바이트가 순서대로 흐를 뿐. 어디까지가 한 메시지인지는 **우리가 직접 표시하고 잘라내야** 한다. 이게 이 강의의 핵심이다.

---

## 2. 직렬화 — 데이터를 바이트로

먼저 보낼 데이터를 바이트로 바꾸는 것부터. 네트워크는 바이트만 안다. `FVector`, `FString`, 구조체를 그대로 못 보낸다. **직렬화(Serialization)** 로 바이트 배열로 펴야 한다. 받는 쪽은 **역직렬화**로 복원한다.

```cpp
// 보낼 구조체 — 플레이어 이동 패킷
struct FMovePacket
{
    int32   PlayerId;
    FVector Location;   // float x,y,z
    float   Yaw;
};

// 직렬화: 구조체 → 바이트
FMovePacket Packet { 7, FVector(100,50,0), 90.f };
TArray<uint8> Bytes;
Bytes.Append((uint8*)&Packet, sizeof(FMovePacket));   // 메모리를 그대로 복사

// 역직렬화: 바이트 → 구조체
FMovePacket Restored;
FMemory::Memcpy(&Restored, Bytes.GetData(), sizeof(FMovePacket));
```

> 주의: 위처럼 구조체를 통째로 memcpy하는 건 같은 컴파일러/플랫폼끼리만 안전하다. 실무에선 멤버를 하나씩 명시적으로 쓰는 방식이나 언리얼 `FArchive`(`<<` 연산자)를 쓴다. 패딩·정렬·엔디안 때문이다(아래).

---

## 3. 함정 셋 — 엔디안, 정렬, 경계

### 함정 1: 엔디안 (바이트 순서)

`int32` 같은 다바이트 숫자를 메모리에 저장하는 순서가 CPU마다 다르다.

```
숫자 0x12345678 을 메모리에 저장하면:

리틀 엔디안 (x86, 대부분 PC):  78 56 34 12   (낮은 자리부터)
빅 엔디안 (일부 장비, 네트워크): 12 34 56 78   (높은 자리부터)
```

PC끼리(둘 다 x86)는 보통 문제없지만, 서로 다른 아키텍처가 섞이면 숫자가 깨진다. 그래서 네트워크 표준은 **빅 엔디안(network byte order)** 이다. 크로스 플랫폼이면 보낼 때 변환해야 한다. 언리얼 `FArchive`는 이런 처리를 추상화해준다.

### 함정 2: 구조체 패딩/정렬

컴파일러가 성능을 위해 구조체 멤버 사이에 **빈 공간(패딩)** 을 넣는다.

```cpp
struct FBad
{
    uint8  Type;    // 1바이트
    int32  Value;   // 4바이트 → 그 앞에 3바이트 패딩이 끼어 sizeof = 8
};
// sizeof(FBad) == 8 (1 + 3패딩 + 4)  ← 1+4=5 가 아님!
```

`sizeof`로 통째 복사하면 이 패딩까지 같이 간다. 컴파일러 설정이 다른 양쪽에선 패딩 크기가 달라 깨질 수 있다. 그래서 멤버를 하나씩 명시적으로 직렬화하는 게 안전하다.

### 함정 3: 메시지 경계 (도입의 그 문제)

TCP는 스트림이라 "여기까지가 한 패킷"을 안 알려준다. 직접 표시해야 한다. 두 가지 표준 방법:

**방법 A — 길이 접두사 (Length Prefix). 가장 흔함.**

패킷 맨 앞에 "이 패킷 몸통이 몇 바이트인지"를 먼저 박는다.

```
[ 길이(4바이트) ][ ───── 몸통 ───── ]
   00 00 00 12      실제 데이터 18바이트

받는 쪽:
1) 먼저 4바이트(길이)를 읽는다 → "18바이트짜리구나"
2) 18바이트가 다 모일 때까지 기다린다 (부분 수신 대비)
3) 18바이트 모이면 한 패킷으로 잘라서 처리
4) 남은 바이트는 다음 패킷의 시작 → 버퍼에 보관
```

**방법 B — 구분자 (Delimiter).**

패킷 끝에 특수 문자(예: `\n`)를 넣고 그걸로 자른다. 텍스트 프로토콜(HTTP 헤더 등)에서 쓴다. 바이너리 데이터엔 구분자가 데이터에 섞일 수 있어 부적합.

게임 바이너리 패킷은 거의 **방법 A(길이 접두사)** 를 쓴다.

## 4. 받는 쪽 — 조립 버퍼 패턴

TCP에서 패킷을 제대로 받으려면, 받은 바이트를 **버퍼에 쌓아두고 완성된 패킷만 꺼내는** 패턴이 필수다.

```cpp
// 수신 버퍼에 계속 누적
TArray<uint8> RecvBuffer;

void OnDataReceived(const uint8* Data, int32 Size)
{
    RecvBuffer.Append(Data, Size);   // 일단 다 쌓는다

    // 완성된 패킷이 있는 동안 계속 꺼낸다
    while (RecvBuffer.Num() >= 4)    // 최소 길이 헤더는 있어야
    {
        // 1) 앞 4바이트 = 몸통 길이
        int32 BodyLen = 0;
        FMemory::Memcpy(&BodyLen, RecvBuffer.GetData(), 4);

        // 2) 몸통이 아직 다 안 왔으면 대기 (부분 수신)
        if (RecvBuffer.Num() < 4 + BodyLen)
            break;   // 더 받을 때까지 기다림

        // 3) 완성된 패킷 하나 꺼내 처리
        const uint8* Body = RecvBuffer.GetData() + 4;
        ProcessPacket(Body, BodyLen);

        // 4) 처리한 만큼 버퍼에서 제거 (남은 건 다음 패킷)
        RecvBuffer.RemoveAt(0, 4 + BodyLen);
    }
}
```

이 패턴이 "HelloGG로 합쳐지거나 Hel/loGG로 쪼개지는" 문제를 전부 해결한다. **쌓고 → 길이 보고 → 완성되면 자르고 → 남기고** 의 반복이다. 게임 네트워크 코드의 기본기다.

---

## 5. 패킷 설계 — 헤더 + 몸통

실전 패킷은 보통 **헤더(메타정보) + 몸통(실제 데이터)** 구조다.

```
┌─────────────────────────┬────────────────┐
│          헤더           │      몸통      │
├──────────┬──────────────┼────────────────┤
│ 길이(4B) │ 패킷타입(2B) │ 타입별 데이터  │
└──────────┴──────────────┴────────────────┘
   얼마나        뭔지          내용
```

- **길이:** 경계를 위해 (4번 참고)
- **패킷 타입(ID):** 이게 이동 패킷인지 채팅인지 거래인지. 받는 쪽이 타입을 보고 알맞은 핸들러로 분기.

```cpp
enum class EPacketType : uint16
{
    Move    = 1,
    Chat    = 2,
    Trade   = 3,
};

void ProcessPacket(const uint8* Body, int32 Len)
{
    uint16 Type = 0;
    FMemory::Memcpy(&Type, Body, 2);
    switch ((EPacketType)Type)
    {
        case EPacketType::Move:  HandleMove(Body + 2, Len - 2);  break;
        case EPacketType::Chat:  HandleChat(Body + 2, Len - 2);  break;
        case EPacketType::Trade: HandleTrade(Body + 2, Len - 2); break;
    }
}
```

> 참고: 언리얼 `Replication`/RPC를 쓰면 이 패킷 설계·직렬화·경계 처리를 엔진이 다 해준다(14강). 직접 소켓으로 커스텀 프로토콜을 짤 때만 이걸 손으로 한다. 면접에선 "TCP 경계 문제를 어떻게 푸나"가 단골이라 원리는 알아야 한다.

## 6. 흔한 오해

### 오해 1: "send 한 번 = recv 한 번"

TCP에선 절대 아니다. send 한 번이 recv 여러 번으로 쪼개지거나, send 여러 번이 recv 한 번으로 합쳐진다. 길이 접두사로 직접 경계를 잡아야 한다. UDP는 데이터그램 단위라 경계가 유지되지만, 대신 유실·순서가 보장 안 된다.

### 오해 2: "구조체를 memcpy로 보내면 끝이다"

같은 컴파일러·플랫폼끼리 테스트할 땐 되는 것처럼 보이지만, 패딩과 엔디안 때문에 환경이 다르면 깨진다. 멤버별 명시적 직렬화나 `FArchive`를 쓰는 게 안전하다.

### 오해 3: "UDP는 경계 문제가 없으니 더 쉽다"

UDP는 데이터그램 단위라 경계는 유지된다. 하지만 유실·순서·중복을 직접 처리해야 해서 다른 종류의 복잡함이 생긴다. "경계 문제 없음"이 "더 쉬움"은 아니다.

### 오해 4: "엔디안은 신경 안 써도 된다"

PC(x86)끼리만 통신하면 대부분 문제없다. 하지만 콘솔·모바일 등 다른 아키텍처가 섞이거나, 정석대로 가려면 네트워크 바이트 오더(빅 엔디안)로 맞춰야 한다. 면접에서 "엔디안 처리는 어떻게 하나" 물으면 모른다고 하면 안 된다.

## 7. 면접에서 나오면

**Q1. TCP에서 메시지 경계 문제가 뭔가요?**
→ "TCP는 메시지 단위가 아니라 바이트 스트림이라, 보낸 단위와 받는 단위가 일치하지 않습니다. 두 번 보낸 게 한 번에 합쳐 오거나, 한 번 보낸 게 쪼개져 올 수 있습니다. 그래서 패킷 앞에 길이를 붙이는 길이 접두사 방식으로 직접 경계를 표시하고 잘라내야 합니다."

**Q2. 길이 접두사 방식으로 어떻게 패킷을 자르나요?**
→ "받은 바이트를 버퍼에 계속 쌓아두고, 먼저 앞쪽 길이 필드를 읽어 몸통 크기를 확인합니다. 그 크기만큼 데이터가 다 모이면 한 패킷으로 잘라 처리하고, 남은 바이트는 다음 패킷의 시작으로 버퍼에 남겨둡니다. 이 과정을 완성된 패킷이 없을 때까지 반복합니다."

**Q3. 직렬화가 뭔가요?**
→ "구조체나 객체 같은 데이터를 네트워크로 보낼 수 있는 바이트 배열로 변환하는 과정입니다. 받는 쪽은 역직렬화로 원래 형태로 복원합니다. 이때 엔디안과 구조체 패딩 때문에, 통째로 memcpy하기보다 멤버를 명시적으로 직렬화하는 게 안전합니다."

**Q4. 엔디안이 뭔가요? 왜 문제가 되나요?**
→ "다바이트 숫자를 메모리에 저장하는 바이트 순서입니다. x86 PC는 리틀 엔디안이고 네트워크 표준은 빅 엔디안인데, 서로 다른 아키텍처끼리 통신할 때 변환하지 않으면 숫자가 깨집니다. 그래서 크로스 플랫폼 통신은 네트워크 바이트 오더로 맞춥니다."

**Q5. UDP도 메시지 경계 문제가 있나요?**
→ "UDP는 데이터그램 단위로 주고받아서 경계는 유지됩니다. 보낸 한 덩어리가 그대로 한 번에 도착합니다. 대신 유실·순서·중복을 보장하지 않아서, 그 부분을 애플리케이션에서 직접 처리해야 합니다."

면접관이 그 다음에 던지기 좋은 질문: *"그럼 로그인이나 랭킹 같은 건 이런 커스텀 패킷을 쓰나요, 아니면 HTTP를 쓰나요?"* → 11강(HTTP/HTTPS)에서 다룬다.

## 8. 셀프 체크

- [ ] TCP가 스트림이라 send/recv 단위가 안 맞는다는 걸 예로 설명할 수 있다.
- [ ] 길이 접두사 방식으로 패킷을 자르는 흐름(쌓고→길이 보고→자르고→남기고)을 안다.
- [ ] 직렬화/역직렬화가 뭔지 말할 수 있다.
- [ ] 엔디안과 구조체 패딩이 왜 함정인지 안다.
- [ ] UDP는 경계가 유지되지만 유실·순서는 직접 처리해야 한다는 걸 안다.
