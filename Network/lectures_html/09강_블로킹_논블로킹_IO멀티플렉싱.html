Part 3 · 소켓 프로그래밍

블로킹·논블로킹과 I/O 멀티플렉싱

recv() 하나가 멈춰 있는 동안 다른 클라이언트는 접속도 못 한다. 한 스레드로 수천 연결을 받는 방법 — 소켓 수백 개를 직접 감시해보며 왜 멀티플렉싱인지 확인한다.

👁️ 준비된 소켓만 골라준다
🧩 선수지식 8강
⏱️ 약 20분
SECTION 01 · 도입

18강 서버의 치명적 결함

서버가 recv()로 한 클라의 데이터를 기다리는 동안 다른 클라는 접속도 못 한다.

FSocket* ClientA = ListenSocket->Accept(...);
ClientA->Recv(Buffer, size, Read);   // ❌ A가 데이터 보낼 때까지 여기서 멈춤(블로킹)
                                     //    그동안 B, C, D는 못 받음

recv()는 데이터가 올 때까지 함수가 리턴을 안 하고 멈춘다 — 이게 블로킹(blocking)이다. 이 상태론 동시 접속 2명도 못 받는다. 서버가 수천 명을 받으려면 이걸 깨야 한다.

SECTION 02 · 개념

2블로킹 vs 논블로킹

블로킹 — 문 앞에 서서 기다림

데이터가 준비될 때까지 함수가 멈춰서 기다린다. 코드는 단순하지만 기다리는 동안 그 스레드는 아무것도 못 한다.

논블로킹 — 가끔 문을 확인함

데이터가 없으면 "지금 없음"을 즉시 리턴하고 코드는 계속 진행한다. 안 묶인다.

// 블로킹
Socket->Recv(Buffer, size, Read);   // 데이터 올 때까지 여기 묶임

// 논블로킹
Socket->SetNonBlocking(true);
if (Socket->Recv(Buffer, size, Read)) { /* 데이터 있으면 처리 */ }
else                                   { /* 없으면 넘어가서 다른 일 */ }

논블로킹이면 한 스레드로 여러 소켓을 "돌아가며 확인"할 수 있다. 하지만 소켓이 수천 개면 매번 전부 확인(폴링)하는 게 낭비다. "데이터 온 소켓만 골라서 알려주면 좋겠다" → I/O 멀티플렉싱.

SECTION 03 · I/O 멀티플렉싱

3여러 소켓을 한 번에 감시

소켓 수천 개를 OS에 맡기고 "이 중에 데이터 온 거 있으면 알려줘" 하고 한 곳에서 기다린다. 스레드 하나로 수천 연결을 감시할 수 있다.

        ┌──────────────────────────┐
        │   감시 함수 (select 등)    │  "이 소켓들 중 준비된 거 알려줘"
        └────────────┬─────────────┘
          소켓1  소켓2  소켓3 ... 소켓5000
                       │  소켓3, 소켓117에 데이터 도착!
        "소켓3이랑 117 준비됨" ──→ 그 둘만 처리
방식특징비고
select가장 기본. 감시할 소켓을 매번 등록, 소켓 많으면 느림이식성 좋음
pollselect 개선판. 개수 제한 완화유닉스
epoll리눅스 고성능. 수만 연결도 효율적리눅스 서버
IOCP윈도우 고성능 모델윈도우 게임 서버

select의 한계: 매번 전체 목록을 넘기고 OS가 전부 훑어야 한다. 연결이 수천이면 훑기 자체가 부담 → 대규모는 epoll/IOCP.

SECTION 04 · 핵심 · 직접 돌려보기

4소켓 감시 시뮬레이터 — 누가 얼마나 헛수고하나

소켓 N개 중 매 라운드 일부에 데이터가 도착한다. 다섯 가지 서버 전략이 같은 도착 패턴을 처리하는 데 드는 작업량을 비교해보자. 헤더의 전략 이름을 누르면 그 전략이 소켓을 어떻게 만지는지 격자에 표시된다.

소켓 수 N 100   라운드당 도착 비율 3%
데이터 도착(ready)이번 라운드 서버가 들여다본 소켓블로킹 서버가 기다리는 소켓도착했지만 못 받음(밀림)

① 100라운드를 돌려보자 — 폴링/select는 확인의 97%가 헛수고(도착 3%인데 N개를 매번 다 확인), epoll/IOCP는 헛수고가 0. ② 블로킹은 한 소켓만 기다리다가 밀린 이벤트가 쌓인다. ③ 연결당 스레드는 잘 처리하지만 스레드 N개 = 스택 메모리 N MB + 컨텍스트 스위칭 부담. ④ N을 400으로 올리면 폴링/select의 낭비가 커지고 스레드 모델도 부담이 된다.

SECTION 05 · IOCP (개념만)

5select는 "물어보기", IOCP는 "통보받기"

윈도우 게임 서버는 거의 IOCP(I/O Completion Port)를 쓴다. 면접에서 "윈도우 고성능 서버"라고 하면 IOCP가 나온다.

select

"준비됐는지 내가 물어본다" — 확인하러 간다.

IOCP

"끝나면 OS가 알려준다" — 완료 통보를 받는다. 비동기 I/O.

요청: "소켓들에서 읽기 시작해" → OS에 맡기고 끝
       ↓ (OS가 백그라운드에서 다 처리)
완료 큐: [소켓3 읽기완료] [소켓117 읽기완료] ...
       ↓
워커 스레드 몇 개가 완료된 것만 꺼내 처리

스레드 몇 개로 수만 연결을 감당한다. 연결마다 스레드를 주면 스레드가 수천 개라 컨텍스트 스위칭 비용으로 죽는다(OS 6강). 클라 개발자 기준: IOCP를 직접 짤 일은 드물지만 "왜 IOCP를 쓰나 → 적은 스레드로 대량 연결을 비동기로 처리하려고"는 답할 수 있어야 한다.

SECTION 06 · 언리얼

6언리얼 클라에선 어떻게 하나

멀티플레이는 Replication/RPC(14강)가 알아서 한다. 직접 소켓을 쓸 땐(커스텀 프로토콜, 외부 서버 연동) 논블로킹 + 별도 스레드 패턴을 쓴다.

class FSocketReceiver : public FRunnable
{
    FSocket* Socket;
    virtual uint32 Run() override
    {
        Socket->SetNonBlocking(true);
        while (bRunning)
        {
            uint32 PendingSize = 0;
            if (Socket->HasPendingData(PendingSize))   // 온 게 있을 때만
            {
                uint8 Buffer[2048]; int32 Read = 0;
                Socket->Recv(Buffer, sizeof(Buffer), Read);
                // 받은 데이터를 게임 스레드로 안전하게 전달 (동기화 필요 — OS 7~8강)
            }
            FPlatformProcess::Sleep(0.001f);   // CPU 다 안 쓰게 살짝 양보
        }
        return 0;
    }
};

수신은 별도 스레드, 게임 스레드로 넘길 땐 동기화(락)가 필요하다. 네트워크와 멀티스레드가 만나는 지점이다.
