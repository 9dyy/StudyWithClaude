TCP, 신뢰성의 대가

"보냈는데 안 왔다"를 누가 책임지나. TCP가 빠짐없이, 순서대로 갖다주는 원리를 패킷 흐름으로 직접 재생하고, 그 신뢰성이 왜 공짜가 아닌지 확인한다.

🤝 3-way handshake
🧩 선수지식 3강
⏱️ 약 20분
SECTION 01 · 도입

1"보냈는데 안 왔다"를 누가 책임지나

채팅 "GG"가 상대한테 안 가면 큰일이다. 거래 시스템이면 더하다 — "골드 1000개 보냄"이 유실되면 게임 경제가 박살난다. 그런데 네트워크는 기본적으로 못 믿는다. 패킷은 사라지고, 순서가 뒤바뀌고, 늦게 온다.

// 거래 패킷을 보냈다. 그런데 도착했는지 내가 어떻게 알지?
SendPacket(TradeRequest);
// 도착했나? 안 했나? 중간에 사라졌나? ... 모름

"답이 없네? 다시 보내야 하나? 근데 사실 도착했고 답만 유실된 거면 두 번 보내지는 거 아냐?" — 이걸 게임 코드에서 직접 처리하면 지옥이다. 이 모든 걸 대신 해결해주는 게 TCP다.

SECTION 02 · 약속

2TCP의 약속 세 가지

① 신뢰성

데이터가 반드시 도착한다. 유실되면 다시 보낸다.

② 순서 보장

보낸 순서대로 도착한다. 뒤바뀌면 재정렬한다.

③ 연결 지향

통신 전에 먼저 "연결"을 맺는다.

이걸 어떻게 하느냐가 면접의 핵심이다. 아래에서 직접 재생해보자.

SECTION 04 · 연결 지향

43-way handshake와 4-way handshake

재생기 앞부분이 이것이다. 데이터를 보내기 전에 양쪽이 "통신 시작하자"고 합의한다. 면접 최빈출.

클라이언트                              서버
   │ ──────  SYN  ───────────────────→ │  "연결하자" (내 시작 번호 x)
   │ ←─────  SYN + ACK  ─────────────── │  "좋아, 나도 연결하자" (내 번호 y, 네 x 받음)
   │ ──────  ACK  ───────────────────→ │  "확인" (네 y 받음)
   │════════  이제 데이터 전송  ════════│

왜 3번인가? 양쪽이 서로 "보낼 수 있고 받을 수 있다"는 걸 확인하려면 최소 3번이 필요하다. 2번이면 서버가 "클라가 내 응답을 받았는지" 확신할 수 없다. 전화 거는 거랑 같다 — "여보세요?"(SYN) / "어 들려, 너도 들려?"(SYN+ACK) / "응 들려"(ACK).

끊을 땐 4-way

클라 ── FIN ──→ 서버     "나 다 보냈어"
클라 ←─ ACK ─── 서버     "알았어"
클라 ←─ FIN ─── 서버     "나도 다 보냈어"
클라 ── ACK ──→ 서버     "알았어"  → 종료

연결은 양방향이라 한쪽이 끝나도 반대 방향은 아직 보낼 게 남았을 수 있다. 그래서 각 방향을 따로 닫는다(half-close 상태가 존재).

SECTION 05 · 신뢰성과 순서

5시퀀스 번호와 ACK

TCP는 데이터를 조각(세그먼트)으로 쪼개 각각 시퀀스 번호를 붙이고, 받는 쪽은 ACK로 "다음엔 이 번호 줘"를 알린다.

보내는 쪽                      받는 쪽
  Seq=1 "Hel" ───────────────→ 받음. "Seq=4 줘" (ACK=4)
  Seq=4 "lo " ───────────────→ 받음. "Seq=7 줘" (ACK=7)
  Seq=7 "GG"  ──────X (유실)    ... 안 옴
  (일정 시간 ACK 안 오면)
  Seq=7 "GG"  ───────────────→ 받음. "Seq=9 줘" (ACK=9)  ← 재전송!

유실 감지

ACK가 타임아웃 안에 안 오면 유실로 판단하고 재전송.

순서 보장

시퀀스 번호를 보고 원래 순서로 재정렬. Seq=9가 먼저 와도 7을 기다렸다 순서대로 올려준다.

중복 제거

같은 번호가 두 번 오면(재전송 때문에) 하나만 쓴다.

SECTION 06 · 대가

6그럼 대가는? — TCP가 느린 이유

TCP의 신뢰성은 공짜가 아니다. 게임 개발자한테 제일 중요한 부분이다.

대가 1 · 연결 비용

데이터 한 글자 보내기 전에 handshake로 왕복 1.5번을 먼저 쓴다. 짧은 통신엔 오버헤드.

대가 2 · 재전송 지연 (HOL)

패킷 하나가 유실되면 그게 도착할 때까지 그 다음 데이터를 위로 안 올려준다. 순서를 보장해야 하니까.

FPS에서 캐릭터 위치를 TCP로 보낸다면:

위치1 도착 ─→ 위치2 유실! ─→ 위치3 도착(했지만 대기) ─→ 위치4 도착(대기)
                  └ 위치2 재전송될 때까지 위치3,4는 묶여서 못 올라감 (Head-of-Line Blocking)

결과: 위치2 기다리는 동안 캐릭터가 멈췄다가, 한꺼번에 순간이동

0.1초 전 위치는 이미 쓸모없는데 TCP는 그 낡은 위치가 도착할 때까지 최신 위치를 막는다. "순서 보장"이 오히려 독이 되는 상황 → 실시간 위치는 UDP(5강), 채팅·거래·로그인처럼 반드시 도착해야 하고 순서가 중요한 건 TCP.

SECTION 07 · 코드 · 스트림

7언리얼 TCP 소켓과 "스트림"이라는 성질

// NAME_Stream = TCP. (UDP는 NAME_DGram, 다음 강의)
FSocket* TcpSocket = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)->CreateSocket(NAME_Stream, TEXT("TcpClient"), false);

bool bConnected = TcpSocket->Connect(*ServerAddr);   // 이 한 줄이 내부적으로 3-way handshake (SYN → SYN+ACK → ACK)

int32 BytesSent = 0;
FString Msg = TEXT("Trade:Gold1000");
TcpSocket->Send((uint8*)TCHAR_TO_UTF8(*Msg), Msg.Len(), BytesSent);   // 시퀀스 번호·ACK·재전송은 TCP가 알아서

TCP를 골랐다는 건 "신뢰성을 위해 지연을 감수하겠다"는 선택이다. 채팅엔 맞고, 실시간 위치엔 안 맞는다.

TCP는 스트림이다 — 메시지 경계가 없다

// 보낸 쪽: Send("Hello") 다음 Send("GG") — 두 번 따로 보냈다
// 받는 쪽이 볼 수 있는 모양들
Recv → "HelloGG"           // 합쳐서 오거나
Recv → "Hel"  ,  "loGG"    // 엉뚱한 곳에서 쪼개져 온다

TCP는 바이트 순서만 보장하지 "메시지 경계"는 보장 안 한다. 이걸 직접 처리해야 한다 — 10강(패킷 설계)에서 다룬다.
