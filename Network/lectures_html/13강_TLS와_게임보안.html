TLS와 게임 보안

핵 문제는 사실 두 개다 — 전송 중 도청·변조(TLS)와 클라의 거짓말(서버 권한 검증). 핸드셰이크를 재생하고, 같은 공격이 두 방어선에서 각각 통과하고 막히는 걸 직접 확인한다.

SECTION 01 · 도입

1"치트 좀 막아주세요"

멀티플레이 게임을 냈더니 핵이 돈다.

  • 누가 패킷을 가로채서 비밀번호를 빼간다.
  • 누가 "내 데미지 9999" 패킷을 서버에 보내 한 방에 보스를 잡는다.
  • 누가 "내 좌표 순간이동" 패킷을 조작해 벽을 통과한다.

이건 사실 두 개의 다른 문제다.

① 전송 중 도청·변조

암호화(TLS, HTTPS)로 막는다.

② 클라가 거짓말

서버 권한 검증으로 막는다 — "클라를 믿지 마라".

면접에서 게임 보안을 물으면 이 두 축으로 답하면 깔끔하다. 아래 시뮬레이터가 이 둘을 분리해서 보여준다.

SECTION 02 · 암호화

2암호화의 두 종류 — 대칭과 비대칭

대칭키 — 같은 키로 잠그고 푼다

빠르다. 문제: 그 키를 상대에게 어떻게 안전하게 전달하지? 그냥 보내면 중간에서 가로챈다.

평문 ─[키 K 암호화]→ 암호문 ─[같은 K 복호화]→ 평문

비대칭키 — 키가 두 개 (공개키·개인키)

공개키로 잠근 건 개인키로만 열린다. 공개키는 뿌려도 되고 개인키는 서버만 쥔다. 안전하지만 느리다.

공개키로 잠금 → 개인키로만 열림

TLS는 둘을 섞는다. 비대칭은 안전하지만 느리니 "대칭키를 안전하게 주고받는 데만" 쓰고, 이후 실제 데이터는 빠른 대칭키로 암호화한다. 비유: 서버가 자물쇠(공개키)를 뿌리고, 클라는 그 자물쇠로 비밀(대칭키 재료)을 잠가 보낸다. 열쇠(개인키)는 서버만 갖고 있으니 가로채도 못 연다.

SECTION 03 · 직접 돌려보기 ①

3TLS 핸드셰이크 재생기 — 중간자 공격이 끼면?

핸드셰이크의 목적은 두 가지다. 인증(이 서버가 진짜 그 서버인가 — 인증서, CA)과 키 교환(대칭키를 안전하게 합의). [다음 단계]로 재생하면서 아래 세 사람이 각각 뭘 아는지 보자. 공격자를 끼워넣고 "인증서 검증"을 켜고 끄면 결과가 어떻게 달라질까?

① 기본(공격자 없음) 끝까지 → 도청자는 공개된 것과 암호문만 안다. 대칭키 K는 개인키를 가진 서버만 풀 수 있는 자물쇠 안에 들어 있었다. ② 공격자를 켜고 끝까지 → 클라가 인증서 검증에서 연결을 끊는다. 인증서의 진짜 목적이 "암호화"가 아니라 신원 증명인 이유다. ③ 공격자 + 검증 끄기 → 가짜 서버를 진짜로 믿어 평문이 다 털린다. (TLS 1.3은 키 교환에 (EC)DHE를 쓰지만 "비대칭으로 대칭키를 안전하게 합의한다"는 골격은 같다.)

4핵 유저 vs 서버 — TLS와 서버 검증은 별개의 방어선

"클라이언트를 믿지 마라" — 클라가 보내는 모든 것은 의심하고 중요한 판정은 서버가 한다. 두 방어선을 켰다 껐다 하며 네 가지 공격을 던져보자. 보스는 사거리 10m, 쿨다운 1초의 공격만 받아야 한다.

SECTION 05 · 코드

  
5나쁜 설계 vs 좋은 설계

  

    
// ❌ 클라가 "나 데미지 9999 줬어"라고 통보 → 서버가 그대로 믿음
void Server_DealDamage(float Damage)   // 클라가 Damage를 보냄
{
    Enemy->HP -= Damage;   // 9999가 와도 그대로 적용 → 핵 천국
}

// ✅ 클라는 "공격하겠다"는 의도만. 데미지 계산·검증은 서버가.
void Server_RequestAttack(int32 TargetId)
{
    AEnemy* Target = FindEnemy(TargetId);
    if (!Target) return;

    // 서버가 직접 검증: 사거리 안인가? 쿨다운 됐나? 살아있나?
    if (!IsInRange(Target) || !IsAttackReady()) return;

    // 데미지도 서버가 가진 정확한 스탯으로 계산 (클라 값 안 씀)
    float Damage = CalculateDamage(MyStats, Target->Defense);
    Target->HP -= Damage;
}

    
시뮬레이터의 "서버가 직접 판정" 모드가 두 번째 함수다. 클라는 의도만 보내고 사거리·쿨다운·데미지는 전부 서버가 자기 데이터로 판정한다. 이게 14강 서버 권한(Server Authority)으로 이어진다 — 언리얼이 서버 권위 구조를 기본으로 미는 이유가 이 보안 원칙이다.

  

  

    
TLS는 언리얼에서 거의 자동이다

    
// https 만 쓰면 TLS는 엔진이 알아서 처리한다 (11강의 HTTP 모듈)
Request->SetURL(TEXT("https://game.example.com/api/login"));   // 자동 암호화
Request->ProcessRequest();

    
클라 개발자가 TLS를 직접 구현할 일은 없다. 신경 쓸 건 로그인·결제·개인정보는 반드시 https라는 것, 그리고 RPC를 만들 때마다 "이 판정을 클라가 하나, 서버가 하나"를 따지는 습관이다. 그게 클라 개발자가 보안에 기여하는 지점이다.
