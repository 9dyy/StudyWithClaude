HTTP와 HTTPS

로그인·랭킹·상점 같은 부가 기능은 왜 커스텀 소켓이 아니라 HTTP인가. 요청을 직접 조립해 게임 서버에 던지고, 돌아오는 상태 코드로 "누구 잘못인지"를 판단하는 감각을 익힌다.

SECTION 01 · 도입

1로그인은 왜 커스텀 패킷으로 안 짤까

10강에서 직접 패킷을 설계했다. 그럼 로그인도 그렇게 짜면 될까? 가능은 하다. 하지만 로그인·랭킹·상점·공지 같은 건 거의 다 HTTP로 짠다.

// 직접 짠다면... 로그인 패킷 타입 만들고, 직렬화하고, 경계 처리하고...
EPacketType::Login, 직렬화, 길이접두사, 핸들러 분기, ...

이미 있는 표준

서버 프레임워크·라이브러리·도구가 다 있다.

요청-응답이 명확

"로그인 정보 줄게 → 토큰 받기" 한 번이면 끝. 실시간 스트림이 아니다.

인프라가 HTTP 기준

웹 서버·CDN·로드밸런서가 HTTP에 맞춰져 있다.

디버깅이 쉽다

브라우저·Postman으로 바로 테스트.

실시간 게임 플레이는 커스텀 UDP/TCP, 그 외 부가 기능은 HTTP — 이게 업계 표준 구도다. 그래서 HTTP를 알아야 한다.

SECTION 02 · 구조

2요청과 응답, 그리고 메서드

HTTP는 요청(Request)을 보내면 응답(Response)이 오는 단순한 약속이다. 응용 계층 프로토콜이고 아래는 TCP(신뢰성 필요)로 돈다. 기본 포트는 80(HTTP)/443(HTTPS).

요청의 생김새

POST /api/login HTTP/1.1
Host: game.example.com
Content-Type: application/json
Content-Length: 24

{"id":"Koo","pw":"1234"}

메서드 + 경로 + 버전 / 헤더(메타정보) / 몸통(Body)

응답의 생김새

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 39

{"token":"abc123","nickname":"코딩전사"}

버전 + 상태 코드 / 헤더 / 몸통

10강에서 손으로 짠 "헤더 + 몸통" 구조를 HTTP가 텍스트로 표준화해놓은 거라고 보면 된다.

메서드 — 요청의 의도

메서드의미게임 예시
GET조회랭킹 조회, 공지 목록
POST생성로그인, 회원가입, 결제
PUT전체 수정프로필 통째로 교체
PATCH부분 수정닉네임만 변경
DELETE삭제계정·친구 삭제

GET은 데이터를 바꾸지 않는다(조회만). GET은 정보를 URL에 담고 POST는 보통 몸통에 담는다. 비밀번호를 GET으로 보내면 URL과 로그에 남는다.

SECTION 04 · 상태 코드

  
4상태 코드 — 결과가 어땠는지

  
응답의 숫자 코드가 결과를 알려준다. 백 자리로 분류한다. 4xx면 내(클라) 요청이 잘못, 5xx면 서버가 잘못 — 이 한 줄이 디버깅 방향을 정한다.

  

    

      
범위의미대표

      
2xx성공200 OK, 201 Created

      
3xx리다이렉트301 이동, 304 안 바뀜

      
4xx클라 잘못400 잘못된 요청, 401 인증 안 됨, 403 권한 없음, 404 없음, 429 너무 많이 요청

      
5xx서버 잘못500 서버 에러, 503 서버 과부하

    

    
401 vs 403: 401은 "너 누군지 모르겠어"(토큰 없음·만료 → 다시 로그인), 403은 "누군지는 아는데 넌 이거 못 해"(권한 없음 → 재시도해도 소용없음). 429는 클라가 요청 폭주 → 호출 빈도를 줄여야 한다. 5xx는 클라가 재시도 로직으로 대응한다.

SECTION 05 · REST

  
5REST — API 설계 스타일

  
게임 백엔드 API는 보통 REST 스타일이다. 핵심: URL은 자원(명사), 메서드는 동작(동사). 콘솔의 경로 목록이 이미 그렇게 생겼다.

  

    
GET    /api/players/7/inventory      → 7번 플레이어의 인벤토리 조회
POST   /api/players/7/items          → 7번 플레이어에게 아이템 추가
DELETE /api/players/7/items/55       → 55번 아이템 삭제
GET    /api/rankings?season=3        → 시즌3 랭킹 조회

GET /api/getPlayerInventory?id=7     ← URL에 동사를 넣는 건 비REST (콘솔에서 보내면 404)

    
URL만 봐도 "무엇을"이 보이고 메서드로 "어떻게"가 정해진다. "REST가 뭐냐" 물으면 "자원을 URL로 표현하고 HTTP 메서드로 행위를 표현하는 API 설계 원칙"이라고 답하면 된다.

  






  
SECTION 06 · 코드

  
6언리얼 FHttpModule로 로그인 요청

  

    
void ULoginSubsystem::RequestLogin(const FString& Id, const FString& Pw)
{
    TSharedRef<IHttpRequest> Request = FHttpModule::Get().CreateRequest();

    Request->SetURL(TEXT("https://game.example.com/api/login"));
    Request->SetVerb(TEXT("POST"));                    // 메서드
    Request->SetHeader(TEXT("Content-Type"), TEXT("application/json"));

    FString Body = FString::Printf(TEXT("{\"id\":\"%s\",\"pw\":\"%s\"}"), *Id, *Pw);
    Request->SetContentAsString(Body);

    // HTTP는 비동기다 — 게임 스레드를 멈추면 안 되니까 콜백으로
    Request->OnProcessRequestComplete().BindUObject(this, &ULoginSubsystem::OnLoginResponse);
    Request->ProcessRequest();
}

void ULoginSubsystem::OnLoginResponse(FHttpRequestPtr Req, FHttpResponsePtr Resp, bool bSuccess)
{
    if (!bSuccess || !Resp.IsValid()) { return; }   // 네트워크 실패 (서버 다운, 끊김)

    int32 Code = Resp->GetResponseCode();
    if (Code == 200)        { /* 토큰 파싱해서 저장 */ }
    else if (Code == 401)   { /* "아이디/비번 확인" 안내 */ }
    else if (Code >= 500)   { /* 서버 문제 → 잠시 후 재시도 */ }
}

    
콘솔의 "클라 코드의 반응" 칸이 바로 이 if 분기다. HTTP 요청은 비동기라 콜백으로 받고(9강의 논블로킹과 연결), 상태 코드로 분기하는 게 실무의 핵심이다. 그리고 HTTP는 무상태라 서버가 "방금 그 사람"을 기억하지 않는다 — 그래서 로그인 후 받은 토큰을 매 요청 헤더에 실어 보내고, 만료되면 401이 돌아온다(콘솔에서 토큰을 바꿔보자).

  






  
SECTION 07 · 보안

  
7HTTPS — HTTP에 자물쇠

  
HTTP는 평문이다. 중간에서 가로채면 아이디·비번이 그대로 보인다. 그래서 실서비스는 전부 HTTPS(HTTP + TLS)를 쓴다. 포트는 443.

  

    
HTTP :  {"pw":"1234"}          ← 중간에서 그대로 읽힘 (위험)
HTTPS:  a8$#kf9@x...           ← 암호화돼서 못 읽음 (안전)

    
TLS가 어떻게 암호화하고 "이 서버가 진짜 그 서버"임을 증명하는지는 13강에서 직접 재생해본다. 지금은 "HTTPS = HTTP + 암호화, 로그인·결제는 무조건 HTTPS"만 기억하자.
