패킷 설계와 직렬화

분명 한 번에 보냈는데 반만 왔다. TCP는 메시지가 아니라 바이트 스트림이기 때문이다. 스트림이 합쳐지고 쪼개지는 걸 직접 재생하고, 길이 접두사와 조립 버퍼로 다시 메시지를 복원한다.

🧵 TCP는 스트림, 경계는 우리가
🧩 선수지식 4강 · 8강
⏱️ 약 25분
SECTION 01 · 도입

1"분명 한 번에 보냈는데 반만 왔다"

채팅 메시지를 TCP로 보내는 코드를 짰다.

// 보내는 쪽: "Hello"와 "GG"를 따로 두 번 보냄
Socket->Send((uint8*)"Hello", 5, Sent);
Socket->Send((uint8*)"GG", 2, Sent);

기대:  "Hello"  그리고  "GG"      (보낸 단위 그대로)
현실:  "HelloGG"                  (합쳐져서 한 번에)
또는:  "Hel"  그리고  "loGG"      (엉뚱하게 쪼개져서)

버그가 아니다. TCP는 "메시지"가 아니라 "바이트 스트림"이다(4강). 보낸 단위를 기억해주지 않고 바이트가 순서대로 흐를 뿐 — 어디까지가 한 메시지인지는 우리가 직접 표시하고 잘라내야 한다. 이 강의의 핵심이다.

SECTION 02 · 직렬화

2직렬화 — 데이터를 바이트로

네트워크는 바이트만 안다. FVector, FString, 구조체를 그대로 못 보낸다. 직렬화(Serialization)로 바이트 배열로 펴고, 받는 쪽은 역직렬화로 복원한다.

struct FMovePacket
{
    int32   PlayerId;
    FVector Location;
    float   Yaw;
};

// 직렬화: 구조체 → 바이트
FMovePacket Packet { 7, FVector(100,50,0), 90.f };
TArray<uint8> Bytes;
Bytes.Append((uint8*)&Packet, sizeof(FMovePacket));   // 메모리를 그대로 복사

// 역직렬화: 바이트 → 구조체
FMovePacket Restored;
FMemory::Memcpy(&Restored, Bytes.GetData(), sizeof(FMovePacket));

⚠️ 구조체를 통째로 memcpy하는 건 같은 컴파일러/플랫폼끼리만 안전하다. 실무에선 멤버를 하나씩 명시적으로 쓰거나 언리얼 FArchive(<< 연산자)를 쓴다. 이유가 바로 다음 절의 함정들이다.

SECTION 03 · 함정 셋 · 엔디안과 패딩은 직접 확인

3함정 셋 — 엔디안, 정렬, 경계

함정 3(경계)은 다음 절의 시뮬레이터에서 본다. 먼저 함정 1·2를 손으로 만져보자.

함정 1 · 엔디안 (바이트 순서)

int32 같은 다바이트 숫자를 메모리에 저장하는 순서가 CPU마다 다르다. x86(대부분 PC)은 리틀 엔디안(낮은 자리부터), 네트워크 표준은 빅 엔디안(높은 자리부터, network byte order)이다. 값을 바꿔보자.

16진수 32비트 값 0x
주소(낮음 → 높음) [0] [1] [2] [3]
리틀 엔디안 (x86 PC의 메모리)
빅 엔디안 (네트워크 바이트 오더 · htonl 결과)

함정 2 · 구조체 패딩 (sizeof가 합이 아니다)

컴파일러가 성능을 위해 멤버 사이에 빈 공간(패딩)을 넣는다. 각 멤버는 자기 크기의 배수 주소에 놓이고, 구조체 전체 크기는 가장 큰 멤버 크기의 배수가 된다. 멤버를 추가하거나 순서를 바꿔 sizeof가 어떻게 변하는지 보자.

메모리 배치 (한 칸 = 1바이트, 빨간 칸 = 패딩)

기본 { uint8, int32, uint8 }는 12바이트(내용은 6바이트). 큰 것부터 정렬하면 8바이트로 줄어든다. 그래서 sizeof로 통째 복사하면 패딩까지 같이 전송되고, 컴파일러 설정이 다른 양쪽에선 패딩이 달라 깨질 수 있다 → 멤버를 하나씩 명시적으로 직렬화하는 게 안전하다.

SECTION 04 · 핵심 · 직접 돌려보기

4TCP 스트림 조립기 — 합쳐지고 쪼개진 바이트에서 메시지 복원

함정 3: TCP는 "여기까지가 한 패킷"을 안 알려준다. 그래서 패킷 맨 앞에 "몸통이 몇 바이트인지"(길이 접두사)를 박는다. 아래에서 메시지를 보내고 네트워크가 바이트를 어떻게 쪼개 전달하는지를 골라, 두 수신 방식을 비교해보자.

네트워크 전달 방식  메시지 추가
① 보낸 것 — 메시지마다 [길이 1바이트(노랑) + 몸통(청록)]
② 네트워크가 실제로 나눠 전달한 recv 단위 (초록 테두리 = 이미 도착)

❌ 순진한 수신 recv 1번 = 메시지 1개라고 가정

✅ 조립 버퍼 쌓고 → 길이 보고 → 자르고 → 남기고

① 3바이트씩으로 돌려보자 — 순진한 수신은 메시지가 반토막 나고 길이 바이트가 글자 사이에 끼어 다 깨진다. ② 전부 합쳐서면 순진한 수신은 메시지 여러 개를 하나로 착각한다. ③ 어떤 방식이든 조립 버퍼는 항상 원래 메시지를 복원한다 — 부족하면 기다리고, 남으면 다음 패킷의 시작으로 보관하기 때문이다. ④ 보낸 그대로일 때만 순진한 수신도 맞지만, 그건 우연이지 보장이 아니다.

SECTION 05 · 패킷 설계

5헤더 + 몸통, 그리고 조립 버퍼 패턴 코드

실전 패킷은 헤더(메타정보) + 몸통(실제 데이터)이다. 헤더의 길이는 경계를 위해, 패킷 타입(ID)은 이동/채팅/거래를 구분해 알맞은 핸들러로 보내기 위해 있다.

┌─────────────────────────┬────────────────┐
│          헤더           │      몸통      │
├──────────┬──────────────┼────────────────┤
│ 길이(4B) │ 패킷타입(2B) │ 타입별 데이터  │
└──────────┴──────────────┴────────────────┘
   얼마나        뭔지          내용

경계 표시 방법 두 가지: A. 길이 접두사(가장 흔함, 위 시뮬레이터) / B. 구분자(끝에 \n 같은 특수 문자 — 텍스트 프로토콜에 적합, 바이너리는 데이터에 구분자가 섞일 수 있어 부적합). 게임 바이너리 패킷은 거의 길이 접두사를 쓴다.

TArray<uint8> RecvBuffer;   // 수신 버퍼에 계속 누적

void OnDataReceived(const uint8* Data, int32 Size)
{
    RecvBuffer.Append(Data, Size);        // 일단 다 쌓는다

    while (RecvBuffer.Num() >= 4)         // 최소 길이 헤더는 있어야
    {
        int32 BodyLen = 0;                // 1) 앞 4바이트 = 몸통 길이
        FMemory::Memcpy(&BodyLen, RecvBuffer.GetData(), 4);

        if (RecvBuffer.Num() < 4 + BodyLen)   // 2) 몸통이 아직 다 안 왔으면 대기 (부분 수신)
            break;

        const uint8* Body = RecvBuffer.GetData() + 4;   // 3) 완성된 패킷 하나 꺼내 처리
        ProcessPacket(Body, BodyLen);

        RecvBuffer.RemoveAt(0, 4 + BodyLen);   // 4) 처리한 만큼 제거 (남은 건 다음 패킷)
    }
}

이 패턴이 "HelloGG로 합쳐지거나 Hel/loGG로 쪼개지는" 문제를 전부 해결한다. 쌓고 → 길이 보고 → 완성되면 자르고 → 남기고의 반복 — 시뮬레이터의 오른쪽 패널이 정확히 이 루프다.

enum class EPacketType : uint16 { Move = 1, Chat = 2, Trade = 3 };

void ProcessPacket(const uint8* Body, int32 Len)
{
    uint16 Type = 0;
    FMemory::Memcpy(&Type, Body, 2);
    switch ((EPacketType)Type)
    {
        case EPacketType::Move:  HandleMove(Body + 2, Len - 2);  break;
        case EPacketType::Chat:  HandleChat(Body + 2, Len - 2);  break;
        case EPacketType::Trade: HandleTrade(Body + 2, Len - 2); break;
    }
}

참고: 언리얼 Replication/RPC를 쓰면 이 패킷 설계·직렬화·경계 처리를 엔진이 다 해준다(14강). 직접 소켓으로 커스텀 프로토콜을 짤 때만 손으로 한다. 면접에선 "TCP 경계 문제를 어떻게 푸나"가 단골이라 원리는 알아야 한다.
