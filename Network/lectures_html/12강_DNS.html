DNS

서버 IP를 코드에 박았다가 이전하면 전 유저가 접속 불가다. 도메인이 IP가 되기까지의 리졸빙 과정과, "IP를 바꿨는데 옛 서버로 가요"의 원인인 캐시·TTL을 시간을 돌려가며 직접 재현한다.

📖 DNS 리졸버 시뮬레이터
🧩 선수지식 2·3·11강
⏱️ 약 15분
SECTION 01 · 도입

1서버 주소를 IP로 박았더니 생긴 일

Connect(TEXT("203.0.113.10"), 7777);   // 서버 IP를 코드에 하드코딩

처음엔 잘 됐다. 몇 달 뒤 서버를 이전하면서 IP가 198.51.100.25로 바뀌었다. 이미 배포된 클라들은 옛 IP로 접속을 시도한다 → 전부 접속 불가, 패치를 다시 내려야 한다. 게다가 사람이 IP를 외울 수도 없다.

Connect(TEXT("connect.mygame.com"), 7777);   // 도메인. IP가 바뀌어도 이건 그대로

도메인을 쓰면 서버 IP가 바뀌어도 도메인 → IP 매핑만 갱신하면 클라는 그대로 접속된다. 그 변환을 해주는 시스템이 DNS(Domain Name System)다.

SECTION 02 · 개념

2DNS = 인터넷의 전화번호부

사람이 기억하는 것:  connect.mygame.com
컴퓨터가 필요한 것:  198.51.100.25
                  ↑
               DNS가 변환

"홍길동"(도메인)을 찾으면 "010-1234-5678"(IP)을 알려주는 전화번호부와 같다. 포트는 53번(3강의 well-known 포트)이고, 주로 UDP(빠르고 작아서), 큰 응답은 TCP로 주고받는다.

SECTION 03 · 리졸빙

3리졸빙 — 도메인이 IP가 되기까지

connect.mygame.com을 입력하면 한 군데에 물어보고 끝나는 게 아니라 여러 DNS 서버를 거친다. 한 곳이 전부 아는 게 아니라 위에서 아래로 위임하며 좁혀간다.

내 PC ─ 1. "connect.mygame.com IP 뭐야?" ─→ [로컬 DNS 서버] (통신사/공유기)
                         │ 캐시에 있으면 바로 응답. 없으면 대신 물어봐줌(재귀 질의)
                         ├─ 2. "com 담당 누구?"          ─→ [루트 DNS]      → ".com 서버는 저기야"
                         ├─ 3. "mygame.com 담당 누구?"    ─→ [.com TLD 서버] → "mygame.com 서버는 저기야"
                         └─ 4. "connect.mygame.com IP는?" ─→ [권한 네임서버]  → "198.51.100.25야"
내 PC ←─ 5. "198.51.100.25래" ─ 로컬 DNS가 돌려주면서 캐시해둔다

비유: 모르는 사람 번호를 찾는데, 안내데스크(루트)가 "인사팀에 물어봐", 인사팀(TLD)이 "그 부서 담당자한테 물어봐", 담당자(권한 서버)가 마침내 번호를 알려주는 식이다. 아래 시뮬레이터에서 이 과정이 실제로 몇 ms 걸리는지, 그리고 캐시가 그걸 어떻게 없애는지 본다.

SECTION 04 · 핵심 · 직접 돌려보기

4DNS 리졸버 — 캐시와 TTL로 "서버 이전" 사고 재현

[조회]를 누르면 앱 캐시 → OS 캐시 → 로컬 DNS → (전체 리졸빙) 순으로 찾는다. 시간을 흘려보내고, 서버를 이전(IP 변경)해서 "옛 IP로 가요" 사고를 만들어보자. (가정: 로컬 DNS 왕복 5ms, 루트 20ms, TLD 25ms, 권한 30ms)

🖥 권한 네임서버의 진짜 기록 (A 레코드)

connect.mygame.com → 203.0.113.10
TTL은 다음 전체 리졸빙부터 적용된다. 이미 캐시된 값의 유효기간은 그대로.

⏱ 지금 시각

0초
▶ 조회 버튼을 눌러 시작하자.
0
조회 횟수
0
전체 리졸빙 횟수
—
마지막 소요 (ms)
0
옛 IP로 간 횟수

① 조회 → 첫 번째는 전체 리졸빙(약 80ms), 바로 다시 조회하면 앱 캐시에서 0ms. ② 조회 후 서버 이전 → 다시 조회하면 캐시가 옛 IP를 준다(빨간 글씨) — TTL이 끝나기 전까지. ③ flushdns를 눌러보자: 앱·OS 캐시는 지워지지만 통신사 로컬 DNS 캐시는 그대로라 여전히 옛 IP가 온다. ④ TTL 30초로 바꾼 뒤 조회 → 이전 → +10초 ×3이면 금방 새 IP로 넘어간다. 이게 "이전 전에 TTL을 줄여둔다"는 운영 기법이다.

SECTION 05 · 코드

5언리얼에서 도메인 → IP (리졸빙)

ISocketSubsystem* SocketSub = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM);

// 도메인 → IP 변환(리졸빙). 이 안에서 위의 DNS 과정이 일어난다.
FAddressInfoResult Result = SocketSub->GetAddressInfo(
    TEXT("connect.mygame.com"),     // 도메인
    nullptr,
    EAddressInfoFlags::Default,
    NAME_None);

if (Result.ReturnCode == SE_NO_ERROR && Result.Results.Num() > 0)
{
    TSharedRef<FInternetAddr> ResolvedAddr = Result.Results[0].Address;
    ResolvedAddr->SetPort(7777);
    UE_LOG(LogTemp, Log, TEXT("Resolved IP: %s"), *ResolvedAddr->ToString(false));
    // 출력 예: 198.51.100.25  ← 도메인이 IP로 바뀌었다

    Socket->Connect(*ResolvedAddr);   // 변환된 IP로 접속
}

주의: 리졸빙은 네트워크를 타는 작업이라 캐시가 없으면 시뮬레이터에서 본 80ms급 시간이 든다. 게임 스레드에서 동기로 부르면 잠깐 멈출 수 있어 비동기로 처리하거나 접속 단계에서만 한다(9강의 블로킹 주의). OpenLevel이나 HTTP 모듈(11강)에 도메인을 넘기면 엔진이 알아서 리졸빙해주므로 GetAddressInfo를 직접 부르는 일은 드물지만, "도메인은 결국 IP로 변환되어 접속된다"는 흐름은 알아야 한다.
