흐름 제어·혼잡 제어와 Nagle

TCP는 "혼자 빨리 가는" 프로토콜이 아니라 상대와 네트워크를 배려하는 프로토콜이다. 그 배려가 게임에선 왜 독이 되는지, 키 입력이 뭉쳐 늦게 도착하는 현장을 타임라인으로 직접 본다.

SECTION 01 · 도입

1"분명 즉시 보냈는데 왜 늦게, 뭉쳐서 도착하지?"

TCP로 키 입력을 1바이트씩 서버에 보내는 게임을 만들었다. 테스트해보니 입력이 뭉쳐서 늦게 처리된다.

// 키 누를 때마다 작은 패킷 전송
TcpSocket->Send((uint8*)&KeyCode, 1, BytesSent);   // 1바이트

내 코드는 분명 즉시 보냈는데 서버는 한참 뒤에 여러 개를 한꺼번에 받는다. 버그일까? TCP가 일부러 모아서 보내고 있다. 범인은 Nagle 알고리즘. 이걸 이해하려면 TCP가 상대와 네트워크를 배려한다는 걸 알아야 한다 — 흐름 제어, 혼잡 제어, 그리고 Nagle.

SECTION 02 · 흐름 제어

2받는 쪽이 감당 못 하면 천천히

빠른 서버가 느린 클라이언트한테 데이터를 쏟아부으면 수신 버퍼가 넘쳐 데이터가 버려진다. 흐름 제어(Flow Control)는 받는 쪽이 "나 이만큼 받을 수 있어"라고 수신 윈도우(남은 버퍼)를 알려주고, 보내는 쪽이 그만큼만 보내게 한다.

받는 쪽:   "내 버퍼 8KB 남았어" (Window = 8KB)
보내는 쪽: 8KB까지만 보내고 ACK 기다림
받는 쪽:   처리해서 비움. "이제 16KB 남았어"
보내는 쪽: 더 보냄

한 개 보내고 ACK 기다리기

왕복(RTT)마다 딱 한 개. 100ms 핑이면 초당 10개 — 너무 느리다.

슬라이딩 윈도우

ACK 없이도 윈도우만큼 미리 여러 개 보낸다. ACK가 오는 만큼 윈도우가 앞으로 미끄러진다.

비유: 흐름 제어는 상대 그릇 크기에 맞춰 음식 덜어주기. 그릇이 작으면 조금씩, 크면 많이. 상대가 감당할 만큼만 준다.

SECTION 03 · 혼잡 제어 · 직접 돌려보기

3네트워크가 막히면 양보 — 혼잡 윈도우 톱니

흐름 제어가 받는 쪽을 배려한다면 혼잡 제어는 네트워크 전체를 배려한다. TCP는 패킷 유실을 "길 막힘 신호"로 해석하고 스스로 속도(혼잡 윈도우 cwnd)를 줄인다. RTT를 한 바퀴씩 진행하며 cwnd가 어떻게 움직이는지 보자.

cwnd (혼잡 윈도우)실제 전송량 = min(cwnd, rwnd)rwnd 상한(흐름 제어)● 3 dup ACK 유실● 타임아웃 유실
수신 윈도우 rwnd 64 세그먼트
▶ 를 눌러 cwnd가 1, 2, 4, 8… 늘어나는 걸 보자.

① 처음엔 1, 2, 4, 8… Slow Start(이름과 달리 지수 증가)로 치솟다가 ssthresh에 닿으면 +1씩 혼잡 회피로 조심스럽게 늘어난다. ② 3 dup ACK 유실은 cwnd를 절반으로만 줄인다. ③ 타임아웃 유실은 cwnd를 1로 떨어뜨려 처음부터 다시 — 훨씬 큰 타격. ④ rwnd를 낮추면 cwnd가 아무리 커도 전송량은 rwnd에서 잘린다(흐름 제어). 실제 TCP는 CUBIC 등으로 더 복잡하지만 뼈대는 같다.

⚠️ 무선 환경에선 신호 간섭으로 유실이 나도 TCP는 "길이 막혔다"고 오해하고 속도를 줄인다. 와이파이에서 TCP 성능이 들쭉날쭉한 이유 중 하나다.

SECTION 04 · 핵심 · Nagle

4Nagle 알고리즘 — 게임이 끄는 이유를 눈으로

1바이트를 보내려고 TCP/IP 헤더 40바이트를 붙이면 내용보다 포장이 더 크다. Nagle의 해법: "아직 ACK 안 받은 데이터가 있으면, 작은 데이터는 모았다가 ACK가 오면 한 번에 보내자." 대역폭은 아끼지만 입력이 그만큼 늦는다. 같은 키 입력 8번을 두 설정으로 보내 비교해보자.

RTT 100ms   키 입력 간격 30ms
수신 측 Delayed ACK

● 청록 점 = 키 입력 시각, 사각형 = 실제로 전송된 패킷(안의 숫자 = 그 패킷에 실린 키 입력 수). 아래 막대 = 각 키 입력이 서버에 도착하기까지 걸린 시간. ① 기본값에서 Nagle은 패킷 수는 줄지만 입력마다 지연이 들쭉날쭉이다. ② Delayed ACK를 200ms로 올려보자 — ACK가 늦게 오니 Nagle이 그만큼 더 오래 모으고 지연이 폭발한다. Nagle + Delayed ACK = 최악의 궁합이다. ③ TCP_NODELAY는 RTT/2 그대로 — 대신 패킷이 8개.

// 언리얼 소켓에서 Nagle 끄기 = 작은 패킷 즉시 전송
TcpSocket->SetNoDelay(true);
//        ↑ TCP_NODELAY 옵션. "모으지 말고 바로 보내"

면접 포인트: "게임은 반응성이 중요해서 TCP_NODELAY로 Nagle을 끈다. 대역폭 효율을 약간 포기하는 대신 지연을 없앤다." — 이렇게 말하면 실무를 아는 답이다.

SECTION 05 · 코드

5게임 클라이언트 소켓 설정의 전형

FSocket* TcpSocket = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)
    ->CreateSocket(NAME_Stream, TEXT("GameTcp"), false);

TcpSocket->Connect(*ServerAddr);

// (1) Nagle 끄기 — 작은 입력 패킷을 즉시 보낸다
TcpSocket->SetNoDelay(true);

// (2) 송수신 버퍼 크기 조절 — 흐름 제어 윈도우에 영향
int32 NewSize = 0;
TcpSocket->SetSendBufferSize(64 * 1024, NewSize);
TcpSocket->SetReceiveBufferSize(64 * 1024, NewSize);

// 이제 작은 패킷을 보내면 모으지 않고 바로 나간다
TcpSocket->Send((uint8*)&KeyCode, 1, BytesSent);   // 즉시 전송됨

SetNoDelay(true) 한 줄이 도입의 "입력이 뭉쳐서 늦게 오던" 문제를 해결한다. 게임 네트워크 코드에 관용구처럼 들어간다.
