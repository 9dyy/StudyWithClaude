# 14강 — 파일 시스템 기본

> **목표:** "파일을 연다"는 게 실제로 무슨 뜻인지 안다. 파일 핸들/디스크립터, inode, 디렉토리, `CreateFile`의 내부.
> **선수 지식:** 2강 (시스템 콜), 3강 (메모리 구조).

> **Part 5 I/O와 파일 시스템 시작.** "비동기 로딩의 정체"로 가는 길.

---

## 1. 도입 — "파일을 연다"는 게 뭘까

게임에서 세이브 파일을 읽는다.

```cpp
FString SaveData;
FFileHelper::LoadFileToString(SaveData, TEXT("Save01.sav"));
```

이 한 줄을 풀어보면 보통 이렇게 동작한다.

```cpp
// 의사 코드로 펼치면
FileHandle = Open("Save01.sav");   // 1. 파일 "열기"
Read(FileHandle, Buffer);          // 2. 내용 읽기
Close(FileHandle);                 // 3. 파일 "닫기"
```

"읽기"는 알겠는데 **"연다"와 "닫는다"는 정확히 뭘 하는 걸까?** 파일은 SSD에 그대로 있는데, 연다고 어디로 옮겨지는 것도 아니고.

답을 알려면 파일 시스템이 파일을 어떻게 관리하는지 봐야 한다.

---

## 2. 파일이란 — 두 부분으로 되어 있다

디스크에 있는 파일 하나는 사실 **두 가지**로 구성된다.

1. **실제 데이터 (내용)** — 바이트들. 디스크 블록 여기저기 흩어져 저장됨.
2. **메타데이터 (정보)** — 크기, 생성/수정 시각, 권한, 그리고 **"데이터가 디스크 어디에 있는지"** 위치 목록.

```
파일 "Save01.sav"
├─ 메타데이터
│   ├─ 크기: 4096 bytes
│   ├─ 수정 시각: 2026-06-15
│   ├─ 권한: 읽기/쓰기
│   └─ 데이터 위치: [블록 17, 블록 42, 블록 9]   ← 핵심!
└─ 실제 데이터
    └─ 블록 17, 42, 9 에 흩어져 저장
```

흥미로운 점: **파일 이름은 메타데이터에 없다.** 이름은 디렉토리가 따로 관리한다(뒤에서).

---

## 3. inode — 파일의 신분증

유닉스 계열(Linux, macOS)에서 이 메타데이터 덩어리를 **inode(아이노드)** 라고 한다. 파일 하나당 inode 하나.

```
inode (파일의 모든 정보, 단 이름 빼고)
┌────────────────────────────┐
│ inode 번호: 12345           │
│ 파일 타입: 일반 파일         │
│ 크기: 4096                  │
│ 소유자, 권한                 │
│ 타임스탬프 (생성/수정/접근)   │
│ 데이터 블록 포인터:          │
│   [블록 17][블록 42][블록 9] │ ← 데이터 실제 위치
└────────────────────────────┘
```

> Windows의 NTFS도 비슷한 걸 한다. MFT(Master File Table)의 레코드가 inode 역할. 개념은 같다: "이름 빼고 파일에 관한 모든 정보 + 데이터 위치".

핵심: **파일 = inode(메타데이터) + 데이터 블록들.**

---

## 4. 디렉토리 — 이름 → inode 매핑표

그럼 파일 이름은 어디에? **디렉토리(폴더)가 "이름 → inode 번호" 매핑을 들고 있다.**

```
디렉토리 "/SaveGames/"
┌──────────────┬───────────┐
│   이름        │ inode 번호 │
├──────────────┼───────────┤
│ Save01.sav   │   12345   │
│ Save02.sav   │   12389   │
│ Config.ini   │    9001   │
└──────────────┴───────────┘
```

디렉토리도 사실 **특별한 파일**이다. 내용이 "이름→inode 표"인 파일.

### 파일을 찾는 과정

`/SaveGames/Save01.sav`를 열면:

```
1. 루트 디렉토리 "/" 에서 "SaveGames" 찾음 → inode 번호 얻음
2. SaveGames 디렉토리 읽음 → "Save01.sav" 찾음 → inode 12345
3. inode 12345 읽음 → 데이터 블록 위치 [17, 42, 9] 얻음
4. 블록 17, 42, 9 읽음 → 실제 내용
```

경로가 깊을수록 이 과정이 길어진다. 그래서 OS는 이 결과를 캐싱한다(dentry cache 등).

### 하드 링크와의 연결 (보너스)

이름과 inode가 분리돼 있으니, **여러 이름이 같은 inode를 가리킬 수 있다.** 이게 하드 링크. 이름은 둘인데 실제 파일은 하나. 면접에서 "하드링크 vs 심볼릭링크" 물으면:
- 하드 링크: 같은 inode를 가리키는 또 다른 이름.
- 심볼릭(소프트) 링크: "다른 경로를 가리키는" 별도 파일 (바로가기). 원본 지워지면 깨짐.

---

## 5. 이제 "파일을 연다"의 진짜 의미

`Open("Save01.sav")` 가 하는 일:

```
1. 경로 해석 → inode 12345 찾음 (위의 디렉토리 탐색)
2. 권한 검사 (이 프로세스가 읽어도 되나?)
3. inode를 메모리에 올림
4. 커널에 "열린 파일" 항목을 만듦 (현재 읽기 위치 = 0 등)
5. 이 프로세스의 파일 디스크립터 테이블에 등록
6. 그 번호(파일 디스크립터 / 핸들)를 반환
```

핵심: **"연다"는 데이터를 옮기는 게 아니라, 커널에 "이 파일을 쓸 준비" 상태를 만들고 그 핸들을 받는 것.**

"닫는다"는 그 핸들과 커널 항목을 정리하는 것.

---

## 6. 파일 디스크립터 / 파일 핸들

열린 파일을 가리키는 **번호표**.

- **유닉스:** 파일 디스크립터(File Descriptor, fd) — 작은 정수 (0, 1, 2, 3...)
- **Windows:** 파일 핸들(HANDLE) — 불투명한 포인터 같은 값

```
프로세스의 파일 디스크립터 테이블
┌─────┬─────────────────────────┐
│ fd  │ 가리키는 것              │
├─────┼─────────────────────────┤
│  0  │ 표준 입력 (stdin)        │
│  1  │ 표준 출력 (stdout)       │
│  2  │ 표준 에러 (stderr)       │
│  3  │ Save01.sav (읽기 위치 0) │ ← Open이 반환한 것
│  4  │ Config.ini              │
└─────┴─────────────────────────┘
```

fd 0,1,2가 입출력에 예약된 게 보인다. `printf`가 stdout(fd 1)으로 나가는 게 이거.

### 왜 직접 inode를 안 주고 핸들을 줄까?

- **보안:** 프로세스가 디스크 구조를 직접 못 만지게. 커널이 핸들을 통해서만 접근 허용.
- **상태 관리:** "지금 어디까지 읽었나(파일 오프셋)" 같은 걸 커널이 핸들마다 관리.
- **추상화:** 파일, 소켓, 파이프, 디바이스가 다 같은 fd로 추상화됨. "Everything is a file" (유닉스 철학).

## 7. 언리얼 / Win32와 연결

```cpp
// 언리얼 추상화
IFileHandle* Handle = IPlatformFile::GetPlatformPhysical().OpenRead(*FilePath);
//          ↑ 내부적으로 Windows의 CreateFile() 호출

// Win32 직접 (언리얼이 내부에서 이렇게 부름)
HANDLE hFile = CreateFile(
    L"Save01.sav",
    GENERIC_READ,           // 읽기 권한
    FILE_SHARE_READ,        // 다른 프로세스도 읽기는 허용
    nullptr,
    OPEN_EXISTING,          // 기존 파일 열기
    FILE_ATTRIBUTE_NORMAL,
    nullptr);
// hFile 이 파일 핸들. 이걸로 ReadFile/WriteFile/CloseHandle.
```

`CreateFile`이라는 이름이 헷갈리는데, **만들기 전용이 아니라 "열기"도 한다.** 위처럼 `OPEN_EXISTING`이면 기존 파일 열기. Windows API의 작명 함정.

언리얼에서 우리가 쓰는 `FFileHelper`, `IFileManager`, `IPlatformFile` 가 결국 이런 OS 콜로 내려간다. (1강에서 본 "엔진이 OS API를 감싼다"의 구체적 사례)

## 8. 버퍼링 — 매번 디스크 가면 느리니까

2강에서 "시스템 콜은 비싸다"고 했다. 파일 I/O는 시스템 콜 + 디스크 접근이라 더 비싸다. 그래서 여러 층의 버퍼/캐시가 낀다.

```
우리 코드
    ↓ fread / 라이브러리 버퍼 (유저 공간)
C 런타임 버퍼
    ↓ read() 시스템 콜
커널 페이지 캐시 (RAM)  ← OS가 디스크 내용을 RAM에 캐싱
    ↓ (캐시 미스일 때만)
디스크 (SSD/HDD)
```

### 페이지 캐시 — 한 번 읽은 파일은 RAM에 남는다

OS는 디스크에서 읽은 파일 내용을 **RAM(페이지 캐시)에 보관**한다. 같은 파일을 또 읽으면 디스크 안 가고 RAM에서 바로 준다.

```cpp
// 처음 읽기 — 디스크 접근. 느림 (수 ms)
FFileHelper::LoadFileToString(S, TEXT("Big.txt"));

// 두 번째 읽기 — 페이지 캐시에서. 빠름 (수 μs)
FFileHelper::LoadFileToString(S, TEXT("Big.txt"));
```

게임 처음 켤 때 로딩이 느리다가 두 번째부터 빨라지는 게 이 캐시 덕분(과 다른 요인들). 12강의 페이지 캐시/메모리 맵과 연결된다.

---

## 9. 게임 개발자 입장 — 알아둘 것

### (1) 핸들은 자원이다 — 반드시 닫아라

파일 핸들은 유한한 자원이다. 안 닫으면 **핸들 누수**. 게임이 오래 돌면 "Too many open files" 에러로 죽을 수 있다.

```cpp
// ❌ 핸들 누수 가능
IFileHandle* H = PlatformFile.OpenRead(*Path);
if (Failed) return;   // H 안 닫고 빠져나감

// ✅ RAII로 자동 정리 (8강 FScopeLock과 같은 원리)
{
    TUniquePtr<IFileHandle> H(PlatformFile.OpenRead(*Path));
    // ... 사용
}   // 스코프 끝 → 자동 닫힘
```

### (2) 작은 파일 많이 < 큰 파일 적게

2강에서 본 것처럼 Open/Close는 시스템 콜 + 디렉토리 탐색이라 비싸다. 작은 파일 1만 개를 여닫느니, 하나로 합쳐서(pak 파일) 한 번에 여는 게 빠르다. **언리얼이 에셋을 `.pak`으로 묶는 이유 중 하나.**

### (3) 경로 탐색도 비용

경로가 깊으면 디렉토리를 단계마다 읽어야 한다. 핫 패스에서 매번 풀 경로로 파일 여는 건 피하라.

## 10. 흔한 오해

### 오해 1: "파일을 열면 내용이 메모리에 다 올라온다"

아니다. `Open`은 핸들만 만든다. 내용은 `Read`를 호출해야 그 만큼만 올라온다. 4GB 파일을 열어도 메모리는 거의 안 늘어남.

### 오해 2: "파일 이름은 파일 자체에 저장돼 있다"

아니다. 이름은 **디렉토리**가 관리하는 "이름 → inode" 매핑에 있다. 파일 본체(inode)에는 이름이 없다. 그래서 같은 파일에 여러 이름(하드링크)이 가능.

### 오해 3: "`CreateFile`은 파일을 만들기만 한다"

Windows API의 `CreateFile`은 **열기도 한다.** 플래그(`OPEN_EXISTING`, `CREATE_ALWAYS` 등)로 동작이 결정됨. 이름이 오해를 부르는 대표 케이스.

### 오해 4: "파일 닫는 건 안 해도 OS가 알아서 한다"

프로세스가 종료되면 OS가 다 정리하는 건 맞다. 하지만 게임처럼 오래 도는 프로세스는 그 사이 핸들이 쌓여서 누수가 된다. **명시적으로 닫아야 한다.** (Heap 메모리 누수와 같은 맥락)

### 오해 5: "두 번 읽으면 두 번 다 디스크에 간다"

OS의 페이지 캐시 덕분에 두 번째부터는 보통 RAM에서 준다. 그래서 두 번째 읽기가 훨씬 빠르다.

## 11. 면접에서 나오면

**Q1. "파일을 연다"는 게 OS 입장에서 무슨 의미인가요?**
→ "데이터를 옮기는 게 아니라, 경로를 해석해 파일의 메타데이터(inode)를 찾고 권한을 검사한 뒤, 커널에 '열린 파일' 항목을 만들고 그 핸들(파일 디스크립터)을 프로세스에 돌려주는 동작입니다. 이후 읽기/쓰기는 이 핸들을 통해 이뤄집니다."

**Q2. inode가 뭔가요?**
→ "유닉스 계열에서 파일의 메타데이터를 담는 구조입니다. 파일 크기, 권한, 타임스탬프, 그리고 실제 데이터가 디스크 어디에 있는지 블록 위치를 담습니다. 특이하게도 파일 이름은 inode에 없고 디렉토리가 따로 관리합니다. Windows NTFS에서는 MFT 레코드가 비슷한 역할을 합니다."

**Q3. 파일 이름은 어디에 저장되나요?**
→ "디렉토리에 저장됩니다. 디렉토리는 '이름 → inode 번호' 매핑을 담은 특별한 파일입니다. 파일 본체인 inode에는 이름이 없어서, 여러 이름이 같은 inode를 가리키는 하드 링크가 가능합니다."

**Q4. 파일 디스크립터(핸들)가 뭔가요?**
→ "열린 파일을 가리키는 번호표입니다. 유닉스에선 작은 정수, Windows에선 HANDLE입니다. 0,1,2는 표준 입출력에 예약돼 있습니다. 프로세스가 디스크 구조를 직접 만지지 못하게 커널이 핸들을 통해서만 접근을 허용하고, 현재 읽기 위치 같은 상태도 핸들 단위로 관리합니다."

**Q5. 하드 링크와 심볼릭 링크의 차이는?**
→ "하드 링크는 같은 inode를 가리키는 또 다른 이름이라 원본을 지워도 다른 이름으로 접근 가능합니다. 심볼릭 링크는 다른 경로를 가리키는 별도 파일(바로가기)이라 원본이 사라지면 깨집니다."

**Q6. 같은 파일을 두 번 읽으면 왜 두 번째가 빠른가요?**
→ "OS의 페이지 캐시 때문입니다. 디스크에서 읽은 내용을 RAM에 캐싱해두고, 같은 파일을 다시 읽으면 디스크에 가지 않고 RAM에서 바로 돌려줍니다. 그래서 두 번째 접근이 수 밀리초에서 수 마이크로초 수준으로 빨라집니다."

**Q7. 게임에서 작은 에셋 파일을 .pak으로 묶는 이유는?**
→ "파일을 여닫는 Open/Close는 시스템 콜과 디렉토리 탐색을 동반해서 비쌉니다. 작은 파일 수만 개를 각각 여는 것보다 하나의 큰 파일로 묶어 한 번 열고 내부 오프셋으로 접근하는 게 시스템 콜 횟수와 탐색 비용을 크게 줄여줍니다."

## 12. 셀프 체크

- [ ] "파일을 연다"가 데이터 이동이 아니라 핸들 생성이라는 걸 안다.
- [ ] 파일이 메타데이터(inode) + 데이터 블록으로 구성된다는 걸 안다.
- [ ] 파일 이름이 디렉토리의 "이름→inode" 매핑에 있다는 걸 안다.
- [ ] 파일 디스크립터/핸들이 뭐고 왜 직접 inode를 안 주는지 안다.
- [ ] 페이지 캐시 덕분에 재읽기가 빠르다는 걸 안다.
- [ ] 핸들을 안 닫으면 누수가 된다는 걸 알고 RAII로 처리할 줄 안다.
- [ ] 에셋을 .pak으로 묶는 이유를 시스템 콜 관점에서 설명할 수 있다.
