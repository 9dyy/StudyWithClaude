# 15강 — 블로킹 vs 논블로킹 I/O, 비동기 I/O

> **목표:** "비동기 로딩"이 정확히 무슨 뜻인지 안다. 블로킹/논블로킹/동기/비동기를 구분하고, 언리얼의 `FStreamableManager`와 IOCP가 뒤에서 하는 일을 이해한다.
> **선수 지식:** 6강 (스레드 상태/Waiting), 14강 (파일 시스템), 5강 (언리얼 스레드).

> **본강의 마지막.** 강의 계획서 첫머리에 약속한 "비동기 로딩의 정체"를 드디어 회수한다.

---

## 1. 도입 — 텍스처 로딩하다 게임이 멈췄다

5강, 12강에서 계속 나온 그 장면.

```cpp
void AMyActor::BeginPlay()
{
    UTexture2D* Tex = LoadObject<UTexture2D>(nullptr, TEXT("/Game/BigTexture"));
    // 이 줄에서 디스크 읽기 끝날 때까지 Game Thread가 멈춤 → 게임 정지
    Mesh->SetMaterialTexture(Tex);
}
```

`LoadObject`는 **디스크에서 텍스처를 다 읽어올 때까지 반환하지 않는다.** 그동안 Game Thread는 6강에서 배운 **Waiting 상태**로 잠들어 있다. 50MB 텍스처면 수십~수백 ms. 게임이 그만큼 멈춘다(hitch).

해결책이 "비동기 로딩"인데, 정확히 뭐가 다른 걸까? 용어부터 정리하자.

---

## 2. 두 개의 축 — 헷갈리는 4개 용어 정리

**블로킹/논블로킹**과 **동기/비동기**는 다른 축이다. 면접에서 자주 섞어 묻는다.

### 축 1: 블로킹 vs 논블로킹 — "기다리느냐?"

- **블로킹(Blocking):** 결과 나올 때까지 **호출이 안 돌아온다.** 스레드가 멈춰서 기다림.
- **논블로킹(Non-blocking):** 결과가 준비 안 됐으면 **"아직 안 됐어"하고 즉시 반환.** 스레드는 안 멈춤.

### 축 2: 동기 vs 비동기 — "누가 결과를 챙기느냐?"

- **동기(Synchronous):** 내가 직접 결과를 받아온다(혹은 직접 폴링).
- **비동기(Asynchronous):** 작업을 맡겨두고 **완료되면 콜백/이벤트로 알려준다.** 나는 내 일 함.

### 조합

```
                동기(직접 챙김)         비동기(알려줌)
블로킹     ┌──────────────────┬──────────────────┐
(기다림)   │ 일반 read()       │ (드묾)            │
           │ 결과 올 때까지 멈춤 │                  │
           ├──────────────────┼──────────────────┤
논블로킹   │ 논블로킹 + 폴링    │ 진짜 비동기 I/O    │
(안 기다림)│ "됐어?" 반복 확인  │ 맡기고 콜백 받음   │
           └──────────────────┴──────────────────┘
```

게임 비동기 로딩이 노리는 건 **오른쪽 아래: 논블로킹 + 비동기.** "로딩 맡겨놓고 Game Thread는 계속 돌다가, 다 되면 콜백 받기."

---

## 3. 각 방식 코드로

### (1) 동기 블로킹 — 가장 단순, 가장 위험

```cpp
// Game Thread를 멈춘다
FString Data;
FFileHelper::LoadFileToString(Data, *Path);   // 끝날 때까지 블록
UseData(Data);                                  // 그 다음 줄
```

직관적이지만 Game Thread에서 쓰면 hitch. 14강의 페이지 캐시에 있으면 빠르지만, 디스크까지 가면 멈춤.

### (2) 논블로킹 + 폴링 — 직접 챙기기

```cpp
// "다 됐니?"를 매 프레임 물어봄
void Tick(float Dt)
{
    if (LoadRequest.IsReady())   // 논블로킹 확인
    {
        UseData(LoadRequest.GetResult());
    }
    // 안 됐으면 그냥 다음 프레임에 또 확인. Game Thread는 안 멈춤.
}
```

Game Thread는 안 멈추는데, 매번 "됐어?" 물어보는 게 좀 번거롭다.

### (3) 비동기 + 콜백 — 게임에서 쓰는 방식

```cpp
// 맡겨놓고, 끝나면 알려달라고 함
StreamableManager.RequestAsyncLoad(
    AssetRef,
    FStreamableDelegate::CreateUObject(this, &AMyActor::OnLoaded)
);
// 이 줄은 즉시 반환. Game Thread 계속 돎.

void AMyActor::OnLoaded()   // 로딩 완료되면 Game Thread에서 자동 호출
{
    UTexture2D* Tex = AssetRef.Get();
    Mesh->SetMaterialTexture(Tex);
}
```

이게 5강에서 예고한 `ENQUEUE`/`AsyncTask` 패턴의 I/O 버전. **맡기고 → 콜백.**

---

## 4. 그럼 비동기 I/O는 누가 기다리나?

"논블로킹이라 아무도 안 기다린다"는 건 거짓말이다. **디스크는 여전히 느리다.** 누군가는 그 디스크 응답을 기다려야 한다. 핵심은 **"누가 기다리느냐"**다.

### 방법 A: 워커 스레드가 대신 블로킹 (간단한 구현)

```
Game Thread:  RequestAsyncLoad() ─→ (즉시 반환, 계속 게임)
                    │ 작업 위임
                    ↓
Worker Thread:  LoadFileToString() ─ [블로킹! 여기서 Waiting] ─→ 완료
                    │ 콜백 큐에 등록
                    ↓
Game Thread:  다음 Tick에서 OnLoaded() 호출
```

5강의 `AsyncTask(BackgroundThread, ...)`가 이 방식. **블로킹을 Game Thread 밖으로 옮긴 것.** Game Thread 입장에선 비동기, 워커 입장에선 블로킹.

이게 가장 이해하기 쉬운 비동기. 다만 I/O 하나당 워커 스레드 하나가 잠들어 있어야 해서, 수천 개 동시 I/O엔 스레드가 부족하다.

### 방법 B: OS의 진짜 비동기 I/O (IOCP)

OS에게 "이 파일 읽어줘, 다 되면 알려줘" 하고 **스레드를 안 재우는** 방식. 디스크 컨트롤러(DMA)가 데이터를 옮기는 동안 CPU도 워커 스레드도 안 기다린다. 완료되면 OS가 통지.

- **Windows:** IOCP (I/O Completion Port)
- **Linux:** io_uring, epoll (+AIO)

```
Game Thread:  ReadFileEx(완료 포트 등록) ─→ 즉시 반환
                    │
                    ↓ (스레드는 아무도 안 기다림. DMA가 일함)
              디스크 → RAM 으로 데이터 이동 (CPU 개입 최소)
                    │ 완료!
                    ↓
              OS가 완료 포트에 통지 → 처리 스레드가 콜백 실행
```

장점: 수만 개의 동시 I/O를 적은 스레드로 처리. **게임 서버 네트워크(수천 접속)의 핵심 기술.** 클라에서도 대량 에셋 스트리밍에 유리.

## 5. 언리얼의 비동기 로딩 시스템

### FStreamableManager — 에셋 비동기 로딩

```cpp
// 멤버
FStreamableManager StreamableManager;
TSoftObjectPtr<UTexture2D> TextureToLoad;   // "약한" 참조 (아직 로드 안 됨)

void StartLoading()
{
    StreamableManager.RequestAsyncLoad(
        TextureToLoad.ToSoftObjectPath(),
        FStreamableDelegate::CreateUObject(this, &AMyActor::OnTextureLoaded)
    );
    // 즉시 반환. 게임 계속.
}

void OnTextureLoaded()
{
    if (UTexture2D* Tex = TextureToLoad.Get())   // 이제 메모리에 있음
        ApplyTexture(Tex);
}
```

- `TSoftObjectPtr` / `FSoftObjectPath`: "이 에셋, 필요하면 그때 로드" 하는 약한 참조. 게임 시작 시 다 안 올리고 필요할 때 스트리밍.
- 내부적으로 워커 스레드 + 플랫폼 비동기 I/O를 섞어 쓴다.

### Async Loading Thread (ALT)

언리얼은 에셋 직렬화/로딩을 전담하는 별도 스레드를 둘 수 있다. 패키지 읽기와 객체 생성 일부를 Game Thread 밖에서 처리해서 hitch를 줄인다.

### Level Streaming

오픈월드에서 플레이어 위치 근처 레벨만 비동기로 올리고 멀어지면 언로드. 12강의 "워킹 셋을 RAM 안에 유지"의 실천.

```cpp
// 레벨 스트리밍 (블루프린트/코드)
UGameplayStatics::LoadStreamLevel(this, TEXT("Forest_01"),
    /*bMakeVisible=*/true, /*bShouldBlock=*/false, LatentInfo);
//                                          ↑ false = 비동기 (블로킹 안 함)
```

`bShouldBlock=true`로 주면 동기 블로킹 로딩이 되어버린다(hitch 발생). 의도하지 않으면 false.

## 6. 전체 그림 — 5강~15강이 다 모인다

```
Game Thread
   │ RequestAsyncLoad() — 즉시 반환 (논블로킹)
   │ ↓ 계속 Tick, 렌더, 입력 처리... (안 멈춤!)
   │
   ├──→ [위임]
   │       ↓
   │   Worker / Async Loading Thread
   │       │ 파일 핸들 열기 (14강)
   │       │ OS 비동기 I/O 요청 (IOCP) 또는 블로킹 읽기
   │       │     ↓
   │       │   디스크 → 페이지 캐시 → RAM (DMA)
   │       │     ↓ 완료 통지
   │       │ 역직렬화, 객체 준비
   │       │ 완료 콜백을 Game Thread 큐에 등록
   │       ↓
   │   [다음 Tick]
   ↓
OnLoaded() — Game Thread에서 안전하게 실행 (5강: UObject는 Game Thread 전용)
```

- **6강:** 블로킹 = Waiting 상태로 잠듦
- **5강:** 워커에서 로딩, 결과는 Game Thread 콜백
- **14강:** 파일 핸들, 페이지 캐시
- **12강:** 디스크 읽기 = major fault급 비용
- **15강:** 그 모든 걸 Game Thread 밖으로 빼는 게 비동기 I/O

## 7. 흔한 오해

### 오해 1: "비동기면 더 빠르다"

총 작업량과 디스크 속도는 그대로다. **디스크 읽기 자체가 빨라지는 게 아니다.** 비동기는 그 대기 시간 동안 **Game Thread가 다른 일을 하게** 해서 체감 성능(반응성)을 올리는 것. throughput이 아니라 responsiveness.

### 오해 2: "논블로킹 = 비동기"

다르다. 논블로킹은 "안 기다리고 즉시 반환", 비동기는 "완료를 알려줌". 논블로킹+폴링은 비동기가 아니다(내가 계속 물어봐야 하니까). 진짜 비동기는 콜백/통지가 온다.

### 오해 3: "비동기 콜백은 워커 스레드에서 실행된다"

언리얼의 `FStreamableManager` 완료 콜백은 **Game Thread에서** 실행된다(그래야 UObject를 안전하게 만짐). 라이브러리마다 다르니 "이 콜백이 어느 스레드에서 도나"를 항상 확인해야 한다. (5강: UObject는 Game Thread 전용)

### 오해 4: "IOCP는 스레드를 안 쓴다"

IOCP도 완료를 처리할 스레드 풀은 있다. 다만 **I/O 대기 동안 스레드를 점유하지 않는다**는 게 핵심. "I/O당 스레드 1개"가 아니라 "적은 스레드로 많은 I/O"가 가능한 것.

### 오해 5: "bShouldBlock=true가 더 안전하다"

레벨 스트리밍에서 block=true는 로딩 끝까지 Game Thread를 멈춰서 **확실히 끊긴다.** 로딩 화면처럼 어차피 멈춰도 되는 상황 아니면 false로 비동기.

## 8. 면접에서 나오면

**Q1. 블로킹과 논블로킹의 차이는?**
→ "블로킹은 작업 결과가 나올 때까지 호출이 반환되지 않고 스레드가 멈춰 기다립니다. 논블로킹은 결과가 준비되지 않았으면 즉시 '아직 안 됐다'고 반환해서 스레드가 멈추지 않습니다."

**Q2. 동기와 비동기의 차이는?**
→ "동기는 호출자가 직접 결과를 받아오거나 직접 완료를 확인합니다. 비동기는 작업을 맡겨두고 완료되면 콜백이나 이벤트로 통지받아서, 그동안 다른 일을 할 수 있습니다. 블로킹/논블로킹은 '기다리느냐'의 축이고, 동기/비동기는 '누가 완료를 챙기느냐'의 축이라 서로 다른 개념입니다."

**Q3. 게임에서 에셋을 비동기 로딩하는 이유는?**
→ "디스크 읽기는 수십에서 수백 밀리초가 걸리는데, Game Thread에서 동기로 읽으면 그동안 Tick이 멈춰 hitch가 발생합니다. 비동기 로딩은 그 대기를 워커 스레드나 OS 비동기 I/O로 넘기고, Game Thread는 계속 게임을 돌리다가 완료 콜백만 받습니다. 디스크가 빨라지는 게 아니라 반응성을 유지하는 것입니다."

**Q4. 비동기 I/O라도 디스크는 느린데 누가 기다리나요?**
→ "두 가지 방식이 있습니다. 하나는 워커 스레드가 대신 블로킹으로 기다리는 방식으로, Game Thread만 자유롭고 워커는 Waiting 상태가 됩니다. 다른 하나는 OS의 진짜 비동기 I/O(Windows IOCP, Linux io_uring)로, DMA가 데이터를 옮기는 동안 어떤 스레드도 점유하지 않고 완료 시 OS가 통지합니다. 후자가 적은 스레드로 대량 I/O를 처리할 수 있습니다."

**Q5. IOCP가 뭔가요?**
→ "Windows의 비동기 I/O 완료 통지 메커니즘입니다. I/O를 요청해두면 스레드를 대기에 묶지 않고, 완료되면 완료 포트를 통해 처리 스레드 풀에 통지합니다. 수천, 수만 개의 동시 I/O를 적은 스레드로 처리할 수 있어서 게임 서버 네트워크나 대량 에셋 스트리밍에 쓰입니다."

**Q6. 비동기 콜백을 작성할 때 주의할 점은?**
→ "그 콜백이 어느 스레드에서 실행되는지 확인해야 합니다. 언리얼의 FStreamableManager 콜백은 Game Thread에서 실행되어 UObject를 안전하게 만질 수 있지만, 라이브러리에 따라 워커 스레드에서 호출되는 경우도 있습니다. 워커 스레드라면 UObject 생성이나 UI 갱신을 직접 하면 안 되고 Game Thread로 다시 넘겨야 합니다."

**Q7. `LoadObject`(동기)와 `RequestAsyncLoad`(비동기)는 언제 각각 쓰나요?**
→ "로딩 화면처럼 어차피 멈춰도 되는 상황이나, 지금 당장 없으면 진행이 불가능한 소량 데이터는 동기 로딩이 단순해서 낫습니다. 게임플레이 도중 들어오는 대형 에셋, 레벨 스트리밍, 텍스처 스트리밍처럼 hitch를 피해야 하는 경우는 비동기 로딩을 씁니다."

## 9. 셀프 체크

- [ ] 블로킹/논블로킹과 동기/비동기가 다른 축이라는 걸 안다.
- [ ] 4가지 조합을 표로 그릴 수 있다.
- [ ] 게임 비동기 로딩이 노리는 조합(논블로킹+비동기)을 안다.
- [ ] "비동기라도 누군가는 디스크를 기다린다"는 걸 안다 (워커 블로킹 vs IOCP).
- [ ] IOCP가 적은 스레드로 대량 I/O를 처리하는 원리를 안다.
- [ ] `FStreamableManager` 콜백이 Game Thread에서 실행되는 이유를 안다.
- [ ] 비동기가 throughput이 아니라 responsiveness를 위한 거라는 걸 안다.
