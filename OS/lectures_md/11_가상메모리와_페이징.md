# 11강 — 가상 메모리와 페이징

> **목표:** 각 프로세스가 어떻게 똑같이 `0x00000000`부터 시작하는 주소를 쓸 수 있는지 이해한다. 가상 주소가 물리 주소로 어떻게 변환되는지, 페이지 테이블과 TLB의 정체.
> **선수 지식:** 3강 (프로세스 메모리 구조), 4강 (프로세스 vs 스레드).

> **Part 4 메모리 관리 시작.** 여기부터는 "성능 최적화의 근거"가 나온다.

---

## 1. 도입 — 이상한 일이 벌어진다

3강에서 본 메모리 구조. 게임을 두 개 띄우고 디버거로 들여다보면 이상한 걸 발견한다.

```cpp
// 프로세스 A에서
int g_Value = 42;
UE_LOG(LogTemp, Log, TEXT("주소: %p"), &g_Value);
// 출력: 주소: 0x00007FF6_12340000

// 프로세스 B (같은 exe)에서
int g_Value = 99;
UE_LOG(LogTemp, Log, TEXT("주소: %p"), &g_Value);
// 출력: 주소: 0x00007FF6_12340000   ← 똑같은 주소!
```

**두 프로세스의 `g_Value`가 똑같은 주소 `0x...12340000`에 있다.** 그런데 A는 42, B는 99다. 같은 주소에 다른 값?

물리 RAM은 하나뿐인데 어떻게 같은 주소가 다른 값을 가질까?

답: 저 주소는 **진짜 주소(물리 주소)가 아니다.** 가짜 주소, **가상 주소(Virtual Address)** 다.

---

## 2. 가상 메모리 — "모든 프로세스에게 거짓말을 한다"

OS는 각 프로세스에게 이렇게 거짓말한다.

> "이 컴퓨터의 메모리는 전부 네 거야. 0번지부터 끝까지 다 너 혼자 써."

프로세스 A도, B도, 크롬도 전부 이 거짓말을 믿는다. 각자 `0x0` 부터 시작하는 **자기만의 완전한 주소 공간**을 가졌다고 생각한다.

```
프로세스 A가 보는 메모리        프로세스 B가 보는 메모리
(가상 주소)                    (가상 주소)
┌──────────────┐ 0xFFFF...    ┌──────────────┐ 0xFFFF...
│   ...        │              │   ...        │
│ g_Value=42   │ 0x1234_0000  │ g_Value=99   │ 0x1234_0000
│   ...        │              │   ...        │
└──────────────┘ 0x0000...    └──────────────┘ 0x0000...
```

둘 다 `0x1234_0000` 을 쓰지만, OS가 뒤에서 **각자 다른 물리 RAM 위치로 연결**해준다.

```
       가상 주소                      물리 RAM (진짜)
A: 0x1234_0000  ─────────────────→  0x0A000000  (값 42)
B: 0x1234_0000  ─────────────────→  0x3F000000  (값 99)
```

이 "가상 → 물리" 변환을 OS와 CPU(MMU)가 자동으로 해준다. 우리 코드는 가상 주소만 보고, 물리 주소는 영원히 모른다.

---

## 3. 왜 이렇게 귀찮은 짓을 하나?

가상 메모리가 주는 이득은 어마어마하다.

### (1) 프로세스 격리 (보안/안정성)

A의 가상 주소 `0x1234_0000`은 A의 물리 영역으로만 연결된다. **A가 무슨 주소를 써도 B의 물리 메모리엔 닿을 수 없다.** 4강에서 말한 "프로세스는 서로 메모리를 못 본다"가 이 구조 덕분.

게임이 크래시 나도 디스코드는 멀쩡한 이유.

### (2) 메모리 단편화 해결

물리 RAM이 여기저기 조각나 있어도, 가상 주소 공간에서는 **연속된 것처럼** 보이게 매핑할 수 있다.

```
가상 (연속):  [████████████]
                 ↓ ↓ ↓ ↓
물리 (흩어짐): [██] [..] [██] [██] [..] [██]
```

`TArray`가 1GB를 연속으로 잡을 수 있는 것도, 실제 물리 RAM은 조각나 있어도 가상에서 연속으로 보여서다.

### (3) 실제 RAM보다 큰 메모리 사용 (스왑)

가상 주소 공간은 RAM보다 클 수 있다. 당장 안 쓰는 부분은 SSD로 내려놨다가(스왑) 필요할 때 다시 올린다. (다음 강의 12강 주제)

### (4) 코드 공유

같은 exe를 두 번 띄우면, 코드(Text) 영역은 물리 RAM에 **한 벌만** 두고 두 프로세스의 가상 주소가 같은 물리 위치를 가리키게 한다. RAM 절약. (3강에서 "Text는 공유 가능"이라 한 게 이거)

## 4. 페이징 — 메모리를 페이지 단위로 쪼갠다

가상 → 물리 변환을 바이트 하나하나 다 기록하면 표가 너무 커진다. 그래서 **일정 크기 덩어리** 단위로 관리한다. 이 덩어리가 **페이지(Page)**.

- **페이지(Page):** 가상 메모리를 자른 고정 크기 덩어리. 보통 **4KB**.
- **프레임(Frame):** 물리 RAM을 자른 같은 크기 덩어리. 역시 4KB.

변환은 "이 가상 페이지 → 저 물리 프레임" 단위로 이뤄진다.

```
가상 주소 공간 (페이지들)        물리 RAM (프레임들)
┌─────┐ Page 0  ───────────────→ Frame 17
├─────┤ Page 1  ───────┐
├─────┤ Page 2  ───┐   └───────→ Frame 3
├─────┤ Page 3  ┐  └───────────→ Frame 42
└─────┘         └──────────────→ Frame 9
```

### 가상 주소의 구조

가상 주소 하나는 두 부분으로 나뉜다.

```
가상 주소 (예: 4KB 페이지 = 12비트 오프셋)
┌────────────────────┬──────────────┐
│   페이지 번호        │   오프셋      │
│   (Page Number)    │   (Offset)   │
└────────────────────┴──────────────┘
        ↓ 페이지 테이블에서 찾기      ↓ 그대로 사용
┌────────────────────┬──────────────┐
│   프레임 번호        │   오프셋      │  = 물리 주소
└────────────────────┴──────────────┘
```

- **페이지 번호** → 페이지 테이블에서 "이 페이지는 몇 번 프레임" 찾음.
- **오프셋** → 페이지 안에서의 위치. 변환 없이 그대로.

예: 가상 주소 `0x1234_5678`, 4KB 페이지라면
- 페이지 번호 = `0x1234_5` (상위 비트)
- 오프셋 = `0x678` (하위 12비트)
- 페이지 테이블: "`0x1234_5` 페이지 → `0x0A00` 프레임"
- 물리 주소 = `0x0A00_678`

## 5. 페이지 테이블 (Page Table)

"가상 페이지 → 물리 프레임" 매핑을 기록한 표. **프로세스마다 하나씩** 있다.

```
프로세스 A의 페이지 테이블
┌──────────┬───────────┬───────┐
│ 페이지번호 │ 프레임번호  │ 유효? │
├──────────┼───────────┼───────┤
│    0     │    17     │   O   │
│    1     │     3     │   O   │
│    2     │   (없음)   │   X   │ ← 아직 할당 안 됨
│    3     │    42     │   O   │
└──────────┴───────────┴───────┘
```

- **유효 비트(Valid bit):** 이 페이지가 실제 물리 메모리에 올라와 있나? X면 → 페이지 폴트(12강).
- 추가로 권한 비트(읽기/쓰기/실행), 더티 비트, 접근 비트 등이 들어간다.

### 컨텍스트 스위칭과의 연결

6강에서 "다른 프로세스로 컨텍스트 스위칭하면 페이지 테이블을 갈아치운다"고 했다. 이제 이해된다. 프로세스마다 페이지 테이블이 다르니까, A→B 전환 시 CPU가 "이제 B의 페이지 테이블 봐" 하고 바꾼다. 그래서 같은 가상 주소가 다른 물리 위치로 연결되는 것.

---

## 6. MMU와 TLB — 변환이 느리면 안 되니까

### MMU (Memory Management Unit)

가상 → 물리 변환을 **하드웨어**로 해주는 CPU 안의 장치. 우리 코드가 메모리 접근할 때마다 MMU가 자동으로 페이지 테이블을 뒤져서 변환한다.

### 문제: 페이지 테이블도 메모리에 있다

변환하려면 페이지 테이블을 읽어야 하는데, 그 테이블도 RAM에 있다. 그럼 메모리 한 번 접근하려고 메모리를 두 번(테이블 읽기 + 실제 데이터 읽기) 읽는 셈. 게다가 현대 페이지 테이블은 다단계(4단계)라 더 많이 읽어야 한다.

### 해결: TLB (Translation Lookaside Buffer)

**자주 쓰는 "가상→물리" 변환 결과를 캐싱하는 작은 초고속 캐시.** MMU 안에 있다.

```
메모리 접근
    ↓
TLB 확인 ──[있음(TLB Hit)]──→ 바로 물리 주소. 빠름!
    │
   [없음(TLB Miss)]
    ↓
페이지 테이블 뒤짐 → 결과를 TLB에 저장 → 물리 주소. 느림.
```

TLB 적중률은 보통 99% 이상. 그래서 대부분의 변환은 거의 공짜.

### 컨텍스트 스위칭이 비싼 이유 (다시)

6강에서 "다른 프로세스로 스위칭하면 TLB를 무효화한다"고 했다. 프로세스가 바뀌면 가상→물리 매핑이 통째로 달라지니까, 이전 프로세스의 TLB 내용이 다 쓸모없어진다. 그래서 비우고(flush) 다시 채워야 함. 한동안 TLB Miss가 쏟아져서 느려진다.

## 7. 게임 개발자 입장에서 — 이게 왜 중요한가

### (1) "메모리 접근이 공짜가 아니다"

포인터 하나 역참조(`*ptr`)할 때마다 뒤에서 가상→물리 변환이 일어난다. TLB Hit이면 빠르지만, 메모리를 마구 뛰어다니면(랜덤 액세스) TLB Miss가 늘어난다. 13강 캐시 강의와 직결.

### (2) 메모리를 연속으로 쓰면 TLB에 유리

```cpp
// TLB 친화적 — 같은 페이지들을 순서대로
TArray<FVector> Positions;   // 연속 메모리
for (const FVector& P : Positions)   // 페이지를 차례로 → TLB Hit 많음
    Process(P);

// TLB 비친화적 — 여기저기 흩어진 포인터
TArray<FVector*> Pointers;   // 각자 다른 페이지에 흩어짐
for (FVector* P : Pointers)          // 매번 다른 페이지 → TLB Miss 많음
    Process(*P);
```

### (3) "Reserve 했는데 메모리가 안 늘어나네?"

```cpp
TArray<int32> Arr;
Arr.Reserve(1000000);   // 가상 주소 공간은 잡았는데...
// 작업 관리자 메모리는 별로 안 늘어남
```

가상 주소를 예약해도 **실제로 그 페이지를 건드리기 전엔 물리 RAM이 안 붙는다.** 처음 쓸 때 페이지 폴트가 나면서 그제서야 물리 프레임이 할당됨. (12강 주제) 이걸 lazy allocation, demand paging이라 한다.

## 8. 흔한 오해

### 오해 1: "포인터 주소는 진짜 메모리 위치다"

C++에서 보는 모든 주소는 **가상 주소**다. 진짜 물리 주소는 커널과 MMU만 안다. 그래서 두 프로세스가 같은 주소 값을 가져도 충돌 안 함.

### 오해 2: "32비트 프로그램은 메모리를 4GB까지 쓸 수 있다"

32비트 가상 주소 공간이 4GB인 거지, 실제 RAM이 4GB 있다는 뜻이 아니다. 또 그 중 일부는 커널 영역이라 유저가 다 못 쓴다(보통 2GB). 64비트는 가상 공간이 훨씬 커서(이론상 16EB) 이 제약이 사실상 사라짐.

### 오해 3: "malloc 하면 바로 물리 RAM이 잡힌다"

대부분의 OS는 **처음 그 메모리에 쓸 때** 물리 프레임을 붙인다(demand paging). `malloc(1GB)` 해도 안 건드리면 물리 RAM은 거의 안 늘어남.

### 오해 4: "페이지 크기는 항상 4KB다"

기본은 4KB지만, 큰 메모리를 다루는 경우 **Large Page / Huge Page**(2MB, 1GB)를 쓰기도 한다. 페이지가 크면 페이지 테이블 엔트리가 줄어서 TLB 효율이 올라간다. 일부 고성능 게임/서버가 활용.

## 9. 면접에서 나오면

**Q1. 가상 메모리가 뭔가요? 왜 쓰나요?**
→ "각 프로세스에게 독립된 연속 주소 공간이 있는 것처럼 보여주는 기법입니다. 실제로는 OS와 MMU가 가상 주소를 물리 주소로 변환해줍니다. 이를 통해 프로세스 격리(서로의 메모리에 접근 불가), 단편화 해결, 실제 RAM보다 큰 메모리 사용, 코드 공유 같은 이점을 얻습니다."

**Q2. 두 프로세스가 같은 주소를 출력하는데 값이 다른 게 어떻게 가능한가요?**
→ "그 주소는 가상 주소이기 때문입니다. 각 프로세스는 자기만의 페이지 테이블을 가지고, 같은 가상 주소라도 서로 다른 물리 프레임으로 매핑됩니다. 그래서 같은 가상 주소가 물리적으로는 다른 위치를 가리킵니다."

**Q3. 페이징이 뭔가요?**
→ "가상 메모리와 물리 메모리를 고정 크기(보통 4KB)의 페이지/프레임 단위로 나누고, 페이지 테이블로 매핑을 관리하는 기법입니다. 가상 주소는 페이지 번호와 오프셋으로 나뉘고, 페이지 번호를 페이지 테이블에서 프레임 번호로 변환한 뒤 오프셋을 붙여 물리 주소를 만듭니다."

**Q4. 페이지 테이블이 뭔가요?**
→ "가상 페이지를 물리 프레임으로 매핑하는 표로, 프로세스마다 하나씩 있습니다. 각 엔트리에는 프레임 번호, 유효 비트, 권한 비트 등이 들어 있습니다. 컨텍스트 스위칭 시 프로세스가 바뀌면 페이지 테이블도 교체됩니다."

**Q5. TLB가 뭔가요?**
→ "가상→물리 주소 변환 결과를 캐싱하는 MMU 안의 고속 캐시입니다. 페이지 테이블은 메모리에 있어서 매번 읽으면 느리기 때문에, 자주 쓰는 변환을 TLB에 저장해 둡니다. TLB Hit이면 변환이 거의 공짜이고, Miss면 페이지 테이블을 직접 뒤져야 해서 느립니다. 컨텍스트 스위칭으로 프로세스가 바뀌면 TLB가 무효화되어 한동안 느려집니다."

**Q6. malloc으로 1GB를 할당하면 즉시 물리 메모리 1GB가 쓰이나요?**
→ "아닙니다. 대부분의 OS는 demand paging을 써서 가상 주소만 예약하고, 실제로 그 메모리에 처음 접근할 때 페이지 폴트를 통해 물리 프레임을 붙입니다. 그래서 할당만 하고 안 건드리면 물리 메모리는 거의 늘지 않습니다."

## 10. 셀프 체크

- [ ] 가상 주소와 물리 주소의 차이를 설명할 수 있다.
- [ ] 두 프로세스가 같은 가상 주소를 쓰는데 충돌하지 않는 이유를 안다.
- [ ] 페이지와 프레임이 뭔지, 보통 크기가 얼마인지 안다.
- [ ] 가상 주소가 페이지 번호 + 오프셋으로 나뉘는 걸 안다.
