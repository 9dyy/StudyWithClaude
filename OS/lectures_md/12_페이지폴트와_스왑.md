# 12강 — 페이지 폴트와 스왑

> **목표:** "메모리는 충분한데 게임이 갑자기 끊기는" 현상의 정체를 안다. 페이지 폴트(major/minor)와 스왑, 그리고 게임에서 이게 어떻게 hitch로 나타나는지.
> **선수 지식:** 11강 (가상 메모리, 페이징, 페이지 테이블).

---

## 1. 도입 — 게임이 갑자기 0.5초 멈춘다

상황: 오픈월드 게임에서 새 지역에 진입하는 순간 게임이 **0.5초 동안 뚝 멈췄다가** 다시 돌아온다. 프로파일러를 보면:

- CPU 사용률: 멀쩡함
- GPU 사용률: 멀쩡함
- 메모리: 16GB 중 10GB 사용 — 여유 있음
- 그런데 한 프레임이 **500ms** 걸림 (정상은 16ms)

CPU도 GPU도 안 바쁘고 메모리도 남는데 왜 멈출까? 이 프레임 동안 CPU는 **뭔가를 기다리고** 있었다. 그 "뭔가"가 디스크다. 범인은 **페이지 폴트**.

---

## 2. 페이지 폴트 (Page Fault)

11강에서 페이지 테이블의 **유효 비트(Valid bit)** 를 봤다. "이 가상 페이지가 지금 물리 RAM에 올라와 있나?"

```
페이지 테이블
┌──────────┬───────────┬───────┐
│ 페이지번호 │ 프레임번호  │ 유효? │
├──────────┼───────────┼───────┤
│    5     │    17     │   O   │ ← RAM에 있음. 바로 접근.
│    6     │   (없음)   │   X   │ ← RAM에 없음! → 페이지 폴트
└──────────┴───────────┴───────┘
```

우리 코드가 페이지 6에 접근하려 하면, MMU가 "유효 비트가 X네?" 하고 **CPU 예외(exception)** 를 발생시킨다. 이게 **페이지 폴트**다.

페이지 폴트가 나면:

```
1. 우리 코드 실행 중단 (트랩 → 커널 모드 진입)
2. OS의 페이지 폴트 핸들러가 작동
3. "이 페이지 데이터가 어디 있지?" 확인
4. 필요하면 디스크에서 읽어와 물리 프레임에 올림
5. 페이지 테이블 갱신 (유효 비트 O, 프레임 번호 기록)
6. 중단됐던 우리 코드를 그 지점부터 재실행
```

핵심: **페이지 폴트는 에러가 아니다.** 가상 메모리가 정상 작동하는 메커니즘의 일부다. 다만 비쌀 수 있다.

---

## 3. Minor Fault vs Major Fault — 둘은 천지차이

페이지 폴트라고 다 같은 게 아니다. **디스크를 건드리느냐**가 갈림길.

### Minor Fault (소프트 폴트) — 빠름

페이지 데이터가 **이미 RAM 어딘가에 있는** 경우. 디스크 접근 없이 페이지 테이블만 고치면 됨.

언제?
- **demand paging 첫 접근:** `malloc`으로 잡은 페이지를 처음 쓸 때. OS가 0으로 채운 프레임 하나 붙여주면 끝.
- **공유 라이브러리:** 이미 다른 프로세스가 올려둔 DLL 페이지를 내 페이지 테이블에 연결만.
- **방금 회수했다가 다시 쓰는 페이지:** 아직 디스크로 안 내려간 경우.

비용: **수 마이크로초.** 빠르다.

### Major Fault (하드 폴트) — 느림

페이지 데이터가 **디스크에 있어서 읽어와야** 하는 경우.

언제?
- **스왑된 페이지 재접근:** RAM이 부족해서 SSD로 내려갔던 페이지를 다시 쓸 때.
- **메모리 맵 파일:** `mmap`으로 연결한 파일 페이지를 처음 읽을 때 (게임 에셋 스트리밍이 종종 이 방식).
- **실행 파일 코드의 첫 실행:** exe/dll의 안 읽은 코드 페이지를 처음 실행할 때.

비용: **수 밀리초 ~ 수십 밀리초.** SSD라도 느리고, HDD면 더 끔찍. **이게 게임 hitch의 주범.**

```
Minor Fault:  수 μs   →  거의 안 느껴짐
Major Fault:  수 ms   →  프레임 드랍, 끊김
```

도입부의 0.5초 멈춤 = major fault가 수백 번 몰린 것.

---

## 4. 스왑 (Swap) / 페이징 아웃

물리 RAM은 유한하다. RAM이 꽉 차면 OS는 **지금 안 쓰는 페이지를 디스크로 내려보낸다.** 이게 **스왑 아웃(swap out / page out)**.

```
RAM 꽉 참
    ↓
OS: "한동안 안 쓴 페이지를 골라서 디스크로 내리자" (페이지 교체)
    ↓
그 프레임을 비워서 새 요청에 줌
    ↓
나중에 그 페이지를 다시 쓰려 하면 → Major Fault → 디스크에서 도로 가져옴 (swap in)
```

- Windows: **페이지 파일(pagefile.sys)**
- Linux: **스왑 영역(swap partition / swapfile)**

### 스래싱 (Thrashing) — 최악의 상황

RAM이 심각하게 부족하면, 페이지를 내리자마자 또 필요해서 도로 올리고, 또 내리고... 디스크 I/O만 미친 듯이 하면서 **실제 작업은 거의 못 하는** 상태. 컴퓨터가 "먹통"이 되는 그 느낌.

```
정상:    [작업][작업][작업][작업]
스래싱:  [스왑][스왑][스왑][스왑]  ← CPU는 노는데 디스크만 100%
```

게임에서 메모리를 너무 많이 쓰면 OS가 스왑을 시작하고, 결국 스래싱으로 게임이 슬라이드쇼가 된다.

---

## 5. 페이지 교체 알고리즘 (어떤 페이지를 내릴까)

RAM이 꽉 찼을 때 "누구를 디스크로 내릴지" 고르는 규칙. 면접 빈출.

### FIFO (First-In First-Out)

먼저 들어온 페이지부터 내림. 단순하지만 멍청함. **Belady's Anomaly**(프레임을 늘렸는데 폴트가 더 늘어나는 역설)가 발생할 수 있음.

### LRU (Least Recently Used) — 핵심

**가장 오랫동안 안 쓰인 페이지**를 내림. "오래 안 썼으면 앞으로도 안 쓰겠지"라는 가정. 실제로 잘 맞아서 이론적 표준.

문제: 진짜 LRU는 모든 접근마다 시간을 기록해야 해서 너무 비쌈.

### Clock (Second Chance) — 실전용 LRU 근사

각 페이지에 **접근 비트(reference bit)** 하나만 둔다. 시계바늘처럼 돌면서:
- 접근 비트 1이면 → 0으로 만들고 한 번 봐줌(second chance)
- 접근 비트 0이면 → 얘를 내림

실제 OS들이 LRU 대신 이런 근사 알고리즘을 쓴다. 진짜 LRU는 너무 비싸서.

### Optimal (OPT) — 이론상 최선

"앞으로 가장 오래 안 쓰일 페이지"를 내림. 미래를 알아야 해서 **현실 불가능.** 다른 알고리즘 성능 비교의 기준선으로만 쓴다.

> 면접 정리: "FIFO는 단순하지만 Belady 이상현상, LRU는 가장 오래 안 쓴 걸 내리는데 구현 비용 때문에 Clock 같은 근사를 실제로 씀, OPT는 이론상 최선이지만 미래를 알아야 해서 불가능."

## 6. 게임 개발자 입장 — hitch를 어떻게 잡나

### (1) 미리 건드려두기 (Pre-touch / Warm-up)

레벨 로딩 중에 필요한 메모리를 **미리 한 번 접근**해서 페이지를 RAM에 올려둔다. 게임플레이 중에 major fault가 안 나게.

```cpp
// 로딩 화면에서 미리 메모리를 워밍업
void PreWarmAssets(TArray<uint8>& AssetData)
{
    volatile uint8 Sum = 0;
    for (int32 i = 0; i < AssetData.Num(); i += 4096)  // 페이지마다 한 번씩
        Sum += AssetData[i];   // 접근 → minor fault 미리 처리
    // 이제 게임플레이 중엔 이 데이터가 RAM에 있음
}
```

### (2) 비동기 스트리밍 (메인 스레드 밖에서 폴트 내기)

major fault로 인한 디스크 대기를 **워커 스레드**에서 처리하면 Game Thread는 안 멈춘다. 언리얼의 에셋 스트리밍이 이걸 한다. (15강 비동기 I/O와 직결)

### (3) 메모리 예산 관리

플랫폼 메모리 한도를 넘으면 스왑/스래싱. 콘솔(PS5, Xbox)은 스왑이 거의 없어서 한도를 넘으면 바로 OOM 크래시. 그래서 **메모리 예산(budget)** 을 엄격히 관리한다.

```cpp
// 언리얼 메모리 상태 확인
FPlatformMemoryStats Stats = FPlatformMemory::GetStats();
UE_LOG(LogTemp, Log, TEXT("사용 중: %llu MB / 가용: %llu MB"),
       Stats.UsedPhysical / (1024 * 1024),
       Stats.AvailablePhysical / (1024 * 1024));
```

### (4) 작업 관리자의 함정

작업 관리자에서 "메모리 10GB 사용 중, 6GB 여유"로 보여도, 그 10GB 안에 **스왑 가능한 페이지**가 섞여 있을 수 있다. 또 "메모리 여유"는 OS 전체 기준이라 게임 프로세스 입장에선 다를 수 있다. 도입부의 "메모리 충분한데 끊김"이 이래서 생긴다.

## 7. 워킹 셋 (Working Set)

프로세스가 **현재 시점에 실제로 활발히 쓰는 페이지들의 집합.** 

- 워킹 셋이 물리 RAM에 다 들어가면 → major fault 거의 없음. 쾌적.
- 워킹 셋이 RAM보다 크면 → 계속 스왑 → 스래싱.

게임 최적화의 목표 중 하나가 "워킹 셋을 물리 RAM 안에 유지"다. 그래서 안 쓰는 에셋은 언로드하고, 자주 쓰는 것만 메모리에 두는 LOD/스트리밍 시스템이 있다.

## 8. 흔한 오해

### 오해 1: "페이지 폴트 = 에러/버그"

아니다. 페이지 폴트는 가상 메모리의 **정상 동작**이다. demand paging, 코드 첫 실행 등 항상 일어난다. 다만 major fault가 너무 많으면 성능 문제. (단, 잘못된 주소 접근으로 인한 폴트는 segfault로 이어지는데 그건 별개)

### 오해 2: "RAM이 남으면 스왑 안 한다"

OS는 RAM이 좀 남아도 **미래를 위해** 안 쓰는 페이지를 미리 내려두기도 한다(proactive paging). 그래서 "메모리 여유 있음"과 "스왑 없음"이 항상 일치하진 않는다.

### 오해 3: "SSD니까 스왑해도 안 느려"

SSD가 HDD보다 훨씬 빠른 건 맞지만, RAM에 비하면 **수백~수천 배 느리다.** SSD 스왑도 major fault라 게임 hitch를 만든다. "RAM ≫ SSD ≫ HDD" 순서는 안 바뀐다.

### 오해 4: "메모리 많이 할당하는 게 페이지 폴트 원인"

할당 자체보다 **접근 패턴**이 문제다. 1GB 할당해도 순차 접근하면 폴트가 예측 가능하게 흩어진다. 반면 작은 메모리라도 여기저기 랜덤하게 튀면 폴트가 몰린다. 13강 캐시와 같은 맥락.

### 오해 5: "콘솔도 PC처럼 스왑한다"

PS5, Xbox 같은 콘솔은 스왑을 거의 안 쓴다(혹은 매우 제한적). 메모리 한도 넘으면 스왑 대신 **크래시(OOM)**. 그래서 콘솔 타겟 게임은 메모리 예산이 PC보다 빡세다.

## 9. 면접에서 나오면

**Q1. 페이지 폴트가 뭔가요?**
→ "프로그램이 접근한 가상 페이지가 물리 메모리에 올라와 있지 않을 때 MMU가 발생시키는 예외입니다. OS의 핸들러가 해당 페이지를 물리 프레임에 올리고 페이지 테이블을 갱신한 뒤, 중단됐던 명령을 재실행합니다. 에러가 아니라 가상 메모리의 정상 동작입니다."

**Q2. Minor Fault와 Major Fault의 차이는?**
→ "Minor Fault는 페이지 데이터가 이미 RAM에 있어서 페이지 테이블만 갱신하면 되는 경우로 수 마이크로초면 끝납니다. Major Fault는 데이터가 디스크에 있어서 읽어와야 하는 경우로 수 밀리초가 걸립니다. 게임에서 프레임 드랍이나 hitching의 주범은 Major Fault입니다."

**Q3. 스왑(swapping)이 뭔가요?**
→ "물리 RAM이 부족할 때 당장 안 쓰는 페이지를 디스크(Windows는 페이지 파일, Linux는 스왑 영역)로 내려보내 RAM을 확보하는 기법입니다. 내려간 페이지를 다시 쓰면 Major Fault가 나서 도로 읽어옵니다."

**Q4. 스래싱(thrashing)이 뭔가요?**
→ "RAM이 심각하게 부족해서 페이지를 내리자마자 다시 필요해 올리고, 또 내리고를 반복하느라 디스크 I/O만 하고 실제 작업은 거의 못 하는 상태입니다. 워킹 셋이 물리 RAM보다 클 때 발생하며, CPU는 노는데 시스템 전체가 먹통이 됩니다."

**Q5. 페이지 교체 알고리즘 종류를 설명해보세요.**
→ "FIFO는 먼저 들어온 페이지를 내리는데 단순하지만 Belady 이상현상이 있습니다. LRU는 가장 오래 안 쓰인 페이지를 내리는 방식으로 효과적이지만 매 접근마다 기록이 필요해 비쌉니다. 그래서 실제 OS는 접근 비트를 쓰는 Clock 같은 LRU 근사를 씁니다. OPT는 미래에 가장 늦게 쓰일 페이지를 내리는 이론상 최선이지만 미래를 알아야 해서 불가능합니다."

**Q6. 메모리는 충분한데 게임이 끊기면 어디를 의심하나요?**
→ "Major Fault를 의심합니다. CPU와 GPU가 한가한데 프레임이 길게 걸리면 디스크 I/O 대기일 가능성이 높습니다. 에셋 스트리밍이 메인 스레드에서 동기적으로 일어나거나, 스왑된 페이지를 다시 읽거나, 메모리 맵 파일을 처음 접근하는 경우입니다. 해결책은 비동기 스트리밍, 사전 워밍업, 메모리 예산 관리입니다."

**Q7. 워킹 셋이 뭔가요?**
→ "프로세스가 현재 활발하게 사용하는 페이지들의 집합입니다. 워킹 셋이 물리 RAM에 다 들어가면 Major Fault가 거의 없어 쾌적하고, RAM보다 크면 스왑이 반복되어 스래싱이 발생합니다. 게임 최적화는 워킹 셋을 RAM 안에 유지하는 걸 목표로 합니다."

---

## 10. 셀프 체크

- [ ] 페이지 폴트가 에러가 아니라 정상 메커니즘이라는 걸 안다.
- [ ] Minor Fault와 Major Fault의 차이와 비용을 설명할 수 있다.
- [ ] 스왑(page out / page in)의 흐름을 안다.
- [ ] 스래싱이 왜 생기고 어떤 증상인지 안다.
- [ ] FIFO, LRU, Clock, OPT를 한 문장씩 설명할 수 있다.
- [ ] "메모리 충분한데 끊김"의 원인으로 major fault를 떠올릴 수 있다.
- [ ] 워킹 셋 개념과 게임 메모리 최적화의 연결을 안다.
