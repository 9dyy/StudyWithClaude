# 7강 — Race Condition과 임계영역

> **목표:** "왜 `Counter++` 가 멀티스레드에서 깨지는가" 를 어셈블리 수준에서 이해한다. 임계영역(Critical Section)의 개념을 잡는다.
> **선수 지식:** 4~6강 (스레드, 컨텍스트 스위칭).

> **여기서부터가 면접 동기화 파트의 본론.** 4강에서 봤던 `g_Shared++` 가 왜 깨졌는지 답이 나온다.

---

## 1. 도입 — 4강의 그 코드, 다시

```cpp
int32 g_Shared = 0;

// 두 스레드가 동시에 실행
for (int i = 0; i < 1000000; ++i)
    g_Shared++;
```

스레드 둘이 각각 100만 번 하면 결과는 **200만**이 나와야 한다.
실제로 돌려보면 **1,234,567** 같은 이상한 값이 나온다. 매번 다르다.

**왜?**

---

## 2. `g_Shared++` 는 한 줄이 아니다

C++에서 `g_Shared++` 는 한 줄이지만, **CPU 입장에서는 3개 명령어**다.

```asm
; g_Shared++
mov  eax, [g_Shared]   ; (1) 메모리에서 값을 레지스터로 읽기
inc  eax                ; (2) 레지스터에서 1 더하기
mov  [g_Shared], eax   ; (3) 레지스터 값을 메모리에 다시 쓰기
```

이 사이에 **컨텍스트 스위칭이 끼어들 수 있다.**

### 시나리오: 둘이 동시에 ++ 한 결과가 +1 만 된다

`g_Shared = 100` 으로 시작.

```
시간    스레드 A                      스레드 B
─────────────────────────────────────────────────────
t1     mov eax, [g_Shared]  → 100
t2     inc eax              → 101
                              ← 여기서 컨텍스트 스위칭
t3                              mov eax, [g_Shared]  → 100  (B의 eax는 별개!)
t4                              inc eax              → 101
t5                              mov [g_Shared], eax  → 100→101
                              ← 다시 A로 컨텍스트 스위칭
t6     mov [g_Shared], eax  → 101→101  (A는 자기 eax 101을 씀)
```

A도 한 번 +1 했고, B도 한 번 +1 했는데 **결과는 101.** 한 번의 증가가 사라졌다(Lost Update).

이게 **Race Condition** 의 본질이다.

> **Race Condition (경쟁 조건):** 여러 스레드가 공유 자원에 동시 접근하는 결과가 **실행 순서에 따라 달라지는** 상황.

---

## 3. 임계영역 (Critical Section)

> **임계영역:** 공유 자원에 접근하는 코드 구간 중, 한 번에 하나의 스레드만 들어가야 정확성이 보장되는 구간.

위 예시에서 `mov, inc, mov` 3개가 한 묶음으로 도는 게 보장돼야 한다. 이 3줄이 임계영역.

목표: **임계영역에서는 한 번에 한 스레드만**.

---

## 4. 임계영역 문제의 3대 조건

OS 교과서 단골 출제 포인트. 임계영역 해결책은 다음 3가지를 다 만족해야 한다.

1. **상호 배제 (Mutual Exclusion)**
   한 스레드가 임계영역 안에 있으면, 다른 스레드는 못 들어옴.

2. **진행 (Progress)**
   임계영역이 비어있고 들어가고 싶은 스레드가 있으면, 누군가는 들어가야 함. 무한정 늦추지 말 것.

3. **한정된 대기 (Bounded Waiting)**
   한 스레드가 들어가려고 기다릴 때, 다른 스레드가 무한히 새치기 못 하게 막아야 함. 굶기지 말 것(Starvation 방지).

> 면접에서 "임계영역 문제의 해결 조건 3가지"는 단골. **Mutual Exclusion, Progress, Bounded Waiting** 외워두면 된다.

---

## 5. 어떤 경우에 Race Condition이 생기나?

다 같이 두 가지 조건을 만족할 때.

1. **공유 데이터**가 있고,
2. **그 중 적어도 하나는 쓰기(Write)** 를 한다.

읽기만 하는 데이터는 Race Condition이 안 난다. 쓰기가 끼어야 문제.

### Race Condition 유형들

#### (1) Lost Update — 위에서 본 거

```cpp
g_Shared++;   // 두 스레드가 동시 → 한 번 사라짐
```

#### (2) Dirty Read — 중간 상태를 본다

```cpp
struct FPlayer { float HP; bool bDead; };
FPlayer Player;

// 스레드 A
Player.HP = 0;
Player.bDead = true;

// 스레드 B (동시에)
if (Player.bDead == false && Player.HP <= 0)
    Crash();   // 일관성 깨진 상태를 봄
```

#### (3) Check-Then-Act — 확인하고 행동 사이가 갈라짐

```cpp
// 두 스레드가 동시에:
if (Inventory.Count > 0)        // 둘 다 통과
{
    Inventory.Remove();           // 둘 다 빼버림 → 인벤토리 음수
}
```

게임에서 유저가 빠른 클릭으로 아이템 두 번 받는 버그 같은 게 이거.

## 6. 언리얼 게임에서 마주치는 진짜 사례

### 사례 1: 카운터

```cpp
// 잘못된 코드
int32 g_ConnectedPlayers = 0;

void OnPlayerConnect()    // 네트워크 워커 스레드에서 호출 가능
{
    g_ConnectedPlayers++;  // 동시에 여러 명 접속하면 카운트 망가짐
}
```

해결: `FThreadSafeCounter` 또는 `std::atomic<int32>`.

### 사례 2: TArray 동시 수정

```cpp
TArray<FString> g_Logs;

void OnEvent(FString S)
{
    g_Logs.Add(S);   // 두 스레드 동시 Add → 내부 재할당 중 충돌, 크래시
}
```

해결: Mutex(다음 강의) 또는 lock-free queue.

### 사례 3: 게임 스레드의 데이터를 워커가 읽기

```cpp
// 워커 스레드에서
float CurrentHP = Player->HP;
if (CurrentHP < Player->MaxHP * 0.5)  // 사이에 Player가 죽어서 메모리 해제됐을 수도
    ...
```

해결: Game Thread에서 값만 복사해서 워커에 넘기기, 또는 적절한 동기화.

## 7. "원자적(Atomic)" 이라는 단어

**원자적(Atomic)** = "중간에 끊길 수 없는 한 덩어리 동작".

- `int32 x = 5;` — 32비트 정렬된 정수 대입은 보통 원자적 (CPU가 한 번에 처리)
- `int32 x++;` — **원자적 아님** (읽기/더하기/쓰기 3단계)
- `int64 x = SomeBigValue;` — 32비트 CPU에서는 원자적 아님 (두 번에 나눠 씀)
- `FVector v = OtherV;` — 절대 원자적 아님 (12바이트, 3번 나눠 씀)

C++의 `std::atomic<T>`, 언리얼의 `TAtomic<T>`, `FThreadSafeCounter` 는 컴파일러+CPU가 원자성을 보장해주는 도구.

```cpp
#include <atomic>

std::atomic<int32> Counter{0};

void Increment()
{
    Counter++;   // 원자적. 멀티스레드 안전.
}
```

이건 9강에서 깊이 다룬다.

---

## 8. 컴파일러 최적화도 한 몫 — Reordering

이건 한 단계 더 깊은 얘기지만 면접에서 가끔 나옴.

```cpp
// 코드 상으로는:
Data = 42;
bReady = true;

// 컴파일러나 CPU가 순서를 바꿀 수 있음:
bReady = true;
Data = 42;
```

단일 스레드에서는 결과가 같으니까 최적화로 허용된다. 하지만 다른 스레드가:

```cpp
if (bReady)
    Use(Data);  // Data는 아직 42 안 됐을 수도! → 옛날 값 사용
```

이걸 막으려면 **메모리 배리어** 가 필요. 9강 atomic / 메모리 모델에서 자세히.

## 9. 흔한 오해

### 오해 1: "`int` 대입은 멀티스레드에서 항상 안전하다"

대부분의 환경에서 **정렬된 32비트 정수의 대입**은 원자적이라 안전. 하지만:
- **연산(++, +=)** 은 안전 아님
- **64비트 값을 32비트 CPU에서** 다루면 안전 아님
- **구조체 대입**은 안전 아님

### 오해 2: "락 안 쓰고 잘 짜면 Race 없게 만들 수 있어"

진짜 천재가 아닌 이상 **공유 자원이 있으면 락 또는 atomic이 필요.** 락 안 쓰고 잘 도는 것처럼 보이는 코드는 대부분 운이 좋았던 것뿐. 부하 늘어나면 깨진다.

### 오해 3: "Game Thread 안에서는 Race 걱정 없다"

Game Thread 1개라 그 안에서 도는 코드끼리는 Race 없음. 다만:
- 다른 스레드(워커, 렌더)에서 같은 데이터를 만지면 그 즉시 Race 등장.
- Tick 중에 다른 액터의 함수 호출 → 그 안에서 워커 스레드 만들고 데이터 공유 → Race.

### 오해 4: "한 번도 안 터졌으니 안전한 코드다"

Race Condition은 **간헐적이고 재현이 어려운 게 특징.** 개발 PC에선 안 터지다가 라이브에서 터진다. 깨질 가능성이 있는 코드는 **수정 대상.** 동작 여부가 아니라 보장 여부로 판단.

## 10. 면접에서 나오면

**Q1. Race Condition이 뭔가요?**
→ "여러 스레드가 공유 자원에 동시에 접근하는데, 그 중 적어도 하나가 쓰기를 하는 경우, 결과가 실행 순서에 따라 달라지는 현상입니다. 예를 들어 `Counter++`는 읽기-증가-쓰기 3단계 명령으로 컴파일되는데, 두 스레드가 동시에 하면 중간에 컨텍스트 스위칭이 일어나 한 번의 증가가 사라질 수 있습니다."

**Q2. 임계영역(Critical Section)이 뭔가요?**
→ "공유 자원에 접근하는 코드 구간 중 한 번에 한 스레드만 들어가야 정확성이 보장되는 구간입니다. 이 구간은 Mutex나 lock-free 기법으로 보호해야 합니다."

**Q3. 임계영역 문제의 해결 조건 3가지는?**
→ "Mutual Exclusion(한 번에 한 스레드만 들어감), Progress(들어가고 싶은 스레드가 있고 영역이 비어있으면 누군가는 들어가야 함), Bounded Waiting(특정 스레드가 무한히 기다리지 않게 함)입니다."

**Q4. `int x = 0; x++;` 가 멀티스레드 환경에서 안전하지 않은 이유는?**
→ "`x++`는 메모리에서 값을 읽어 레지스터에 올리고, 1을 더하고, 다시 메모리에 쓰는 3개의 CPU 명령으로 나뉩니다. 두 스레드가 동시에 실행하면 둘 다 같은 값을 읽고 같은 결과를 쓰게 되어, 두 번 증가해야 할 게 한 번만 증가하는 Lost Update가 발생합니다."

**Q5. 원자적 연산이 뭔가요?**
→ "중간에 다른 스레드의 개입 없이 한 덩어리로 실행되는 연산입니다. 정렬된 32비트 정수의 단순 대입은 보통 원자적이지만, 증감이나 비교-교환은 명시적으로 atomic 도구(`std::atomic`, `TAtomic`)를 써야 원자성이 보장됩니다."

**Q6. 같은 코드를 100번 돌렸는데 다 잘 나왔으면 멀티스레드 안전한가요?**
→ "아닙니다. Race Condition은 타이밍에 따라 간헐적으로 발생하고 재현이 어렵습니다. 안전성은 동작 결과가 아니라 보장 여부로 판단해야 하고, 공유 데이터에 쓰기가 일어나면 반드시 동기화나 atomic으로 보호해야 합니다."
