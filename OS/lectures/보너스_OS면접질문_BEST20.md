# 보너스 — 클라 개발자가 받는 OS 면접 질문 BEST 20

> **목표:** 1~15강에서 배운 걸 면접 답변으로 묶는다. 각 질문에 "모범 답변" + "면접관이 그 다음에 던지는 꼬리질문"까지.
> **선수 지식:** 1~15강 전체.

> **쓰는 법:** 답변을 통째로 외우지 마라. 키워드(굵은 글씨)를 기억하고, 자기 말로 재구성하는 연습을 해라. 면접은 암송이 아니라 대화다.

---

## 사용 가이드

각 문항 구성:
- **Q:** 실제 면접에서 나오는 표현
- **A:** 입으로 말할 수 있는 답변 (존댓말)
- **꼬리:** 면접관이 이어서 던지기 좋은 질문 → 어느 강의로 가야 하는지
- **🔑:** 이 답에서 면접관이 듣고 싶어하는 핵심 키워드

---

## Part 1. 기초

### Q1. 프로세스와 스레드의 차이를 설명해보세요. (★최빈출)

**A:** "프로세스는 실행 중인 프로그램으로 각자 독립된 가상 주소 공간을 가집니다. 스레드는 한 프로세스 안의 실행 흐름이고, 같은 프로세스 안의 스레드끼리는 Heap·Data·코드 영역을 공유하고 Stack과 레지스터만 따로 가집니다. 그래서 스레드는 데이터 공유가 쉽지만 동기화 문제가 생기고, 프로세스는 격리되어 안전하지만 통신에 IPC가 필요합니다."

🔑 가상 주소 공간, Stack만 독립, Heap 공유, 동기화 문제
**꼬리:** "스레드끼리 뭘 공유하죠?" → 4강 / "그럼 동기화는 어떻게?" → 7~8강

---

### Q2. 시스템 콜이 뭔가요? 왜 비싼가요?

**A:** "유저 모드 프로그램이 커널 기능을 호출하는 통로입니다. `syscall` 명령으로 커널 모드로 진입하는데, 레지스터를 저장하고 커널 스택으로 전환하고 인자를 검증하는 모드 스위치가 일어나서 일반 함수 호출보다 훨씬 비쌉니다. 그래서 게임 엔진은 시스템 콜 횟수를 줄이려고 I/O를 배치하거나 메모리를 풀로 관리합니다."

🔑 유저/커널 모드, 모드 스위치, ring 0/3
**꼬리:** "유저 모드와 커널 모드 차이는?" → 2강

---

### Q3. 프로세스의 메모리 구조를 설명해보세요.

**A:** "Text, Data, BSS, Heap, Stack 다섯 영역입니다. Text는 코드로 읽기 전용, Data는 초기화된 전역변수, BSS는 초기화 안 된 전역변수로 0으로 채워집니다. Heap은 동적 할당 영역으로 아래에서 위로 자라고, Stack은 함수 호출과 지역변수로 위에서 아래로 자랍니다."

🔑 5영역, Stack/Heap 성장 방향, BSS는 0
**꼬리:** "`new`로 만든 객체와 그 포인터 변수는 각각 어디 있죠?" → 3강 (포인터는 Stack, 대상은 Heap)

---

## Part 2. 스케줄링

### Q4. 컨텍스트 스위칭이 뭐고 왜 비싼가요? (★최빈출)

**A:** "OS가 CPU에서 도는 스레드를 다른 스레드로 바꾸는 동작입니다. 현재 스레드의 레지스터를 TCB에 저장하고 새 스레드 것을 복원합니다. 직접 비용도 있지만 더 큰 건 간접 비용으로, 스위칭 후 캐시와 TLB가 식어서 한동안 캐시 미스가 많이 나 느려집니다. 다른 프로세스로 바꾸면 페이지 테이블과 TLB까지 교체해서 더 비쌉니다."

🔑 레지스터 저장/복원, 캐시·TLB 식음(간접 비용), 페이지 테이블 교체
**꼬리:** "그래서 스레드를 많이 만들면?" → Q5

---

### Q5. 스레드를 코어 수보다 훨씬 많이 만들면 어떻게 되나요?

**A:** "동시에 도는 건 결국 코어 수만큼이고 나머지는 Ready 큐에서 대기합니다. 스레드가 많을수록 컨텍스트 스위칭이 잦아져 오버헤드가 늘고 캐시 효율이 떨어집니다. CPU 바운드 작업은 보통 코어 수만큼만 만드는 게 최적이라 스레드 풀 패턴을 씁니다. 언리얼은 TaskGraph가 이걸 자동으로 해줍니다."

🔑 코어 수 = 최적, 스레드 풀, TaskGraph
**꼬리:** "I/O 바운드면요?" → 약간 더 만들어도 됨 (대기 동안 다른 스레드가 일)

---

### Q6. 우선순위 역전(Priority Inversion)이 뭔가요?

**A:** "낮은 우선순위 스레드가 락을 잡고 있는데 높은 우선순위 스레드가 그 락을 기다리는 사이, 중간 우선순위 스레드가 CPU를 차지해서 낮은 우선순위 스레드가 못 돌고, 결과적으로 높은 우선순위 스레드가 무한정 기다리는 현상입니다. 해결책은 Priority Inheritance로, 락을 잡은 스레드의 우선순위를 일시적으로 올려줍니다."

🔑 H-M-L, Priority Inheritance
**꼬리:** "실제 사례 아세요?" → 화성 탐사선 Pathfinder (6강)

---

## Part 3. 동시성 (가장 중요한 파트)

### Q7. Race Condition이 뭔가요? (★최빈출)

**A:** "여러 스레드가 공유 자원에 동시 접근하는데 하나 이상이 쓰기를 할 때, 결과가 실행 순서에 따라 달라지는 현상입니다. 예를 들어 `Counter++`는 읽기·증가·쓰기 3개 명령으로 컴파일되는데, 두 스레드가 동시에 하면 중간에 컨텍스트 스위칭이 끼어 한 번의 증가가 사라질 수 있습니다."

🔑 공유 + 쓰기, `Counter++`는 3개 명령, Lost Update
**꼬리:** "그걸 어떻게 막죠?" → Q8

---

### Q8. Mutex와 Semaphore의 차이는? (★최빈출)

**A:** "Mutex는 동시 진입을 한 명으로 제한하고 락을 잡은 스레드만 풀 수 있는 소유권 개념이 있습니다. 세마포어는 N명까지 허용하는 카운터이고 소유권이 없어 아무 스레드나 Signal로 올릴 수 있습니다. Mutex는 임계영역 보호에, 세마포어는 자원 풀 제한이나 생산자-소비자 패턴에 씁니다."

🔑 소유권, N명, 임계영역 vs 자원 풀
**꼬리:** "Mutex 쓸 때 주의점은?" → Q9

---

### Q9. `std::lock_guard`(FScopeLock)를 왜 쓰나요?

**A:** "RAII로 락 수명을 객체 수명에 묶어 자동 해제를 보장합니다. return이든 예외든 어떤 경로로 함수를 빠져나가도 소멸자가 호출되어 자동 Unlock되므로, Lock/Unlock을 직접 부를 때 생기는 락 누수를 막습니다."

🔑 RAII, 자동 Unlock, 예외 안전
**꼬리:** "락을 잡고 무거운 작업을 하면?" → 동시성 사라짐, Amdahl's Law (8강)

---

### Q10. atomic이 Mutex보다 빠른 이유는?

**A:** "atomic은 CPU의 LOCK 접두사나 CMPXCHG 같은 원자 명령으로 처리되어 락 획득·해제 비용이 없고, 락을 못 받았을 때 컨텍스트 스위칭이 일어나지 않습니다. 다만 한 변수에 대한 짧은 연산만 가능하고, 여러 변수의 일관성이 필요하면 여전히 Mutex가 필요합니다."

🔑 CPU 원자 명령, 컨텍스트 스위칭 없음, 단일 변수 한정
**꼬리:** "Lock-free는 항상 빠른가요?" → 아니다, CAS retry 폭주·캐시 핑퐁 (9강)

---

### Q11. 데드락이 뭐고 어떻게 해결하나요? (★최빈출)

**A:** "둘 이상의 스레드가 서로 상대가 가진 자원을 기다리며 영원히 멈추는 상태입니다. 발생 조건은 Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait 네 가지이고 다 만족해야 생깁니다. 해결은 예방·회피·탐지·무시가 있는데, 실무에선 락에 전역 순서를 부여해서 순환 대기를 깨는 방법을 가장 많이 씁니다."

🔑 4조건, 순환 대기, 락 순서 고정
**꼬리:** "Deadlock이랑 Livelock 차이는?" → 10강 / "어떻게 디버깅?" → 디버거로 콜스택 (10강)

---

## Part 4. 메모리

### Q12. 가상 메모리가 뭔가요? 왜 쓰나요? (★최빈출)

**A:** "각 프로세스에게 독립된 연속 주소 공간이 있는 것처럼 보여주고, OS와 MMU가 가상 주소를 물리 주소로 변환하는 기법입니다. 프로세스 격리, 메모리 단편화 해결, 실제 RAM보다 큰 메모리 사용, 코드 공유 같은 이점이 있습니다."

🔑 가상→물리 변환, MMU, 격리, 페이지 테이블
**꼬리:** "변환을 매번 하면 느리지 않나요?" → TLB (11강)

---

### Q13. 페이지 폴트가 뭔가요?

**A:** "접근한 가상 페이지가 물리 메모리에 없을 때 발생하는 예외입니다. OS가 해당 페이지를 프레임에 올리고 페이지 테이블을 갱신한 뒤 중단된 명령을 재실행합니다. 에러가 아니라 정상 동작입니다. Minor Fault는 데이터가 이미 RAM에 있어 빠르고, Major Fault는 디스크에서 읽어와야 해서 느려 게임 hitch의 주범입니다."

🔑 정상 동작, Minor(μs) vs Major(ms), 디스크 대기
**꼬리:** "메모리 충분한데 게임이 끊기면?" → Major Fault 의심 (12강)

---

### Q14. TLB가 뭔가요?

**A:** "가상→물리 주소 변환 결과를 캐싱하는 MMU 안의 고속 캐시입니다. 페이지 테이블은 메모리에 있어 매번 읽으면 느리니까 자주 쓰는 변환을 TLB에 저장합니다. TLB Hit이면 변환이 거의 공짜이고, 컨텍스트 스위칭으로 프로세스가 바뀌면 TLB가 무효화되어 한동안 느려집니다."

🔑 변환 캐시, Hit/Miss, 컨텍스트 스위칭 시 무효화
**꼬리:** Q4(컨텍스트 스위칭)와 연결해서 물어봄

---

### Q15. 배열이 링크드 리스트보다 순회가 빠른 이유는? (★최빈출)

**A:** "배열은 메모리에 연속 배치되어 공간 지역성이 좋습니다. 캐시는 64바이트 라인 단위로 가져오기 때문에 한 번 미스 후 옆 원소들은 캐시 히트가 됩니다. 링크드 리스트는 노드가 힙에 흩어져 있어 매 노드 접근이 캐시 미스라, 같은 O(n)이라도 실제로는 몇 배 느립니다. 빅오만으로 성능을 판단하면 안 되는 대표 사례입니다."

🔑 공간 지역성, 캐시 라인 64B, 빅오 ≠ 실제 성능
**꼬리:** "캐시 친화적 코드는 어떻게?" → 순차 접근, SoA (13강) / "False Sharing 아세요?" → 13강

---

### Q16. 캐시 메모리 계층을 설명해보세요.

**A:** "레지스터, L1, L2, L3, RAM, 디스크 순으로 위로 갈수록 빠르고 작고 비쌉니다. L1은 4사이클 정도인데 RAM은 200사이클로 약 50배 차이라, 자주 쓰는 데이터를 CPU 가까운 캐시에 둬서 이 격차를 메웁니다. 캐시는 시간 지역성과 공간 지역성을 활용합니다."

🔑 계층 순서, L1 4 vs RAM 200, 두 지역성
**꼬리:** Q15와 연결

---

## Part 5. I/O

### Q17. 블로킹과 논블로킹, 동기와 비동기의 차이는?

**A:** "블로킹/논블로킹은 '기다리느냐'의 축으로, 블로킹은 결과까지 멈추고 논블로킹은 즉시 반환합니다. 동기/비동기는 '누가 완료를 챙기느냐'의 축으로, 동기는 직접 확인하고 비동기는 콜백이나 이벤트로 통지받습니다. 서로 다른 축이라 조합이 가능합니다."

🔑 두 개의 축, 기다림 vs 완료 통지
**꼬리:** "게임 비동기 로딩은 어느 조합?" → 논블로킹+비동기 (15강)

---

### Q18. 게임에서 에셋을 비동기 로딩하는 이유는?

**A:** "디스크 읽기는 수십~수백 ms가 걸리는데 Game Thread에서 동기로 읽으면 그동안 Tick이 멈춰 hitch가 납니다. 비동기 로딩은 그 대기를 워커 스레드나 OS 비동기 I/O로 넘기고 Game Thread는 계속 돌다가 완료 콜백만 받습니다. 디스크가 빨라지는 게 아니라 반응성을 유지하는 겁니다."

🔑 hitch 방지, 대기를 Game Thread 밖으로, responsiveness
**꼬리:** "비동기라도 누가 디스크를 기다리죠?" → 워커 블로킹 or IOCP (15강)

---

### Q19. "파일을 연다"는 게 무슨 의미인가요?

**A:** "데이터를 옮기는 게 아니라, 경로로 파일 메타데이터(inode)를 찾아 권한을 검사하고, 커널에 '열린 파일' 항목을 만들어 그 핸들(파일 디스크립터)을 반환하는 겁니다. 이후 읽기·쓰기는 이 핸들로 합니다. 파일 이름 자체는 inode가 아니라 디렉토리의 '이름→inode' 매핑에 있습니다."

🔑 핸들 생성, inode, 이름은 디렉토리에
**꼬리:** "왜 두 번째 읽기가 빠르죠?" → 페이지 캐시 (14강)

---

## 종합 / 응용

### Q20. 멀티스레드 프로그래밍 경험을 말해보세요. (★오픈 질문)

이건 정답이 없는 경험 질문. 1~15강을 엮어서 **스토리**로 답하라. 예시 틀:

**A:** "언리얼에서 무거운 [경로 탐색/세이브 직렬화 등]을 Game Thread에서 하다가 hitch가 발생한 적이 있습니다. 이걸 `AsyncTask`로 워커 스레드에 옮겼는데, 결과를 적용할 때 공유 데이터에서 Race Condition이 생겨서 `FCriticalSection`으로 보호했습니다. 그런데 단순 카운터였던 부분은 `FThreadSafeCounter`로 바꿔서 락 비용을 줄였고, UObject를 만지는 부분은 반드시 Game Thread로 콜백을 넘겨서 처리했습니다."

🔑 (한 답변에 여러 개념을 자연스럽게) hitch → 워커 → Race → Mutex → atomic → Game Thread 콜백
**꼬리:** 답변에 등장한 키워드 아무거나 깊게 파고듦. 그래서 **자기가 진짜 아는 것만 말해야 한다.**

> 팁: 모르는 걸 키워드로 던지면 꼬리질문에서 무너진다. 위 20문항 중 **자신 있는 것 위주로 스토리를 짜라.**
