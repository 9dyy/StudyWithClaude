# 6강 — CPU 스케줄링과 컨텍스트 스위칭

> **목표:** OS가 어떻게 16코어로 100개 스레드를 굴리는지 이해한다. 컨텍스트 스위칭 비용이 왜 비싼지, 스레드를 함부로 많이 만들면 왜 안 되는지.
> **선수 지식:** 4~5강 (스레드, 언리얼 스레드 구조).

---

## 1. 도입 — CPU는 한 번에 하나만 한다

CPU 코어 1개는 **물리적으로 한 순간에 명령어 하나**만 처리한다. (하이퍼스레딩/SMT는 잠깐 옆에 둔다.)

그런데 내 PC를 보면:
- 게임 1개
- 디스코드 1개
- 크롬 (탭 10개, 각 탭이 프로세스)
- 비주얼 스튜디오 1개
- Windows 자체 서비스 수십 개
- ... 총 프로세스 200+, 스레드 2000+

이게 다 동시에 도는 것처럼 보인다. **어떻게?**

답: OS가 **빠르게 스레드를 갈아끼우면서** "지금 0.01ms는 너, 다음 0.01ms는 너" 하고 돌린다. 우리 눈에는 동시처럼 보임. 이걸 **CPU 스케줄링** 이라고 한다.

---

## 2. 스레드의 상태 (Thread State)

스레드는 항상 한 가지 상태에 있다.

```
              ┌─────────────┐
              │   New       │  ← 막 만들어짐
              └──────┬──────┘
                     │
                     ↓
        ┌────────────────────┐
        │      Ready          │ ← 돌 준비 됨, CPU 기다리는 중
        └────────┬───────────┘
                 │  스케줄러가 "너 차례" 라고 함
                 ↓
        ┌────────────────────┐
        │     Running         │ ← CPU에서 실제로 도는 중
        └────────┬───────────┘
                 │
                 ├─ 시간 다 씀 ──→ Ready
                 │
                 ├─ I/O 대기, 락 대기 ──→ Waiting (Blocked)
                 │                            │
                 │                            ↓ I/O 끝남, 락 받음
                 │                          Ready
                 │
                 └─ 끝남 ──→ Terminated
```

핵심 4상태: **New, Ready, Running, Waiting, Terminated.**

언리얼에서 `WaitForCompletion()` 부르면 그 스레드는 Waiting 상태로 들어가고, 깨워주면 Ready로 돌아온다.

---

## 3. 컨텍스트 스위칭 (Context Switching)

CPU 코어에서 도는 스레드를 바꾸는 동작.

```
시간 →
코어 0:  [스레드 A 실행 중] ─→ [스위칭] ─→ [스레드 B 실행 중] ─→ [스위칭] ─→ [스레드 A 다시]
                              ↑
                          여기서 OS가 개입
```

스위칭 시 OS가 하는 일:

1. **현재 스레드의 레지스터 값을 다 저장** (TCB에)
   - PC(Program Counter), SP(Stack Pointer), 범용 레지스터 16개, 부동소수점 레지스터 등등
2. **다음 스레드의 TCB에서 저장돼있던 레지스터 값을 복원**
3. (다른 프로세스로 바꾸는 거면) **페이지 테이블, TLB 갈아치우기**
4. **캐시는 그대로지만, 다른 스레드가 쓰면서 다 밀려나감**

비용:
- 직접 비용: 수천 사이클 (몇 μs)
- 간접 비용: **캐시/TLB가 식어서** 새 스레드가 한동안 느림. 이게 직접 비용보다 큼.

---

## 4. 언제 스위칭이 일어나나?

**1) 시간 할당량 소진 (Preemption)**

OS가 각 스레드에 **타임 슬라이스(quantum)** 를 준다. Windows는 보통 10~15ms. 다 쓰면 강제로 빼고 다음 스레드.

**2) 자발적 양보**

스레드가 직접 "나 잠깐 쉴게" 함. 예:
- `Sleep(100)` → 100ms 동안 Waiting
- `WaitForSingleObject(mutex, INFINITE)` → 락 받을 때까지 Waiting
- `ReadFile` 같은 블로킹 I/O → 디스크 응답 올 때까지 Waiting

**3) 우선순위 변동**

더 높은 우선순위 스레드가 Ready 상태로 들어오면 현재 거 밀어내고 그게 들어옴.

**4) 인터럽트**

키보드 입력, 타이머, 네트워크 패킷 도착 같은 하드웨어 이벤트가 발생하면 OS가 잠깐 끼어든다.

## 5. 게임 개발자가 알아야 할 핵심: "스레드 너무 만들지 마라"

**오해:** "스레드 100개 만들면 100배 빨라지겠지?"

**현실:** 코어가 16개인데 스레드 100개면:
- 동시에 도는 건 결국 16개
- 나머지 84개는 Ready로 줄 서서 기다림
- 컨텍스트 스위칭이 미친 듯이 일어남 → 오버헤드 폭증
- 캐시가 계속 식음 → 평균 성능 더 나빠짐

```cpp
// 나쁜 예: 적 100마리에 각자 스레드 하나씩
for (int i = 0; i < 100; ++i)
{
    new FRunnableThread(...);   // 100개 스레드. 컨텍스트 스위칭 지옥.
}

// 좋은 예: Worker Pool에 100개 "Task"를 넣기
for (int i = 0; i < 100; ++i)
{
    AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, [i]()
    {
        UpdateEnemyAI(i);
    });
}
// 실제 워커 스레드는 코어 수만큼만. 100개 작업을 줄 세워 처리.
```

이게 **스레드 풀(Thread Pool)** 패턴이다. 언리얼의 TaskGraph가 정확히 이걸 해준다.

## 6. 스케줄링 알고리즘 (간단히)

면접 빈출만 짚고 간다.

### FCFS (First-Come, First-Served)

먼저 온 놈부터 끝까지 돌림. 단순하지만 짧은 작업이 긴 작업 뒤에 끼면 한참 기다림 (Convoy Effect).

### Round Robin (RR)

각자 타임 슬라이스만큼 돌리고 다음 사람. **현대 OS의 기본.**

```
타임 슬라이스 = 10ms 일 때
스레드 A → 10ms → 스레드 B → 10ms → 스레드 C → 10ms → 스레드 A → ...
```

### Priority Scheduling

우선순위 높은 놈부터. **Windows, Linux 둘 다 이걸 RR과 섞어서 씀.**

게임은 보통:
- Game Thread, Render Thread: 높은 우선순위
- Worker Thread: 보통
- 백그라운드 로딩: 낮음

### MLFQ (Multi-Level Feedback Queue)

여러 단계 큐를 두고, "오래 도는 놈은 점점 우선순위 내림" "I/O 자주 하는 놈은 우선순위 올림" 식으로 동적 조정. 현대 Windows/Linux가 비슷한 방식.

> 면접에서 "스케줄링 알고리즘 종류 아는 거 다 말해보세요" 들으면 FCFS, SJF, RR, Priority, MLFQ 정도 나열하면 충분.

---

## 7. 우선순위 역전 (Priority Inversion) — 면접 단골

**상황:**
- 우선순위: H > M > L
- L이 락(mutex)을 잡고 있음
- H가 그 락을 기다림 → H가 멈춤
- M이 깨어남 → L보다 우선순위 높으니까 M이 돌음 → L이 못 돔 → 락 해제 안 됨 → H도 못 돔
- **결과: 최고 우선순위 H가 중간 우선순위 M 때문에 멈춰있는 어이없는 상황.**

**해결책:** Priority Inheritance(상속)
- L이 H가 기다리는 락을 잡으면, L의 우선순위를 일시적으로 H 수준으로 올려줌. M이 못 끼어들게.

실화: 1997년 화성 탐사선 Pathfinder가 이 문제로 계속 리셋됨. 우선순위 상속 끄고 보냈더니 발생. 패치로 켜서 해결.

## 8. 코드로 — 컨텍스트 스위칭 비용 체감

```cpp
void DemoContextSwitchCost()
{
    const int N = 1000;
    FEvent* Ev1 = FPlatformProcess::GetSynchEventFromPool();
    FEvent* Ev2 = FPlatformProcess::GetSynchEventFromPool();

    double Start = FPlatformTime::Seconds();

    // 두 스레드가 Ping-Pong — 매번 컨텍스트 스위칭 강제
    auto Pinger = [&]()
    {
        for (int i = 0; i < N; ++i)
        {
            Ev1->Trigger();
            Ev2->Wait();
        }
    };
    auto Ponger = [&]()
    {
        for (int i = 0; i < N; ++i)
        {
            Ev1->Wait();
            Ev2->Trigger();
        }
    };

    // (실제 코드는 FRunnable로 래핑 필요. 의사 코드)
    StartThread(Pinger);
    StartThread(Ponger);
    WaitBoth();

    double Elapsed = (FPlatformTime::Seconds() - Start) * 1000.0;
    UE_LOG(LogTemp, Log, TEXT("%d ping-pongs took %.3f ms (~%.2f us/switch)"),
           N, Elapsed, Elapsed * 1000.0 / (N * 2));
}
```

대개 1회 컨텍스트 스위칭에 **수 μs** 정도 나온다. 평범한 함수 호출(나노초 단위)과 비교하면 1000배 비싸다.

## 9. 흔한 오해

### 오해 1: "코어 수보다 스레드를 많이 만들면 더 빠르다"

명확한 NO. CPU 바운드 작업이면 **코어 수 = 최적**. I/O 바운드 작업이면 약간 더 만드는 게 좋지만 100배 만들지 마라.

### 오해 2: "Sleep(0)은 아무것도 안 한다"

Windows에서 `Sleep(0)`은 "동등한 우선순위의 다른 Ready 스레드가 있으면 양보" 의미. 흔한 트릭이지만 권장 X.

### 오해 3: "컨텍스트 스위칭은 OS만의 문제다"

스위칭 후 **캐시가 식어** 그 다음 우리 코드 실행이 느려지는 게 진짜 비용. OS만 신경 쓰는 일이 아니라 게임 성능에 직접 영향.

### 오해 4: "Game Thread는 OS가 무조건 빠르게 돌려준다"

OS는 게임 Game Thread가 뭔지 모른다. 그냥 우선순위를 높게 설정해뒀을 뿐. 다른 우선순위 높은 프로세스가 있으면 밀린다. (안티치트, 백신, 윈도 업데이트 등이 게임 끊김의 원인이 되기도 함)

## 10. 면접에서 나오면

**Q1. 컨텍스트 스위칭이 뭔가요?**
→ "OS가 CPU 코어에서 도는 스레드를 다른 스레드로 바꾸는 동작입니다. 현재 스레드의 레지스터 상태를 TCB에 저장하고, 새 스레드의 저장된 상태를 복원합니다. 다른 프로세스로 바꾸는 경우엔 페이지 테이블과 TLB도 바꿔야 해서 더 비쌉니다."

**Q2. 컨텍스트 스위칭 비용은 왜 큰가요?**
→ "직접 비용은 레지스터 저장/복원이지만, 더 큰 건 간접 비용입니다. 스위칭 후 캐시가 다른 스레드 데이터로 덮여 있어서, 원래 스레드가 다시 돌 때 캐시 미스가 많이 나서 한동안 느리게 돕니다. TLB도 마찬가지입니다."

**Q3. 스레드를 코어 수보다 훨씬 많이 만들면 어떻게 되나요?**
→ "동시에 도는 건 결국 코어 수만큼이고, 나머지는 Ready 큐에서 대기합니다. 스레드가 많을수록 컨텍스트 스위칭이 자주 일어나서 오버헤드가 늘고 캐시 효율이 떨어집니다. CPU 바운드 작업은 보통 코어 수만큼만 만드는 게 최적이고, 그래서 스레드 풀 패턴을 씁니다."

**Q4. 스레드의 상태들을 설명해보세요.**
→ "Ready는 돌 준비가 됐지만 CPU를 기다리는 상태, Running은 실제로 CPU에서 도는 상태, Waiting(Blocked)은 I/O나 락 등을 기다리는 상태, Terminated는 끝난 상태입니다. 타임 슬라이스가 끝나면 Running→Ready, I/O를 시작하면 Running→Waiting, I/O가 끝나면 Waiting→Ready로 갑니다."

**Q5. 우선순위 역전이 뭔가요? 어떻게 해결하나요?**
→ "낮은 우선순위 스레드가 락을 잡고 있는데 높은 우선순위 스레드가 그 락을 기다리는 사이, 중간 우선순위 스레드가 CPU를 차지해 낮은 우선순위 스레드가 못 돌고 결과적으로 높은 우선순위 스레드가 무한정 기다리는 현상입니다. 해결책은 Priority Inheritance — 락을 잡은 스레드의 우선순위를 일시적으로 그 락을 기다리는 가장 높은 스레드의 우선순위로 올려주는 방식입니다."

**Q6. Round Robin 스케줄링이 뭔가요?**
→ "각 스레드에게 같은 크기의 타임 슬라이스를 주고 돌아가면서 CPU를 할당하는 방식입니다. 공정성이 높고 응답성이 좋아서 대부분의 현대 OS가 우선순위 스케줄링과 결합해서 사용합니다."

## 11. 셀프 체크

- [ ] 스레드의 4가지 상태(Ready, Running, Waiting, Terminated)와 전이 조건을 안다.
- [ ] 컨텍스트 스위칭의 직접 비용과 간접 비용을 구분해 설명할 수 있다.
- [ ] 스레드를 코어 수보다 훨씬 많이 만들면 안 되는 이유를 안다.
- [ ] Round Robin, Priority Scheduling이 뭔지 한 문장으로 말할 수 있다.
- [ ] 우선순위 역전 문제와 해결책(Priority Inheritance)을 안다.
