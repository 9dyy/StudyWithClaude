# 13강 — 캐시와 메모리 계층

> **목표:** `TArray`가 `TList`(링크드 리스트)보다 빠른 진짜 이유를 안다. 캐시 계층, 캐시 라인, 캐시 미스, 그리고 데이터 지향 설계(DOD)의 근거.
> **선수 지식:** 11강 (가상 메모리), 3강 (메모리 구조).

> **Part 4 메모리 관리의 마지막.** 언리얼 클라 개발자가 실무에서 가장 자주 써먹는 강의다. 면접 성능 질문의 핵심.

---

## 1. 도입 — 같은 100만 개인데 10배 차이

원소 100만 개를 순회하면서 더하는 코드. 자료구조만 다르다.

```cpp
// (A) TArray — 연속 메모리
TArray<int32> ArrayData;
ArrayData.SetNum(1000000);
int64 SumA = 0;
for (int32 V : ArrayData)
    SumA += V;

// (B) 링크드 리스트 — 노드가 힙 여기저기 흩어짐
struct FNode { int32 Value; FNode* Next; };
FNode* Head = BuildLinkedList(1000000);
int64 SumB = 0;
for (FNode* N = Head; N; N = N->Next)
    SumB += N->Value;
```

같은 100만 번 덧셈. 그런데 (A)가 (B)보다 **5~10배 빠르다.**

연산 횟수는 똑같다. 차이는 **메모리를 어떻게 읽느냐**다. 그 답이 캐시에 있다.

---

## 2. 메모리는 한 종류가 아니다 — 메모리 계층

CPU 입장에서 데이터를 가져오는 곳은 여러 단계로 나뉜다. 위로 갈수록 빠르고 작고 비싸다.

```
            빠름/작음/비쌈
        ┌──────────────────┐
        │   레지스터        │  ~1 사이클,   수백 바이트
        ├──────────────────┤
        │   L1 캐시         │  ~4 사이클,   ~32KB (코어당)
        ├──────────────────┤
        │   L2 캐시         │  ~12 사이클,  ~256KB~1MB
        ├──────────────────┤
        │   L3 캐시         │  ~40 사이클,  ~8~32MB (공유)
        ├──────────────────┤
        │   메인 메모리(RAM) │  ~200 사이클, ~16~32GB
        ├──────────────────┤
        │   SSD / 디스크    │  ~수만~수십만 사이클
        └──────────────────┘
            느림/큼/쌈
```

**숫자의 의미를 체감해보자.** L1이 4사이클인데 RAM은 200사이클. **약 50배 차이.** CPU가 RAM에서 데이터를 기다리는 동안 수백 사이클을 그냥 논다.

> 비유: L1 = 책상 위, L2 = 책상 서랍, L3 = 방 책장, RAM = 도서관, SSD = 다른 도시 도서관.
> 책상 위에 있으면 바로 보는데, 도서관까지 갔다 오면 한참 걸린다.

---

## 3. 캐시는 "라인" 단위로 가져온다

핵심 중의 핵심. CPU가 RAM에서 데이터를 가져올 때 **딱 필요한 1바이트만** 가져오지 않는다. 그 주변을 통째로 가져온다. 이 덩어리가 **캐시 라인(Cache Line)**, 보통 **64바이트**.

```cpp
int32 x = ArrayData[0];   // 0번 하나 읽으려 했는데...
```

CPU는 `ArrayData[0]`만 읽는 게 아니라, 그게 속한 64바이트 라인을 통째로 L1에 올린다. `int32`가 4바이트니까 **`[0]`을 읽으면 `[0]~[15]`까지 16개가 캐시에 따라온다.**

```
RAM:    [0][1][2][3][4]...[15][16]...   ← int32 배열
         └──── 한 캐시 라인(64B) ────┘
                 ↓ 통째로
L1 캐시: [0][1][2][3]...[15]   ← 다음에 [1] 읽으면 캐시에 이미 있음! 빠름.
```

그래서 `ArrayData`를 순서대로 돌면:
- `[0]` 읽음 → 캐시 미스 → RAM에서 라인 가져옴 (200사이클)
- `[1]`~`[15]` 읽음 → **전부 캐시 히트** (4사이클씩)
- `[16]` 읽음 → 캐시 미스 → 다음 라인 가져옴
- ...

16개 중 1번만 느리고 15번은 빠르다. 이게 도입부 (A)가 빠른 이유.

## 4. 두 가지 지역성 (Locality)

캐시가 효과를 보는 원리. 면접 단골.

### 시간 지역성 (Temporal Locality)

"한 번 쓴 데이터는 곧 또 쓸 가능성이 높다."

```cpp
for (int i = 0; i < N; ++i)
    Total += Multiplier * Data[i];   // Multiplier, Total을 매번 다시 씀 → 캐시에 머묾
```

### 공간 지역성 (Spatial Locality)

"한 데이터를 쓰면 그 옆 데이터도 곧 쓸 가능성이 높다."

```cpp
for (int i = 0; i < N; ++i)
    Sum += Data[i];   // Data[i] 다음엔 Data[i+1] → 같은 캐시 라인에 이미 있음
```

`TArray`의 순차 순회는 **공간 지역성을 극대화**한다. 링크드 리스트는 노드가 힙 여기저기 흩어져서 공간 지역성이 없다. → 매 노드가 캐시 미스.

---

## 5. 그래서 링크드 리스트가 느리다

```
TArray (연속):
RAM:  [0][1][2][3][4][5][6][7]...   ← 한 줄로 쭉
      순회: 캐시 미스 거의 없음

링크드 리스트 (흩어짐):
RAM:  [노드3]......[노드1]....[노드5]...[노드2]......
      Head→노드1→노드2→노드3...
      순회: 매번 다른 캐시 라인 → 캐시 미스 폭발
```

링크드 리스트는 이론적 시간복잡도(O(n) 순회)는 배열과 같지만, **실제 성능은 캐시 미스 때문에 훨씬 느리다.** 빅오만 보면 안 되는 대표 사례.

> 그래서 게임 코드에서 링크드 리스트는 거의 안 쓴다. 중간 삽입/삭제가 O(1)이라는 장점이 캐시 미스 손해를 못 이긴다. 언리얼도 `TArray`가 기본 컨테이너.

## 6. 데이터 지향 설계 (DOD, Data-Oriented Design)

캐시를 이해하면 자연스럽게 따라오는 설계 철학. **"데이터를 CPU가 읽기 좋게 배치하자."**

### AoS vs SoA — 면접/실무 단골

같은 데이터를 두 가지로 배치할 수 있다.

```cpp
// AoS (Array of Structs) — 객체지향의 자연스러운 방식
struct FEnemy
{
    FVector  Position;   // 12B
    FVector  Velocity;   // 12B
    float    Health;     // 4B
    int32    AIState;    // 4B
    // ... 64B 정도
};
TArray<FEnemy> Enemies;

// "모든 적의 위치만 업데이트" 할 때
for (FEnemy& E : Enemies)
    E.Position += E.Velocity * Dt;   // Position만 필요한데 Health, AIState까지 캐시에 끌려옴
```

```cpp
// SoA (Struct of Arrays) — DOD 방식
struct FEnemyData
{
    TArray<FVector> Positions;
    TArray<FVector> Velocities;
    TArray<float>   Healths;
    TArray<int32>   AIStates;
};
FEnemyData Enemies;

// "모든 적의 위치만 업데이트" 할 때
for (int i = 0; i < Count; ++i)
    Enemies.Positions[i] += Enemies.Velocities[i] * Dt;  // 필요한 것만 빽빽이 → 캐시 효율 최고
```

**한 가지 필드만 대량으로 처리할 땐 SoA가 캐시에 훨씬 유리하다.** Position만 보는데 AoS는 64바이트 라인에 Position 12바이트만 쓸모있고 나머지 52바이트는 낭비. SoA는 라인 전체가 Position.

언리얼의 ECS 계열(Mass Entity), Niagara 파티클 시스템이 이 SoA/DOD를 적극 쓴다.

> 주의: SoA가 항상 옳은 건 아니다. **한 객체의 여러 필드를 한꺼번에** 자주 쓰면 AoS가 낫다. "어떻게 접근하느냐"에 따라 고른다.

## 7. False Sharing — 멀티스레드 + 캐시의 함정

9강에서 살짝 언급한 거. 캐시 라인이 64바이트 단위라서 생기는 멀티스레드 성능 문제.

```cpp
struct FCounters
{
    int64 CounterA;   // 스레드 1이 씀
    int64 CounterB;   // 스레드 2가 씀
};
FCounters Shared;   // A와 B가 같은 64바이트 캐시 라인에 있음
```

스레드 1이 `CounterA`를 쓰고 스레드 2가 `CounterB`를 쓴다. 서로 다른 변수라 충돌이 없어 보이는데...

**같은 캐시 라인에 있어서** 한 코어가 쓰면 다른 코어의 캐시 라인이 무효화된다. 서로 영향 없는 변수인데 캐시 라인을 공유해서 핑퐁이 일어남. → 성능 폭락.

해결: 캐시 라인 크기만큼 띄우기 (패딩).

```cpp
struct alignas(64) FPaddedCounter   // 각자 다른 캐시 라인
{
    int64 Value;
    uint8 Padding[56];
};
```

> 면접에서 "False Sharing 아세요?" 들으면 가산점. "서로 다른 스레드가 같은 캐시 라인의 다른 변수를 쓸 때 불필요한 캐시 무효화로 성능이 떨어지는 현상"이라고 답하면 됨.

## 8. 캐시 친화적 코드 — 실전 정리

### (1) 순차 접근하라

```cpp
// ✅ 캐시 친화적: 행 우선 순회 (C++ 메모리 레이아웃에 맞음)
for (int y = 0; y < H; ++y)
    for (int x = 0; x < W; ++x)
        Grid[y][x] = ...;   // 연속 접근

// ❌ 캐시 적대적: 열 우선 순회
for (int x = 0; x < W; ++x)
    for (int y = 0; y < H; ++y)
        Grid[y][x] = ...;   // 매번 W칸씩 점프 → 캐시 미스
```

2차원 배열에서 안쪽 루프가 어느 인덱스를 도느냐로 몇 배 차이 난다. **C++은 행 우선(row-major)** 이라 마지막 인덱스가 안쪽 루프여야 한다.

### (2) 포인터 추적(pointer chasing)을 줄여라

```cpp
// ❌ UObject 포인터 배열 순회 — 각 객체가 힙에 흩어짐
TArray<AEnemy*> Enemies;
for (AEnemy* E : Enemies)
    E->UpdateAI();   // 매번 다른 힙 위치 → 캐시 미스

// ✅ 데이터를 값으로 묶어 연속 배치
TArray<FEnemyAIData> AIData;
for (FEnemyAIData& D : AIData)
    UpdateAI(D);   // 연속 → 캐시 히트
```

언리얼에서 `TArray<UObject*>` 순회는 어쩔 수 없는 경우가 많지만, 핫 패스(매 프레임 도는 대량 루프)라면 데이터를 따로 빼는 걸 고려.

### (3) 구조체를 작게, 핫 데이터를 모아라

자주 쓰는 필드끼리 모으고, 가끔 쓰는 필드는 따로 빼면 한 캐시 라인에 유용한 데이터가 더 많이 들어간다.

## 9. 흔한 오해

### 오해 1: "빅오만 좋으면 빠르다"

링크드 리스트(O(1) 삽입)가 배열(O(n) 삽입)보다 이론상 유리해 보여도, 캐시 미스 때문에 실제론 배열이 빠른 경우가 많다. **빅오는 연산 횟수지 메모리 접근 비용이 아니다.**

### 오해 2: "캐시는 OS가 관리한다"

L1/L2/L3 캐시는 **하드웨어(CPU)가 자동 관리**한다. OS나 우리 코드가 직접 "이거 캐시에 넣어" 못 한다(프리페치 힌트 정도만). 우리가 할 수 있는 건 **접근 패턴을 캐시에 유리하게 짜는 것**뿐.

### 오해 3: "캐시 미스 한 번이 뭐 그리 비싸"

L1 히트 4사이클 vs RAM 200사이클. 한 번은 별거 아니지만 100만 번 루프에서 매번 미스나면 그게 누적돼서 10배 차이를 만든다. 도입부 예시가 그거.

### 오해 4: "SoA가 항상 AoS보다 빠르다"

아니다. **접근 패턴에 따라 다르다.** 한 필드만 대량 처리하면 SoA, 한 객체의 여러 필드를 함께 쓰면 AoS. 무조건 SoA로 바꾸면 오히려 느려질 수 있다.

### 오해 5: "멀티스레드면 변수만 나누면 안전하고 빠르다"

안전한 건 맞아도 빠른 건 아니다. False Sharing 때문에 같은 캐시 라인에 있으면 느려진다. 핫한 카운터는 캐시 라인 단위로 띄워야 한다.

## 10. 면접에서 나오면

**Q1. 캐시 메모리가 왜 필요한가요?**
→ "CPU와 RAM의 속도 차이가 너무 크기 때문입니다. RAM 접근은 200사이클 정도인데 CPU는 그동안 놀게 됩니다. 자주 쓰는 데이터를 CPU 가까이의 빠른 캐시(L1은 4사이클 정도)에 둬서 이 격차를 메웁니다. 레지스터-L1-L2-L3-RAM-디스크로 이어지는 메모리 계층을 형성합니다."

**Q2. 캐시 라인이 뭔가요?**
→ "CPU가 메모리에서 데이터를 가져올 때의 최소 단위로 보통 64바이트입니다. 1바이트만 필요해도 그게 속한 64바이트를 통째로 캐시에 올립니다. 그래서 데이터를 순차적으로 접근하면 한 번 미스 후 나머지는 캐시 히트가 되어 빠릅니다."

**Q3. 배열이 링크드 리스트보다 순회가 빠른 이유는?**
→ "배열은 메모리에 연속으로 배치되어 공간 지역성이 좋습니다. 한 캐시 라인에 여러 원소가 함께 올라와서 순회 시 캐시 히트가 많습니다. 링크드 리스트는 노드가 힙 여기저기 흩어져 있어 매 노드 접근마다 캐시 미스가 나기 때문에, 같은 O(n) 순회라도 실제로는 몇 배 느립니다."

**Q4. 시간 지역성과 공간 지역성이 뭔가요?**
→ "시간 지역성은 한 번 접근한 데이터를 곧 다시 접근할 가능성이 높다는 것이고, 공간 지역성은 한 데이터에 접근하면 그 주변 데이터도 곧 접근할 가능성이 높다는 것입니다. 캐시는 이 두 지역성을 활용해 동작합니다. 순차 배열 순회는 공간 지역성을, 반복문의 누적 변수는 시간 지역성을 활용합니다."

**Q5. AoS와 SoA의 차이는?**
→ "AoS는 Array of Structs로 객체 단위로 묶어 배열에 담는 방식이고, SoA는 Struct of Arrays로 필드별로 따로 배열을 만드는 방식입니다. 한 필드만 대량 처리할 때는 SoA가 그 필드만 캐시에 빽빽이 올라와 유리하고, 한 객체의 여러 필드를 함께 쓸 때는 AoS가 유리합니다. 파티클 시스템이나 ECS가 SoA를 많이 씁니다."

**Q6. False Sharing이 뭔가요?**
→ "서로 다른 스레드가 같은 캐시 라인에 있는 다른 변수를 각각 수정할 때, 논리적으로는 충돌이 없는데도 한 코어가 쓰면 다른 코어의 캐시 라인이 무효화되어 성능이 떨어지는 현상입니다. 자주 쓰이는 변수들을 캐시 라인 크기(64바이트)만큼 패딩으로 띄워서 해결합니다."

**Q7. 캐시 친화적인 코드를 짜려면 어떻게 해야 하나요?**
→ "데이터를 연속으로 배치하고 순차적으로 접근합니다. 2차원 배열은 메모리 레이아웃에 맞는 순서로 순회하고(C++은 행 우선), 포인터 추적을 줄이고, 자주 쓰는 데이터를 한 곳에 모읍니다. 한 필드만 대량 처리하는 핫 패스라면 SoA 배치를 고려합니다."

---

## 11. 셀프 체크

- [ ] 메모리 계층(레지스터-L1-L2-L3-RAM-디스크)과 대략적 속도 차이를 안다.
- [ ] 캐시 라인이 64바이트 단위로 통째로 올라온다는 걸 안다.
- [ ] 시간 지역성과 공간 지역성을 구분해서 설명할 수 있다.
- [ ] 배열이 링크드 리스트보다 순회가 빠른 이유를 캐시로 설명할 수 있다.
- [ ] AoS와 SoA를 구분하고 각각 언제 유리한지 안다.
- [ ] False Sharing이 뭔지, 어떻게 해결하는지 안다.
- [ ] 2차원 배열 순회 순서가 왜 성능에 영향을 주는지 안다.

## Part 4 마무리 (메모리 관리)

| 강의 | 주제 | 한 줄 요약 |
|------|------|-----------|
| 11강 | 가상 메모리와 페이징 | 모든 프로세스가 0번지부터 쓰는 마술. 페이지 테이블 + TLB. |
| 12강 | 페이지 폴트와 스왑 | 메모리 충분한데 끊김 = major fault. 디스크 대기. |
| 13강 | 캐시와 메모리 계층 | 연속 메모리 + 순차 접근. 빅오보다 캐시. |

이 세 강의가 "왜 게임이 메모리 때문에 느려지는가"의 거의 모든 답을 담는다.
- **갑작스런 hitch** → 페이지 폴트 (12강)
- **꾸준한 느림** → 캐시 미스 (13강)
- **이 모든 게 가능한 토대** → 가상 메모리 (11강)
