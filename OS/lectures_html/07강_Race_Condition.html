SECTION 01 · 큰 그림

12 + 2 = ... 어라?

두 스레드가 각각 전역 카운터를 100만 번씩 증가시킨다. 결과는 당연히 200만이어야 한다. 버튼을 눌러 실제로 돌려보자.

int32 g_Shared = 0;
// 스레드 2개가 동시에:
for (int i = 0; i < 1000000; ++i)
    g_Shared++;   // 과연 안전할까?

100만 × 2

SECTION 02 · 핵심 · 현미경

2g_Shared++ 는 한 줄이 아니다

CPU에겐 읽고 · 더하고 · 쓰는 3개 명령이다. 두 스레드의 명령이 어떤 순서로 끼워지냐(인터리빙)에 따라 결과가 달라진다. 직접 골라 재생해보자.

메모리 g_Shared
0
스레드 A · eax
–
스레드 B · ebx
–

● 스레드 A

mov eax, [g] ; 읽기
inc eax ; +1
mov [g], eax ; 쓰기

● 스레드 B

mov ebx, [g] ; 읽기
inc ebx ; +1
mov [g], ebx ; 쓰기

두 스레드가 각각 한 번씩만 ++ 했는데도, 인터리빙이 나쁘면 결과가 1이 된다. 한 번의 증가가 통째로 사라진다(Lost Update). 이게 Race Condition의 정체다.

3게임에서 만나는 Race 3종

공유 데이터가 있고 그 중 하나라도 쓰기를 하면 위험하다. 읽기만 하면 안전.

💸

방금 본 그것. g_ConnectedPlayers++ 를 동시 접속 처리하면 카운트가 샌다.

👻

Dirty Read

중간 상태를 읽음. HP=0 직후 bDead 세팅 전에 다른 스레드가 보면 "살아있는데 HP 0"인 모순 상태.

🎁

Check-Then-Act

SECTION 04 · 면접 단골

4임계영역 — 한 번에 한 스레드만

공유 자원에 접근하는 코드 구간 중, 한 번에 한 스레드만 들어가야 하는 곳. 해결책은 다음 3조건을 다 만족해야 한다.

1

상호 배제

Mutual Exclusion

한 스레드가 안에 있으면 다른 스레드는 못 들어옴.

2

진행

Progress

비어 있고 들어가려는 스레드가 있으면 누군가는 들어가야 함.

3

한정된 대기

Bounded Waiting

특정 스레드가 무한히 새치기당해 굶지 않게.

그럼 이걸 어떻게 보장할까? 가장 직관적인 답은 "자물쇠" — Mutex다.

→ 8강에서 FCriticalSection 과 FScopeLock 으로 이 인터리빙을 막는 법을 다룬다.
