언리얼의 스레드 구조

디버거로 언리얼 게임에 붙여보면 스레드가 30~50개 떠 있다. Game·Render·RHI·Worker가 어떻게 나뉘어 한 프레임을 만드는지, 파이프라인을 직접 돌려보고 병목이 어디서 생기는지 손으로 만져본다.

🧵 Game · Render · RHI · Worker
🧩 선수지식 4강

SECTION 01 · 도입

1한 게임에 스레드가 몇 개나 도는가

언리얼로 만든 게임을 Visual Studio 디버거에 붙여 스레드 창을 열어보면 30~50개가 떠 있다. 우리가 직접 만든 적도 없는데 왜 이렇게 많을까?

답: 언리얼이 내부적으로 굴리는 주요 스레드들이 다 떠 있어서다. 큰 그림으로 보면 4개 카테고리로 나뉜다.

🎮

1개

게임 로직 — Tick, Blueprint, AI, Physics

🖼️

1개

렌더링 명령 만들기 — 컬링, 정렬

⚡

여기에 Audio Thread, Loading Thread, IO Thread 등이 추가로 더 붙는다. 이번 강의는 이 중 Game / Render / RHI / Worker 네 가지에 집중한다.

SECTION 02 · 구조

2Game → Render → RHI, 왜 셋으로 쪼갰나

셋 다 그냥 스레드를 나눈 게 아니라, 한 스레드가 다음 프레임을 준비하는 동안 다른 스레드가 이전 프레임을 그리게 하려고 나눈 것 — 파이프라이닝이다.

Game Thread — "게임의 메인"

우리가 짠 코드 대부분이 도는 곳. 액터·컴포넌트·UObject는 거의 다 여기서만 만지는 게 원칙이고, Blueprint 실행도 여기서 돈다. 단 1개뿐이며, 60FPS면 한 프레임 = 16.6ms 안에 끝나야 다음 프레임이 안 밀린다.

// AMyActor.cpp
void AMyActor::Tick(float DeltaTime)        // ← Game Thread
{
    SetActorLocation(...);                   // ← Game Thread
    PlayAnimation();                         // ← Game Thread
}

void AMyActor::BeginPlay()                   // ← Game Thread
{
    UE_LOG(LogTemp, Log, TEXT("Begin"));
}

Game Thread에서 무거운 작업(파일 로딩, 복잡한 알고리즘)을 하면 즉시 끊김(hitch)이 난다. → Worker Thread로 빼야 한다.

Render Thread — "렌더링 명령을 만들어라"

Game Thread는 "캐릭터 위치는 (1,2,3), 이 메시 그려" 같은 명령만 만들고, 실제 렌더링은 Render Thread가 한다. 그래서 Render Thread는 항상 Game Thread보다 1프레임 늦게 본다.

// Game Thread에서 실행
ENQUEUE_RENDER_COMMAND(MyCommand)(
    [Data = LocalData](FRHICommandListImmediate& RHICmdList)
    {
        // 이 람다는 나중에 Render Thread에서 실행됨
        // Data는 복사돼서 안전 — 포인터를 그대로 넘기면
        // Game Thread가 그 사이 값을 바꿔 Race Condition
    }
);

ENQUEUE_RENDER_COMMAND = "이 작업을 Render Thread 큐에 넣어줘." 람다 캡처는 복사가 원칙.

RHI Thread — "GPU랑 진짜 대화"

RHI(Rendering Hardware Interface)는 DirectX/Vulkan/Metal을 추상화한 층. Render Thread가 "메시 그려" 같은 추상 명령을 만들면, RHI Thread가 그걸 실제 API 호출로 번역해 GPU에 보낸다. DX/Vulkan 호출 자체가 무거울 수 있어 한 번 더 분리했다.

Game Thread:    [로직]
                  ↓ (커맨드 큐)
Render Thread:  [렌더 명령 만들기]
                  ↓ (RHI 명령 큐)
RHI Thread:     [DX12/Vulkan 호출 → GPU]
                  ↓
GPU:            [실제 픽셀 그리기]

총 3프레임 정도의 파이프라인이 형성된다 — 마우스 클릭이 화면에 반영되기까지 약간의 입력 지연이 생기는 이유. 모바일·저사양에서는 RHI Thread 없이 Render Thread가 직접 그리는 모드도 있다.

SECTION 03 · 킬러 · 인터랙션

3프레임 파이프라인 시뮬레이터 — 병목은 어디서 생기나

프레임 N의 Game 작업은 곧 Render로, 그다음 RHI로 흘러간다. 각 스레드가 프레임 하나를 처리하는 데 걸리는 시간을 슬라이더로 바꿔보면서 병목이 어디서 생기고 어디까지 퍼지는지 확인해보자.

각 프레임은 Game이 끝나야 Render가 시작하고, Render가 끝나야 RHI가 시작한다. 뒷 단계가 느리면 앞 단계도 3프레임 이상 앞서가지 못하게 대기(백프레셔)한다 — 실제 언리얼도 파이프라인 깊이를 제한한다. 트랙에 빈 칸(버블)이 보이면 그 스레드가 다음 프레임을 기다리는 중.

SECTION 04 · 워커

4Worker Thread Pool — 잡일 처리반

언리얼은 TaskGraph와 FRunnable 두 가지 방식으로 워커 스레드를 굴린다.

TaskGraph — 대부분 이걸 쓴다

병렬화 가능한 작은 작업을 큐에 넣으면 워커 스레드들이 알아서 가져가 처리한다.

AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, []()
{
    // 워커 스레드에서 실행됨
    HeavyComputation();

    // 결과를 다시 Game Thread로 넘기고 싶으면:
    AsyncTask(ENamedThreads::GameThread, []()
    {
        UpdateUI();   // 이건 Game Thread에서 실행돼야 안전
    });
});
경로 탐색(A*) 백그라운드 처리절차적 생성(지형·던전)JSON/Save 파일 파싱
FRunnable — 평생 도는 워커가 필요할 때
class FMyWorker : public FRunnable
{
public:
    virtual uint32 Run() override
    {
        while (!bStop)
        {
            DoWork();
            FPlatformProcess::Sleep(0.016f);
        }
        return 0;
    }
    virtual void Stop() override { bStop = true; }
private:
    FThreadSafeBool bStop = false;
};

// 사용
FMyWorker* W = new FMyWorker();
FRunnableThread* T = FRunnableThread::Create(W, TEXT("MyWorker"));

SECTION 05 · 실전

5Game Thread에서 하면 안 되는 일

원칙: UObject, Actor, Component, Slate UI는 거의 다 Game Thread 전용. 워커는 순수 데이터 계산만.

❌ 나쁜 예 1 — 큰 파일 동기 로딩
void AMyActor::BeginPlay()
{
    FString Huge;
    FFileHelper::LoadFileToString(Huge, TEXT("HugeFile.txt"));
    // 100ms 걸리면 60FPS 기준 게임이 6프레임 통째로 멈춘다
}
✅ 좋은 예 — 비동기로 빼기
void AMyActor::BeginPlay()
{
    AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, [this]()
    {
        FString Huge;
        FFileHelper::LoadFileToString(Huge, TEXT("HugeFile.txt"));

        AsyncTask(ENamedThreads::GameThread, [this, Huge]()
        {
            ApplyContent(Huge);   // 결과 사용은 다시 Game Thread에서
        });
    });
}
❌ 나쁜 예 2 — 워커 스레드에서 UObject 생성
AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, []()
{
    AMyActor* Actor = NewObject<AMyActor>();  // 크래시 가능! GC와 충돌
});
❌ 나쁜 예 3 — 워커 스레드에서 UI 업데이트
AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, []()
{
    MyWidget->SetText(TEXT("Done"));  // Slate는 Game Thread 전용
});
