Part 5 · I/O와 파일 시스템

파일 시스템 기본

세이브 파일 한 줄 읽는 코드 뒤에서, Open은 정확히 뭘 하고 있을까? 파일 핸들, inode, 디렉토리 매핑을 직접 추적해본다.

🗂️ 파일 = 메타데이터 + 데이터
🧩 선수지식 2강 · 3강
⏱️ 약 20분
SECTION 01 · 의문

1"파일을 연다"는 게 뭘까

게임에서 세이브 파일을 읽는 코드는 이렇게 생겼다.

FString SaveData;
FFileHelper::LoadFileToString(SaveData, TEXT("Save01.sav"));

이 한 줄은 내부적으로 세 단계로 펼쳐진다.

// 의사 코드로 펼치면
FileHandle = Open("Save01.sav");   // 1. 파일 "열기"
Read(FileHandle, Buffer);          // 2. 내용 읽기
Close(FileHandle);                 // 3. 파일 "닫기"

"읽기"는 알겠는데, "연다"와 "닫는다"는 정확히 뭘 하는 걸까? 파일은 SSD에 그대로 있는데, 연다고 어디로 옮겨지는 것도 아닌데.

답을 알려면 파일 시스템이 파일을 어떻게 관리하는지 봐야 한다. ↓

SECTION 02 · 구조

2파일은 두 부분 + 이름표는 따로

디스크에 있는 파일 하나는 사실 메타데이터와 실제 데이터 두 가지로 구성된다. 그리고 놀랍게도 파일 이름은 이 안에 없다.

📋 메타데이터 (inode / MFT 레코드)

inode 번호12345
크기4096 bytes
수정 시각2026-06-15
권한읽기/쓰기
데이터 위치[블록 17, 42, 9]

💾 실제 데이터 (디스크 블록)

블록 17바이트 조각 A
블록 42바이트 조각 B
블록 9바이트 조각 C

순서대로 붙어있지 않고 디스크 여기저기 흩어져 있을 수 있다.

유닉스 계열(Linux, macOS)에서 메타데이터 덩어리를 inode(아이노드)라 부른다. 파일 하나당 inode 하나. Windows NTFS는 MFT(Master File Table)의 레코드가 같은 역할을 한다 — 이름은 다르지만 개념은 같다: "이름 빼고 파일에 관한 모든 정보 + 데이터 위치".

핵심: 파일 = inode(메타데이터) + 데이터 블록들. 이름은 다른 곳이 관리한다.

그럼 이름은 어디에? — 디렉토리가 관리

디렉토리(폴더)는 "이름 → inode 번호" 매핑표를 들고 있는 특별한 파일이다.

이름inode 번호
Save01.sav12345
Save02.sav12389
Config.ini9001
→

inode 12345

실제 파일 본체. 이름은 없고 크기·권한·데이터 위치만.

이름과 inode가 분리돼 있으니 여러 이름이 같은 inode를 가리킬 수 있다 — 이게 하드 링크다. 심볼릭(소프트) 링크는 반대로 "다른 경로를 가리키는" 별도 파일(바로가기)이라 원본이 지워지면 깨진다.

SECTION 03 · 킬러 · 직접 추적

3파일 열기 ~ 읽기 경로 추적기

경로를 입력하면 디렉토리 엔트리 → inode/MFT 레코드 → 데이터 블록 순서로 실제 조회 과정을 단계별로 보여준다. 페이지 캐시 HIT/MISS를 바꿔가며 디스크까지 내려가는지, 시간이 얼마나 달라지는지 비교해보자.

/SaveGames/Save01.sav /Config.ini /Content/Maps/World/Zone3/Level.umap
페이지·디렉토리 캐시 상태
커널 캐시 (dentry / inode / page cache)
⇅
디스크 (SSD/HDD)
경로를 입력하고 ▶ 재생을 눌러보세요.
HIT
MISS

경로가 깊을수록 디렉토리 탐색 단계가 늘어난다. OS는 이 경로 해석 결과를 dentry 캐시에, 파일 내용은 페이지 캐시에 담아 재접근을 빠르게 만든다.

SECTION 04 · 진짜 의미

4"연다" = 핸들을 받는 것

Open("Save01.sav")이 하는 일을 순서대로 풀면 이렇다.

1. 경로 해석 → inode 12345 찾음 (위의 디렉토리 탐색)
2. 권한 검사 (이 프로세스가 읽어도 되나?)
3. inode를 메모리에 올림
4. 커널에 "열린 파일" 항목을 만듦 (현재 읽기 위치 = 0 등)
5. 이 프로세스의 파일 디스크립터 테이블에 등록
6. 그 번호(파일 디스크립터 / 핸들)를 반환

핵심: "연다"는 데이터를 옮기는 게 아니라, 커널에 "이 파일을 쓸 준비" 상태를 만들고 그 핸들을 받는 것. "닫는다"는 그 항목을 정리하는 것.

열린 파일을 가리키는 번호표

유닉스는 파일 디스크립터(fd) — 작은 정수, Windows는 파일 핸들(HANDLE) — 불투명한 값을 쓴다.

fd가리키는 것
0표준 입력 (stdin)
1표준 출력 (stdout)
2표준 에러 (stderr)
3Save01.sav (읽기 위치 0) ← Open이 반환한 것
4Config.ini

fd 0, 1, 2가 입출력에 예약돼 있다. printf가 stdout(fd 1)으로 나가는 게 이거다.

왜 직접 inode를 안 주고 핸들을 줄까

보안 — 프로세스가 디스크 구조를 직접 못 만지게, 커널이 핸들을 통해서만 접근을 허용한다. 상태 관리 — "지금 어디까지 읽었나(오프셋)"를 커널이 핸들마다 관리한다. 추상화 — 파일, 소켓, 파이프, 디바이스가 다 같은 fd로 추상화된다("Everything is a file").

언리얼 / Win32와 연결
// 언리얼 추상화
IFileHandle* Handle = IPlatformFile::GetPlatformPhysical().OpenRead(*FilePath);
//          ↑ 내부적으로 Windows의 CreateFile() 호출

// Win32 직접 (언리얼이 내부에서 이렇게 부름)
HANDLE hFile = CreateFile(
    L"Save01.sav",
    GENERIC_READ,           // 읽기 권한
    FILE_SHARE_READ,        // 다른 프로세스도 읽기는 허용
    nullptr,
    OPEN_EXISTING,          // 기존 파일 열기
    FILE_ATTRIBUTE_NORMAL,
    nullptr);
// hFile 이 파일 핸들. 이걸로 ReadFile/WriteFile/CloseHandle.

CreateFile이라는 이름이 헷갈리는데, 만들기 전용이 아니라 "열기"도 한다. 위처럼 OPEN_EXISTING이면 기존 파일 열기 — Windows API의 대표적인 작명 함정이다. 언리얼의 FFileHelper, IFileManager, IPlatformFile이 결국 이런 OS 콜로 내려간다.

SECTION 05 · 성능

5매번 디스크 가면 느리니까 — 버퍼링

2강에서 "시스템 콜은 비싸다"고 했다. 파일 I/O는 시스템 콜 + 디스크 접근이라 더 비싸다. 그래서 여러 층의 버퍼/캐시가 낀다.

우리 코드
    ↓ fread / 라이브러리 버퍼 (유저 공간)
C 런타임 버퍼
    ↓ read() 시스템 콜
커널 페이지 캐시 (RAM)  ← OS가 디스크 내용을 RAM에 캐싱
    ↓ (캐시 미스일 때만)
디스크 (SSD/HDD)
페이지 캐시 — 한 번 읽은 파일은 RAM에 남는다

OS는 디스크에서 읽은 파일 내용을 RAM(페이지 캐시)에 보관한다. 같은 파일을 또 읽으면 디스크에 안 가고 RAM에서 바로 준다.

// 처음 읽기 — 디스크 접근. 느림 (수 ms)
FFileHelper::LoadFileToString(S, TEXT("Big.txt"));

// 두 번째 읽기 — 페이지 캐시에서. 빠름 (수 μs)
FFileHelper::LoadFileToString(S, TEXT("Big.txt"));

게임 처음 켤 때 로딩이 느리다가 두 번째부터 빨라지는 게 이 캐시 덕분(과 다른 요인들). 12강의 페이지 캐시/메모리 맵과 같은 메커니즘이다.

SECTION 06 · 실무

6게임 개발자 입장 — 알아둘 것

🔓

핸들은 자원이다

안 닫으면 핸들 누수. 게임이 오래 돌면 "Too many open files"로 죽을 수 있다.

📦

작은 파일 많이 < 큰 파일 적게

Open/Close는 시스템 콜 + 디렉토리 탐색이라 비싸다. 언리얼이 에셋을 .pak으로 묶는 이유.

🧭

경로 탐색도 비용

경로가 깊으면 디렉토리를 단계마다 읽어야 한다. 핫 패스에서 매번 풀 경로로 여는 건 피하라.

🗄️

RAII로 자동 정리

스코프를 벗어나면 자동으로 닫히게 만들면 누수 걱정이 없다. 8강 FScopeLock과 같은 원리.

핸들 누수 방지 — RAII
// ❌ 핸들 누수 가능
IFileHandle* H = PlatformFile.OpenRead(*Path);
if (Failed) return;   // H 안 닫고 빠져나감

// ✅ RAII로 자동 정리 (8강 FScopeLock과 같은 원리)
{
    TUniquePtr<IFileHandle> H(PlatformFile.OpenRead(*Path));
    // ... 사용
}   // 스코프 끝 → 자동 닫힘
