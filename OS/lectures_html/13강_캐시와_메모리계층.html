캐시와 메모리 계층

같은 100만 개 순회인데 TArray가 링크드리스트보다 5~10배 빠르다. 빅오는 같은데 왜? 직접 레이스를 시켜본다.

📏 캐시 라인 64B
🧩 선수지식 11강
⏱️ 약 20분
SECTION 01 · 수수께끼

1연산 횟수는 같은데 속도가 다르다

원소 100만 개를 더하는 코드. 한쪽은 연속 메모리(TArray), 한쪽은 힙에 흩어진 링크드리스트. 덧셈 횟수는 똑같다. 그런데…

// (A) 연속 메모리
TArray<int32> Arr;  for (int32 v : Arr) Sum += v;

// (B) 힙에 흩어진 노드
for (FNode* n = Head; n; n = n->Next) Sum += n->Value;

(A)가 (B)보다 5~10배 빠르다. 차이는 단 하나 — 메모리를 어떻게 읽느냐.

그 비밀은 캐시에 있다. 아래에서 직접 확인하자. ↓

SECTION 02 · 속도 격차

SECTION 03 · 핵심 원리

3캐시는 "라인" 단위로 끌어온다

CPU는 1바이트만 필요해도 그게 속한 64바이트(여기선 8칸)를 통째로 캐시에 올린다. "다음 원소 읽기"를 눌러 순차 접근을 따라가보자.

― 캐시 라인 0 (64B) ―
― 캐시 라인 1 (64B) ―
L1 캐시에 올라온 라인
비어있음
인덱스 0부터 순서대로 읽어봅니다.

경계 칸(0, 8…)에서만 캐시 미스로 64B를 통째로 올리고, 그 다음 7칸은 전부 캐시 히트다. 순차 접근이 빠른 이유.

빅오는 둘 다 O(n)이지만 실제 사이클이 몇 배 차이난다. 빅오는 연산 횟수지 메모리 접근 비용이 아니다 — 게임에서 링크드리스트를 거의 안 쓰는 이유.

SECTION 05 · 설계

5데이터 지향 설계 — AoS vs SoA, False Sharing

🗃️

AoS vs SoA

한 필드만 대량 처리할 땐 SoA(필드별 배열)가 캐시에 그 필드만 빽빽이 올라와 유리. 한 객체의 여러 필드를 함께 쓰면 AoS. 파티클·ECS가 SoA를 쓴다.

⚔️

False Sharing

서로 다른 스레드가 같은 캐시 라인의 다른 변수를 수정하면, 충돌이 없는데도 라인 무효화로 성능이 폭락. 핫한 카운터는 alignas(64)로 띄운다.

2차원 배열 — 순회 순서가 곧 속도
// ✅ 행 우선 (C++ 메모리 레이아웃과 일치 → 연속)
for (int y=0; y<H; ++y)
  for (int x=0; x<W; ++x) Grid[y][x] = ...;

// ❌ 열 우선 (매번 W칸씩 점프 → 캐시 미스 폭발)
for (int x=0; x<W; ++x)
  for (int y=0; y<H; ++y) Grid[y][x] = ...;
