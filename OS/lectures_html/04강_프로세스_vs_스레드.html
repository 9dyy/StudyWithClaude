프로세스 vs 스레드

언리얼 게임이 멀티스레드로 돈다는 건 다들 안다. 근데 왜 멀티프로세스가 아니라 멀티스레드인가? 전역 변수 하나 공유해보면 답이 바로 보인다.

🧠 공유냐 독립이냐
🧩 선수지식 3강
⏱️ 약 20분
SECTION 01 · 도입

1게임은 왜 멀티스레드인가?

언리얼 게임 하나가 매 프레임 처리하는 일을 나열해보자 — 입력, 물리, AI, 애니메이션, 렌더링, 네트워크, 에셋 로딩, 사운드. 이걸 한 줄로 순서대로 다 처리한다고 해보자.

while (true)  // 메인 루프
{
    UpdateInput();      // 1ms
    UpdatePhysics();    // 5ms
    UpdateAI();         // 3ms
    UpdateAnimation();  // 4ms
    Render();           // 10ms   ← GPU 기다리는 동안 CPU 놀음
    SendNetwork();      // 2ms
    LoadAssets();       // 100ms  ← 디스크 기다리는 동안 다 멈춤
    // 합: 125ms → 8 FPS. 게임 끝.
}
🐢

문제 1. 한 작업이 느리면 모든 게 멈춘다. 에셋 로딩 중엔 캐릭터도 못 움직인다.

🧊

문제 2. CPU 코어가 16개여도 1개밖에 못 쓴다.

해결: 여러 일을 동시에. 그게 멀티스레드다.

그런데 "동시에 여러 일"이 필요하면 프로세스를 여러 개 띄워도 되는 거 아닌가? 그 차이부터 보자. ↓

SECTION 02 · 개념

2프로세스 — 실행 중인 프로그램 하나

3강에서 이미 본 그거다. 실행 중인 프로그램 하나가 프로세스다.

프로세스 A (MyGame.exe)
├─ 자기만의 가상 주소 공간 (Text/Data/BSS/Heap/Stack)
├─ 열어둔 파일 핸들
├─ 환경 변수
├─ 현재 디렉토리
└─ 보안 컨텍스트 (어느 유저가 실행했나)
🔒

메모리 공간이 독립적이다. A의 변수를 B가 못 본다.

🛡️

그래서 안전하다. 한 프로세스가 죽어도 다른 프로세스는 멀쩡하다.

📮

그래서 통신이 어렵다. IPC(Inter-Process Communication: 파이프, 공유 메모리, 소켓 등)가 필요하다.

💸

만들고 없애는 비용이 비싸다. 메모리 공간을 통째로 잡아야 한다.

SECTION 03 · 개념

3스레드 — 프로세스 안에서 도는 실행 흐름

같은 프로세스 안에서 도는 실행 흐름. 한 프로세스에 여러 개 있을 수 있다.

프로세스 (MyGame.exe)
├─ Text/Data/BSS/Heap   ← 스레드들이 공유
├─ 파일 핸들 등         ← 스레드들이 공유
│
├─ 스레드 1 (Game Thread)
│   └─ 자기만의 Stack, 레지스터, PC(Program Counter)
├─ 스레드 2 (Render Thread)
│   └─ 자기만의 Stack, 레지스터, PC
├─ 스레드 3 (Audio Thread)
│   └─ 자기만의 Stack, 레지스터, PC
└─ 스레드 4 (Worker)
    └─ 자기만의 Stack, 레지스터, PC
🔗

Heap, Data, BSS, 코드를 공유한다. 전역 변수 하나 바꾸면 다른 스레드도 영향을 받는다.

🗂️

Stack과 레지스터(실행 상태)만 따로 가진다.

⚡

만들고 없애는 비용이 싸다. 프로세스 만들기보단 훨씬 가볍다.

🤝

통신이 쉽다. 그냥 전역 변수, 힙 객체로 데이터를 주고받는다.

⚠️

그래서 위험하다. 동기화 문제가 생긴다 (7강 Race Condition의 원인).

SECTION 05 · 킬러 · 직접 실험

5메모리 공유 비교기 — 정말로 공유되는가?

모드를 골라서 Worker 1이 전역 변수 g_Shared를 증가시켰을 때, Worker 2가 그 변화를 보는지 직접 확인해보자.

Worker 1을 눌러 g_Shared를 증가시켜보자.

스레드 모드에서는 Heap/Data/BSS가 같은 메모리라 상대방이 즉시 새 값을 본다. 프로세스 모드에서는 각자 독립된 가상 주소 공간이라, 한쪽이 값을 바꿔도 다른 쪽은 전혀 모른다 — 값을 주고받으려면 IPC가 필요하다.

SECTION 06 · 코드로 체감

6같은 프로세스의 두 스레드는 메모리를 진짜로 공유한다

방금 실험한 걸 실제 언리얼 코드로 보면 이렇다.

#include "HAL/Runnable.h"
#include "HAL/RunnableThread.h"

int32 g_Shared = 0;   // 전역 변수 — 모든 스레드가 공유 (BSS/Data)

class FWorker : public FRunnable
{
public:
    virtual uint32 Run() override
    {
        for (int i = 0; i < 1000000; ++i)
        {
            g_Shared++;   // 같은 메모리 주소를 여러 스레드가 같이 건드림
        }
        return 0;
    }
};

void Test()
{
    FWorker* W1 = new FWorker();
    FWorker* W2 = new FWorker();

    FRunnableThread* T1 = FRunnableThread::Create(W1, TEXT("W1"));
    FRunnableThread* T2 = FRunnableThread::Create(W2, TEXT("W2"));

    T1->WaitForCompletion();
    T2->WaitForCompletion();

    UE_LOG(LogTemp, Warning, TEXT("Result = %d"), g_Shared);
    // 기대값: 2,000,000
    // 실제값: 매번 다름. 1,200,000 정도 나올 수 있음. ← Race Condition!
}

이게 7강에서 자세히 다룰 Race Condition의 정체다. g_Shared++는 "읽고, 1 더하고, 쓰고"인데 두 스레드가 동시에 하면 서로 덮어쓴다.

만약 이걸 별개 프로세스 두 개로 했다면? 각자 자기 g_Shared를 가지니까 충돌이 없다. 둘 다 1,000,000으로 끝난다. 그런데 둘을 합산해서 결과를 보려면 별도 통신(IPC)이 필요하다.

SECTION 08 · 실전 판단

8언제 프로세스, 언제 스레드?

스레드를 쓰는 경우
🤝

같은 데이터를 여러 작업이 빠르게 공유해야 할 때

🎮

게임처럼 한 화면을 위해 여러 일이 협력해야 할 때

✅

대부분의 게임 클라이언트, 게임 서버는 멀티스레드다.

프로세스를 쓰는 경우
🧱

격리(Isolation)가 중요할 때 — 크롬은 탭 하나가 죽어도 다른 탭이 안 죽게 탭마다 프로세스를 쓴다.

🚀

게임 런처가 게임 본체와 분리되어 있는 것 (런처가 죽어도 게임은 OK)

🔑

다른 권한이 필요할 때, 장애 격리가 중요할 때

게임 개발자의 현실: 게임 클라이언트는 한 프로세스 + 많은 스레드 구조가 거의 표준이다. 언리얼도 그렇다. 프로세스는 보통 런처 ↔ 게임, 게임 ↔ 안티치트(예: BattlEye)처럼 격리가 필요할 때만 나눈다.
SECTION 09 · OS 내부

9PCB와 TCB — OS가 기억하는 것들

OS는 모든 프로세스와 스레드를 추적하기 위해 자료구조를 들고 있다.

📋

PCB (Process Control Block) — 프로세스 하나당 1개. PID, 가상 주소 공간 정보, 파일 핸들 목록, 보안 컨텍스트 등을 담는다.

🧾

TCB (Thread Control Block) — 스레드 하나당 1개. 스레드 ID, 레지스터 상태, 스택 포인터, 우선순위 등을 담는다.

CPU가 스레드를 바꿔 돌릴 때(컨텍스트 스위칭, 6강), TCB에서 레지스터 값을 꺼내거나 저장한다.

면접 팁: "PCB/TCB가 뭐냐?" 물어보면 "OS가 프로세스/스레드를 관리하기 위한 자료구조이고, 컨텍스트 스위칭 시 여기 저장된 레지스터 상태를 꺼내 씁니다" 정도면 충분하다.
