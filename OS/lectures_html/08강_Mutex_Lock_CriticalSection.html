SECTION 01 · 해결책

1임계영역에 자물쇠를 채우자

7강 결론: "임계영역은 한 번에 한 스레드만 들어가야 한다." 가장 직관적인 해결책은 자물쇠다.

공유 데이터
↓
🔒 열쇠가 있어야 들어갈 수 있는 방
↓
임계영역 — Counter += 1 (한 명만 진입)
↓
나오면서 열쇠 반납

이 "자물쇠"가 Mutex (Mutual Exclusion)다.

SECTION 02 · 원리

2Lock()은 블로킹 호출이다

스레드 A가 먼저 Lock을 잡으면, 뒤이어 온 스레드 B는 A가 Unlock 할 때까지 잠들어 기다린다.

● 스레드 A

Lock() ← 열쇠 받음 (성공)
Counter++;
Unlock() ← 열쇠 반납

● 스레드 B

Lock() ← A가 열쇠 보유 중, Waiting 상태로 잠듦
… A가 Unlock 하는 순간 OS가 깨움
Counter++; → Unlock()
🔑Lock()은 블로킹 호출. 락이 이미 잡혀있으면 풀릴 때까지 잠든다.
😴잠든 스레드는 OS의 Waiting 상태로 들어가고, CPU를 다른 스레드에 양보한다.
🔔Unlock() 하면 기다리던 스레드 중 하나가 깨어난다.
언리얼에서 — FCriticalSection

표준 C++의 std::mutex와 같은 역할.

#include "HAL/CriticalSection.h"

class FInventory
{
public:
    void AddItem(int32 ItemId)
    {
        Lock.Lock();
        Items.Add(ItemId);
        Lock.Unlock();
    }

    int32 GetCount()
    {
        Lock.Lock();
        int32 Count = Items.Num();
        Lock.Unlock();
        return Count;
    }

private:
    TArray<int32>      Items;
    FCriticalSection   Lock;
};

이제 여러 스레드가 AddItem을 동시에 불러도 안전하다.

SECTION 03 · 실무 필수

3Lock/Unlock 직접 호출 금지 — FScopeLock

위 코드는 사실 함정이 있다. Unlock()을 안 부르고 빠져나가는 경로가 있으면 다른 스레드가 영원히 잠든다.

❌ 거의 항상 터지는 함정
void Foo()
{
    Lock.Lock();

    if (SomeCondition)
        return;          // ❌ Unlock() 안 부르고 빠져나감 → 락 영구 보유

    DoStuff();           // 여기서 예외 throw 가능 → 마찬가지

    Lock.Unlock();
}

이런 식으로 락을 안 풀고 빠져나가면 다른 스레드가 영원히 잠든다. 게임 멈춤.

✅ 해결책 — RAII 패턴

객체 수명에 락 수명을 묶어버린다. 언리얼은 FScopeLock을 제공한다.

void AddItem(int32 ItemId)
{
    FScopeLock LockGuard(&Lock);   // 생성자에서 Lock(), 소멸자에서 Unlock()
    Items.Add(ItemId);
}   // ← 여기서 LockGuard 소멸 → 자동 Unlock

return, 예외, 어떤 경로로 빠져나가든 소멸자가 호출되니까 락이 풀린다. C++ 표준의 std::lock_guard, std::unique_lock과 같은 패턴.

실무 원칙: FCriticalSection의 Lock/Unlock을 직접 부르지 마라. 무조건 FScopeLock.
추가 원칙 — 락 잡는 범위는 최소로
// ❌ 락 너무 넓게
void Heavy()
{
    FScopeLock G(&Lock);

    int32 Item = Items.Last();
    HeavyComputation(Item);    // 1초 걸리는 작업을 락 잡은 채로 → 다른 스레드 1초 대기
    NetworkCall();
}

// ✅ 락은 데이터 만질 때만
void Heavy()
{
    int32 Item;
    {
        FScopeLock G(&Lock);
        Item = Items.Last();
    }
    HeavyComputation(Item);   // 락 없이
    NetworkCall();             // 락 없이
}

락을 잡고 있는 동안은 다른 스레드가 멈춰 있다. 락 안에서 무거운 일, I/O, 시스템 콜은 피하라.

SECTION 04 · 킬러 · 손으로 만져보기

4락 획득/대기 시뮬레이터

스레드 4개(T1~T4)가 동시에 임계영역 진입을 시도한다. 동기화 방식을 바꿔가며 누가 들어가고 누가 큐에서 대기하는지 직접 비교해보자.

🔒 임계영역 (안에 있는 스레드)
⏳ 대기 큐
0
최대 동시 진입
0
경과 틱

FScopeLock은 항상 1명, Semaphore(N)은 최대 N명까지 동시 진입을 허용한다. FRWLock은 읽기(R)끼리는 같이 들어가지만 쓰기(W)는 항상 혼자다. "락 없음"은 전원이 동시에 밀고 들어간다 — 7강의 Race Condition이 그대로 재현된다.

SECTION 05 · 정리

5Mutex의 종류, 세마포어, 그리고 비용

🔒

기본 Mutex

std::mutex, FCriticalSection. 같은 스레드가 두 번 Lock 하면 데드락이다.

♻️

재귀 Mutex

std::recursive_mutex. 같은 스레드가 여러 번 Lock 해도 OK지만, 푸는 것도 같은 횟수 Unlock 해야 한다. 남용 X.

📖

Read-Write Lock

FRWLock. 여러 스레드의 읽기는 동시 허용, 쓰기는 단독. 읽기가 압도적으로 많은 설정값·캐시에 유리.

🌀

Spinlock

기다릴 때 자지 않고 빙빙 돌면서 대기. 컨텍스트 스위칭 비용은 없지만 CPU를 낭비한다. 락을 아주 짧게만 잡을 때 유리.

재귀 Mutex가 필요한 이유 — 기본 Mutex는 이렇게 멈춘다
FCriticalSection Lock;

void A() { FScopeLock G(&Lock); B(); }
void B() { FScopeLock G(&Lock); ... }   // ❌ 같은 스레드가 또 락 → 영원히 멈춤
FRWLock 사용 예
FRWLock RWLock;

// 읽기
RWLock.ReadLock();
int32 V = Cache[Key];
RWLock.ReadUnlock();

// 쓰기
RWLock.WriteLock();
Cache[Key] = NewValue;
RWLock.WriteUnlock();
Spinlock 사용 예 — 아주 짧은 구간 전용
FSpinLock Spin;

Spin.Lock();
SmallOperation();    // 1μs 이하
Spin.Unlock();

쓰는 경우가 드물고, 잘못 쓰면 코어 하나가 100%가 된다.

세마포어 (Semaphore) — Mutex의 일반화

Mutex가 "한 명만 들어가는 자물쇠"라면, 세마포어는 "N명까지 들어가는 자물쇠"다.

세마포어 = 카운터
Wait()    → 카운터 0이면 잠, 아니면 카운터-1 하고 진입
Signal()  → 카운터+1, 기다리던 스레드 깨움

용도: 자원 풀(동시 커넥션 N개, 동시 비디오 디코더 N개), 생산자-소비자 패턴(버퍼에 데이터 있는 만큼만 소비자가 깨어남).

// 의사 코드
FSemaphore Sem(/*Count=*/4);   // 동시 4개 허용

void HandleRequest()
{
    Sem.Wait();
    DoWork();    // 동시에 최대 4명만 여기 있음
    Sem.Signal();
}

Mutex는 N=1인 세마포어와 비슷하지만, "락 잡은 스레드만 풀 수 있다"는 소유권 개념이 있다. 세마포어는 그게 없다 — 아무나 Signal 가능. 이진 세마포어(N=1)는 소유권 없이 시그널 용도로 쓰이며, 언리얼의 FEvent가 이 패턴에 가깝다.

락은 공짜가 아니다 — 잠재 비용
1

잠금/해제 비용

보통 수십 나노초. 많이 잡으면 누적된다.

2

대기 비용

락 못 받은 스레드는 잔다 → 컨텍스트 스위칭 비용.

3

직렬화 비용

락 안의 코드는 결국 한 명만 도므로, 그 부분이 전체 성능 상한을 만든다 (Amdahl's Law).

4

데드락 위험

다음 강의(10강)에서 다룬다.

그래서 공유를 줄이는 게 최선, 어쩔 수 없으면 락 범위 최소화, 그래도 부족하면 lock-free / atomic(9강)으로 간다.

코드로 — 7강의 망가진 카운터 고치기
// Before (7강)
int32 g_Shared = 0;
void Worker()
{
    for (int i = 0; i < 1000000; ++i)
        g_Shared++;   // Race
}

// After
int32 g_Shared = 0;
FCriticalSection g_Lock;

void Worker()
{
    for (int i = 0; i < 1000000; ++i)
    {
        FScopeLock G(&g_Lock);
        g_Shared++;
    }
}

이제 결과는 정확히 2,000,000이 나온다. 하지만 굉장히 느리다. 매 ++마다 락/언락 비용 + 두 스레드가 직렬로 도는 셈이라.

// 더 좋은 버전 (9강에서 다룸)
std::atomic<int32> g_Shared{0};
void Worker()
{
    for (int i = 0; i < 1000000; ++i)
        g_Shared.fetch_add(1, std::memory_order_relaxed);
}

→ 이런 단순 카운터엔 atomic이 훨씬 빠르다. 다음 강의에서 다룬다.
