Part 4 · 메모리 관리

가상 메모리와 페이징

모든 프로세스가 똑같이 0x0부터 시작하는 주소를 쓰는데도 충돌하지 않는 마술. 그 비밀을 직접 눌러보며 이해한다.

SECTION 01 · 미스터리

1이상한 일이 벌어진다

게임을 두 개 띄우고 같은 코드의 전역 변수 주소를 찍어본다. 버튼을 눌러 실행해보자.

프로세스 A (게임.exe)

&g_Value = 0x1234_0000
?

프로세스 B (같은 게임.exe)

&g_Value = 0x1234_0000
?
두 프로세스의 변수가 똑같은 주소에 있다. 값은?
저 주소는 진짜 주소가 아니다. 물리 RAM은 하나뿐인데 같은 주소에 다른 값이라니 — 답은, 각 프로세스가 보는 0x1234_0000은 가상 주소(Virtual Address)이고, OS가 뒤에서 둘을 서로 다른 물리 위치로 연결해주기 때문이다. 아래에서 그 변환을 직접 돌려보자. ↓
SECTION 02 · 인터랙티브

2가상 주소를 물리 주소로 변환해보기

가상 주소는 페이지 번호 + 오프셋으로 나뉜다(4KB 페이지 = 하위 12비트가 오프셋). 페이지 번호만 페이지 테이블에서 프레임으로 바꾸고, 오프셋은 그대로 붙인다.

0x
페이지 번호 (VPN)
0x12345
오프셋
0x678
↓  페이지 테이블 조회  ↓
프레임 번호
0x0A00
＋
오프셋
0x678
＝
물리 주소 (Physical)
0x0A00678

오프셋(하위 12비트)은 변환 없이 그대로 따라옵니다. 페이지 번호만 테이블을 거칩니다.

SECTION 03 · 클릭해보기

3페이지 테이블 — 프로세스마다 하나씩

"가상 페이지 → 물리 프레임" 매핑표. 각 행을 클릭해보자. 유효 비트가 O면 변환 성공, X면 페이지 폴트가 난다(→ 다음 강의 12강).

SECTION 04 · 시뮬레이션

4TLB — 변환 결과를 캐싱한다

매번 페이지 테이블을 뒤지면 느리니까, 최근 변환을 TLB라는 초고속 캐시(여기선 4칸)에 저장한다. 핵심 질문: 메모리를 어떻게 접근하느냐에 따라 Hit율이 갈린다.

접근을 시작하면 여기에 로그가 쌓입니다.
0
TLB Hit (4 cyc)
0
TLB Miss (200 cyc)
0
총 사이클

순차 순회는 같은 페이지를 연달아 건드려 Hit이 많고, 랜덤 접근은 매번 다른 페이지라 Miss가 쏟아진다. 13강 캐시 강의의 "연속 메모리가 빠른 이유"가 여기서 시작된다.

SECTION 05 · 왜 이렇게까지

5가상 메모리가 주는 4가지 이득

🛡️

프로세스 격리

A가 무슨 주소를 써도 B의 물리 메모리엔 닿을 수 없다. 게임이 죽어도 디스코드는 멀쩡한 이유.

🧩

단편화 해결

물리 RAM이 조각나 있어도 가상에선 연속으로 보인다. TArray가 1GB를 연속으로 잡는 비결.

💽

RAM보다 큰 메모리

안 쓰는 페이지는 SSD로 내려놨다가(스왑) 필요할 때 올린다. 12강 주제.

♻️

코드 공유

같은 exe를 두 번 띄워도 코드 영역은 물리적으로 한 벌만. 두 프로세스가 같은 물리 위치를 가리킨다.

게임 개발자 관점

"Reserve 했는데 작업 관리자 메모리가 안 늘어나네?"

TArray<int32> Arr;
Arr.Reserve(1000000);   // 가상 주소 공간은 잡았지만…
// 실제로 그 페이지를 건드리기 전엔 물리 RAM이 안 붙는다

처음 쓸 때 페이지 폴트가 나면서 그제서야 물리 프레임이 할당된다. 이걸 demand paging(lazy allocation)이라 한다.
