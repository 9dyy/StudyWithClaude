"비동기 로딩"이 정확히 뭘 하는 건지 강의 계획서 첫머리에 약속했던 그 답을 지금 회수한다. 블로킹/논블로킹, 동기/비동기를 구분하고 FStreamableManager와 IOCP가 뒤에서 하는 일을 직접 타임라인으로 본다.

SECTION 01 · 사고 현장

1텍스처 로딩하다 게임이 멈췄다

5강, 12강에서 계속 나왔던 그 장면이다.

void AMyActor::BeginPlay()
{
    UTexture2D* Tex = LoadObject<UTexture2D>(nullptr, TEXT("/Game/BigTexture"));
    // 이 줄에서 디스크 읽기 끝날 때까지 Game Thread가 멈춤 → 게임 정지
    Mesh->SetMaterialTexture(Tex);
}

LoadObject는 디스크에서 텍스처를 다 읽어올 때까지 반환하지 않는다. 그동안 Game Thread는 6강에서 배운 Waiting 상태로 잠들어 있다.

50MB 텍스처면 수십~수백 ms. 게임이 그만큼 멈춘다(hitch). 해결책이 "비동기 로딩"인데, 정확히 뭐가 다른 걸까? 용어부터 정리하자. ↓

SECTION 02 · 헷갈리는 용어

2두 개의 축 — 블로킹/논블로킹, 동기/비동기

블로킹/논블로킹과 동기/비동기는 서로 다른 축이다. 면접에서 자주 섞어 묻는다. 칸을 눌러서 차이를 확인해보자.

축 1 — 블로킹 vs 논블로킹: "기다리느냐?" 블로킹은 결과가 나올 때까지 호출이 안 돌아오고 스레드가 멈춘다. 논블로킹은 결과가 준비 안 됐으면 "아직 안 됐어" 하고 즉시 반환, 스레드는 안 멈춘다.

축 2 — 동기 vs 비동기: "누가 결과를 챙기느냐?" 동기는 내가 직접 결과를 받아오거나 직접 폴링한다. 비동기는 작업을 맡겨두고 완료되면 콜백/이벤트로 알려준다.

동기
(직접 챙김)
비동기
(알려줌)
블로킹
(기다림)
일반 read()결과 올 때까지 멈춤
(드묾)실무에서 거의 안 씀
논블로킹
(안 기다림)
논블로킹 + 폴링"됐어?" 반복 확인
진짜 비동기 I/O맡기고 콜백 받음
칸을 클릭해보면 설명이 뜬다. 게임 비동기 로딩이 노리는 건 오른쪽 아래(초록 강조) 칸이다 — "로딩 맡겨놓고 Game Thread는 계속 돌다가, 다 되면 콜백 받기."
SECTION 03 · 코드로

3세 가지 방식, 코드로 비교

같은 파일 읽기를 세 가지 방식으로 짜면 코드가 이렇게 달라진다.

(1) 동기 블로킹 — 가장 단순, 가장 위험

// Game Thread를 멈춘다
FString Data;
FFileHelper::LoadFileToString(Data, *Path);   // 끝날 때까지 블록
UseData(Data);                                  // 그 다음 줄

직관적이지만 Game Thread에서 쓰면 hitch. 14강의 페이지 캐시에 있으면 빠르지만, 디스크까지 가면 멈춘다.

(2) 논블로킹 + 폴링 — 직접 챙기기

// "다 됐니?"를 매 프레임 물어봄
void Tick(float Dt)
{
    if (LoadRequest.IsReady())   // 논블로킹 확인
    {
        UseData(LoadRequest.GetResult());
    }
    // 안 됐으면 그냥 다음 프레임에 또 확인. Game Thread는 안 멈춤.
}

Game Thread는 안 멈추는데, 매번 "됐어?" 물어보는 게 좀 번거롭다 — CPU를 조금씩 계속 태운다.

(3) 비동기 + 콜백 — 게임에서 쓰는 방식

// 맡겨놓고, 끝나면 알려달라고 함
StreamableManager.RequestAsyncLoad(
    AssetRef,
    FStreamableDelegate::CreateUObject(this, &AMyActor::OnLoaded)
);
// 이 줄은 즉시 반환. Game Thread 계속 돎.

void AMyActor::OnLoaded()   // 로딩 완료되면 Game Thread에서 자동 호출
{
    UTexture2D* Tex = AssetRef.Get();
    Mesh->SetMaterialTexture(Tex);
}

이게 5강에서 예고한 ENQUEUE/AsyncTask 패턴의 I/O 버전. 맡기고 → 콜백.

SECTION 04 · 진실

4그럼 비동기 I/O는 누가 기다리나?

"논블로킹이라 아무도 안 기다린다"는 건 거짓말이다. 디스크는 여전히 느리다. 누군가는 그 디스크 응답을 기다려야 한다. 핵심은 "누가 기다리느냐"다.

방법 A · 워커 스레드가 대신 블로킹 (간단한 구현)
Game Thread:  RequestAsyncLoad() ─→ (즉시 반환, 계속 게임)
                    │ 작업 위임
                    ↓
Worker Thread:  LoadFileToString() ─ [블로킹! 여기서 Waiting] ─→ 완료
                    │ 콜백 큐에 등록
                    ↓
Game Thread:  다음 Tick에서 OnLoaded() 호출

5강의 AsyncTask(BackgroundThread, ...)가 이 방식. 블로킹을 Game Thread 밖으로 옮긴 것. Game Thread 입장에선 비동기, 워커 입장에선 블로킹이다. 가장 이해하기 쉬운 비동기지만, I/O 하나당 워커 스레드 하나가 잠들어 있어야 해서 수천 개 동시 I/O엔 스레드가 부족하다.

방법 B · OS의 진짜 비동기 I/O (IOCP)

OS에게 "이 파일 읽어줘, 다 되면 알려줘" 하고 스레드를 안 재우는 방식. 디스크 컨트롤러(DMA)가 데이터를 옮기는 동안 CPU도 워커 스레드도 안 기다린다. 완료되면 OS가 통지한다.

Windows: IOCP (I/O Completion Port) · Linux: io_uring, epoll(+AIO)

Game Thread:  ReadFileEx(완료 포트 등록) ─→ 즉시 반환
                    │
                    ↓ (스레드는 아무도 안 기다림. DMA가 일함)
              디스크 → RAM 으로 데이터 이동 (CPU 개입 최소)
                    │ 완료!
                    ↓
              OS가 완료 포트에 통지 → 처리 스레드가 콜백 실행

장점: 수만 개의 동시 I/O를 적은 스레드로 처리. 게임 서버 네트워크(수천 접속)의 핵심 기술. 클라에서도 대량 에셋 스트리밍에 유리하다.

SECTION 05 · 킬러 · 프레임 타임라인 비교기

5같은 로딩 요청, 세 방식으로 동시에 흘려보기

에셋 로딩 요청 2건을 같은 타이밍에 발생시킨다. 아래 세 레인은 같은 시간축 위의 Game Thread 프레임이다. 어느 레인이 멈추고, 어느 레인이 헛수고를 하고, 어느 레인이 멀쩡한지 직접 눌러서 보자.

🧱 블로킹 (동기)0 / 0 frame
🔁 논블로킹 + 폴링0 / 0 frame · poll 0
📬 비동기 + 콜백 (IOCP/FStreamableManager)0 / 0 frame · cb 0
정상 프레임 블로킹으로 드랍된 프레임 낭비된 폴링 (황색 점) 완료 콜백 도착
블로킹 드랍
폴링 낭비
비동기 드랍

블로킹 레인은 로딩 구간 동안 프레임이 아예 안 찍힌다 — 그게 hitch. 폴링 레인은 프레임은 다 찍히지만 로딩 구간 내내 "됐어?"를 헛되이 반복한다(황색 점). 비동기 레인은 프레임이 끊기지 않고, 로딩이 끝나는 정확한 순간에만 콜백이 딱 한 번 온다(황색 칸). 셋 다 "디스크가 느리다"는 사실은 같다 — 그 느림을 누가/어떻게 흡수하느냐만 다르다.

SECTION 06 · 실전

6언리얼의 비동기 로딩 시스템

FStreamableManager — 에셋 비동기 로딩

// 멤버
FStreamableManager StreamableManager;
TSoftObjectPtr<UTexture2D> TextureToLoad;   // "약한" 참조 (아직 로드 안 됨)

void StartLoading()
{
    StreamableManager.RequestAsyncLoad(
        TextureToLoad.ToSoftObjectPath(),
        FStreamableDelegate::CreateUObject(this, &AMyActor::OnTextureLoaded)
    );
    // 즉시 반환. 게임 계속.
}

void AMyActor::OnTextureLoaded()
{
    if (UTexture2D* Tex = TextureToLoad.Get())   // 이제 메모리에 있음
        ApplyTexture(Tex);
}

TSoftObjectPtr/FSoftObjectPath: "이 에셋, 필요하면 그때 로드" 하는 약한 참조. 게임 시작 시 다 안 올리고 필요할 때 스트리밍한다. 내부적으로는 워커 스레드 + 플랫폼 비동기 I/O를 섞어 쓴다.

Async Loading Thread (ALT)

언리얼은 에셋 직렬화/로딩을 전담하는 별도 스레드를 둘 수 있다. 패키지 읽기와 객체 생성 일부를 Game Thread 밖에서 처리해서 hitch를 줄인다.

Level Streaming

오픈월드에서 플레이어 위치 근처 레벨만 비동기로 올리고 멀어지면 언로드한다. 12강의 "워킹 셋을 RAM 안에 유지"의 실천이다.

// 레벨 스트리밍 (블루프린트/코드)
UGameplayStatics::LoadStreamLevel(this, TEXT("Forest_01"),
    /*bMakeVisible=*/true, /*bShouldBlock=*/false, LatentInfo);
//                                          ↑ false = 비동기 (블로킹 안 함)

bShouldBlock=true로 주면 동기 블로킹 로딩이 되어버린다(hitch 발생). 의도하지 않으면 false로 둔다.

7전체 그림 — 5강~15강이 다 모인다

Game Thread
   │ RequestAsyncLoad() — 즉시 반환 (논블로킹)
   │ ↓ 계속 Tick, 렌더, 입력 처리... (안 멈춤!)
   │
   ├──→ [위임]
   │       ↓
   │   Worker / Async Loading Thread
   │       │ 파일 핸들 열기 (14강)
   │       │ OS 비동기 I/O 요청 (IOCP) 또는 블로킹 읽기
   │       │     ↓
   │       │   디스크 → 페이지 캐시 → RAM (DMA)
   │       │     ↓ 완료 통지
   │       │ 역직렬화, 객체 준비
   │       │ 완료 콜백을 Game Thread 큐에 등록
   │       ↓
   │   [다음 Tick]
   ↓
