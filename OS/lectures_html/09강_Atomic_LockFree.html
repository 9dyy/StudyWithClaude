Part 3 · 동시성

Atomic과 Lock-Free

락 없이 멀티스레드 안전이 가능할까? CAS(Compare-And-Swap)가 경쟁 속에서 어떻게 동작하는지 직접 돌려보고, Mutex와 속도를 비교한다.

⚛️ CPU 원자 명령
🧩 선수지식 7~8강
⏱️ 약 18분
SECTION 01 · 동기

1락은 비싸다

8강에서 카운터를 Mutex로 지켰다. 정확하지만 느리다 — 매 ++마다 락/언락 비용 + 두 스레드가 직렬로 돈다.

// 8강: 안전하지만 느림
for (...) { FScopeLock G(&Lock); g_Shared++; }

// 9강: 락 없이, 더 빠르게
std::atomic<int32> g_Shared{0};
for (...) g_Shared.fetch_add(1);   // CPU 원자 명령 하나로 끝

`++` 한 줄을 위해 자물쇠를 채우는 게 과하다. CPU가 직접 보장하는 원자 명령이 있다. 그 핵심이 CAS. ↓

SECTION 02 · 핵심 시뮬레이터

2CAS는 "비교해서 같으면 바꾼다"

CAS(주소, 예상값, 새값) — 현재 값이 예상값과 같으면 새 값으로 바꾸고 성공, 다르면 실패하고 재시도. 두 스레드가 같은 카운터를 +1 하는 경쟁을 단계별로 보자.

atomic counter
0

● 스레드 A

① old = load()
② new = old + 1
③ CAS(old, new)
expected=– new=–

● 스레드 B

① old = load()
② new = old + 1
③ CAS(old, new)
expected=– new=–
시나리오를 골라 ▶ 재생을 누르세요.

B가 먼저 CAS에 성공하면, A의 예상값(old=0)이 현재값(1)과 달라져 CAS 실패. A는 새 값을 다시 읽어 재시도한다. 실패해도 데이터는 안 깨진다 — 단지 다시 시도할 뿐. 이게 lock-free의 핵심.

SECTION 03 · 벤치마크

3Mutex vs Atomic vs Lock-Free

같은 카운터를 1천만 번 증가시킬 때 상대 소요 시간. "벤치마크" 버튼을 눌러보자. (대표적 경향치)

🔒 Mutex
⚛️ Atomic
🔀 Lock-Free queue

단순 카운터는 atomic이 mutex보다 보통 10~50배 빠르다. 다만 경쟁이 심하면 CAS 재시도가 폭주하고 캐시 라인 핑퐁이 생겨 오히려 느려질 수 있다 — lock-free가 항상 빠른 건 아니다.

SECTION 04 · 실무 판단

4언제 무엇을 쓸까

원칙: 가장 간단한 도구부터. mutex → atomic → lock-free 순으로, 측정해보고 진짜 필요할 때만 위로.

ATOMIC

단일 변수

카운터 FThreadSafeCounter, 플래그 FThreadSafeBool, 포인터 하나 교체. 짧은 연산엔 atomic이 정답.

MUTEX

여러 변수·컬렉션

TArray·TMap 수정, 여러 변수가 일관되게 바뀌어야 할 때, 임계영역이 좀 길 때.

LOCK-FREE

검증된 자료구조

생산자-소비자가 진짜 병목일 때. 직접 짜지 말고 TLockFreePointerList 같은 검증된 걸 쓴다.

메모리 배리어 한 줄 정리

컴파일러·CPU는 단일 스레드 결과가 같으면 명령 순서를 재배치한다. 다른 스레드가 그걸 보면 "데이터 준비 → 플래그" 순서가 뒤집혀 보일 수 있다. acquire/release 배리어가 이 재배치를 막는다. (면접에선 이 정도면 충분)

Data.store(42, memory_order_relaxed);
bReady.store(true, memory_order_release);  // 이 앞의 쓰기가 다 보이게
// 읽는 쪽
if (bReady.load(memory_order_acquire)) Use(Data);  // 안전하게 42
